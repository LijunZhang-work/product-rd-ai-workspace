# BEH 控制工具调研与源码调查任务单

> 2026-09-20 观测规则：解释或定位 BEH 值时，先引用[BEH 已知问题与观测适用边界](../../工具接入与共享能力/BEH原生能力/BEH已知问题与观测适用边界.md)。界面当前值不能直接证明早先执行值，Debug 对运行的影响要核实；引擎实际输出和业务应有结果分开。

日期：2026-09-17｜版本：v1.0｜环境：Windows、DeepSeek Harness 主窗口。

## 1. 先看结论

下一步做两件可独立推进的事：让公司环境中的 AI 查清 BEH 的连接、数据、断点调用链；同时在实际桌面软件上试验工具是否能识别并操作控件。暂不选定一个包办全部任务的 Agent，也不预设必须改源码。

本报告的顺序是“优先试验顺序”，不是成功率排行榜。已查官方仓库和文档，没有访问公司 BEH 源码、设备或 Windows 桌面，因此没有任何一项被标为“已适配 BEH”。官方提供功能 ≠ 当前版本可安装 ≠ BEH 操作成功 ≠ 产品业务正确。

**优先尝试：BEH 原生接口调查；SWTBot 作为 BEH 界面候选；Windows-MCP 作为通用桌面接入候选；pywinauto 与 Cua Driver 作为不打扰桌面的对照候选。** 产品 Web 延续现有 Playwright，不必为了统一品牌而更换。

## 2. 需求边界与已有成果

用户要实现的是：真实设备连接 BEH，AI 获得设备真实运行值、对象位置和必要的调试操作，协同产品 Web、北向工具、南向 Python 模拟脚本、另一套专用 RS485 模拟工具以及日志解析器，完成有证据的端到端测试。

复杂图元上的真实值不采用截图识数作为主通道。图像可以帮助确认界面状态，但不承担每拍数据采集。结构模型、设备回传、界面缓存、本地仿真值必须区分。

历史用户确认的技术线索是 Java、Ptolemy II、Eclipse RCP/SWT、JDK 8、Maven 多模块；本次没有复核当前工程。SWT 外壳不能证明画布一定使用 GEF/Draw2D，也不能排除嵌入 Swing/Diva。需查实际依赖、导入、启动配置和加载的 JAR。

## 3. 先分清四种东西

| 名称 | 大白话 | 在这里的职责 |
|---|---|---|
| 主窗口／主 Agent | 听懂任务、安排步骤、解释结果 | 继续使用 DeepSeek Harness |
| Skill | 操作说明书 | 告诉 AI 先做什么、如何判断、失败怎么办 |
| MCP 或普通工具接口 | 主窗口调用工具的接头 | 返回结构化结果；本身不保证后台运行或真实数据 |
| 实际控制工具 | 真正干活的手 | 调 BEH 原生功能、操作控件或移动鼠标 |

所谓“组合使用”，只是不同操作选不同的手：读 BEH 值直接读数据，网页操作用浏览器工具，另一个软件的按钮用桌面控件工具。用户仍然在一个主窗口下任务。若现有 Harness 的普通脚本调用已足够，不必先增加 MCP 服务。

## 4. BEH 专用候选：先调查，再选择

| 试验顺序 | 候选 | 能解决什么 | 接入方式／成本判断 | 必须实测的边界 |
|---|---|---|---|---|
| 1 | 已有原生接口，必要时加薄插件 | 连接、真实值订阅、断点与状态查询 | 先复用完整业务入口；缺少入口再加插件或适配层。成本取决于内部耦合 | 入口是否依赖选中对象、活动窗口、线程、登录和目标状态 |
| 2 | SWTBot | SWT/RCP 菜单、树、表格、按钮的重复操作 | Java 测试代码与目标应用测试运行环境；不是装个外部 MCP 就能任意附着。成本中 | 自绘画布、原生文件对话框、启动流程、JDK/Eclipse 兼容性 |
| 3 | RCPTT | 录制和回放 RCP 流程，恢复初始状态、验证结果 | RCPTT 测试环境／目标应用启动与 ECL；可扩展自定义命令。成本中 | 目标版本、定制控件、运行时注入兼容、是否抢焦点 |
| 4 | Arthas | 查清值经过哪个方法、哪里抛异常／耗时 | 对目标 JVM 做有范围的诊断。用于定位入口，不作为长期业务 API | 附着能力、类加载器、采集开销、JDK 版本 |
| 5 | JMX/MXBean，必要时 Jolokia | 暴露选定的状态、指标、操作 | 若已有 MBean 成本较低，否则仍需写业务包装 | 通道存在不等于真实值已暴露；JDK 8 兼容性 |
| 6 | SWT Accessibility 补齐 | 让外部工具识别自绘对象的名称、状态、动作 | 修改特定控件的无障碍实现。成本中至高 | 是否真能被 Windows 外部工具识别；不是完整运行数据接口 |
| 7 | Java Access Bridge Python wrapper | 读取和操作兼容 Java 无障碍对象 | 仅在发现兼容组件后试；需要匹配 Java、Python 和位数 | Java 不等于 Swing；SWT 自绘画布不能默认可用 |
| 8 | Byte Buddy／Java Agent | 在难重编译的模块中试验事件插桩 | 字节码增强，涉及类加载与生命周期。成本较高 | 有源码时通常先用正常回调；避免诊断改变任务时序 |

### 4.1 哪些能力不能从工具名称推断

SWTBot 和 RCPTT 可以帮助操作 BEH 的界面，但并不自动懂得设备的通信协议，也不自动拥有“设备真实值”。点击断点按钮后，还需通过 BEH 的调试状态或设备回复确认是否设置、是否命中。SWTBot 的官方 FAQ 特别说明原生对话框有限制；它能投递 SWT 事件，不等于每个动作都不抢焦点。

Eclipse Command/Handler 是可调查的入口，不代表 BEH 的所有操作都走该机制。操作可能在鼠标监听器、控制器或其他服务中。不能只监控命令就声称捕获全部人工操作。

Ptolemy 官方有 IOPort 事件监听等能力，但这只能提示查源码的方向：BEH 的真实设备回传可能走另一条通信链。不能把 Ptolemy 本地执行事件当成实机断点事件；不能额外调用会消费数据的 get() 作为旁路采样。[IOPort 官方 API](https://ptolemy.berkeley.edu/ptolemyII/ptII11.0/ptII11.0.1/doc/codeDoc/ptolemy/actor/IOPort.html)

### 4.2 版本与接入建议

逐项记录 BEH 启动 JVM、编译 JDK、Eclipse/OSGi/SWT 版本、插件依赖及 32/64 位；测试工具的启动 JVM与注入目标的运行组件分别核对。不能仅凭“工具支持 Java”安装最新版。

Jolokia 2 最低 JDK 11，Spring 相关模块要求更高，不能直接假定兼容历史 JDK 8。SWTBot/RCPTT 当前具体组件的 JDK 8 兼容组合本次未确认；相关 manifest 页面未能取得，不据此编造版本号。由源码窗口核对 `Bundle-RequiredExecutionEnvironment`、目标平台与发布说明。

若需要现代 MCP SDK，可考虑让外部进程承担 MCP，BEH 内只保留兼容当前 Java 的薄接口，避免为接 AI 升级整个 BEH。到底用本地 JSON、JMX、插件服务还是已有通道，应由现有实现决定，不同时新建多套。

## 5. 推荐榜 A：允许占用鼠标时，新增桌面工具怎么选

榜单面向“接入已有主窗口并控制其他桌面软件”，BEH 数据通道和现有 Playwright 单列，不参与通用桌面比拼。

| 顺序 | 候选 | 推荐理由 | 主要代价／限制 |
|---|---|---|---|
| 1 | Windows-MCP | 已有 MCP 入口，适合先检查普通 Windows 软件的可访问控件并执行操作 | 有坐标点击与键盘输入能力，不能承诺不抢鼠标；当前文档要求 Python 3.13+，中文 Windows 需注意 App-Tool 限制 |
| 2 | Cua Driver | CLI/MCP/SDK，多种动作路线，可同时比较前台和后台效果 | 这里指 Driver，不是整个云平台；BEH/SWT 未在已验证覆盖中，需要实测 |
| 3 | pywinauto | Python 生态，适合把重复流程固化成可复用脚本 | 需要写适配，不是开箱自主 Agent；控件暴露不足时受限 |
| 4 | Midscene Desktop | 适合控件识别不足时试验视觉操作，有交互记录 | Windows 本地桌面采用键鼠输入；需要兼容视觉模型，不能假设现有 DeepSeek 模型能承担 |
| 5 | UFO²／UFO³ | 值得研究 Windows 原生控制和后续跨设备协同 | 引入完整调度体系的成本较大；当前一个主窗口加工具的需求未必需要 |
| 6 | Agent S3 | 适合对比较复杂视觉桌面任务的规划和执行 | 官方示例依赖截图及 pyautogui 路径，需要模型与定位配置；不适合做高频真实值采集 |
| 7 | UI-TARS Desktop | 作为视觉桌面控制的另一条试验线 | 模型、桌面应用与 Agent TARS 要区分；不等于能结构化读取 BEH 内部数据 |

依据：[Windows-MCP](https://github.com/CursorTouch/Windows-MCP)、[Cua](https://github.com/trycua/cua)、[pywinauto](https://github.com/pywinauto/pywinauto)、[Midscene Desktop](https://midscenejs.com/platforms/desktop)、[UFO](https://github.com/microsoft/UFO)、[Agent S](https://github.com/simular-ai/Agent-S)、[UI-TARS Desktop](https://github.com/bytedance/UI-TARS-desktop)。以上顺序来自本项目的集成成本和用途判断，没有比较实测成功率。

Browser Use 专注浏览器，无法接管 BEH 原生 Java 桌面。已有 Playwright 跑通时，它是动态网页任务的备选，不是必须替换项。[Browser Use](https://github.com/browser-use/browser-use)

FlaUI 是 .NET UIA 候选，适合已有 .NET 工具链的团队；若目前已有 Python 脚本，先用 pywinauto 可减少新增生态。它也不能补出应用没有暴露的控件和数据。[FlaUI](https://github.com/FlaUI/FlaUI)

## 6. 推荐榜 B：同一台电脑上，用户还要正常使用鼠标键盘

这份按“实现路径”排名，范围不同，不能理解成第一名能替代其余全部软件。

| 顺序 | 路线 | 适用范围 | 达标条件 |
|---|---|---|---|
| 1 | 已有 API／脚本／BEH 原生调用与订阅 | 有接口或可加薄适配的操作 | 不打开强制模态窗口、不激活前台；读的是正确设备与会话的数据 |
| 2 | Playwright 独立浏览器实例，优先 headless | 产品 Web | 使用浏览器内操作；验证登录、下载、弹窗等目标流程，避免系统键鼠注入 |
| 3 | pywinauto 限定语义动作 | 暴露相应 UIA/Win32 能力的 Windows 控件 | 逐控件验证 Invoke、Select、SetValue 等；不自动换成真实输入 |
| 4 | Cua Driver 限定后台路线 | 可支持后台动作的应用 | 后台不支持就返回失败；适配层明确禁止自动前台升级 |
| 条件候选 | SWTBot／RCPTT | BEH 的部分界面流程 | 在实际目标上验证激活窗口、键盘和弹窗行为后才能进入后台白名单 |
| 浏览器备选 | Browser Use headless／Midscene Web | 动态 Web 流程 | 与现有 Playwright 比较增益；不能据此推断 Desktop 版本也不抢鼠标 |

pywinauto 的 UIA ButtonWrapper.click 使用 Invoke/Select，和 click_input 不是一回事；后者及 set_focus、type_keys 等真实输入相关路径不能直接放入无打扰路线。具体类和方法逐项检查。[UIA API](https://pywinauto.readthedocs.io/en/latest/code/pywinauto.controls.uia_controls.html)、[远程执行限制](https://pywinauto.readthedocs.io/en/latest/remote_execution.html)

Cua 官方将后台描述为 best-effort，Windows 主要依靠 UIA 和定向消息；其已验证列表不能证明 BEH 可用。因此 pywinauto 的可限定脚本排在探索性更强的 Cua 之前。Cua 若在实际目标上表现更好，可以交换顺序。[后台机制](https://cua.ai/docs/concepts/the-no-foreground-contract)、[平台覆盖](https://cua.ai/docs/reference/cua-driver/platform-support)

需要同时检查鼠标位置、前台窗口、键盘输入去向、剪贴板副作用。窗口被遮挡、最小化、锁屏、远程断开是不同条件，不能把其中一种成功推广到全部。Windows-MCP、UFO、Agent S、UI-TARS、Midscene Desktop 均不凭名称列为同机无打扰方案。

若某软件只能用真实前台输入，现阶段选择“明确占用桌面的执行时段”或“已有独立测试机”。用户不接受虚拟机，不将虚拟机作为默认方案。增加显示器或切换普通虚拟桌面也不应被当作输入隔离的证明；远程执行必须另测交互会话和设备连接条件，不能假设断开 RDP 后仍正常。

## 7. 最小验证：怎么试，才知道该选谁

先选已有、可复现的一条业务场景。建议只包含一个连接流程、三个有稳定标识的观测点、一个调试位置、一个外部工具操作。以下是建议实验设计，不是已经完成的测试。

| 编号 | 实验 | 通过标准 | 失败后怎么办 |
|---|---|---|---|
| T0 | 核对源码和运行版本 | 对应 commit、实际加载 JAR/插件、JVM、固件和配置可追溯 | 先解决版本不一致，不拿旧源码解释当前执行 |
| T1 | 识别连接按钮和一个表格／树节点 | 能稳定定位对象，重开软件后重新定位成功；保存识别结果 | 外部 UIA 不通，试 SWTBot；自绘对象继续查模型入口 |
| T2 | 找到三个真实观测点并读取 | 每个值有设备、会话、对象与来源；与同一采样事件或停稳状态下人工读数一致 | 定位缓存、映射或单位问题；没有真实入口就标记未取得 |
| T3 | 建立值变化订阅 | 记录设备时间或接收时间，说明采样率、丢样和覆盖区间 | 只支持快照就明确降级；不能宣称逐拍完整 |
| T4 | 设置一个断点并确认命中 | 设置返回与命中状态分别有证据；暂停范围明确 | 仅 UI 图标变化属于不足，继续查回包／状态机 |
| T5 | 单步／继续 | 明确单步单位、命令完成和真实运行状态，不靠按钮变灰猜测 | 返回不支持或未知；不自行补造单步语义 |
| T6 | 同机后台试验 | 用户在无关文本编辑器持续输入，工具操作正确，鼠标焦点输入与剪贴板不受非预期影响 | 禁止前台回退；记录具体失败动作，改原生路线或前台时段 |
| T7 | 一次外部刺激与跨通道核对 | 外部工具准备完成后发刺激，取得实际接收、BEH 观测、页面或日志等对应证据 | 分别记录哪个环节失败，不能把发送成功当端到端成功 |
| T8 | 中断与恢复 | 断线／工具退出可识别；保存部分结果，清理订阅，旧值不会伪装成新值 | 修复生命周期，再扩展长任务 |

T6 可先建议重复 20 次操作并持续观察约 10 分钟作为冒烟试验，记录原始次数和故障；它不证明长期可靠性。出现一次抢焦点，就不能声称该动作满足严格无打扰。只有准备长期运行时，再按实际批次持续时间验证，不无边界扩展测试。

GUI 路线与原生路线分开记录。API 成功可证明业务入口执行，不能替代“用户能否在产品页面完成操作”的测试。浏览器 UI 测试保留正常点击与输入，不通过直接修改页面内部状态来制造成功。[Playwright Actions](https://playwright.dev/docs/input)

## 8. 可直接复制给源码窗口的任务单

以下整段可以交给能访问公司 BEH 源码的 DeepSeek Harness 窗口。第一阶段仅调查与形成可审查结论，不修改源码、不改变真实设备状态。已经获准的现有只读验证可以复用；任何设备调试试验遵守当前实际设备授权范围。

---

### 任务：调查 BEH 真实设备连接、运行值与调试能力的 AI 接入路线

**目标**：我们有 BEH 源码。人工能连接真实设备，在复杂图元界面观察设备真实值并使用断点等调试功能。请查清实际实现，判断如何让 AI 获得结构化真实数据、调用已有操作。当前不要求自动绘图，不要求建立新 Agent 框架，不以截图识数为主要数据来源。

**环境与复用**：本工作区主入口是 Windows DeepSeek Harness。先读工程现有说明和当前测试／解释文档，发现并复用已有 Runner、Runtime、通信模块、脚本与构建方式。历史技术栈线索为 Java/Ptolemy II/Eclipse RCP/SWT/JDK 8/Maven；你必须核对，不将线索当结论。记录哪些源码可用、哪些仅有 JAR，以及当前运行软件与代码的对应关系。

**A. 技术栈与入口盘点**

检查 pom.xml、MANIFEST.MF、plugin.xml、产品启动配置和相关依赖。列出启动类／插件、界面框架、实际画布框架、通信服务、调试服务、模型和显示层。确认 SWT 与 Swing/Diva/GEF 是否实际使用，不按项目名称猜测。每个关键结论给相对路径、类／方法、必要代码位置及版本。

**B. 连接设备调用链**

从界面连接动作追到业务校验、会话创建、通信连接、握手或登录、目标身份确认和成功／失败状态。查清断开、超时、重连、重复连接及资源清理。标明依赖当前活动窗口／选中工程的地方，以及可以传入显式参数的服务入口。不要只找到底层 socket 就说连接能力已经可复用。

**C. 真实值调用链**

从设备接收回调或解析函数，追到缓存／订阅、对象标识映射、图元／端口模型、界面显示。分别说明设备真实回传、本地计算、仿真、上次缓存和格式化显示值。查清设备是否逐周期上报，客户端是否抽样、合并或覆盖；有无设备时间、周期序号、接收时间及丢样标识。不足以证明时写“未知”。

回答：同一个图元的多个实例如何区分？端口如何映射到设备地址或信号？单位、缩放、浮点精度和无效值在哪里处理？断线后旧值是否仍显示？能否以非消费方式订阅原始更新？批量读取是不是同一拍的一致快照？不要拿不同时间顺次读取的值拼成同一拍。

**D. 调试调用链**

分别跟踪设置／删除断点、断点命中、暂停、单步、继续。找出命令发送、应答、状态转换与界面更新。明确断点作用于设备执行还是本地引擎；暂停影响一个对象、任务还是更大范围；单步究竟对应何种执行单位。区分“命令已发送”“设备已接受”“断点已命中”，不要拿一个布尔返回值代表全部完成。

**E. 原生接入与界面接入比较**

每项操作填写：已有公开接口／可复用完整内部入口／需小幅改动／暂仅 GUI／未知。优先完整业务入口，保留上下文校验、权限、线程和状态更新。检查调用是否弹窗、激活窗口或依赖全局选中对象；核对 SWT UI 线程与通信线程，避免在 UI 线程阻塞等回包。

评估 SWTBot 和 RCPTT 的目标版本兼容、插件加载、定制控件支持及现有测试集成。外部控件路线可先检查 UIA/Win32 可见性，再决定 pywinauto/Cua/Windows-MCP；只有确认兼容 Java 无障碍组件后才试 JAB。需要 MCP 时比较外部适配进程与进程内方案，不为接工具先升级整个 Java 栈。

**F. 数据真实性与授权**

原生入口复用现有身份、目标选择、允许操作范围和校验；“同进程／同源码”不等于自动获得所有操作权限。不要把调试接口做成任意 Java 方法执行器。观察接口与改变运行状态的操作分开说明。数据包含实际可获得的设备／会话／对象身份、值、来源与时间；没有的字段标记缺失，不造值。

**G. 交付物**

1. 调查摘要：已确认事实、仅由代码推断、运行证据、未知事项分开。
2. 四张调用链表：连接、真实值、断点、单步／继续。每张注明入口→业务处理→设备/模型→结果反馈。
3. 能力矩阵：`能力｜文件/方法｜前置条件｜数据来源/目标｜是否依赖焦点｜候选接入方式｜版本限制｜证据｜下一步`。
4. 最小改动建议：若需要新增接口，给出拟改位置和职责，暂不实现；说明哪些功能无需修改即可使用。
5. 一个小验证方案：连接一个目标、读取三个点、确认一个断点及其运行状态；无设备时完成静态调查和已有本地检查，实机结论留待验证。
6. 列出待用户补充的最少信息，优先自己从代码与现有配置中查明；报告中不输出密码、令牌等凭据。

**停止条件**：四条调用链与候选入口足以判断下一轮试验即可提交，不要求全库通读。依赖缺失时指出具体断点及影响，不把“找不到实现”写成“不支持”。未经源码和运行证据，不承诺逐拍完整、后台无打扰或 UI/原生路径完全等价。

## 9. 回到主窗口后，如何作决定

| 调查／试验结果 | 下一步 |
|---|---|
| BEH 已有完整数据和调试接口 | 直接包装少量工具，验证真实性和状态反馈 |
| 数据可取，但操作依赖 GUI | 数据先结构化；操作试 SWTBot/RCPTT 或外部控件，不等待所有能力统一 |
| 只有内部方法且耦合较重 | 先提出薄服务／插件改动，验证保持原有业务语义 |
| 外部软件 UIA 能稳定识别 | 用 pywinauto 固化流程，或用 Windows-MCP/Cua 接主窗口 |
| 外部软件只接受前台视觉输入 | 使用允许占用桌面的模式；严格后台模式返回不支持 |
| BEH 只接收到低频最新值 | 明确报告只能观察采样值；再研究设备/协议是否支持更完整采集 |

主窗口对每个工具保留少量统一信息：目标身份、能力、启动方式、是否就绪、动作状态、结果来源、证据位置、取消与清理。高频采样由程序持续执行，AI 按需读取摘要和片段，不让大模型逐拍点击或逐条搬运。

端到端执行先启动需要持续工作的模拟器和采集器并确认就绪，再发刺激，最后等待各自完成条件、收集原始证据、按独立业务规则判断。南向 Python 模拟脚本与专用 RS485 模拟工具是两个适配器，北向工具单列；串口、设备调试会话和工程资源的占用关系必须记录，避免两个工具同时争用。

AI 的解释关联输入、对象、版本、时间区间和证据，但相关时间或同一个任务编号不自动证明因果关系。接收侧证据与发送日志分开，页面展示、内部观测、外部输出分别判定。实际输出不能同时被用来生成“标准答案”再证明自己正确。
