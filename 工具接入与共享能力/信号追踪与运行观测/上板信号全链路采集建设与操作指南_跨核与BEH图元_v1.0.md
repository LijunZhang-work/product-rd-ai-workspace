## 1. 目标、已有条件与完成标准

### 1.1 始终围绕整条信号链

目标覆盖实际外部输入、产品多组件处理、真实跨核通信、接收侧业务、相关换算、图元交接以及 BEH 对应处理。GOOSE、Modbus、算法分支是否属于所选信号，应按产品当前配置查证，不能把所有候选模块强行串成一条线。

沿用不上板阶段已经建立的节点和连接标识，在同一张链路表上补充设备实测。若不上板成果尚有缺项，针对本次信号补齐，不重做整个环境审计，也不把上板任务缩减为 x86 DT。

“首条链”可以只选一个代表信号，但应包含实际跨核边界和 BEH 交接。只看某个函数的值、只跑一个图元或只看到发送成功，都属于阶段成果。

### 1.2 必须继承的条件

| 项目 | 当前依据 | 执行方式 |
| --- | --- | --- |
| CodeQL | 用户已说明追踪跑通过 | 复用现有数据库、查询、宏入口和节点表，核对与本轮源码及配置是否匹配 |
| BEH | Windows Java 引擎的 AI 图元测试已跑通 | 同时检查工具源码、测试入口和产品实际图元工程，复用原引擎 |

| 发送侧位置 | 需要由当前工程定位 | 可修改的产品调用点可以接入；不可见的一侧保留缺口，不默认两核源码都完整 |

### 1.3 什么才算完成

分别给出三项状态：**采集能力建到哪里、实际链路验证到哪里、业务数值正确性确认到哪里。** 每项使用“完成／部分完成／阻塞”，并说明范围。

完整首条链应至少具备：可重跑的产品测试构建与采集入口、关键节点清单、原依赖参与运行的证据、跨核两端的对应记录、浮点原始数据、BEH 交接／回放结果、采集丢失与扰动检查，以及一份结果报告。依赖内部仍不可观察时，注明未观测区；这不妨碍报告已验证的两端交接，但不等于已经看清依赖内部每一步。

若设备尚不可用，先完成可完成的产品接入、编译、解码验证及待执行步骤，状态写“已准备，未上板”。不能将构建成功、主机测试通过或空白表格写成设备验证完成。

## 2. 工具分工与实施顺序

### 2.1 只保留必要工具

| 工具／模块 | 大白话职责 | 本轮使用原则 |
| --- | --- | --- |
| CodeQL＋源码检查 | 找出信号经过哪里、该在哪儿取值 | 复用现有能力；查询结果不自动等于实际执行 |
| 产品侧统一采集接口 | 在程序处理信号的那一刻，保存值和身份信息 | 本轮核心；优先接已有记录库，缺什么补什么 |
| SystemView | 收集、显示带时间的事件和部分数值 | 已有记录器/导出不足时按需评估；不是安装后自动取得所有变量 |
| 现有调试器／导出接口 | 将板端内存中的记录取回电脑 | 选一种已证实可用的方式，避免同时重建所有通道 |
| 电脑端解析和合并脚本 | 正确解释浮点、匹配消息、生成节点表 | 沿用现有 Python 等工具及不上板结果格式 |
| BEH 源码与 AI 图元测试 | 确认映射并运行原图元引擎 | 板端观测与 Java 引擎观测分别标记 |
| Ghidra 等二进制分析 | 在关键疑点处辅助解释调用或数据布局 | 按需使用，不当作板上采集器，不先反编译整个依赖 |

本轮不以 Renode 适配为前提，也不因构建机是 Linux 就默认板端能运行 Frida、eBPF 或 Linux 跟踪工具。发现现成可用能力时可以复用，但必须记录目标适用证据。

### 2.2 顺序与每一步的结束点

| 步骤 | 实际操作 | 结束条件 |
| --- | --- | --- |
| A | 对齐版本、环境、真实输入与现有节点表 | 知道本轮测哪份产品、哪条信号、从哪里进入 |
| B | 在一个可控业务点打通记录、取回、解码 | 能读出一次真实板端事件；只是接入验证，不是整链完成 |
| C | 批量接入所选链的跨核两端、换算和交接点 | 点位有来源，产品测试固件构建完成 |
| D | 运行真实产品通信，采集短窗口 | 两端记录可关联，丢失／覆盖情况可解释 |
| E | 对照 BEH，检查采集扰动和一个合适的异常场景 | 结果来源清楚，异常不被误判为正常 |
| F | 扩展必要场景并输出唯一报告 | 完成状态、证据、缺口及最小下一步明确 |

工具适配遇到具体阻塞时，先判断能否换已有导出方式继续。不要无限排查一个探针型号，也不要停在“建议以后开发”。

## 3. 开工准备与两种构建环境

### 3.1 先从工程取得信息

读取已完成的环境排查报告和不上板建设结果；旧任务书只能说明检查要求，不能充当已完成报告。以下信息能从文件、构建日志、现有脚本取得的，由执行 AI 自行取得，不逐项追问用户。

| 要取得什么 | 优先从哪里找 | 对本轮的作用 |
| --- | --- | --- |
| 产品源码、配置、未提交改动 | 工作区、成功构建日志、配置入口 | 保留当前工作，确定测试版本 |
| 两侧实际执行程序与核角色 | 链接／打包记录、最终产物、设备启动资料 | 确认观测点属于哪一侧，不把文件名当型号证明 |
| 编译器、链接器、优化和对齐选项 | 实际编译／链接命令 | 决定包装方式和数据解释方式 |
| 依赖版本、头文件、实际链接路径 | artget 清单、链接记录、最终产物 | 保证采集测试没有换成 DT 桩或另一套库 |
| 真实测试输入入口 | 现有界面、协议发送工具、测试场景 | 明确是否覆盖外部入口；若绕过，应写实际注入点 |
| 板端连接和取回方法 | 现有烧录、调试、串口、导出操作记录 | 避免猜测端口和设备地址 |
| BEH 对应材料 | 工具源码、Java 引擎、产品图元文件、已有测试 | 对齐实例、端口、配置和执行状态 |

ELF 可以理解为包含程序代码及装载信息的可执行产物，不一定以 `.elf` 结尾；通过链接与打包记录寻找。MAP 是地址分布资料，ASM 是反汇编／汇编资料，它们有定位价值，但不自动等于完整可执行程序。匹配的符号产物应尽量保留，不为寻找固定后缀而卡住整个工作。

### 3.2 两种环境择一执行，不重复造环境

| 方式 | 怎么用 | 需要保持 |
| --- | --- | --- |
| WSL＋现有产品镜像 | 沿用当前 WSL、镜像、挂载和产品构建入口 | 产品配置、依赖、构建工具以及可持续保存的输出路径 |
| SSH＋远程 Linux 执行器 | 使用已有 SSH 连接和服务器上已配好的版本环境 | 原环境初始化方式、远程源码路径及构建入口 |

两种方式均受支持，但本轮只需采用适用的一种。远程执行器不需要再套 WSL，也不要求把全部源码和依赖复制回 Windows。BEH 可继续在 Windows 执行；只传递必要的版本记录、输入与结果，核对文件哈希。

查到 CPU／操作系统实际配置之前，保持待核实。构建在 Linux 完成不代表板端运行 Linux。

### 3.3 Docker 和 CodeQL 的资源复用约束

1. 先识别镜像 ID／digest、容器、挂载、缓存和 CodeQL 数据库；它们是不同对象。相同镜像的多个容器不等于完整复制了多份镜像，名称相近也不能证明由 CodeQL 创建。[Docker 镜像说明][S10]
2. 优先复用现有产品镜像和可用容器。不得按每条信号、每次查询、每轮失败重试重复 `pull`、`build`、`commit`、`save/load` 同一套环境；需要隔离时可以从适用的现有镜像启动本任务临时容器。
3. 只改查询或换信号时，优先使用仍匹配源码、配置和工具的现有 CodeQL 数据库。产品插入采集代码后旧数据库的行号／源码快照可能过期，应重新映射或更新对应数据库，并注明原因；不能借复用之名使用失效事实。
4. 真正缺少工具或存在不兼容版本时，说明缺口后做最小环境扩展，不默认再造产品镜像。SSH 环境已够用时直接使用。
5. 查询、数据库、补丁、输入、关键日志、产物和报告保存在明确的持久目录，不能只留在临时容器可写层。并行构建时各任务使用独立可写输出，避免覆盖。
6. 收尾只清理本任务创建且确认不再需要的资源，保留共享环境和有效数据库。不得执行全局 `docker system prune -a`、全局数据卷清理或按“像重复”批量删除。

在唯一报告中简短记录复用／新增／保留原因即可。本任务不要求顺便清理用户整个 Docker 环境。

### 3.4 可复制的只读检查模板

以下 Bash 模板在选定构建执行器运行；先由执行 AI 填入核实过的值。不能把尖括号占位符当真实路径。它们不连接或刷写设备，也不代替产品构建。

```bash
product_repo='<本轮产品仓库绝对路径>'
product_program='<已核实的最终程序绝对路径>'
cd "$product_repo" || exit 1
git status --short
git rev-parse HEAD
file "$product_program"
sha256sum "$product_program"
llvm-readelf -h -l -S "$product_program"
llvm-nm --defined-only --numeric-sort "$product_program"
```

这些工具输出用于核对程序架构、段和符号。若工具不存在或产物并非其支持格式，使用原工具链对应工具；无符号也不能解释成无代码。日志只摘取有关内容，不把整个符号表灌入报告。[LLVM readelf][S08]、[LLVM nm][S09]

Docker 仅在当前方式确实使用 Docker 时检查：

```bash
docker image ls --no-trunc
docker ps -a --no-trunc --format '{{.ID}}\t{{.Image}}\t{{.Names}}\t{{.Status}}'
```

真实产品构建命令从已有成功入口取得，不编造 `build.sh` 参数，也不把运行 DT 的脚本当作产品固件编译入口。若需重新提取 CodeQL 数据库，提取器必须能观察到实际编译；本地开 CodeQL 后通过 SSH 编译，不自动构成远程编译已被收集。

## 4. 生成和核实统一采集点清单

### 4.1 按“哪里改变了值或交接了数据”选点

优先沿现有信号宏和节点表寻找以下位置。清单中的核角色、函数、变量和消息对应关系必须替换为真实项目证据。

| 点位类型 | 在哪里接 | 最少记录 | 不能据此直接得出的结论 |
| --- | --- | --- | --- |
| 初始化／订阅 | 产品启动、注册调用前后、业务就绪处 | 阶段、状态、配置或订阅身份 | 业务就绪不等于所有外设／任务都正常 |
| 输入接收 | 产品实际接收外部设置的位置 | 原输入、信号身份、来源 | 界面按钮已点击不等于设备收到 |
| 依赖调用前 | 产品把数据交给依赖之前 | 实际参数、有效载荷、可用消息身份 | 表示交出什么，不等于对侧到达 |
| 依赖调用返回 | 原调用返回后 | 返回状态、本地调用关联号 | 返回成功含义须按接口约定解释 |
| 接收回调 | 依赖调用本仓业务回调，完成必要有效性检查后 | 本次收到的字段、身份、长度 | 不代表可看到此前依赖内部路由 |
| 关键换算 | 本次业务换算的输入／输出已产生处 | 前后实际值、类型、单位 | 值变化本身不能说明违反设计 |
| 图元交接 | 已确认的订阅分发／图元输入边界 | 实例、端口、值、有效状态、周期 | 向图元交出不等于图元已经执行 |
| 图元执行后 | 板上确有对应可观测执行位置时 | 本次输出、状态与执行周期 | Java 回放不能冒充这一处板端记录 |

“每节点都写出来”指业务链关键节点，不要求记录每条指令。已经确认但暂时采不到的节点仍保留一行，标为“未观测”，不要删掉。

### 4.2 清单最小字段

每个点保留：稳定点位 ID、所属程序／核角色、源码 commit 和文件函数、信号宏及实际 ID、通道／实例、要取的表达式或字段、类型／单位、取值时机、接入方式、可用消息关联字段、对应证据、当前状态。

稳定 ID 不依赖易变化的行号；行号用于定位，另保留函数和源码锚点。同名宏、同类型图元不能替代实际消息通道和实例身份。

下例只是配置结构示意，**不是本项目已有接口，也不是直接可运行的工具配置**：

```yaml
schema_version: 1
signal:
  macro: "<真实信号宏>"
  resolved_id: null        # 由当前产品配置求得，未知不能填 0
points:
  - point_id: P_SEND
    core_role: "<实际发送角色>"
    location: "<文件与函数>"
    moment: before_dependency_call
    value_expression: "<已核实的本次参数字段>"
    value_type: "<实际类型>"
    unit: "<已确认单位；未知注明>"
    message_identity: "<已有协议字段；没有则 null>"
    capture_status: pending
    evidence: "<当前版本源码或配置依据>"
```

### 4.3 CodeQL 查不到连接时怎么办

分别核对起终点是否选中、相关实现是否入库、跟踪的是地址还是地址所指的值、字段访问和运算是否被查询覆盖。官方明确指出，指针层级选错或字段写入实现不可见会影响结果。[CodeQL C/C++ 数据流说明][S07]

查询暂未连接时写“当前查询未连接”，不要直接写“真实链路断了”。修改结论必须说明新证据、查询或配置变化及重跑结果。采集点选择不能只接受 AI 的文字解释，至少检查一次真实调用、参数与接收位置。

## 5. 统一接入：尽量一次接入、多处复用

### 5.1 接入方式按实际条件选择

| 优先级 | 工程条件 | 采用方法 | 改动范围 |
| --- | --- | --- | --- |
| 1 | 已有产品公共封装／记录钩子 | 接入统一记录接口，按信号筛选 | 本仓少量公共代码 |
| 2 | 多处调用同一外部依赖符号，链接条件合适 | 用链接包装集中记录，再调用真实实现 | 包装文件和产品测试链接配置 |
| 3 | 调用分散、内联、模板或无法包装 | 按核实的点位清单批量改本仓调用点／回调 | 测试构建中的受控源码改动 |

不强制先使用链接包装。已有公共封装最容易核对时，直接复用。公共入口在依赖内部也不必先取得依赖源码，可以在本仓调用边界和接收业务入口记录；依赖内部独有状态仍留作未观测。

### 5.2 所有方式共用一个采集接口

接口应接收点位 ID、当前信号身份、消息关联信息、类型和本次值的快照。具体函数名沿用项目命名；采集后端优先接已有可靠记录器，SystemView 不满足时可接一个最小的有界二进制记录实现。不要同时建设两套内容相同的采集系统。

统一接口必须满足：

- 调用者仍执行原业务和原依赖；采集失败只更新采集状态，不改业务返回值。
- 记录函数不抛异常、不做动态内存分配、不递归进入被记录的接口，不在热路径等待文件或网络发送。
- 关闭采集时不执行附加读取，不对带副作用的表达式重复求值；确认不会改变原接口调用次数。
- 原函数在 ISR、启动早期或特定任务调用时，采用该上下文可用的实现，不能未经核实调用会调度或阻塞的 API。
- 一个小配置控制使能、信号范围、点位集合、记录窗口与满缓冲策略；初版不启用全函数、全信号采集。

### 5.3 取值时机比函数名字更重要

取程序**本次实际处理的参数或局部结果**。如果产品先读取共享变量得到局部值，记录这个局部值；不要为了采集再次读取共享变量。对清读寄存器、带副作用的 getter、临时对象，也不能重复执行。

异步发送接口返回后，原缓冲区可能已转移所有权或失效，不能再解引用。需要的发送快照应在有效窗口取得；若异步机制允许依赖稍后再读可变内容，调用前快照只证明当时交出内容，需要按接口所有权约定解释，不能保证底层稍后发送的字节完全相同。

回调中的指针先经过产品已有的长度和有效性检查，在内容仍有效时复制所需字段。字段正在被其他核／任务修改时，遵循原有同步和所有权协议；普通 `memcpy` 本身不能解决并发快照一致性。

以下仅说明接入位置，名称和类型均为示意，执行者应从真实工程生成代码，不能原样编译：

```cpp
ReturnType ProductSend(const Message& msg) {
    trace_send_snapshot(msg);       // 在约定有效窗口记录必要字段
    auto result = dependency_send(msg);  // 原依赖仍实际执行一次
    trace_send_status(result);      // 不再假定 msg 的内容仍可读取
    return result;
}

void ProductReceive(const Message& msg) {
    // 沿用原有校验；在数据有效且未被改变的位置采集。
    trace_receive_snapshot(msg);
    original_business_processing(msg);
}
```

这是位置示意，不替代项目的异常、错误码、资源生命周期和 C／C++ 调用约定。若原调用可能以异常或非本地跳转退出，“调用返回”事件可能缺失，不能强行写成功。

### 5.4 链接包装怎样验证

GNU 链接器的 `--wrap` 会把符合条件的未定义符号引用改到包装函数，再通过 `__real_…` 调回真实实现；同一编译单元内部已解析的引用并不普遍被替换。[官方说明][S06]

若选择这一方式，依次检查：实际链接器是否支持；原导出符号和 C++ 名字修饰；原型、参数、返回值及浮点 ABI；内联／LTO 是否改变调用；最终链接图或反汇编中包装和真实调用是否成立。不能凭编译器叫 LLVM 就认定所有包装功能可用。

先对一个真实接口验证“包装进入、原实现执行、返回保持”，再扩展到需要的接口。接收回调可直接在本仓函数内接入，不必为了形式统一而强行包装回调。依赖内部不可见调用没有被覆盖时，清单要如实反映。

### 5.5 批量接入如何避免漏点和错点

优先根据产品实际编译参数构建 Clang 语法分析，按函数、字段和调用位置修改源码；Clang LibTooling 支持基于编译数据库处理源码，但具体接入工具需要实现和适配。[Clang 官方说明][S05]

生成前核对源码版本，生成后给出命中、未命中、歧义和跳过点位。重复运行不得重复插入；宏展开、模板、生成代码或厂商扩展无法可靠处理时，报告具体位置，改用明确的小补丁。不要使用全仓字符串替换去猜 C++ 语义。

产品测试构建保留接入开关和可撤销补丁，沿用原产品编译选项。若已有用户改动，避免覆盖。记录基础 commit、实际工作区差异及采集补丁，使源码和最终固件能对应。

## 6. 数据格式、浮点数和对齐

### 6.1 人看的字段与板端编码分开

下面是解码后应能取得的信息，并不要求板端每条记录都重复存完整字符串。版本、单位、点位名称等可放在一次性的元数据表，事件使用短 ID。

| 字段 | 含义与要求 |
| --- | --- |
| 测试编号、各核启动标识 | 区分测试轮次和某核重启；电脑端测试编号不自动等于板端已有字段 |
| 程序／配置／依赖版本 | 使用元数据关联实际固件及配置，防止混入旧日志 |
| 核角色、点位 ID、事件阶段 | 标明哪里发生、是调用前、返回、接收还是输出 |
| 信号 ID、通道、实例 | 标明哪个业务信号；保留宏到当前实际 ID 的映射 |
| 协议消息身份／业务周期 | 若接口暴露则保存；没有就写不可用，不伪造全链编号 |
| 本地记录序号 | 用来检查采集缺失，与协议消息序号分开 |
| 时间戳及时间源 | 原始 tick、频率、宽度、回绕和校准信息；接收电脑的时间不能替代发生时间 |
| 类型、有效载荷长度、字节序、原始字节 | 正确恢复本次值；支持实际使用的 float／double 等类型 |
| 状态／长度／错误码 | 按真实接口语义解释；缺少返回事件时保留未知 |
| 采集质量 | 丢弃、覆盖、截断、重启、导出不完整等计数或状态 |

第一版可沿用已有可靠二进制格式；若需要自定格式，明确版本、记录长度、固定宽度头字段、头字段字节序和有效发布标识。浮点载荷可保存源端原始字节，并用元数据指明编码和字节序。不能把本地 C++ 结构体未经定义直接当跨平台文件格式。

### 6.2 浮点数必须保留原始精度

核对实际字段是 32 位 float、64 位 double，还是其他格式；以产品类型和编译 ABI 为准。对于已确认的 IEEE 754 格式，同时保存原始位表示和电脑端显示值。double 不先转为 float，浮点不先转为整数，也不只保存保留两位小数的字符串。

协议原始字段、业务解码后值、换算结果是不同观测对象。例如协议可能使用整数缩放，而业务内使用浮点，不能用一种解释覆盖全部节点。原始字节一致检查与业务数值容差检查分别报告；NaN、无穷、正负零按已确认语义处理，不能直接套普通相等判断。

板端尽量做字节复制与固定开销记录，将十进制格式化放在电脑端。采集代码仍需检查编译生成的指令及调用上下文：字节复制的设计意图不自动保证编译器没有使用浮点／向量寄存器，尤其不能给原本不保存相应上下文的中断引入隐患。

### 6.3 4 字节与 2 字节对齐怎么处理

分别核对产品和相关 DT 的字段类型、`sizeof`、合法可用时的 `offsetof`、`alignof`、pack 宏／选项及真实协议布局。非标准布局 C++ 类型不能机械套用 `offsetof`。记录差异对应的具体类型和构建条件，不笼统写“产品全部 2 字节对齐”。

采集模块按产品原配置编译；不为方便电脑解码改产品 pack。电脑解析时按明确格式和字段偏移处理，不把原始缓冲区强转为 x86 自己定义的结构体。只保存有意义且有效的字段，避免把填充字节当业务数据比较。

对不对齐的载荷，优先沿用产品已核实的解码方式，或在合法读取范围内复制到适当对齐的对象再解释。采集不能新增原程序没有的未对齐宽访问。

### 6.4 一个电脑端解码自检示例

下例仅验证“小端 IEEE 754 浮点原始字节如何解释”，不是设备日志，不证明目标也采用这个格式。目标格式核实为别的情况时应调整。

```python
import struct

assert struct.unpack("<f", bytes.fromhex("00004842"))[0] == 50.0
assert struct.unpack("<f", bytes.fromhex("0000003f"))[0] == 0.5
assert struct.unpack("<d", bytes.fromhex("000000000000e03f"))[0] == 0.5
```

实际解析器应保留原始十六进制值、拒绝不完整记录，并按版本表解释类型。64 位地址、计数或 double 不得因某个展示接口只接收 32 位参数而被截断。

## 7. 高频函数、缓冲区和取回记录

### 7.1 在处理发生时记录

函数每 100 毫秒调用一次，相当于该点通常每秒约 10 次；函数本次执行很短，也可以在它处理数据的那一刻写入。不要用另一个任务每 100 毫秒轮询变量来代替，它可能错过中间状态或混合不同次输入。

所选信号在验证窗口内优先逐事件记录；确需抽样时使用一致的选择条件，并标明抽样范围。只记录“值变化”不能验证每次相同值消息是否到达；为了通信完整性，仍需消息事件或相应计数。

### 7.2 先本地保存，再安排导出

每核使用本地有界缓冲或已验证记录器，尽量避免采集写入本身依赖另一核。核内多任务／中断并发仍需要正确保护：可以按执行上下文分缓冲，也可使用适合目标的短临界区／成熟并发实现。不要把“每核一个缓冲区”误写成“不用考虑并发”。

记录必须写完整后才发布为有效；导出方不得读取半写记录。64 位数据在 32 位系统上的读取不能假设天然原子。共享内存或调试器直接读 RAM 时，还要处理实际内存映射、缓存可见性和必要的内存顺序；仅加 `volatile` 不足以解决这些问题。

首轮推荐短窗口逐事件采集，缓冲不足时明确停止记录或丢弃并计数，验证段有无法解释的丢失时不判“消息全到”。长时间异常复现可改用滚动保留最近记录，注明被覆盖区间，并在适用时触发保留故障前后窗口。

### 7.3 容量怎样估算

按“每秒事件数 × 每条最大实际编码长度 × 需要保留秒数”估算，并加上启动元数据、突发与对齐开销。持续导出时检查平均和峰值带宽以及后台调度能否及时排空。

示意：1 条信号、8 个点、每点每秒 10 条、每条按 64 字节估算，约为 5,120 字节／秒；30 秒约为 153,600 字节，尚未计附加开销。增加到 100 条同样频率的信号会相应扩大，不能直接沿用一个“小缓冲肯定够”的结论。实际记录器的编码长度可能不同，最终用测得事件率和实际记录大小更新。

### 7.4 选一个可用导出通道

| 已有条件 | 操作路线 | 验证点 |
| --- | --- | --- |
| 原产品已有导出接口，带宽和上下文适合 | 后台任务取缓冲数据，沿现有接口传到电脑 | 不在业务热路径阻塞，记录长度／分块编号完整 |
| J-Link／RTT 可不停核读内存 | 接入 SystemView／RTT 或现有 RTT 记录方案 | 各核地址可达、缓存正确、传输无未解释丢失 |
| 可调试读内存，但没有连续通道 | 短窗口记录后冻结记录，按现有调试器流程导出 | 取回正确地址、长度、环形顺序和版本信息 |
| 只有串口或网络 | 在可用产品接口上增加小型后台导出适配 | 带宽、任务负载、断连与重试处理明确 |

两核记录若只能通过待测核间链路转发，仍各自在本地保留，并说明该通道坏时可能同时失去远端记录。优先核实是否能独立读出两侧内存。电脑端重新连接不能让板端自动清空尚未取回的故障记录。

自定义二进制记录使用自己的解析器；不能简单改名为 `.SVDat` 就声称 SystemView 能打开。使用 SystemView 记录器时按其实际格式和官方导出方法处理。

## 8. SystemView 适配和使用操作

### 8.1 已核实的工具能力与产品待确认项

截至本文查阅日期，SystemView 官方已提供多核采集方式；每核可以运行不同 RTOS。官方多核接法采用各核独立 RTT 缓冲及统一控制块，要求按其方案满足访问和初始化条件。[官方多核接入][S02]

在线用户手册标识为 SystemView 4.10，本文不据此断言所有下载包的最新版本。手册说明可在未接入 RTOS 跟踪的系统使用应用事件；DataPlot 列出 U32、I32、float，未列出 double。多核统一时间显示要求共同时间基础。[SystemView 手册][S01]

| 产品检查项 | 怎样确认 | 不满足时怎样继续 |
| --- | --- | --- |
| 工具与目标匹配 | 记录 PC 软件、目标记录源码、编译器版本；检查本工程的编译结果 | 使用已适配记录器／最小后端，不擅自升级产品工具链 |
| A7 等 ARMv7-A 的不停核读内存能力 | 查具体 SoC 的调试访问通道、现有探针配置和实际读写结果 | 采用后台导出或短窗口事后取回，不默认停核读取满足实时要求 |
| A55 等 ARMv8-A 的 RTT 条件 | 查是否存在且已选定可访问记录内存的 BG MEM-AP | 没有该能力则换导出方式；不能假设 RTT Stop Mode 可替代 |
| 两核记录可达 | 验证所选调试接法能读到两侧实际缓冲 | 分别取回或使用可证明正确的另一接法，标明时间关联限制 |
| 缓冲区内存属性 | 检查地址映射、缓存、对齐及初始化时序 | 调整采集缓冲的放置／访问方式，不改变业务协议布局 |
| 应用事件与系统事件 | 检查是否已有 RTOS 钩子和可用中断／任务信息接口 | 先记录本仓应用事件，不能假装已获得完整调度轨迹 |

ARMv8-A/R 的官方 J-Link 说明明确：RTT 需要后台内存访问 AP，且不支持 RTT Stop Mode；选通道可能需要芯片专用配置。[ARMv8-A/R 说明][S03] Cortex-A 的后台内存访问会绕过 CPU 缓存，因此需落实对应内存可见性要求。[RTT 说明][S04]

这些资料证明方法存在，不证明用户板卡已经适配。不得照抄官方样例中的芯片地址、AP 编号、Cortex-M 时间戳寄存器或中断号获取方式到 A7／A55。

### 8.2 先打通一个应用事件

1. 从当前已有环境取得匹配的目标端记录源码和 PC 工具，优先使用现成配置。加入的是采集组件，仍不要求下载或重编通信依赖源码。
2. 在产品测试构建中接入记录组件，配置本目标可用的时间源、缓冲区、并发保护和初始化位置。首轮先在明确安全的业务任务点记录一个事件。
3. 按已核实的方式取回该事件；检查设备版本、点位、原始值和计数，证明记录来自本次板端运行。
4. 把同一公共采集接口接到已确认的点位，重新构建产品。若缺完整 RTOS 适配，报告只显示应用事件的范围。

不照搬“几行代码、几分钟完成”的宣传估时；本任务结束条件是实际事件能取回并正确解码。

### 8.3 多核接入

按所采用的 SystemView 官方多核方案，配置每核通道和缓冲、控制块的初始化归属、主连接侧的可访问范围以及各核身份。共享控制块只由指定初始化方建立，其他核不能在启动或重启时无意清掉已有记录。[多核配置说明][S02]

单核复位后需要新启动标识，并重新确认缓冲和时间轴状态。如果芯片隔离条件无法满足统一读取，可分别采集再在电脑端关联，但不能把任意两份文件直接叠加为已校准的多核轨迹。

### 8.4 浮点展示与业务原始记录

对于经验证的 float 曲线，使用实际版本提供的数据注册和采样接口；手册给出的入口为 `SEGGER_SYSVIEW_RegisterData()`、`SEGGER_SYSVIEW_SampleData()`。先注册实际类型，再传样本。[数据采样接口][S01]

曲线用于查看趋势，完整的消息身份、原始字节和状态仍由统一事件格式保留。若使用自定义事件承载 double 原始字节，应验证编码和电脑端解析；不能将 double 数值强转成一个 32 位参数。若图形界面暂时不能无损显示该类型，先在统一节点表展示原始数据和正确解码值。

若样本先放入本地缓冲，稍后由后台转发给 SystemView，必须确认展示时间使用的是原始采集时刻；普通发送时刻不能冒充原业务发生时刻。适配暂不支持原始时间时，SystemView 展示注明转发时间，因果和延迟分析使用原始记录。

### 8.5 三种使用流程

| 方式 | 操作顺序 | 必须留意 |
| --- | --- | --- |
| 连续读取 | 配好目标与通道，启动记录，执行测试，停止并保存 | 连续读取是否停核、带宽、丢失、时间戳和保存文件是否完整 |
| 短窗口记录 | 产品端启用记录，执行指定窗口，停止写入，按调试器／工具流程读回 | 停止记录不同于暂停 CPU；缓冲大小和实际长度要准确 |
| 故障前记录 | 设置滚动记录并保留最近事件，运行复现，异常后读回 | 旧记录覆盖范围、复位清 RAM、连接调试器是否改变现场 |

SystemView 的短窗口方式可在没有连续 RTT 的条件下记录后读出；应遵循实际版本对缓冲地址、长度和文件格式的要求。[单次记录操作][S11] 故障后分析利用滚动缓冲保留最近事件，前提是现场仍能读出；记录工具不会自动保证断电或复位后的 RAM 留存。[故障后记录说明][S12]

如果暂时没有探针，不先要求购买。先查产品现有串口、网络或导出能力是否能完成本轮短窗口；没有任何读取办法时，明确阻塞在“记录取回”，继续完成可完成的构建与解析工作。

## 9. 真正上板的一轮操作

### 9.1 构建测试固件

在选定执行器运行产品原构建入口，启用本轮点位和采集开关，保持原产品配置、依赖、浮点 ABI、pack 和优化级别。记录退出状态、实际输出路径、固件／依赖哈希与本次编译证据；不能只看最后一行成功提示。

核对本轮改动确实参与了编译／链接，旧增量产物没有掩盖新增点位。若需重编，只重建原构建系统判断必要的目标；发现增量失效时按其正常清理机制处理相应输出，不删除整个环境。

保留符号／MAP／匹配的反汇编等定位材料，并核对最终使用真实通信库。查清 DT 宏、测试桩、链接替代和配置分支，避免把上板采集构建成“看似收到”的桩路径。

### 9.2 部署并确认跑的是本次版本

使用已指定测试设备和原有部署流程，按实际范围更新需要接入的程序／核镜像，不猜测刷写命令。两核程序可能独立加载，也可能打包在一个产品镜像中，应以产品原流程为准。

核对板端报告的版本／构建标识和采集点集，与本轮元数据对应。若无法直接读取固件哈希，可结合实际部署记录、板端构建标识和本轮独有点位元数据确认，并说明证据强度。仅有电脑上编译成功或文件上传成功，不能证明板上执行的是这份程序。

若执行 AI 当前只具备构建机访问能力，先准备完整构建产物、部署目标、原操作入口和验证方法；不能虚构设备已连接、已烧录或自动新增一套连接流程。

### 9.3 校验记录器已准备好

在真正发测试输入前，检查可接入两侧的启动标识、采集使能、缓冲状态、点位集和时间源。采集从业务启动前开始还是启动后开启，要写清楚：启动后才开启的记录不能用于证明此前启动阶段发生了什么。

每核先发一个已知应用事件验证取回；确认数据不会混入上一轮，解码器能识别当前格式，并且控制命令确实生效。没有“接收就绪”事件时，先区分没接入、没开启、没执行到和导出失败。

### 9.4 按真实入口注入信号

沿原界面／协议工具／产品测试入口输入所选信号，记录实际注入位置、原始值、时间或序号，以及需要的其他输入与模式。测试值从合法业务范围选取；文中的 `50` 和 `0.5` 只是解释例子，不自动成为所有信号的合法用例。

如果实际从某个中间接口注入，就从那里计算本轮动态覆盖，外部界面之前的部分保留原状态。绕过的环节不能因为拓扑图上存在就填“设备实测通过”。

先执行一个足够排空前序消息的受控短场景，随后根据结果增加连续更新和必要状态变化。不能通过修改消息协议、改变业务 pack 或用成功桩来方便本轮采集。

### 9.5 停止记录并取回

按选定策略停止采集或冻结记录窗口，保持产品处理是否继续运行的事实清楚。先读元数据和缓冲索引，再按记录器要求取回完整数据、丢弃／覆盖统计及结束标记；环形缓冲须按实际顺序重组。

导出前后核对记录数、有效区间和完整性。若只能在停机后读取，说明采集阶段是否一直自由运行以及何时暂停；不能把暂停后的值当作暂停前某次处理的值。

将两核原始记录、对应元数据和必要异常资料保存在按测试编号组织的目录，记录路径所属环境和文件哈希。正式报告引用这些证据，不复制全部原始数据。

### 9.6 异常出现时怎样保留现场

尽可能先取回已保存的记录，再按原测试流程复位／重跑。若故障导致记录器无法结束，解码器仍应识别此前完整记录和最后的不完整尾部。自动复位或断电会清掉哪些内存必须查清；`.noinit` 名称本身不保证硬件复位、启动代码或电源变化不会清掉数据。

已暴露的复位原因、异常状态、任务信息可以并入同一测试证据。统一信号记录能缩小故障前后经过的位置，不保证自动得到崩溃调用栈或精确定位到二进制依赖内部函数。

## 10. 两核记录如何配对和判断

### 10.1 先验证记录质量，再判断通信

电脑解析顺序为：校验版本与记录完整性，标出重启和覆盖区间，按各核本地记录序号检查缺失，再按实际消息身份匹配业务事件。时间线、曲线和节点表都从同一份解析结果生成，不能让 AI 单独另算一份数值填表。

优先使用已有协议序号，加上来源／目的、通道、信号和启动轮次等必要信息形成匹配条件。记录器自己生成的本地序号用于采集完整性，不是跨核共享消息序号。两侧都叫第 18 条或都显示 `50`，不能直接配对。

如果接口没有可透传的消息身份，不擅自修改原协议。可在明确排空、无其他同类消息且仅一条在途的受控场景下建立有条件对应；记录残余队列、重复输入和后台消息的限制。内容摘要、接近时间或特征值只能作为匹配线索，不能证明唯一身份。

### 10.2 数量关系遵循实际产品语义

不能默认每次发送一定对应一次回调。队列可能合并更新，订阅可能一对多，周期处理可能重复读取最近值，协议也可能重试。先核对本信号允许的行为，再检查丢失、重复、顺序与延迟。

实际关系为一对多／多对一时，节点表保存消息到多个消费事件、或多个输入到一次执行的对应，不强压成一条直线。明确触发、使能、订阅和默认值：未触发／未使能应显示对应状态，不能统一显示为“丢包”。

### 10.3 时间与跨核延迟

各核先保留自己的原始时钟。若有已核实的共同计时器，可建立共同时间轴；若需校准，保留偏移、频率／漂移及误差范围。SystemView 手册也要求多核统一时间有共同基础。[时间显示条件][S01]

时钟关系未确定时，仍可以按消息身份核对是否到达和数值，但不要直接相减两核 tick 给出精确延迟。频率相同不等于时钟起点相同；PC 收到两条日志的先后顺序也不等于板端事件顺序。

“调用前到业务回调”的耗时包含排队、调度和处理等环节，准确名称应是该两点之间的端到端耗时；不能未经拆分写成纯核间硬件传输耗时。

### 10.4 常见现象与下一步

| 看到的记录 | 当前可以说什么 | 下一步重点 |
| --- | --- | --- |
| 有调用前，未见返回 | 调用退出尚未被证明 | 看异常／阻塞／非正常退出和采集完整性 |
| 调用返回成功，未匹配到接收 | 业务接收尚未被证明 | 核对返回语义、订阅与路由、队列条件及接收侧是否漏采 |
| 两端消息匹配，字段不同 | 该两点的数据存在差异 | 查协议解码、布局、类型、合法换算及并发快照 |
| 接收正常，图元未执行 | 接收已证实，图元执行未证实 | 查使能、触发、实例、周期和输入更新方式 |
| 某核没有就绪／心跳记录 | 未观测到该核对应阶段 | 区分核未启动、程序未到业务、记录未启用及读回失败 |
| 两核记录同时中断 | 记录中断事实成立 | 区分采集通道断开、缓冲满、复位和系统故障 |

不能把缺记录直接升级为硬件丢包，也不能把一次受控场景成功扩大为所有运行条件可靠。

## 11. 与 BEH 工具源码和 AI 图元测试结合

### 11.1 三份材料一起核对

读取 BEH 工具源码仓，定位图元文件加载、信号订阅、实例／端口标识、执行入口和输出读取；读取已跑通 AI 图元测试，复用其真实 Java 引擎调用；读取产品实际使用的图元工程和配置，确认文件／格式版本、连线、参数和执行模式。

工具源码说明通用能力，产品图元工程才说明本次实际连接。编辑器源码不自动等于引擎实现；引擎位于 JAR 等依赖时，应绑定其版本和实际测试入口。

### 11.2 先确认板端图元是什么关系

| 实际情况 | 应怎样采集和对照 | 结果名称 |
| --- | --- | --- |
| 板上存在对应图元执行代码，且可接入 | 记录真实输入、状态／周期和输出，再与匹配条件下的 BEH 结果比较 | 板端图元实测＋BEH 引擎对照 |
| 板上只能取得向图元交接的数据 | 保存交接值和条件，回放到 Windows 原引擎 | 板端交接实测＋BEH 回放 |
| Java 引擎与板端是同一图元的不同实现 | 同输入、配置、状态和时序语义下分别运行 | 实现一致性对照；不能当作两个串行节点 |
| 对应关系尚未明确 | 根据源码、生成记录和实际图元工程补查 | 映射待确认，不伪造交接已完成 |

### 11.3 回放的具体操作

1. 从已核实交接点提取本轮输入，绑定图元工程和引擎版本；记录每个输入对应的实例、端口、类型、单位和有效状态。
2. 建立原测试引擎所需初始状态，明确复位／初始化、使能、参数、必要其他输入及计时方式。状态型图元需要输入历史或足够的初始化过程，仅一个当前值可能不足。
3. 按已核实的更新顺序和执行周期回放，包括无更新周期、保持值、边沿和超时等本场景确实相关的行为。缺少必要条件时标明受限回放，不让 AI 猜成实测输入。
4. 读取图元输入、相关内部可观测点和输出，保存原引擎的成功／异常状态。测试入口出错、图元未执行或读到旧输出时不能写通过。
5. 合并到同一链路表，来源分别标为“设备实测”“BEH 引擎实测／回放”。与不上板推算、DT 实测保持各自来源，不用一种值替代另一种。

若已经能取得板上图元输出，比较前先明确双方精度、舍入、状态和容差依据；若只完成回放，只能证明该输入与这些条件下 Java 引擎的处理结果，不能证明板上图元及真实交接均已运行正确。

## 12. 验证采集本身，并验收首条链

### 12.1 只做能解决具体风险的检查

| 检查 | 怎么做 | 通过要求 |
| --- | --- | --- |
| 版本与点位命中 | 核对最终固件、板端构建标识、实际事件和清单 | 能对应到当前源码、采集配置及依赖，不混入旧轮次 |
| 原通信仍执行 | 检查最终链接和一次真实收发 | 原接口调用及接收可证明，没有成功桩代替 |
| 类型与精度 | 使用合法范围内可辨识的值，检查实际字段及原始字节 | 没有 double 截断、对齐误读或字符串精度损失 |
| 并发与完整性 | 在实际会出现的任务／中断上下文和负载下短测 | 无半写、错误配对、未说明的覆盖或丢失 |
| 采集扰动 | 在同条件下比较关闭采集与开启采集 | 周期耗时、抖动、CPU／内存与超时满足本产品测试预算 |
| 合并器能发现缺口 | 对一份离线记录副本删除／打乱一个事件，再解析 | 明确指出缺记录或无法匹配；此项不计作设备通信故障测试 |
| 适用异常场景 | 利用现有测试条件构造一种可控制的实际异常 | 报告能区分业务异常、未观测与采集故障；保留真实执行范围 |
| BEH 对照 | 原引擎按对应配置和输入执行 | 结果和错误状态可重跑，来源及回放边界明确 |

离线破坏记录只测试解析器；DT 中打桩只测试相应软件逻辑。只有在已指定测试设备和既有操作范围内实际触发的异常，才能标为板端异常验证。没有合适板端故障条件时保留缺项，不为凑验收随意制造崩溃。

### 12.2 对开销不预填一个“安全百分比”

先读取产品已有周期和资源预算；没有明确预算时报告开启前后的测量差异，由对应人员确认可接受程度。不能把官方在其他 CPU 上的典型耗时直接套给本板，也不能以采集后“看起来还能跑”作为实时性判定。

测量包含记录器本身、导出任务、缓存维护与新增中断等本轮实际开销。必要时区分编译移除采集、采集运行时关闭和采集开启的版本差异，避免把开关关闭状态当作与原固件完全相同。

## 13. 工程交付、唯一报告与有限收尾

### 13.1 最小工程成果

优先放入产品已有测试／工具目录，不要求新建仓库或平台。至少保留点位清单、统一采集接口与接入补丁、必要后端配置、电脑端解码／匹配代码、BEH 适配以及实际运行证据。

提供一个主入口或一份按序执行的操作入口清单，能够完成准备／构建、按现有方式采集／取回、分析、BEH 对照、更新报告。能直接复用原脚本的就调用原脚本。需要新入口时，给出真实命令、参数和示例运行结果；本文没有规定一个已存在的脚本名字。

构建与设备操作分阶段调用，运行报告生成不应顺带刷写或复位设备。脚本处理空文件、版本不匹配、命令失败和记录不完整时应返回清楚的失败／部分成功状态，不能仅因成功创建 Markdown 就返回“整链通过”。

### 13.2 只交一份正式结果报告

正式报告固定为 **`上板信号全链路采集建设与验收报告.md`**，后续在同一份更新。原始日志、输入、脚本、数据库、固件和查询是可重跑的支撑，不另外生成一堆环境报告、工具报告、浮点报告、BEH 报告和摘要文件。

报告按以下顺序组织：本轮目标与三项完成状态；版本和执行环境；真实链路与点位；接入和导出方法；上板操作及原始证据；跨核对应与节点值；BEH 对照；扰动和异常检查；缺口、结论修订和下一步；最后简短概述。

每项关键结论保留“证据位置、实际命令／步骤、关键输出、可以证明的范围”。路径注明 WSL／远程执行器／Windows／板端，源码记录 commit、文件、函数和位置，运行记录带测试编号。决定结论的证据不能只留在即将清除的临时目录。

## 17. 设备信号与 POU 执行采集：复用开关、数据库和导出（2026-09-20）

本节承接用户可修改的现有设备信号采集逻辑，不要求保留定时采样。作为[真实场景方案](../../真实场景集成验证/端到端用例与POU验证/01_场景实施方案.md)的公共采集设计复用。被场景调用时，本文的结果报告作为总任务报告相应章节或已有报告引用，不强制维护第二份结论。

### 17.1 先盘点现有实现，再改取值时机

查明开关的实际入口/调用链、记录读的是接收载荷还是转换后的对象/缓存、写库线程、表结构、导出、保留和容量策略。按真实信号从接收/解析/更新处保存一次事件；对选定 POU 保存每次必要执行的实际输入、阶段和结果；模式、负载等背景按需定时记录。已有成熟记录器先复用，缺少能力才增加最小适配。

定时方案仍可用于慢变或趋势场景，报告其采样周期和局限。不能由稀疏样本证明没有短暂跳变。只记“值变化”也可能丢失重复接收、质量/使能变化、超时或版本推进，应按场景的回放及诊断需求决定事件范围。确认同一次接收中各字段是否属于同一设备采样，不能靠同时入库伪造原子快照。

### 17.2 一次会话的控制与状态

1. 先准备已核实的设备/信号/POU 白名单、点位与格式版本、容量和导出路径，不改变业务状态；若测试要求业务初始化，将其作为独立用例步骤记录。
2. 打开现有开关后创建采集会话，分发适用配置；各执行域记录实际启用状态、启动代次及首序号。部分域未开启时显示部分采集，不声称同时全开。
3. 确认采集就绪再执行用例，保存必要初始化/预热数据。手工标记异常或按已确认契约触发保留窗口，记录触发依据及各域实际覆盖。
4. 关闭开关停止新增采集；后台排空已有记录并导出。区分“停止请求”“各域已停止”“导出完成”；某域收不到控制、写库失败或仍有未导出数据须可见，不虚报全部停止或成功。

窗口时长由事件长度、实际峰值速率、可用容量和导出速率决定；异常前数据保留依赖环形缓冲或持续可靠导出。记录自动触发/冻结本身的实际时刻，不宣称所有核瞬时同步冻结。

### 17.3 关键路径只做有界记录

在合法取值点复制原代码当次实际使用的必要数据；保留类型/位模式、对象身份、阶段和关联。不能仅存指针，不能后台重读已经更新的变量，不能为日志重复执行 getter、短路条件、读清寄存器或改变锁范围。POU 内部读取发生在不同阶段时分别留证；多字段非一致快照明确标记。

复用适合平台的预分配缓冲与并发记录器。每核仍可能有多任务/中断，不等于单生产者；明确预留、写入、提交、读取、重入和溢出策略。热路径不同步写数据库/文件、不等待导出、不无限分配；满时保持业务行为并使丢失可见，不把“未见事件”直接当没发生。

有文件系统的环境由后台批量写文件或入库；没有文件系统的核使用可用的共享区、诊断、串口或已验证探针通道导出到主核/电脑。共享通道和缓存一致性按平台约定处理，不借采集给业务偷偷增加同步。受调查 IPC 不应成为未说明风险的唯一取证通道。需跨复位保留时核实介质和启动覆盖，普通 RAM/noinit 不保证所有复位或断电保留。

### 17.4 数据库与文件各自承担什么

现有数据库用于查询、筛选和索引；原始记录可以是数据库原始事件行，也可以是文件，按既有工程选择，避免双写失去对应。若表原先只覆盖“最新值”或聚合趋势，应在兼容现有功能的前提下增加事件保存能力，并记录格式/表版本及迁移。

后台异步保存应保留源域启动代次和事件序号；断线/重试的重复导出用完整身份去重，不能按值相同或时间接近删除合法事件。批量顺序不是跨核因果顺序。保存来源/接收/执行时间的可用值及语义，入库时间另列；未知设备时间不伪造。

导出一份可携带的数据包：原始事件或数据库一致导出、格式/字典、产品/EMAP/模型/配置身份、映射与采集配置、每域起止序号/丢弃覆盖统计、控制/Debug 状态和文件摘要。确认导出完整性；仅导出部分窗口必须声明。电脑端再转换成可读表或 Runner 输入，保留原始证据，不在实时路径生成大段 JSON。

### 17.5 关联、机制与回放验收

capture_id 只关联同一场测试，跨核还需真实消息/对象/数据版本以及拆分、合并、重试和替代关系；跨域时钟不默认同步。关联不唯一时保留候选，不按相同数值强行拼链。原协议无适用身份时先核实已有键或旁表能证明的范围，不能未经验证改变报文布局。

除值以外，记录实际执行的决策条件及结果、采用版本/缓冲、使能/模式、返回语义、覆盖/合并/超时和相关状态修改者。机制由实际代码确认，翻面只是候选之一。首次异常只能缩小区间；追到状态来源或最早违约还需要对应证据。

首轮验证：已知输入能否在预期点位被正确记录和解码；同一执行能否关联；采集关闭/开启对业务结果、周期耗时和负载有何影响；缓冲溢出/导出失败是否可见；文件与数据库能否完整取回。不要宣称零扰动。必要对照使用匹配业务条件，BEH Debug 默认不作为采集前提，按[已知问题](../BEH原生能力/BEH已知问题与观测适用边界.md)独立记录开关。

设备输入与 POU 实际消费值分开保存。回放优先用后者，连同状态、参数、质量/使能和时间/事件；仅有设备输入时需经过已验证的上游转换。不能将缺失状态补零或稀疏采样补成逐拍真值。按场景方案输出板端实际、离线实际和独立预期，相关软件未执行或底层不可见时保留边界。
