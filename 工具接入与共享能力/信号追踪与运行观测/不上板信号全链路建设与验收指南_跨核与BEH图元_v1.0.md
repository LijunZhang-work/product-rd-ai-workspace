## 1. 目标、范围与完成含义

由真实场景入口调用时，按声明的 POU/业务边界选用本指南的方法；下文“整链完成”的要求只用于宣称整链覆盖，不是先运行一个 POU 的前置条件。结果可并入总任务报告或引用既有报告，不强制维护第二份结论；未执行的跨核/硬件段继续明确标出。

### 1.1 必须保持的整链目标

围绕一条已经开展过追踪的业务信号，从外部设置入口开始，把产品组件内的处理、跨组件／跨核边界、接收侧业务、图元订阅、BEH 内部处理和最终输出对应起来。实际存在的算法分支、条件分支、反馈和多周期状态也要纳入该信号的相关范围。

第一条可以只做一个代表信号，但其范围必须延伸到跨核和 BEH 图元。不得把“某个 DT 通过”“查到发送接口”“图元单独运行成功”当作整项任务的终点。具体拓扑以产品当前配置、源码、二进制证据及图元工程为准；GOOSE、Modbus、算法层是否在这条路径上，应查证，不能把所有候选模块硬串成一条线。

最终建立两种可配合使用的能力：

| 能力 | 建成后能回答什么 | 主要依据 |
| --- | --- | --- |
| 不上板整链分析 | 信号经过哪些位置，跨核两端怎样对应，图元接在哪里，各处可能怎样转换，哪里仍缺证据 | 产品配置下的 CodeQL、源码和配置、必要的二进制检查、BEH 源码与实际图元工程 |
| 不上板运行与对照 | 哪些产品业务段能在电脑上实际执行，如何与原 BEH 引擎衔接，各节点取得什么值，结果与产品定义存在什么差异 | 现有 DT／测试入口、适用的 Linux 依赖、明确标注的衔接适配、原 Java 引擎和运行记录 |

不上板也包含真实的软件执行。需要区分执行的是哪份程序、哪种依赖、哪个入口，以及哪些硬件和调度行为没有进入这次运行。

### 1.2 本期交付的是可用能力

执行 AI 需要在现有工程中落地必要的查询、映射、适配和总控入口，运行代表信号及必要的检验用例，并输出一份有证据的结果报告。不能只写“建议以后接入”，也不能只生成漂亮的链路图而没有来源和执行记录。

必须分别报告三个完成状态，避免一个“完成”掩盖含义：

| 状态维度 | 完成的含义 |
| --- | --- |
| 建设完成度 | 查询、映射、运行衔接、取值、差异检查、结果汇总等约定功能实际实现并验证到了哪一步 |
| 所选链验证范围 | 哪些连接有静态／接口证据，哪些在主机实际执行，哪些通过回放，哪些仍被替代或阻塞 |
| 业务正确性 | 哪些期望有设计依据且已检查，哪些只有观测结果、仍待用户和设计人员核对 |

存在缺口时可以交付已经能用的部分，但状态应写“部分建成，具体阻塞为……”。不能因报告已列出缺口就自动宣布全链已跑通。反过来，真实板硬件时序尚未验证，不应否定已经取得的不上板分析和软件执行结果。

### 1.3 必须继承的已知条件

下表中的“用户已说明”来自当前对话；执行时补充工程证据，不重新让用户逐项解释。

| 项目 | 当前条件 | 执行要求 |
| --- | --- | --- |
| CodeQL | 已按产品业务侧配置跑通追踪 | 复用原数据库、查询和结果；改动影响数据库时按实际范围更新 |
| 现有节点值 | 用户确认来自源码推算 | 标为条件推算，保留公式和前提，不自动转成实测 |
| DT | x86 Linux 中已有脚本实际运行用例 | 复用现有入口；记录真正执行的用例与代码范围 |
| DT 跨边界接口 | 发送接口目前打桩 | 查清桩的范围；为整链测试增加能够保留真实输出的衔接方式 |
| 接收侧业务 | 本产品仓库可见 | 纳入静态分析及可运行的业务联调，不停在发送侧 |
| 通信实现 | 消息路由、核间传输、GOOSE／Modbus 驱动位于 `art get` 下载的二进制包 | 使用现有包、头文件、配置和产物；只研究本信号相关实现 |
| Linux 测试依赖 | 有对应版本，但用户发现过与产品侧的差异 | 单独核对依赖行为与数据表示，不能仅凭同名认定等价 |
| 对齐问题 | 用户指出过 4 字节与 2 字节的差别 | 定位具体类型、成员、地址及构建条件，不预设哪边是 4、哪边是 2 |
| 主核／实时核 | 用户提供“主核 RTOS、LLVM；实时核 A55、RTOS、lite RT”线索 | 原样保留并查构建证据；LLVM 不作为 CPU 型号，系统正式名称和运行模式仍需核实 |
| BEH | Windows Java 引擎的 AI 图元测试已跑通 | 结合工具源码仓、测试代码和实际图元工程，复用已有能力 |
| 业务期望 | 先展示各节点值，再与设计人员核对 | 未确认期望写待核对；已有明确接口规则可以先自动检查 |

### 1.4 本期边界与自主推进原则

本期建设不上板能力，不实施上板采集，不以 Renode 或重建整块板的仿真环境作为前提。优先复用已有依赖；当前已准备的匹配 EMAP 源码可参与分析和必要的测试改动，重编/替换须核实版本及产品消费关系。更深第三方不能默认可改；允许修改、编译可控制的产品/EMAP 代码和必要适配。

优先采用现有查询、编译器、测试框架、BEH 引擎和脚本。缺少某个公共入口时做最小适配，不为这一条链新建大型平台、统一插件框架或全产品知识库。接口、路径、宏和命令由执行 AI 从工程查明；只有工程无法回答且影响任务目标或业务期望的问题，才集中向用户确认。

## 2. 必须结合的材料与版本关系

### 2.1 四类工程材料一起进入分析

| 材料 | 至少取得什么 | 对应工作 |
| --- | --- | --- |
| 产品业务源码及正式构建资料 | 仓库版本、产品配置、相关生成代码、CodeQL 数据库、实际编译／链接记录 | 外部入口、业务字段、发送、接收、配置和目标数据表示 |
| BEH 工具源码仓 | 当前分支／commit，图元模型、加载、生成及引擎调用相关代码 | 区分编辑器结构、生成规则与真正执行逻辑，建立可溯源映射 |
| 已跑通的 AI 图元测试 | 原测试代码／脚本、实际 Java 可执行入口、引擎文件、输入输出和至少一个已有结果 | 复用加载、输入设置、执行、取值及错误处理 |
| 产品实际使用的图元工程和配置 | 图元文件、实例、端口、连线、参数、默认值、使能、初始化及周期相关设置 | 确定这条产品信号真正落到哪个图元和哪次执行 |

工具源码只说明通用编辑或执行能力，不能代替实际图元工程。已有测试样例也不能代替产品正在使用的图元版本。若引擎实现位于 JAR 或其他依赖中，记录真实调用及二进制版本，不把编辑器源码当作引擎实现。

同时读取已完成的环境排查报告，直接采用有证据且仍有效的结论。只有版本变化、证据矛盾或缺项影响本轮实现时，才针对该项补查。旧任务书是检查要求，不能当作已完成的检查结果。

### 2.2 建立一份最小版本记录

记录产品 commit 和相关未提交改动、产品配置、DT 配置、实际依赖包版本／哈希、最终链接或装载到的实现、CodeQL 工具与查询版本、BEH 工具源码版本、Java 引擎哈希、图元工程和测试输入哈希。

下载包名与实际参与链接的包可能不同，应跟随链接记录核实；静态库最终合入程序时，用链接记录和最终产物共同定位。存在重复包、缓存或不同目录同名库时，不以“最近下载”代替实际使用证据。

所有本地／远程路径带所属环境标识。跨环境传递的输入和结果绑定同一个运行编号及版本记录；文件内容需要传输时核对哈希。日志出现成功但找不到本轮输出时，先排除旧结果复用。

## 3. 两种执行方式与最小工程组织

### 3.1 执行方式

| 方式 | 产品分析与主机测试 | BEH 执行 | 对接方法 |
| --- | --- | --- | --- |
| A：WSL＋现有产品镜像 | 沿用已成功的源码挂载、环境初始化、产品构建和 DT 命令 | Windows 原 Java 入口 | 总控调用已有 WSL 入口，交换带版本的输入／结果 |
| B：SSH＋现成 Linux 执行器 | 在远程已有对应产品环境内执行，不先复制整套环境 | Windows 原 Java 入口 | 调用已有 SSH 配置和远程脚本，传递必要数据，再调用本地 BEH |

两种方式都要能配置接入，按实际可用条件验证其中一种即可。不要求为证明双环境支持而重复构建。只有实际验证过的方式才能标为已运行；另一种写清已实现的配置能力与未验证项。

构建目标程序与在主机运行 DT 是两个入口。不能把为 RTOS／目标 CPU 编译的可执行文件或库直接当成 x86 Linux 程序运行。CodeQL 建库需要观察真实构建，不能因为本地命令触发了远程编译，就默认远程编译已被本地提取器收集。

Windows 与 WSL 可通过已有命令入口互相调用；采用哪一侧作为总控，优先沿用现有 AI 图元测试的组织方式，不强行迁移 Java 引擎。[Microsoft WSL 互操作说明](https://learn.microsoft.com/en-us/windows/wsl/filesystems)

### 3.2 Docker／CodeQL 资源复用与清理约定

沿用此前约定：**优先复用现有产品镜像、已有运行环境和仍然有效的 CodeQL 数据库，不因每次任务、每条信号、每轮查询或失败重试，重复创建一套同样的环境。** 编译、分析、DT、图元联调和 AI 辅助定位均遵循这项要求。

1. **先检查已有资源，再决定是否新增。** 确认当前执行器、产品镜像 ID／digest、已有容器和挂载、源码／产物目录及数据库对应版本。已有排查记录仍有效时直接复用，不能只因容器名称不同或镜像显示大小相近就认定需要重建。
2. **有效数据库和产物优先复用。** 只修改查询、切换信号或重跑分析时，先使用与源码、产品配置及工具兼容条件匹配的已有数据库。源码、构建条件或依赖变化导致旧结果失效时，才更新相应结果或另建所需数据库，并记录原因；不能为节省空间误用过期数据库，也不能把每次分析默认变成重新建库。
3. **必要隔离或并行允许临时容器。** 需要隔离版本、避免相互污染或并行执行时，可从适用的现有镜像启动本任务容器，明确用途和生命周期。不同任务的可写构建目录、输出或数据库应避免互相覆盖；不要仅为获得另一个容器而复制一份相同镜像。
4. **仅在现有环境确实不满足时新增镜像。** 先指出缺少的编译器、工具依赖或版本条件，确认无法直接复用现有合适环境，再新增必要镜像并记录用途。已有 SSH 执行器满足要求时直接使用，不额外在 WSL 重建同一套环境。
5. **成果必须保存在容器外的明确持久位置。** 数据库、查询、输入、必要产物、日志、报告、补丁和分析缓存按需放到挂载的持久目录，不能只留在临时容器可写层或未明确管理的数据卷。临时容器移除后，保留的结果仍应能从执行器取得并用于重跑。
6. **结束时清理本任务的可丢弃资源。** 清理前核对成果已保存、资源由本任务创建、没有其他任务占用、也不再承担后续重跑所需内容。随后清理本次临时容器及确认无用的临时资源；需要保留的对象记录用途。失败或中断后的下次恢复，也要识别本任务残留，避免每次重试再留一套。
7. **保护共享和已有资源。** 保留产品原有环境、共享镜像／缓存、仍有效的数据库及其他任务资源。不使用 `docker system prune -a`、全局数据卷清理或按名称批量删除作为本任务收尾；不凭“看起来重复”就删除历史资源。

镜像、容器、数据卷、构建缓存和 CodeQL 数据库分别识别；外观相似不能证明它们都由 CodeQL 创建，也不能据此相加估算实际占用。唯一报告中简短记录复用了什么、为何新增、成果位置及本次清理／保留情况，不另交一份资源审计报告。本段规定后续执行方式，不要求本轮顺便清理用户的整个 Docker 环境。

### 3.3 最小工程组织

实现优先放在已有工具／测试目录。没有合适入口时，可使用下列最小组织；名称只是建议，不代表已存在：

| 内容 | 建议位置或复用方式 |
| --- | --- |
| 总控入口 | 一个 `chain_run` 脚本，语言沿用现有 Python／PowerShell 等 |
| 场景配置 | 一份配置描述执行器、已有入口、信号、图元与测试场景 |
| 代码关系 | 复用原查询目录，补充少量查询及结构化链路输出 |
| 运行适配 | 在现有 DT 和 BEH 测试旁增加必要适配；仅新增确实缺少的接口 |
| 原始证据 | 按运行编号保存必要命令、输出、值记录和版本信息 |
| 用户报告 | 统一更新一份 `不上板信号全链路建设与验收报告.md` |

“只交一份报告”不等于禁止运行所需的代码、JSON 或原始日志。用户阅读一个主文档，脚本和原始证据作为可重跑的支撑，不另写多份环境、工具、图元和总结报告。

## 4. 建立覆盖跨核与图元的链路模型

### 4.1 先选完整范围，再确定观察粒度

优先从已有 CodeQL 结果选择一条用户熟悉、信号宏明确、确实涉及跨核边界且能对应 BEH 的代表信号。先检查已有候选，避免要求用户重新手工列全链。

分析覆盖外部入口、协议／配置转换、业务处理、发送、跨核接收、后续处理、图元订阅、图元相关内部节点和最终输出。每个已确定的链路节点都有一行记录；不能因为某处取不到值就把该节点删除。

节点粒度以会改变数值、身份、路由、状态或时序的关键位置，以及组件和图元端口边界为主。无需把每条汇编指令变成节点。相关反馈环、多次更新和周期性状态必须保留，不能假设整个图一定没有环。

### 4.2 节点与连接使用不同记录

| 对象 | 最小字段 |
| --- | --- |
| 节点 | 稳定 ID、所属仓库／环境／组件／核角色、代码或图元位置、信号身份、字段类型、单位、取值时机、证据引用 |
| 连接 | 起点和终点、关系类型、启用条件、实际承载字段／通道、类型或缩放变化、依据、静态状态、运行状态 |
| 观察记录 | 运行／场景／事件标识、节点、值来源、真实类型、原始表示、显示值、有效性、关联依据 |

信号身份至少包含宏展开后的 ID 及必要的通道、方向和实例。图元类型名不能代替实例 ID，显示标签不能代替端口标识。若宏在不同产品配置下有不同定义，分别记录对应版本。

连接的静态状态与运行状态分开。例如可以同时存在“源码中有调用关系”和“本次没有执行到”；运行失败不能抹去已经确认的代码关系，源码关系成立也不能自动填成运行通过。

### 4.3 跨工具和跨仓库如何关联

CodeQL 内的数据流、依赖的二进制关系、消息／订阅映射和图元连线分别保存来源，再用已核实的接口与字段关系拼接。多个数据库或不同语言的分析结果不自动拥有统一数据流。

必须核对的连接包括：外部设置项与产品信号、发送字段与消息格式、接收字段与业务输入、产品信号与图元订阅、图元端口与引擎观察位置。查到同名宏是定位入口，还需要调用、配置或实现证据支持连接。

对 AI 推断的关系使用“待核实”状态。后续补证据时保留原判断、新证据、实际查询改动及重跑结果，避免只有文字结论反复变化。

## 5. 产品配置下的业务分析与配置核对

### 5.1 复用并校正 CodeQL

确认已有数据库对应本轮产品配置，相关源文件、有效宏分支和生成代码已纳入。按样本信号分别查外部输入、写入、发送、接收回调、转换、图元相关接口，保留查询文件和原始结果。

数值计算记录“公式＋类型＋启用条件＋初始状态／周期依赖”。已知输入不代表每个分支都能得到唯一输出；条件不足时列出可能分支或待定条件，不让 AI 猜一个数字填满表格。整数截断、浮点转换、限幅和状态保持应按当前实现分别说明。

把已有推算整理为可复查的变换表：输入节点／字段、输出节点／字段、表达式、类型、条件、状态和源码依据。简单且条件完整的变换可由透明的小型计算脚本重算，并明确其为推算器；复杂指针、未知状态、未定义行为或尚未确认的目标浮点语义不能靠宿主计算随意补齐。无需为首版开发通用 C++ 解释器，也不能以该推算器取代产品或 BEH 原实现。

CodeQL 的常规数据流与经过运算后的影响关系有区别；根据问题选择已有查询或相应模型，不能把“找到了影响关系”直接写成“完成了精确数值求值”。[CodeQL 数据流说明](https://codeql.github.com/docs/writing-codeql-queries/about-data-flow-analysis/)

### 5.2 对未连接位置使用固定排查顺序

1. 验证起点和终点集合确实命中预期位置。
2. 确认实现是否进入数据库，当前查询是否选对指针、指向内容和字段。
3. 检查数值变换、调用模型、屏障、范围限制和有效宏条件。
4. 用实际版本的 partial flow 分别向前、向后探索，定位两侧最后一个有证据的位置。
5. 需要新增模型时，限定到匹配版本、接口及字段，并用已知连通和已知不相关的关系检验错连。

缺少函数定义可能造成漏查；官方也说明补充传播规则过宽会引入错误关系。新增规则必须附依据，不能用“相同 ID 就连接一切”的方式追求满图。[C/C++ 复杂数据流](https://codeql.github.com/docs/codeql-language-guides/advanced-dataflow-scenarios-cpp/)、[partial flow 排查](https://codeql.github.com/docs/writing-codeql-queries/debugging-data-flow-queries-using-partial-flow/)

### 5.3 把漏配、漏调用与参数含义纳入本信号

| 检查对象 | 应建立的检查 | 依据不足时怎样处理 |
| --- | --- | --- |
| 触发／初始化接口 | 有效配置下是否有调用或注册；调用次序是否符合现有接口约定 | 区分静态可达、实际已执行与尚未证明 |
| 发送／订阅／路由表 | 本信号需要的项、实例、方向和字段是否一致 | “是否必须配置”要有依据，不把所有缺项都判缺陷 |
| 结构体数组／配置表字段 | 记录类型、默认值、有效范围、使用位置、影响的分支和下游节点 | 区分代码实际含义与设计期望，发现冲突分别列出 |
| BEH 连线与参数 | 对应端口是否绑定、图元实例和使能是否正确、参数来自哪里 | 未确认图元版本时不跨版本套结论 |

需要检查从 A 改为 B 的影响时，保持其他条件固定，生成相关节点、分支、接口和测试输入的差异清单；能运行的部分再执行对照。静态可能受影响不等于本场景必然改变数值，运行未变化也不等于所有场景均无影响。

首版只建立所选信号相关字段的含义表和规则，不提前扩成全产品配置百科。规则优先依赖真实接口、有效配置和确认过的设计，不根据注释臆造必配关系。

## 6. 不取依赖源码时，跨核边界如何继续

### 6.1 把现有包与真实调用对应起来

从现有 `art get` 脚本、锁定记录、解包目录和链接命令，找到本信号实际经过的依赖。分别记录产品包和 Linux DT 包，不能按同名接口推断内部实现相同。

对于缺源码的实现，先读取已有头文件、配置、符号、MAP、实际库及最终产物。`.a`、`.so`、`.lib` 的后缀不能单独确定是否包含所需实现；导入库仍需找到承载实现的文件。

形成一张跨边界对照表：

| 项目 | 发送侧 | 接收侧 | 连接依据 |
| --- | --- | --- | --- |
| 信号身份 | 宏值、消息 ID、方向、实例 | 订阅和回调绑定 | 有效配置及调用位置 |
| 数据表示 | 字段、长度、编码、缩放 | 解包、类型转换和使用 | 头文件、编码实现或二进制证据 |
| 路由 | 目标、通道、发布方式 | 实际映射和使能 | 配置与接口约定 |
| 有效时机 | 初始化、提交、缓冲区寿命 | 就绪、通知、消费和释放 | 可见实现与版本匹配资料 |
| 错误处理 | 返回值、重试、队列满等实际约定 | 拒收、超时或恢复路径 | 适用于本场景的规则 |

接口返回成功可能只代表提交完成，应按真实约定解释。两侧通道号可以不同；同样的地址数字也不自动代表同一块共享存储。库之间完全内部传递且无可用证据的段，保留明确边界。

### 6.2 Ghidra 只补影响本链判断的实现缺口

为关键缺口确定目标函数或对象后，再使用匹配架构和文件格式的 Ghidra 分析产品二进制。通过导出符号、MAP、调用位置、常量 ID 和字段访问定位；核对关键指令、调用约定和类型，保留二进制哈希及地址依据。

优先回答有限问题，例如实际复制多少字节、哪些字段决定路由、调用哪个回调、是否存在特定转换。不要为一条信号全面反编译整个依赖生态。反编译器恢复的变量名、类型和伪代码属于分析结果，不等于原始源码。

需要批量化时，使用当前安装版本的 Headless 模式及其随包说明；现有分析工程可复用。官方入门文档给出了批处理入口及说明文件位置，具体参数以该版本为准。[Ghidra 官方入门](https://github.com/NationalSecurityAgency/ghidra/blob/master/GhidraDocs/GettingStarted.md)

二进制分析可以补实现证据，不能证明目标上本次数据已经到达，也不会自动把整个库转成 CodeQL 源码数据库。确需依据二进制新增传播模型时，模型与原始证据分别保存。[Ghidra 官方项目](https://github.com/NationalSecurityAgency/ghidra)

### 6.3 明确本段采用哪种不上板连接

| 连接方式 | 建设动作 | 可以支持的结论 |
| --- | --- | --- |
| 现有 Linux 依赖可运行相关逻辑 | 核对实际实现范围，接入真实发送、路由／协议处理和接收入口 | 本 Linux 实现及本场景的软件集成结果 |
| 只能运行两侧业务，通信需要替代 | 捕获发送侧实际输出，按有依据的接口契约交给接收侧真实业务入口 | 两侧业务在声明的替代传输下衔接；被替代硬件和内部逻辑另列 |
| 只能得到跨边界静态证据 | 完成接口、布局和必要实现对照，保留可运行两侧及 BEH 的独立结果 | 整链分析中的该连接有何依据，尚未证明连续执行 |
| 接口契约或关键实现仍未知 | 针对具体缺口继续诊断，列清阻塞对象和最小所需资料 | 当前证据不足，不能编造适配后宣称通过 |

同一条链可以同时包含多种连接。必须逐段标注，不能用一个“全链运行”标签覆盖其中的静态推算或回放。主机内的线程、进程或 Socket 衔接，也不能直接代表目标的核间共享内存、中断或驱动已被执行。

这里的“契约适配”就是按照已经核实的输入输出约定编写测试衔接，把前一段实际输出交给后一段。它的依据、替代范围和失败条件都应可检查；未知的通信行为仍然保留未知。

## 7. 产品与 DT 的对齐、类型和浮点差异

### 7.1 先定位差异，随后判断影响

用户指出的 4 字节／2 字节对齐差异必须作为首版专项。分别确认它指的是结构体对齐要求、成员偏移、实际指针地址、缓冲区起点还是报文布局。不能只写“x86 与板端不同”，也不能看见两个数字不同就认定一定存在传输错误。

| 对照项 | 产品目标构建 | x86 DT 构建 | 判断方式 |
| --- | --- | --- | --- |
| 类型定义与宏分支 | 实际生效的头文件及别名 | 实际生效定义 | 是否在测试另一种类型或代码分支 |
| `sizeof`／`alignof` | 对目标编译配置取得的值 | 对 DT 编译配置取得的值 | 差异是否跨越原始内存接口 |
| 成员偏移与填充 | 各实际传输／读取字段的位置 | 对应字段的位置 | 是否按相同字节位置解读，是否有显式序列化 |
| 字节序与字宽 | 目标事实 | 主机事实 | 转换是否按协议进行，而非依赖宿主默认值 |
| 实际缓冲区地址 | 不上板时通常没有现场地址 | DT 执行中可采集 | 类型要求与每次实际地址分别判断 |
| 编译与依赖行为 | ABI、打包、优化、浮点参数和实际包 | 对应参数和包 | 哪些差异影响当前检查，哪些仅是内部实现差异 |

内部结构体可以因平台而不同；若两边都按同一协议显式编码，内部布局不同未必影响通信。直接复制整个结构体或按固定偏移读取的接口，必须核对实际布局。不能为了让 DT 通过直接给所有结构体加 `packed`、强制 2 字节对齐，或替换产品定义。

### 7.2 不上板也能取得目标编译侧的布局依据

优先使用目标构建已有调试类型信息、编译器布局输出和相关 MAP／头文件。MAP 通常只能提供部分地址和符号线索，不能单凭它保证恢复所有成员布局。需要补探测源文件时，包含原产品头文件，使用原目标参数单独编译到隔离输出目录；不用手工抄一份结构体代替真实定义。

ABI 指平台约定的类型布局、函数传参等规则；DWARF 是编译器保存类型、源码位置等调试资料的一种格式。取得这些目标编译信息，不需要把程序放到板上执行。

对已确认包含所需 DWARF 类型信息的产物，以下是可改用真实路径的检查模板；命令不运行目标程序：

```bash
chain_target_artifact='/实际/目标构建产物或匹配的调试文件'
chain_dt_artifact='/实际/DT产物或匹配的调试文件'
chain_type_name='替换为实际类型的调试名称'

llvm-dwarfdump --help
llvm-dwarfdump --name="$chain_type_name" --show-children "$chain_target_artifact"
llvm-dwarfdump --name="$chain_type_name" --show-children "$chain_dt_artifact"
```

`llvm-dwarfdump` 可按名称查调试条目并显示子条目。提取时核对类型、大小、成员位置、嵌套定义及所属编译单元；同名类型可能有多个版本。调试信息缺失或被裁剪时，无结果不等于类型不存在。对齐属性也不保证总有显式条目，需要补充编译器依据。[LLVM 工具说明](https://llvm.org/docs/CommandGuide/llvm-dwarfdump.html)

若实际工具链不支持上述格式或工具，使用其已有等价输出。采用 Clang 布局诊断时，先核对该版本支持的选项，并保留真实目标、头文件、宏和 ABI 参数；禁止悄悄改用宿主默认编译来得到“目标布局”。

有明确接口常量时，可在产品和 DT 各自构建中增加适用的编译期检查。`offsetof` 等检查要满足类型和工具链的适用条件；复杂非标准布局类、位域等不能机械套用。没有权威预期时先输出对照，不把当前 DT 数字直接升格为产品规范。

### 7.3 浮点保存与比较

确认每个位置的实际类型、位宽、字节顺序及转换。对真实采用 binary32／binary64 的字段，保留对应表示及足够精度的文本，禁止先把 double 降成 float 或把浮点强转为整数。其他格式按目标事实处理。

浮点优化设置也是对照内容。Clang 的浮点模式、融合运算和快速数学选项可能改变允许的变换，不能只看公式文本相同就假定所有结果逐位相同。[Clang 浮点行为说明](https://clang.llvm.org/docs/UsersManual.html#controlling-floating-point-behavior)

比较分三类：原样传递按有效载荷或已定义编码比较；明确变换按公式、类型和已确认容差比较；缺少业务期望时只展示差异和来源。容差不能在看到失败后临时放宽。结构体未定义的填充字节不作为业务数值是否一致的判断依据。

NaN、无穷、负零和非规格化数按真实接口需求测试。它们及原始位模式不能全部依赖普通 JSON 数字保存；可以使用带类型的十六进制表示和显式状态字段。Python 解码时依据真实协议选择字节序和格式，不使用宿主原生布局猜测产品报文。[Python 二进制编码说明](https://docs.python.org/3/library/struct.html)

## 8. BEH 工具源码与 AI 图元测试的接入

### 8.1 先核对“定义在哪里、执行在哪里”

在 BEH 工具源码和已有 AI 测试中定位图元模型、文件加载、端口绑定、参数应用、初始化、周期执行和结果读取的真实入口。对每项记录实际文件、函数／类、版本和原测试调用位置。

| 对象 | 要核实什么 |
| --- | --- |
| 图元工程加载 | 真实读取哪份文件，有没有版本迁移、自动默认值或额外配置 |
| 信号订阅 | ID 怎样映射到图元实例和输入端口，是否还有实例／通道条件 |
| 图元内部语义 | 计算由编辑器、生成代码、Java 引擎或外部实现中的哪一部分负责 |
| 状态与调度 | 初始化、复位、先后顺序、周期、反馈、保持值及延迟规则 |
| 观察能力 | 哪些输入、输出和内部节点可读，读到的是当前值还是上一周期缓存 |
| 产品对应关系 | 图元工程、生成代码、产品订阅和运行引擎之间有哪些实际映射 |

已有 Java 测试成功，保留这一事实；本轮仍需证明新选择的产品图元、版本和输入确实由原引擎执行。若产品使用生成后的 C++ 实现，源码分析应延伸到相关生成代码；Java 引擎与产品实现一致到哪里，按对应证据分别说明。

### 8.2 复用现有入口，建立薄适配

以下是适配必须提供的动作，不是 BEH 已有 API 名称。执行 AI 应把动作映射到原接口，优先加在现有测试脚本层：

| 动作 | 实现要求 |
| --- | --- |
| 加载 | 读取指定版本图元工程和配置，返回真实实例／端口目录及版本 |
| 初始化／复位 | 按原引擎流程恢复该用例需要的初始状态，记录参数与状态来源 |
| 设置输入 | 将指定信号交给已核实的实例和端口，保留实际类型、单位和关联编号 |
| 推进执行 | 按原引擎支持的周期／步骤执行，明确调用次数、逻辑时间和观察阶段 |
| 读取节点 | 返回选定端口及可观察内部节点的实际值，保留类型、有效性和来源 |
| 结束／异常 | 返回执行状态和必要错误现场，正常退出不能掩盖失败用例 |

不得用 AI 重新写一套图元数学逻辑来代替原引擎。独立公式可用于对照，但要有独立来源；以同一段 AI 代码同时生成结果和期望，不能作为有效验证。

若现有接口只能读最终输出，先接入已有能力，再根据工具源码在可控制的测试／引擎接口层补关键观察。确实无法读取的内部节点保留“未采集”；不能根据输出倒算内部值后写成引擎实测。必要改动单独记录对原引擎版本和行为的影响。

### 8.3 产品交接点到图元端口

建立明确映射：产品信号及业务字段、交接函数／配置、图元工程版本、实例 ID、端口 ID、类型、单位、缩放、输入生效周期和证据。默认不要求人工重新维护全部信号名称；从现有宏、配置和图元数据抽取，核对后复用。

根据查实的关系选择衔接：

| 已确认关系 | 运行组织 |
| --- | --- |
| 产品业务输出与图元输入确为上下游 | 取业务实际输出，按真实交接规则送入对应图元 |
| BEH 是产品生成逻辑的另一种执行环境 | 对齐输入、参数、初始状态和执行步骤，分别运行并比较 |
| 只有订阅／配置关联，执行关系尚未明确 | 先保存映射及独立执行证据，继续核实，不宣布一次连续整链运行 |

对于有状态图元，需要连续输入序列。每个周期都重启引擎，可能改变原本的保持、积分、延迟或反馈行为；初始化一次还是每用例重置，应依据场景及原引擎机制确定。

## 9. 把可运行业务段与 BEH 连续执行起来

### 9.1 先识别真实注入点

全链分析仍覆盖外部界面设置项。如果已有界面／协议测试入口能运行，则沿用它触发；否则选择现有最靠前且可运行的产品入口，并在报告中写明外部界面到该入口的部分采用何种静态证据。

不能因为运行从中间接口开始，就把前段从链路表中删除；也不能把中间注入写成已执行外部界面。首版无需重新开发完整 GUI 自动化平台，先接已有入口及其真实覆盖范围。

下述连续串接适用于第 8.3 节已确认的上下游关系。若 BEH 与产品是对应实现，保持共同输入和两条执行支路，汇入同一业务链对照；不要让本应对照的同一段逻辑串行计算两次。

### 9.2 从“发送桩”取得真实业务输出

定位当前 DT 替换的是发送、路由、序列化、接收注册中的哪一层，以及是否一并改变初始化和返回码。按第 6.3 节为该边界选择现有依赖或受控衔接。

当使用契约适配时，至少实现：

1. 原发送业务函数实际执行；在替代边界捕获其本次输出，而非重新按测试输入生成一份预想输出。
2. 在数据仍有效时复制实际字段／有效载荷，保留长度、类型、实例和关联信息；不能只保存随后会失效或被改写的指针。
3. 按已确认契约进行必要解码、映射或显式转换；记录转换规则，不能只传一个 float 而丢掉影响行为的标志、质量、使能或时间字段。
4. 优先经主机环境中可运行的真实注册和分发入口到达接收业务。只能直接调用业务入口时，标明跳过了注册、路由或解包中的哪些部分。
5. 接收侧真实业务运行后，再取实际交接输出送入 BEH，按该用例的状态和周期推进，并记录各段状态。

适配不能把发送状态码当成信号值，也不能收到错误码后仍默认进入下一段。需要模拟返回行为时，依据接口约定和测试场景设置；保持成功常量而没有载荷记录和接收处理，不满足整链运行要求。

### 9.3 优先采用实际可用的 Linux 实现

若现有 Linux 包包含可运行的真实路由或协议逻辑，优先评估接入它的修改量和行为范围，并保留与产品包的差异。不能因为某个包名包含 Linux 就认定其中没有桩，也不能因它是 Linux 版本就直接排除其软件集成价值。

两侧可以在同一测试进程中衔接，也可以复用现有多进程测试；根据当前入口选择最小实现。无需为表现“两个核”强行创造两台虚拟机器。目标核间硬件和 RTOS 调度是否执行，始终单独标注。

### 9.4 连续执行、分段回放和独立试验分别记录

| 执行关系 | 必须保留的依据 |
| --- | --- |
| 一段实际输出直接进入下一段 | 输出记录与输入记录关联，转换和传递动作可重放 |
| 使用上一轮输出回放 | 原运行编号、数据哈希、回放输入、配置和状态一致性说明 |
| 从代码推算值开始测试下游 | 明确该输入为条件推算，后续引擎执行可实测，前段不升级为实测 |
| 两边独立使用同一组输入 | 说明是在做一致性对照，不能只凭结果相同宣布直接交接 |

总控不得强求每个输入立即产生一个输出；过滤、保持、聚合、多周期计算可能是正常规则。等待和观察条件先写清，未知业务超时只能设为本轮测试等待上限。Windows／Linux 的墙钟差值不直接解释为目标跨核延迟。

## 10. 节点取值、关联和统一结果格式

### 10.1 一个链路表容纳不同来源

结果至少分别保留源码条件推算、主机 DT 执行、主机依赖执行、BEH 引擎执行、适配／回放动作及未采集状态。产品编译时的类型布局属于构建证据，不能写成运行观察。

| 节点／边界 | 产品代码或图元依据 | 本场景条件推算 | 主机业务实测 | BEH 实测 | 连接方式／差异 | 业务期望及结论 |
| --- | --- | --- | --- | --- | --- | --- |
| 执行时按真实节点填写 | 文件／实例／端口及版本 | 公式和前提，或待定 | 本轮值或未执行 | 本轮值或未执行 | 实际依赖、适配、回放或未确认 | 有依据则检查，否则待核对 |

不强求每个节点同时有所有来源；空白项写不适用、未执行或未采集及其原因。值为 0 与没有值必须区别处理。图元只给出部分中间值时，不通过 AI 补全缺失实测列。

### 10.2 事件关系和时序

复用协议已有消息序号、周期或业务关联字段。在主机适配中可以添加旁路元数据关联上游输出与下游输入，但不得声称这个新增编号已经存在于产品核间协议。

同一数值连续出现时，也需要区分不同事件。循环和扇出关系应能记录父事件及实例，不能简单按日志行号一一配对。取值时刻标为输入设置后、执行步骤后或实际回调内等明确阶段；不同环境的时间戳注明时钟来源。

记录运行耗时、模型步骤或已知逻辑延迟时分别命名。不上板所得的主机耗时不作为目标 RTOS 的实时性能证明。缓冲区覆盖、事件过滤和丢记录情况应记录，不能把采集空白直接判为业务断开。

### 10.4 统一采集优先放在可控制位置

在主机业务和测试包装层的公共入口、发送边界、接收回调、关键转换前后及 BEH 测试接口采集。没有共同入口时，依据已核对的点位清单批量生成必要接入代码，并做差异检查，防止重复调用、重复求值或改变返回行为。

统一接口负责类型化快照、过滤、关联和导出；不要求用户手动逐点维护日志。对并发数据使用原有一致性机制取得有效快照，避免在对象改变后才读取。内部不可见的依赖状态保留未观测，不把普通函数进出记录等同于业务值已经取到。

## 11. 总控入口与失败处理

### 11.1 一次调用完成一个场景

总控按已有测试架构实现，至少完成以下顺序：加载场景与版本记录，检查必要输入是否可用，复用或更新受影响的静态结果，完成适用的布局检查，运行主机业务及已选择的衔接方式，调用原 BEH 测试，校验记录与关联，更新唯一报告。

已有结果版本匹配时允许复用静态查询；本轮要求实际执行的测试不能只读取旧日志冒充新运行。每次结果带自己的运行编号，关联到真正执行的命令和数据。

若现有 AI 图元测试已经有总控入口，直接扩展它。没有入口时，可约定如下最小使用方式；这是需要执行 AI 实现或映射到现有命令的接口示例，本文没有附带该脚本：

```text
chain_run --config <已核实的场景配置> --case <代表信号场景> --output <本轮输出目录>
```

场景配置至少指定执行方式、真实工作目录、已有产品／DT／BEH 命令入口、输入文件、选定节点、跨边界连接方式、运行等待上限和报告位置。各参数采用结构化传递；远程执行按已有 SSH 身份及环境初始化方式，不把用户输入拼成任意 Shell 代码。

主机编译器、目标编译器和 BEH Java 路径分别配置。其他工具需要不同 Java 时使用其独立入口，保持现有 BEH 可运行环境。WSL 与远程路径分别解析，跨环境引用不得混用。

### 11.2 失败不能被包装成成功

| 现象 | 必须给出的状态 |
| --- | --- |
| 某阶段命令失败或必要程序无法启动 | 本阶段执行失败，保留命令、退出码和关键错误；后续有效的独立分析仍可完成 |
| 工具正常退出但目标用例未执行 | 未运行，不能只看进程退出码判通过 |
| 测试通过但所有发送仍只返回固定成功 | 只证明现有局部测试，整链运行未完成 |
| BEH 加载成功但没有所选图元或端口 | 映射失败，不能改用同名的其他实例继续判通过 |
| 没有结果、缺节点、错版本或无法关联 | 结果不完整或关联失败，不能填默认值 |
| 实际路径与图元关系和先前假设不符 | 更新拓扑及证据，保留已经取得的结果来源，重新安排相应连接 |

保存首次有效失败现场：场景、版本、输入、最后一个有证据的节点、对应错误及下一段是否真的被调用。主机测试出现崩溃时可以利用该环境已有调试／错误记录定位，结论限定到本次运行；本任务不扩成完整板端崩溃定位工程。

### 11.3 修改后的更新范围

产品源代码、宏或依赖变化时，更新对应分析和编译结果；图元工程、引擎或参数变化时，更新相关映射和测试；输入或初始化变化时，重跑相应场景。缓存键包含实际影响项，不能只用信号名。

首版不要求搭建流水线或网页。先实现可重复的命令入口和报告；已有流水线可用时再挂接同一入口，不复制第二套判断规则。

## 12. 分阶段建设任务与每阶段的结束条件

下面是执行顺序，不是再次开展无期限环境摸底。每阶段都应产生可检查的工程变化或结果，在唯一报告中更新状态；遇到阻塞先推进其他可完成部分。

| 阶段 | 要实际完成的工作 | 本阶段结束条件 |
| --- | --- | --- |
| B1：接续已有成果 | 读取排查报告和四类工程材料，固定版本，选定代表信号与完整范围 | 找到实际入口、输入和产物；缺项定位明确，无重复基础问答 |
| B2：建立整链分析 | 复用 CodeQL，连接外部入口、跨核两端、接收业务和 BEH 映射；补相关配置规则与必要二进制证据 | 节点和连接均有来源或具体缺口，跨核和 BEH 已进入同一模型 |
| B3：完成产品／DT 差异检查 | 核对所选字段的类型、对齐、布局、编码、宏、浮点和依赖行为 | 差异能落实到类型、接口及受影响结论；需要的诊断和检查可重复运行 |
| B4：接入 BEH 原测试 | 复用真实引擎，加载产品图元，配置状态和周期，获取选定节点值 | 所选图元及关键观察点实际运行，有版本和原始结果 |
| B5：打通主机执行衔接 | 运行真实业务段，捕获发送输出，使用已选连接方式到接收业务，再串接或对照 BEH | 一次场景驱动产生可关联结果，所有替代、回放和静态段可区分 |
| B6：检验是否能发现问题 | 完成第 13 章适用测试，处理实际暴露的适配、关联或产品问题 | 正常流程可重跑，受控错误能按规则被识别，结果没有伪通过 |
| B7：形成稳定交付 | 整合总控入口、实际配置、必要代码及唯一报告；从该入口重跑一次 | 用户或另一执行 AI 可按记录重跑，完成范围与阻塞项明确 |

B3 与 B4 的资料核查可穿插推进，不需要在等一个缺失类型信息时停掉全部工作。B5 必须依据已经明确的交接关系，不能为了阶段进度猜接口或强改产品逻辑。

在一条链上验证过的查询、取值和映射应支持通过配置扩展到下一条信号。新增信号仍需要核对独有路由和字段，不能把“配置化”解释为自动适用于所有协议、核或图元。

## 13. 必要测试与验收用例

### 13.1 最小检验集

所有输入取自实际接口允许范围，或明确标注为异常测试。以下是检验目的；具体数值、函数、端口和预期根据工程确定，不能把示意值 50 当成所有产品的规范。

| 用例 | 需要证明什么 | 验证方式 |
| --- | --- | --- |
| T1：代表信号正常流程 | 实际业务输出能进入选定衔接和原 BEH 引擎，节点值来源可核对 | 保留输入、发送快照、接收处理、图元步骤和输出；未执行段明确标注 |
| T2：连续输入与状态 | 记录确实来自本轮不同事件，图元状态和周期处理符合该用例设置 | 至少连续两次输入，核对事件对应、取值时刻和复位边界；不能假定输出必然不同 |
| T3：错信号／错端口／缺配置 | 查询或运行检查能识别具体错连与遗漏 | 在隔离测试配置中选一种有明确规则的错误，确认检查准确指出对应边界 |
| T4：布局与编码差异 | 能发现有影响的字段偏移、长度或编码不匹配 | 使用目标／DT 实际构建对照；对已定义的接口加入一处受控错误，内部允许差异不误报 |
| T5：浮点精度保留 | 传递、保存和展示不会静默降精度 | 对实际使用的类型选代表值，比较有效原始表示；工程用 double 时覆盖能暴露降精度的值 |
| T6：缺失与失败传播 | 无输出、阶段失败或错版本不会被解释为 0 或通过 | 选择一处适用故障，检查总控状态、缺失节点及唯一报告保持一致 |

受控错误先写明预期发现方式，再运行；发现结果后不能临时修改通过规则。故障注入用例成功识别预期问题时，该检验可通过，但其被注入的业务场景仍是异常场景，两种状态分开保存。

T3 的“缺配置”必须基于已确认的必要关系。若注册逻辑被适配跳过，运行测试不能声称检测了原注册过程；可以由静态配置规则发现缺项，报告说明证据来源。

T4 不要求产品与 DT 的所有内存布局完全相等，只要求相关差异得到解释且未破坏本次声明的接口。T5 可以使用 Python 等工具校验导出格式，但图元和业务计算结果必须来自对应执行入口。

### 13.2 期望值的来源

首版允许业务期望待确认，但以下机械性问题可以有明确规则：版本和实例是否匹配、必要节点是否有结果、声明原样传递的数据是否一致、协议长度是否合法、记录能否关联、命令是否实际执行。

设计人员确认期望后，记录适用配置、单位、初始状态、周期、允许范围／容差及依据，再纳入自动检查。现有代码、DT 和 BEH 都得到同一个结果，仍不自动证明它符合设计。

不得将运行结果直接复制成期望后宣布验证通过；也不得把 AI 的条件推算当作唯一权威。推算可以参与交叉核对，前提、类型和公式必须透明。

### 13.3 验证到足够就进入交付

先完成代表链和上述与本次改动相关的检验。只有出现具体剩余风险或既有工程要求时，才扩大回归。不要为了“更全面”反复跑全部依赖测试、分析所有图元或搭建与首条链无关的设施。

证据充分时停止可选测试，进入 B7。真实阻塞不能通过继续增加无关测试消除，应明确缺口和下一项必要动作。

## 14. 建设完成标准与唯一结果报告

### 14.1 可对照的完成检查

| 检查项 | 完成所需证据 |
| --- | --- |
| 完整范围 | 外部入口、相关组件、跨核边界、接收业务、BEH 订阅与内部处理／输出均进入链路模型；实际分支和条件有交代 |
| 业务分析 | 产品配置下的查询、配置核对和条件推算可复查，关键依赖缺口有具体处理状态 |
| BEH 接入 | 产品图元版本、真实引擎、输入、状态、周期和节点取值实际接通 |
| 主机执行 | 约定可运行段已执行，衔接确实使用上游输出；无法执行的段有明确原因和影响 |
| 跨核说明 | 每个边界的映射、实现依据、主机连接方式与未执行的目标机制分别记录 |
| 差异核对 | 2／4 字节相关问题及实际涉及的布局、编码、宏和浮点差异有证据，未用 DT 替代目标事实 |
| 数据与判定 | 推算、主机实测、BEH 实测、回放和缺失可区分；期望来源清楚 |
| 有效检验 | 适用的正常、状态、错连／配置、布局、精度和失败传播检查有结果 |
| 可重跑 | 一个实际入口、所需配置、版本和支撑文件齐全，复跑记录可追溯 |
| 资源复用与收尾 | 复用和必要新增有说明，成果在容器外持久保存，本任务可丢弃临时资源已清理或有保留理由，未误删共享及其他任务资源 |
| 文档交付 | 一份报告能够独立说明范围、结果、限制、改动、使用方法和下一步，末章有简短概述 |
