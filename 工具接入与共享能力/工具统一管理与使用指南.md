# 工具统一管理与使用指南

版本：v1.1，2026-09-19。面向能够访问用户电脑、真实产品仓和对应版本 EMAP 仓的本地 AI。

**本文件统一维护工具的盘点、下载、安装、存放、环境接入、调用方法与验收规则。** 当前机器上到底有哪些工具、在哪里、能用于什么，由同目录的 [工具状态与验收报告.md](工具状态与验收报告.md) 记录。业务任务文档负责说明“查什么、接受什么业务证据”，不再各自维护一套工具安装说明。

本文不是用户电脑的实测报告。已知前提是：普通产品编译没有生成 `compile_commands.json`；产品实际编译在对应 Docker 环境中。发行版、目录、镜像、工具路径和编译配置仍须依据已有执行成果核对，不从示例推断产品的核数、OS 或盒间拓扑。

## 1. 唯一规则、唯一当前报告、每次任务自己的证据

三者职责固定如下：

| 资料 | 唯一职责 | 不能代替什么 |
| --- | --- | --- |
| 本指南 | 工具的准备、运行、验证和复用规则 | 不能证明用户机器已执行 |
| [当前工具状态报告](工具状态与验收报告.md) | 按机器、环境、工具实例登记实测状态和证据入口 | 不能代替某次任务真实使用记录 |
| 各任务结果目录 | 保存本次输入、命令、日志、数据库/查询结果、业务复核与缺口 | 不另写一份独立安装规范或宣称全局环境状态 |

旧 `05_成熟工具执行手册.md`、`08_工具盘点下载安装与存放指南.md` 仅作兼容入口。已有环境报告、旧任务日志、下载包和历史 ZIP 是来源证据，保留原貌；历史说明与本指南冲突时不作为当前操作依据。

工具状态报告只有一个**当前入口**。不同电脑、WSL 发行版、Docker 镜像和运行方式在报告里分行登记，不争用一个“CodeQL 已装”布尔值。历史快照、CSV 导出和任务附带的报告副本只能注明来源修订和摘要，不能升级成第二个当前底账。

工作区名称由用户本地决定。引用环境依据时只沿 `Windows与WSL开发环境` 文件夹寻找，不假定其父目录名称；相对链接只表达本交付包内的目录关系。单独复制任务子目录时，必须连同本指南、当前报告和必要脚本一并保留约定的相对目录，否则先补齐依赖，不回退到旧安装规则。

## 2. 先承接已做过的 Windows/WSL 工作

先定位 [Windows与WSL开发环境](../Windows与WSL开发环境/README.md)，通过其中的指南和交接记录找到**按指南实际执行后产生的结果**：现状报告、目录用途、仓与镜像关系、部署配置、挂载表、成功构建记录。找到指南不等于找到执行成果；缺少一项就只补查本次所需的一项，不重新迁盘、同步全部代码或重建所有镜像。

优先从用户指定路径、当前工作区、旧报告引用和既有脚本查找。确需检索时先用 `rg --files` 限定这些已知根；同名文件夹出现多份时核对来源和修订，不选第一个就开始安装。

| 要继承的成果 | 本次最小核对 | 写入报告的内容 |
| --- | --- | --- |
| Windows/WSL 现状及目录用途 | 目标发行版、实际用户、路径仍存在、磁盘容量与权限 | 来源文件、日期/修订、真实工具/缓存/结果根 |
| 多仓多镜像关系 | 当前产品及 EMAP 版本、选定镜像、Docker context | 仓路径、配置 ID、镜像不可变 ID/digest |
| 原构建入口及部署配置 | workdir、user、挂载、初始化、生成步骤 | 可复用入口和所用配置，不复制另一套环境定义 |
| 成功编译记录 | 与本次源码/依赖/配置是否一致 | 可证明的环境或产物身份，以及不可复用的部分 |
| 旧工具盘点/安装记录 | 工具是否仍在、版本和运行环境是否变动 | 候选工具及其原证据，重新确认的范围 |

`/home/...` 只说明 Linux 路径，不能证明 VHDX 在 C 盘或 D 盘。系统包留在包管理器管理的位置；不为了目录整齐迁走 `/usr/bin`、改变用户 HOME 或覆盖原 SDK。工具原包、工具本体、缓存、任务输出分别登记；大型数据库放在已有规划的结果盘，不能塞进代码同步根。

当前不知道“目标核”时，以**已有真实编译配置 ID**开展工作。脚本中的 `--target`/`targets` 在这里就是配置/组合标识；执行域仍可为“未知，待代码证据确认”。

## 3. 盘点：有没有、在哪里、在哪个环境能用

### 3.1 每个候选实例至少记这些字段

工具 ID、实例 ID、环境 ID、实际可执行路径及软链接目标、完整发行目录、版本、来源、安装方式、所需配套文件/运行库、许可适用性（需要时）、用途、状态、证据引用。系统软件包补充包名/版本；独立包补充原包路径和摘要；容器补充镜像身份与容器内路径。

同名多版本先全部登记，再为任务选中一个。`command -v` 未命中只能说明当前 PATH 找不到；不能直接标“未安装”。依次查：当前 PATH → 已有工具报告 → 包管理器 → 已确认工具根/环境管理器 → 编辑器配置和构建脚本引用。搜索到这里仍未找到，再把“在已检查范围内缺失”写清楚。

WSL 的只读查询示例：

```bash
cat /etc/os-release
uname -m
id
type -a git python3 codeql clang clangd clang-query bear
type -a clang-18 clangd-18 clang-query-18 nm readelf objdump
type -a cmake ninja make mkid lid cscope ctags und clang-uml
type -a addr2line llvm-symbolizer gdb gdb-multiarch
```

逐条保留输出和退出码，允许部分命令不存在。Ubuntu 可用 `dpkg-query -W` 查包状态、`dpkg -L 包名` 查文件、`apt-cache policy 包名` 查候选版本。检查已知目录时核对 `readlink -f`、文件权限与包归属；独立下载包还要找提取器、库、资源目录和代理等配套内容。不要运行来源不明的任意可执行文件来“试一下”。

Windows 工具在 Windows 环境里查 `Get-Command 工具名 -All`、已知工具目录和现有脚本；Windows 的 CodeQL/LLVM 不登记为 WSL 的 Linux 安装。已启动容器可以沿既有入口只读核对；不为盘点启动所有未知镜像。

### 3.2 清单：全部有结论，不等于全部安装

| 工具/组件 | 本场景用途 | 采用条件与最低实际验收 |
| --- | --- | --- |
| Git、Python 3.10+ | 基线、随包脚本、结果核验 | 优先已有 Python 3.12/pixi；脚本实际解释器及 Git 路径可追溯 |
| 原编译器、链接器、SDK、生成器、依赖获取器 | 真实产品构建及宏/布局来源 | 复用原镜像；代表配置原入口可工作，不替换为宿主 Clang |
| CMake / Make / Ninja | 工程原有生成/构建及目标关系 | 工程用哪个就核哪个；不强制改构建系统 |
| Bear | 无 CDB 时捕获实际编译命令 | 当前重点；必须在真实编译环境验证关键源码捕获 |
| Clang、clangd、clang-query | 解析、定义/引用、AST 定点查询 | 编译上下文可用，关键真实文件与已知关系核对 |
| CodeQL 完整 bundle | C/C++ 提取、定制关系/数据流查询 | CLI、提取器、查询包可用；许可范围核实；真实建库与查询分开验收 |
| GNU Binutils / LLVM / 厂商对象工具 | ELF/库/map/符号及少量指令核对 | 对所用产物格式兼容；记录 `nm/readelf/objdump` 或实际等价工具 |
| ripgrep、jq | 文件候选、JSON 辅助 | 已有等价工具可代替；不承担语义关系证明 |
| Universal Ctags、cscope、GNU IDutils | 有界文件集的重复符号/文本导航 | 按需要择用；不是全程序语义、IPC 或运行因果证明 |
| Understand | 架构浏览、关系/影响分析、条件性语义补充 | 已有许可或组织认可渠道；真实参数导入、小范围解析质量先验收 |
| clang-uml；Graphviz/PlantUML | 有实际需要的结构图及渲染 | 图形不是运行事实；只装所选输出格式需要的组件 |
| 工程原有 BEH/模型/协议解析器 | 注册、生成绑定、模型连接与契约 | 版本/schema 与工程匹配；普通 XML parser 不代表装载语义 |
| strace | Linux 构建端缺失进程/文件依赖线索 | 有明确问题和权限时小范围采集，不默认全仓执行 |
| ftrace/trace-cmd、perf、Perfetto | 条件性运行观测与时间线 | 先确认设备 OS、事件、权限、时钟、开销；不因主机是 Linux 推断设备也是 |
| addr2line / llvm-symbolizer / 厂商符号工具 | 离线还原异常地址、行号和内联帧 | 工具支持产物格式；ELF、调试信息、加载映射与部署身份一致 |
| GDB / 厂商调试器及调试服务、探针 | 条件性断点、监视点和异常前取证 | 客户端、服务、探针、目标分别验收；停止范围和行为实测 |
| ASan / UBSan / TSan 与匹配运行库 | 支持环境内定点复现内存/未定义行为问题 | 编译和链接接入，代表用例与阳性对照通过；不默认板端支持 |
| RTOS/厂商 trace、调试探针 | 已确认平台的运行观察 | 平台、接口、许可/硬件、缓冲预算明确后单列接入 |
| Mutagen、OpenSSH、可选 rsync | Windows/WSL 同步及只读差异核对 | 仅选择双份工作树同步方案时需要；见[同步工具](#sync) |
| 随包 scripts / queries / config | 录制、审核、流程检查、初始查询 | 同版本完整任务包；脚本存在不等于工具已执行 |

GNU **IDutils** 和 GNU **Binutils** 是不同工具组。`compile_commands.json`、CodeQL 数据库、ELF、link map 是输入/输出资料，不是要下载安装的软件。“不采用”要写原因，“受阻”要写失败范围；不要为了表格全绿安装所有可选项。

<a id="install"></a>
## 4. 缺什么补什么：下载、安装和验证

### 4.1 位置与状态分开

| 对象 | 位置依据 | 下载/安装阶段的验证 |
| --- | --- | --- |
| 系统软件包 | 已有发行版包管理器默认位置 | 包管理器状态、文件、版本和必要依赖 |
| CodeQL/Understand 等完整独立包 | 已确认工具根下固定版本/运行平台目录 | 官方或组织来源、原包摘要、完整解压结构、可执行路径 |
| 下载原包 | 已有下载/缓存根 | 文件大小、摘要、发布方校验/证明（存在时） |
| 用户缓存、查询包缓存 | 既有缓存根，按工具实际配置方式接入 | 实际可写，不与源码混放 |
| 数据库、日志、报告 | 既有结果根下任务/配置/运行编号 | 不覆盖已有结果；宿主与容器映射可核验 |

下载归档先校验再解压到新版本目录，核对内部路径，避免覆盖现有版本。记录官方资产名称、来源、版本、平台、字节数、本地 SHA-256；有发布方校验材料时核对。**本地自算摘要只用于识别文件，不能独自证明官方来源可信。** 下载成功、解压完整、能启动、适配某镜像、完成某任务是不同结论。

报告已显示可用时直接复用。未入 PATH 时采用绝对路径或任务局部配置；版本不兼容时留下证据再并存补装。不要自动改软件源、代理、系统默认编译器或全局运行库。

### 4.2 已确认 WSL Ubuntu 24.04 的示例

以下只在盘点证实缺失时选择执行；**容器不是必然 Ubuntu 24.04**。先看软件源候选和模拟依赖变化：

```bash
apt-cache policy clang-18 clangd-18 clang-tools-18 bear binutils
apt-get -s install clang-18 clangd-18 clang-tools-18
# 确认确实需要这三项且依赖变化可接受后：
sudo apt update
sudo apt install clang-18 clangd-18 clang-tools-18
# Bear 缺失且当前需要捕获编译时：
sudo apt install bear
```

示例不要求先装三项再发现已有。已有部分项目时只列缺失包；软件索引已足够新且可用时不为形式重复刷新。通用对象工具 `binutils`、辅助 `ripgrep/jq`、索引 `id-utils/cscope/universal-ctags`、同步 `rsync/openssh-server` 等也先用本机 `apt-cache policy` 核实包名、版本和需要性，再选装。不要依赖未经核对的包名清单执行整批安装。

安装后使用实际路径检查，例如 `clangd-18 --version`、`clang-query-18 --version`、`bear --version`，并读相关 `--help`。记录带版本后缀的路径，不创建覆盖系统默认命令的软链接。`clang-query` 通常由 `clang-tools-18` 提供；不能认为只安装 `clang` 已包含整组工具。[Ubuntu 工具包](https://packages.ubuntu.com/noble/clang-tools-18)、[Ubuntu Bear 手册](https://manpages.ubuntu.com/manpages/noble/man1/bear.1.html)。

### 4.3 CodeQL 完整 bundle

先核对已有解压目录和下载缓存。需要时从 [CodeQL 官方安装说明](https://docs.github.com/en/code-security/how-tos/find-and-fix-code-vulnerabilities/scan-from-the-command-line/set-up-codeql-cli) 指向的 [完整 bundle 发布页](https://github.com/github/codeql-action/releases) 选择固定版本；选的是**运行工具的 Linux/Windows 主机平台**，不是板端芯片。保留 CLI、提取器及配套查询包整体结构，不能只装编辑器扩展或只复制可执行文件。

在真实运行环境设置实际路径后检查：

```bash
FACT_CODEQL='/实际完整bundle目录/codeql/codeql'
"$FACT_CODEQL" version
"$FACT_CODEQL" resolve languages
"$FACT_CODEQL" resolve packs
```

旧 CLI 的包解析命令可能是 `resolve qlpacks`；按本机帮助记录实际调用。检查 C/C++ 提取器和 `codeql/cpp-all` 等所需包的位置；包依赖锁在实际查询副本里生成，不能写一个猜测版本充数。Linux 运行库要求和容器兼容性需按所选版本核实，不承诺挂载后所有镜像可运行。私有商业代码的适用许可按组织已有合同和 [官方使用范围](https://docs.github.com/en/code-security/concepts/code-scanning/codeql/codeql-cli) 核实，本地 CLI 可运行不等于已证明任意用途均获许可。

### 4.4 其他独立/可选工具

Understand 先查现有安装、`und`、许可和组织分发渠道；缺失时从 [官方渠道](https://scitools.com/) 获取适用版本，不自动购买许可。clang-uml 按 [官方安装说明](https://github.com/bkryza/clang-uml) 核对 LLVM/系统依赖，不为画一张图强迫升级整个 SDK。模型生成器、厂商编译器和探针工具优先工程原渠道；遇到不兼容、权限、许可或下载受阻时记录具体原因，不悄悄换成不同语义的工具。

<a id="containers"></a>
## 5. 工具在 WSL，编译在 Docker：怎样接入

### 5.1 执行位置由所需上下文决定

| 动作 | 通常位置 | 必须可见的上下文 |
| --- | --- | --- |
| 阅读源码、Git 基线、报告整理 | 真实 WSL 源码/结果目录 | 正确工作树和未提交修改 |
| Bear 捕获、CodeQL 跟随构建建库 | **真正产生编译进程的容器/远端环境** | 原初始化、编译器、SDK、生成步骤、工作目录 |
| clangd / clang-query | 优先原构建上下文可访问的环境 | CDB、源文件、生成头、sysroot、编译器默认参数 |
| 完成后的 CodeQL 数据库查询 | WSL 或兼容容器 | 正确数据库、匹配 CLI/查询包/锁及作用域 |
| 二进制与 map 核对 | 兼容对象工具所在环境 | 对应版本产物与构建/链接身份 |
| 设备运行观测 | 实际设备/受管采集端 | 已确认平台和权限、事件/时钟/开销约束 |

WSL PATH 不会自动进入容器；挂载只提供文件，不会自动执行分析。若编译入口还会进入另一容器或远程编译端，捕获工具要进入**最终编译端**。外层 `bear -- docker ...` 不能作为容器内采集方案。[Bear Docker 说明](https://rizsotto.github.io/Bear/guides/recipes/docker.html)、[CodeQL 容器运行](https://docs.github.com/en/code-security/tutorials/customize-code-scanning/run-in-a-container)。

### 5.2 多容器复用的优先次序

1. 复用目标镜像已经具备且验收过的工具。
2. 完整、兼容的独立发行包可从已有工具根只读挂入多个容器，缓存和结果另给可写路径。
3. Bear/LLVM 若属于系统软件包，不能只挂 `/usr/bin/bear` 或一个 `clangd`；它们可能依赖辅助程序、拦截库、LLVM 资源和运行库。不要挂整个宿主 `/usr`、覆盖容器库或全局设置宿主 `LD_LIBRARY_PATH`。
4. 无法直接共享时，在相应镜像支持的包环境按需补齐；反复创建容器可基于**原产品镜像固定 ID/digest**建立一次可复用工具层。按兼容镜像准备，不按每个容器手动重装。保留原编译器、SDK、ENTRYPOINT、用户和初始化；保存 Dockerfile 和依赖变化。

镜像工具层改变后重新验证受影响的构建环境。不要把多个 OS/libc/主机架构的镜像标成一个已通过环境。

### 5.3 在既有启动配置上追加工具与结果挂载

先核对 Docker context 与引擎位置：bind source 是**引擎主机**路径，远程引擎不能直接挂本机 WSL 文件。复用原 Compose/脚本，不新造一套仓与镜像调度体系。已有容器不能靠 `docker exec` 增加持久 bind mount；需要新挂载时按原配置建立独立探查容器并保留已有数据。[Docker bind mounts](https://docs.docker.com/engine/storage/bind-mounts/)。

下列仅是追加到现有服务的 Compose 片段，服务名和变量必须由真实结果填写；不改变原 image、command、entrypoint、user、workdir：

```yaml
services:
  REPLACE_EXISTING_BUILD_SERVICE:
    volumes:
      - type: bind
        source: ${FACT_KIT_HOST:?fill verified task package path}
        target: /opt/fact-kit
        read_only: true
      - type: bind
        source: ${FACT_CODEQL_ROOT_HOST:?fill directory containing codeql executable}
        target: /opt/fact-tools/codeql
        read_only: true
      - type: bind
        source: ${FACT_RUN_HOST:?fill isolated result directory}
        target: /out/facts
```

`FACT_KIT_HOST` 是脚本实际所在任务目录；共享文档依赖可在宿主阅读，不必为调用脚本挂整个工作区。先解析合并后的 Compose 配置，再沿已确认入口启动。原来使用 `docker run` 时追加等价 `--mount`，不强制改 Compose。

保存镜像身份、Mounts、用户和 workdir；在本次结果目录写唯一小标记并从 WSL 读取，核验映射。不要在源码或正式输出文件上试写。验证调用位置可用：

```bash
docker --context "$FACT_DOCKER_CONTEXT" exec \
  --workdir "$FACT_BUILD_CWD_IN_CONTAINER" "$FACT_CONTAINER" \
  /opt/fact-tools/codeql/codeql version
```

这只证明该环境能运行 CLI。`docker exec` 不自动重演首次构建 shell 的初始化；正式采集仍须沿原工具链入口。缓存可写要求按工具实际机制配置，不为缓存便利改变 HOME。

### 5.4 每个环境绑定真实路径

在即将运行工具的环境里填入当前报告选中的路径；WSL 与容器分别填，不能混用：

```bash
FACT_PYTHON='/实际环境/python3'
FACT_BEAR='/实际环境/bear'
FACT_CLANG='/实际环境/clang或带版本名称'
FACT_CLANGD='/实际环境/clangd或带版本名称'
FACT_CLANG_QUERY='/实际环境/clang-query或带版本名称'
FACT_CODEQL='/实际环境/完整codeql包/codeql'
FACT_READELF='/实际兼容工具链/readelf'
FACT_NM='/实际兼容工具链/nm'
FACT_OBJDUMP='/实际兼容工具链/objdump'
```

把对应路径写入任务配置。环境记录 `execution.json` 只是记录，不会自动启动容器；`project.json.tools` 也不会改写之后手工输入的命令。任务调用必须显式使用已选路径，或保存能证明局部 PATH 解析结果的证据。

## 6. 怎样证明 AI 确实用了，而且用对了

### 6.1 每次动作的最小记录

| 必留内容 | 解决的问题 |
| --- | --- |
| 任务 ID、配置 ID、工具实例/环境 ID、采用的工具报告修订及摘要 | 用的是哪套环境与规则 |
| 实际 argv、cwd、开始/结束、退出码、必要初始化说明 | 真正运行了什么，失败在何处 |
| 输入基线与关键文件/配置/锁摘要，数据库身份和覆盖 | 分析的是哪个版本、哪一部分 |
| stdout/stderr、原始结果文件、输出摘要、超时/丢失/告警 | 是否真的执行、输出是否完整 |
| 事先选定的已知文件/符号/关系及预期，实际对照结果 | 工具是否理解本任务，而非只会打印版本 |
| 人工/AI 复核项、已知局限、未覆盖范围及结论引用 | 输出支持何种事实，不能推出什么 |

命令成功与内容正确分开验收。空结果可能是零命中，也可能是作用域错误、解析失败或根本没采到输入；未核实覆盖前不能据空结果宣称“没有问题”。日志和摘要提高可复核性，但不构成无法伪造的证明；仍须将关键输出与独立源文件、构建记录或已知事件核对。

可复用旧结果时，本次仍记录一次**实际复用动作**：旧结果的身份/摘要、输入一致性核对、覆盖适配判断以及从中取用的行/事实。标“复用已核验结果”，不冒充这次重新执行了工具。新写查询必须有新查询运行证据；安装报告不能抵扣。

### 6.2 用现有录制器，不新增一套工具平台

成熟工具任务包中 `scripts/probe.py record` 可直接记录真实命令：

```bash
"$FACT_PYTHON" "$FACT_KIT/scripts/probe.py" record \
  --out-dir "$FACT_CASE/runs/clangd-key-file" --cwd "$FACT_PRODUCT" \
  --target "$FACT_TARGET" --input "$FACT_COMPDB" --input "$FACT_SOURCE" \
  --timeout 300 -- "$FACT_CLANGD" --check="$FACT_SOURCE" \
  --compile-commands-dir="$FACT_COMPDB_DIR" --log=verbose
```

执行前替换真实路径和已存在输入。`--` 后逐项传 argv，不把整串命令当一个参数，不用 JSON 字符串转义冒充 shell 引用。录制器保存 run.json、stdout/stderr、摘要和输入变动状态；不会保存所有环境变量，另记必要 SDK/工具链配置，避免记录凭据。

不同尝试使用新 run 目录；保留失败原文，不覆盖后把历史失败写成一直成功。辅助检查的退出 0 只代表其机械检查通过；warnings、编译器诊断、提取覆盖和业务含义还须审阅。

暂不使用任务包脚本时也须保存同等字段，不能只留截图、聊天里的“已运行”或待执行命令。输出巨量时保留完整原始文件和摘要，正文引用相关位置；不将截断显示冒充完整日志。

## 7. 当前状态报告：格式、更新和失效

### 7.1 一份报告内部按层验收

当前报告的格式由本指南维护；报告只记录数据和结论，避免在两处复制操作规则。每个工具实例分别记录这些层级的 `未检查 / 通过 / 失败 / 不适用 / 已失效`：

| 层级 | 通过至少需要什么 |
| --- | --- |
| 发现/身份 | 精确路径、版本、所属环境、来源/包归属 |
| 原包/安装 | 原包校验（若适用）、完整组件、依赖状态；已安装系统包可引用包管理器证据 |
| 可启动 | 在该环境实际启动，记录输出/退出码 |
| 环境接入 | 原初始化、真实路径/挂载、必要源码/SDK/缓存/输出可访问 |
| 代表任务 | 真实代表输入、执行记录、预先指定核对项、通过范围 |
| 本次业务任务 | **由本次任务单独记录**；不能从上五层自动推导 |

代表任务通过只覆盖写明的镜像、配置与能力。例如 clangd 能解析某文件，不能写“所有 90 GB 源码均支持”；CodeQL 版本成功，不能写“建库成功”。仅下载可以交付下载结果，但后续层级保持未检查。

报告保留八块数据：①状态与修订；②引用的环境成果；③机器/环境表；④路径表；⑤工具实例表与分层验收；⑥本轮任务引用与原始证据索引；⑦缺口、失效范围及下一步；⑧更新历史。模板即 [工具状态与验收报告.md](工具状态与验收报告.md)。

### 7.2 更新方式

1. 开始前读取当前报告。文件未实测就开始有界盘点；已经有结果则先核对本轮涉及的环境和实例。
2. 单一写入者更新报告；并行任务先保存各自证据，由汇总者合并，避免最后写入覆盖前一项。
3. 保留旧证据；记录修订号、时间、操作者/执行方式、变化原因。需要历史快照时保存到既有结果根，不产生另一个名叫“最新”的底账。
4. 当次任务保存它采用的报告修订与该文件 SHA-256，后续报告更新不改写旧任务的引用。
5. CSV/JSON 导出必须带来源报告修订、摘要和生成时间；只作为机械接口或快照，不在导出里独立改工具状态。

### 7.3 有效性按变化判断，不按“以前装过”判断

| 变化 | 重新验证范围 |
| --- | --- |
| 工具路径、软链接、版本、运行库、许可条件改变 | 该实例身份/启动/受影响能力 |
| 镜像 digest、初始化、用户、挂载或 Docker context 改变 | 该执行环境接入及受影响代表任务 |
| 源码/生成头/SDK/构建宏或配置改变 | 相应 CDB、语义数据库、查询覆盖；不必重装工具 |
| 查询、Scope、依赖锁或自定义模型改变 | 查询解析与代表对照、相应任务结果 |
| 产物/部署版本、运行时钟/事件配置改变 | 相应产物身份和运行观测验收 |
| 很久未使用、无法核实路径或证据 | 标“待复验”；先最小检查，不直接延用通过 |

新镜像 tag 相同不代表镜像没变；记录不可变 ID/digest。普通翻译单元各自不同的宏和 include 并不自动要求拆库，但互斥产品配置、不同来源版本不能拼成假想构建。大仓库避免为工具报告全量计算 90 GB 摘要；记录仓基线、相关未提交改动、有效构建配置和关键输入，并明确证据覆盖范围。

## 8. 当前没有编译数据库：怎样可靠取得

### 8.1 先选最小可行来源

当前不能要求用户“找一个本来没有的 JSON”。若已有工程入口能**原生导出**，采用经核实的入口；否则用 Bear 跟随真实构建。历史数据库只有在版本/配置/路径和关键覆盖一致时才能复用。CDB 是参数资料，不独自证明每条命令本次实际执行过。

| 来源 | 使用条件 | 证据边界 |
| --- | --- | --- |
| CMake 原生导出 | 确认该配置使用支持的 Makefile/Ninja 生成器，在原配置入口启用 `CMAKE_EXPORT_COMPILE_COMMANDS=ON` | 不需逐个改所有 CMakeLists；独立配置工程需分别处理；导出不是执行记录 |
| Ninja 的 compdb 能力 | 已有 build 图，按所装版本帮助选规则/目标范围 | 图中命令不等于本次执行；生成代码和构建仍需完成 |
| Bear | 无可用原生入口，实际编译可捕获 | 只覆盖实际可观察且识别的编译；包装/远端/缓存要验收 |
| 历史日志/dry-run 恢复 | 以上暂受阻，明确作为候选上下文 | 标“恢复/推测”，不能改称实际采集 |

CMake 显式选项的参考形式是 `-DCMAKE_EXPORT_COMPILE_COMMANDS=ON`，追加到**原来已经验证的配置入口**；不丢失 toolchain、preset、生成器和业务选项后另运行一个简化 `cmake -S . -B build`。配置步骤可能执行探测/下载，不能当成无副作用只读操作。Unity Build 等限制需核对。[CMake 导出说明](https://cmake.org/cmake/help/latest/variable/CMAKE_EXPORT_COMPILE_COMMANDS.html)、[Ninja 手册](https://ninja-build.org/manual.html)。

### 8.2 为真实配置准备一次结果位置

所有变量由已有环境和当前报告填写；含 `/`、`..` 等片段的任意文字不能直接当目录 ID：

```bash
FACT_KIT='/实际位置/产品与EMAP事实探查/成熟工具增强事实探查'
FACT_RUN='/实际环境中/本次任务结果根'
FACT_TARGET='已确认且适合作目录名的编译配置ID'
FACT_CASE="$FACT_RUN/configurations/$FACT_TARGET"
FACT_PRODUCT='/实际环境中/产品仓'
FACT_EMAP='/实际环境中/对应EMAP仓'
FACT_BUILD_CWD='/实际环境中/原构建工作目录'
FACT_COMPDB="$FACT_CASE/compile_commands.json"
FACT_COMPDB_DIR="$FACT_CASE"
FACT_SOURCE='/实际环境中/事先确定的关键实现.cpp'
mkdir -p "$FACT_CASE"
```

本次任务总入口已建结果根时沿用，不能重新初始化流程状态。输入基线由任务记录：Git HEAD 还不够，需包括相关未提交变更、子仓和生成配置；不要求先遍历整个 EMAP 下载树。

首次从随包 [project.example.json](../产品与EMAP事实探查/成熟工具增强事实探查/config/project.example.json) 复制配置；续接只读已有配置，不覆盖已填写内容。`FACT_EMAP` 必须是本次选中的真实仓，不能机械填写约 90 GB 的下载总目录。此脚本会检查全部未跟踪文件、读取包含二进制的全仓差异到内存，并递归查询子模块状态；只对已确认规模可控的仓执行，先评估时间、内存和输出预算。若单体大仓执行代价超预算，复用适用的现有基线，或按本次相关仓/文件记录版本、差异与生成输入，并写明覆盖范围和未捕获输入，不能为了表格完整盲跑递归，也不能把局部记录冒称全仓基线：

```bash
if [ ! -e "$FACT_CASE/project.json" ]; then
  cp "$FACT_KIT/config/project.example.json" "$FACT_CASE/project.json"
fi
"$FACT_PYTHON" "$FACT_KIT/scripts/probe.py" baseline \
  --repo "product=$FACT_PRODUCT" --repo "emap=$FACT_EMAP" \
  --out "$FACT_CASE/baseline.json"
```

第一次 baseline 使用新输出路径；已有 baseline 时按输入是否变化决定复用或另存新文件，不覆盖旧结果。填写配置中的 `repositories`、当前执行环境 `tools` 绝对路径、`required_tools` 所代表的本次能力，以及 `targets` 的真实配置 ID、compiler、build_cwd、compdb、构建说明、关键翻译单元、产物和身份依据。`state: resolved` 只表示仓与构建配置身份已核对，不代表核/OS 已查清；`execution_domain` 未知就保留未知。关键文件由任务预先确定，产品仅链接预编译 EMAP 时不能强填未在该配置编译的 EMAP 实现。

容器/远端关系可从 [execution.example.json](../产品与EMAP事实探查/成熟工具增强事实探查/config/execution.example.json) 建立记录副本；该文件只记录现有启动/初始化/挂载，不自动实施。必要的原始输入变更和关键文件快照由任务补存，baseline 不是完整源码备份。先完成真实 CDB，再运行下一节 preflight。

### 8.3 Bear 在最终编译端捕获

恢复原初始化后，在真实编译环境使用实际 Bear 路径。以下 Bear 3.x 形式仍须与本机帮助核对：

```bash
FACT_BUILD_ARGV=(/实际已审核的构建入口 原有参数)
"$FACT_PYTHON" "$FACT_KIT/scripts/probe.py" record \
  --out-dir "$FACT_CASE/runs/bear-capture" --cwd "$FACT_BUILD_CWD" \
  --target "$FACT_TARGET" --timeout 7200 -- \
  "$FACT_BEAR" --output "$FACT_COMPDB" -- "${FACT_BUILD_ARGV[@]}"
```

先用工程支持的隔离构建目录或限定目标重编译，确保计划核验的源码实际参与；不随意 `git clean`、删除正式 build 或清空全局缓存。空 CDB 时查增量是否无工作、launcher/拦截方式、编译器识别和实际编译进程位置。不能一概说所有 ccache 命中必然漏捕：Bear 版本/launcher 处理存在差别，实测关键条目；CodeQL 的提取覆盖另行核验。不要无条件 `--append` 混入过期或互斥配置。[Bear 空数据库](https://rizsotto.github.io/Bear/guides/recipes/empty-compilation-database.html)、[launcher 处理](https://rizsotto.github.io/Bear/guides/recipes/ccache-distcc-icecc.html)。

产品只链接预编译 EMAP 库时，本轮不会凭空取得库内部的 CDB。查找匹配版本 EMAP 的真实构建入口并单独采集；入口/源码不可得就记录边界，不能伪造条目。研究 EMAP 构建入口与下载依赖时先看现有脚本和清单，受控试点，避免自动拉取所有产品依赖。

### 8.4 审核和路径适配

关键文件清单应从业务入口、构建目标和独立源码证据形成，不能从采集结果反推一份必然全覆盖的清单。只传本次配置本应包含的关键实现：

```bash
"$FACT_PYTHON" "$FACT_KIT/scripts/probe.py" compdb \
  --db "$FACT_COMPDB" \
  --repo "product=$FACT_PRODUCT" --repo "emap=$FACT_EMAP" \
  --key "$FACT_SOURCE" --out "$FACT_CASE/compdb-audit.json"
"$FACT_PYTHON" "$FACT_KIT/scripts/probe.py" preflight \
  --config "$FACT_CASE/project.json" --out "$FACT_CASE/preflight.json"
```

第二条前须填写配置副本；`preflight` 依赖 CDB，安排在采集后，不用它阻止首次采集。审核源文件、`directory`、compiler、宏/include/target/sysroot、强制头、响应文件、生成文件和重复配置。优先原生 `arguments`，不直接执行来路未审查的 `command`。脚本不会解释全部厂商参数和响应文件语法，仍需原工具链核对。

从容器转到 WSL 不只是复制 JSON：所有路径和编译器默认上下文必须对应同一版本。优先同路径可访问或在原环境分析；确需转换时保留原始数据库、映射规则和差异，不能删去未知参数后声称与板端等价。[CDB 格式](https://clang.llvm.org/docs/JSONCompilationDatabase.html)。

## 9. 原编译器、clangd 和 clang-query

从真实 CDB 复制相应翻译单元的工作目录和参数；原编译器可按其文档生成预处理、宏和包含路径证据。GCC/兼容工具链常用 `-E`、`-dM`、`-H`，需移除/重定向与目的冲突的 `-c/-o` 和依赖输出，保存差异，不能删掉目标语义。目标布局用目标编译器/对应调试信息核对，不在 x86 主机编译一个 `sizeof` 程序就断言板端布局。

clangd 定点解析可用第 6 节录制命令。审阅日志中的有效命令、fallback/inferred、缺头文件、语言、宏和目标。头文件可能借用相似源文件参数，须回到实际翻译单元。`--query-driver` 只允许可信的真实编译器路径，它会执行驱动查询；不是给 clang-query 的通用开关。查询到 include/target 也不保证支持所有厂商扩展。[clangd 编译命令](https://clangd.llvm.org/design/compile-commands)、[系统头和驱动](https://clangd.llvm.org/guides/system-headers)。

定点 AST 查询示例：

```bash
"$FACT_PYTHON" "$FACT_KIT/scripts/probe.py" record \
  --out-dir "$FACT_CASE/runs/clang-definitions" --cwd "$FACT_PRODUCT" \
  --target "$FACT_TARGET" --input "$FACT_COMPDB" --input "$FACT_SOURCE" \
  --input "$FACT_KIT/queries/clang/definitions.matcher" --timeout 300 -- \
  "$FACT_CLANG_QUERY" -p "$FACT_COMPDB_DIR" \
  -f "$FACT_KIT/queries/clang/definitions.matcher" "$FACT_SOURCE"
```

随包 `definitions.matcher`、`named_calls.matcher` 是定点起步样例，不是全仓调用图。模板、头文件、间接调用和虚调用需要单独核对；静态绑定不代表运行唯一目标。真实宏/include 保持不了时写解析限制，用原编译器和产物补证，不把 SDK 换成宿主头文件来“消红”。

大型仓库先限定输入文件/有效配置，再决定是否建立后台索引；打开编辑器可能触发后台索引，不等于免费只读浏览。记录索引范围、资源预算与缓存，避免默认全量扫 90 GB。[clangd 索引](https://clangd.llvm.org/design/indexing)。

## 10. CodeQL：建库、覆盖、查询分别证明

### 10.1 采用模式与真实构建

当前 C/C++ 有 `none/autobuild/manual` 等构建选项。none 模式会推断上下文，其结果不能直接证明本产品真实宏、生成文件和依赖。已有真实嵌入式构建时优先评估跟随原构建采集；不把此选择描述为 CodeQL 永远只有一种模式。[官方构建选项](https://docs.github.com/en/code-security/reference/code-scanning/codeql/build-options-for-compiled-languages#building-cc)。

先确认适用许可、CLI/提取器和编译环境，在最终编译端运行。下面 `FACT_BUILD_COMMAND` 是已审核的实际命令字符串，必须正确做 shell 引用；可用 Python `shlex.join` 从真实 argv 构造，或调用审核过的包装脚本，不能用 JSON 转义代替 shell 引用：

```bash
FACT_CODEQL_DB="$FACT_CASE/codeql-db"
FACT_ANALYSIS_ROOT='/实际分析源码根'
FACT_BUILD_COMMAND='./已审核的真实构建入口及参数'
"$FACT_PYTHON" "$FACT_KIT/scripts/probe.py" record \
  --out-dir "$FACT_CASE/runs/codeql-create" --cwd "$FACT_BUILD_CWD" \
  --target "$FACT_TARGET" --timeout 7200 -- \
  "$FACT_CODEQL" database create "$FACT_CODEQL_DB" \
  --language=cpp --source-root="$FACT_ANALYSIS_ROOT" \
  --command="$FACT_BUILD_COMMAND"
```

确保关键编译真的被捕获：增量、构建守护进程、远端编译和复用产物可能造成漏提取。只重编计划所需范围，先试点，不默认全仓 clean。Bear 和 CodeQL 首次分别验证，不未经测试嵌套进同一次命令。[CLI 建库](https://docs.github.com/en/code-security/tutorials/customize-code-scanning/prepare-code-for-analysis)、[无源码被提取的排查](https://docs.github.com/en/code-security/reference/code-scanning/troubleshoot-analysis-errors/no-source-code-seen-during-build)。

预编译 EMAP 库不会因 `--source-root` 包含源码就被自动还原。若两仓在相容的真实构建中共同编译，可按其实际提取范围安排；否则分别建库和关联契约。互斥部署配置/不同来源版本隔离，普通 TU 参数差异由实际构建保留。不要为“跨两仓”混成一个不存在的程序。

### 10.2 初始查询与项目查询

将随包 `queries/codeql` 复制到本次结果的查询工作副本，保留原包。依据数据库实际提取路径填写 `Scope.qll`，清掉 `__SET_` 占位；单仓库只留该仓的有效范围。`qlpack.yml` 中 `*` 不是锁：按组织已有方式解析兼容依赖，确需联网时执行该版本支持的 `codeql pack install`，保存实际生成的 `codeql-pack.lock.yml`；复跑复用锁。

```bash
FACT_QUERY_DIR="$FACT_CASE/queries-codeql"
"$FACT_PYTHON" "$FACT_KIT/scripts/run_codeql.py" \
  --database "$FACT_CODEQL_DB" --target "$FACT_TARGET" \
  --codeql "$FACT_CODEQL" --queries "$FACT_QUERY_DIR" \
  --out "$FACT_CASE/codeql-inventory"
```

runner 只执行真实 `query run` 和 `bqrs decode`，不安装、不建库、不补模型。保留 summary、每条命令、BQRS/CSV、查询源码、Scope 和锁；查询失败不能被其他成功结果掩盖。

| 初始查询 | 验收要点与限制 |
| --- | --- |
| Q00 Definitions | 独立选定的关键实现/定义是否出现；有几行不证明全配置完整 |
| Q01 ExtractionErrors | 已记录 ErrorExpr 等提取问题；零行不排除漏采或其他诊断 |
| Q10 / Q11 / Q12 | 命名调用、函数引用、其他调用点分别留证；不自动确定所有函数指针运行目标 |
| Q20 DirectVariableWrites | 写入候选；不是所有别名、DMA、闭源写入清单 |
| Q30 Conditions | 分支候选；业务含义必须回到代码、配置和状态解释 |

可用以下检查关键文件的定义出现情况；只能传确实有定义且本库应覆盖的文件：

```bash
"$FACT_PYTHON" "$FACT_KIT/scripts/probe.py" compare-definitions \
  --compdb-report "$FACT_CASE/compdb-audit.json" \
  --csv "$FACT_CASE/codeql-inventory/Q00_Definitions/result.csv" \
  --key "$FACT_SOURCE" --out "$FACT_CASE/definition-presence.json"
```

路径适配使用有证据的前缀映射，不能借映射把不同版本对上。纯数据文件和关键生成代码另行验证。后续业务查询的 source/sink、机制、不变量和验收由相应任务文档定义；每条新查询在已知代表项上校验并保存实际结果。

局部/全局数据流和 taint 的含义不同，指针地址与指向内容不同。Global Data Flow 不等于自动跨多个数据库、私有消息总线或盒间网络串通全链路。消息/注册/序列化/共享对象的附加模型必须有接口契约依据，缺边就标未证，不能为画通而补边。[C++ 数据流](https://codeql.github.com/docs/codeql-language-guides/analyzing-data-flow-in-cpp/)、[C++ 模型](https://codeql.github.com/docs/codeql-language-guides/customizing-library-models-for-cpp/)。

## 11. 构建关系、二进制、链接与模型

先用工程已有目标图、构建日志、depfile、manifest 和链接 map 收敛实际范围。CMake File API、Ninja query/graph/commands/compdb 等可在原有构建系统适用时使用；按所装版本帮助保存实际参数和输入身份。生成器给出的候选命令不等于执行过，文件访问也不等于最终链接采用；不得只根据 `all output` 名字认定其中全是实际运行依赖。[CMake File API](https://cmake.org/cmake/help/latest/manual/cmake-file-api.7.html)、[Ninja 手册](https://ninja-build.org/manual.html)。

选择兼容目标格式的对象工具，宿主通用 `readelf` 可读部分格式不代表 `objdump` 能解码所有架构。GNU/ELF 的典型调用如下；非 ELF 用厂商等价工具：

```bash
FACT_ELF='/实际位置/本次目标.elf'
FACT_LIB='/实际位置/实际被消费的EMAP库.a'
"$FACT_PYTHON" "$FACT_KIT/scripts/probe.py" record \
  --out-dir "$FACT_CASE/runs/elf-info" --cwd "$FACT_CASE" \
  --target "$FACT_TARGET" --input "$FACT_ELF" --timeout 120 -- \
  "$FACT_READELF" -h -l -S -n -s -W "$FACT_ELF"
"$FACT_PYTHON" "$FACT_KIT/scripts/probe.py" record \
  --out-dir "$FACT_CASE/runs/library-symbols" --cwd "$FACT_CASE" \
  --target "$FACT_TARGET" --input "$FACT_LIB" --timeout 120 -- \
  "$FACT_NM" -A -C "$FACT_LIB"
```

按问题再选重定位/动态项/属性，不能为了工具名齐全对全部产物反汇编。核对实际链接命令、库路径与摘要、对象/库成员、weak/别名/节丢弃、打包和加载配置。strip、LTO、内联、GC、动态加载会影响可见信息；一次符号未命中不证明实现不存在，符号相同也不证明源码版本相同。ELF OSABI 字段不单独证明设备 OS；磁盘 ELF 身份也不自动证明当前设备装载身份。[GNU readelf](https://sourceware.org/binutils/docs/binutils/readelf.html)、[nm](https://sourceware.org/binutils/docs/binutils/nm.html)、[objdump](https://sourceware.org/binutils/docs/binutils/objdump.html)、[GNU ld](https://sourceware.org/binutils/docs/ld/Options.html)。

BEH/XML/协议结构可用原解析器和对应 schema 导出，但保留生成器版本、输入摘要、实例/端口/字段、生成绑定和消费位置。普通 XML 读取成功不能证明产品装载和运行机制正确；模型字段与代码字段相连须核对类型、单位、缩放、端序、版本和实例。

## 12. 可选索引、Understand 和图形工具

可选工具也遵守“先盘点、后采用、实际执行、代表复核”。不要仅在报告列名字后无条件下载，更不要为 90 GB 先建全量库。

| 工具 | 可操作的使用方式 | 必留证据/限制 |
| --- | --- | --- |
| Universal Ctags | 先导出经核对的文件清单，按本机帮助用 `-L` 输入、`-f` 独立输出 | 工具类型/版本、文件清单、tags、已知定义对照；标签不等于语义调用图 |
| cscope | 对已确认文件清单用 `-i`、独立数据库 `-f`，需要时 `-q`；不用根目录 `-R` | 清单、命令、库和实际查询结果；预处理、C++ 和函数指针存在识别限制 |
| GNU IDutils | 根据已装版本 `mkid` 输入/语言映射选项建立限定语料 ID，再用 `lid` 查已知标识符 | 明确输入范围、ID 文件、token 查询结果；不是类型/控制流分析 |
| Understand | 按所装版本 CLI/API 帮助建立隔离项目，导入真实宏/include/生成文件/配置后解析和导出 | 项目配置、`und` 实际命令或可回放 GUI/API 记录、解析日志、关系导出、代表核对；不能只交图片 |
| clang-uml | 基于真实 CDB 和独立配置指定所需结构范围，运行后再用源码/语义证据核对边 | 配置、CDB 身份、命令、原始图文件和核对项 |
| Graphviz/PlantUML | 仅对上游已生成的结构文本按所选格式渲染 | 输入/输出；渲染成功不提高上游事实的可靠性 |

执行时先保存各工具的 `--help`/对应本地手册，使用实际版本参数；不同 Ctags 实现不能混称。工具无法导入真实配置时如实写限制，不能给 Understand 一个文件夹就称“完整语义”。厂商扩展和嵌入式汇编尤其需要产物补证。[Ctags](https://docs.ctags.io/en/latest/man/ctags.1.html)、[cscope](https://cscope.sourceforge.net/cscope_man_page.html)、[GNU IDutils](https://www.gnu.org/software/idutils/manual/html_node/mkid-invocation.html)、[Understand 准确配置](https://docs.scitools.com/help/accuracy/accurate-c-cpp-projects.html)、[固件边界](https://docs.scitools.com/help/accuracy/embedded-firmware-projects.html)。

## 13. 运行观测工具：确认平台后按疑点启用

静态分析解决可能路径与契约，运行观测解决本次发生了什么；二者都不能仅凭“第一个异常日志”保证已经找到最早根因。业务任务负责定义要观察的值、状态、机制和因果假设，本节统一管理工具接入和验收。

| 条件性工具 | 起步方式 | 通过前必须核验 |
| --- | --- | --- |
| 构建端 strace | Linux 构建端确有缺失依赖疑点时，限一次目标构建、子进程与必要 syscall 类 | 跟踪进程范围、失败探测与有效依赖区别、已有 daemon/远端未覆盖；不能当作板端执行证据 |
| ftrace / trace-cmd | 设备确为支持相关功能的 Linux 时，先列可用事件/时钟，限定窗口和范围 | 权限、事件存在、过滤是否误删唤醒、per-CPU overrun、时钟和扰动 |
| perf / perf sched | 分别用于已明确的热点或调度等待问题 | 内核/工具/PMU或软件事件支持、权限、符号和展开条件；热点不是根因证明 |
| Perfetto | 已有有效事件时导入/采集业务与调度事件、用 SQL 对照 | 事件语义、clock_id/同步映射、丢失统计；不同 writer 文件顺序不是全局时序 |
| RTOS/厂商 trace | 复用已有 hook/工具/探针，小窗口代表实验 | 具体平台、ISR/重入、时钟、缓冲预算、导出通道及开销 |

在设备平台、权限和构建选项尚不清楚时，不给一段 Linux 命令要求所有盒执行。先查现有设备成果和工具帮助，设计最小实验，再保存实际命令、配置、输入/固件身份、事件原文件、丢失/开销和已知事件对照。修改业务代码或上板采集属于对应实施任务的授权范围，不因“工具盘点”自动开展。

Linux trace 的本地时钟可能跨 CPU 不同步；本机全局时钟也不自动解决跨盒同步。无可靠跨盒时钟映射时保留 send→receive 因果约束和盒内耗时，不计算伪精确单向延迟。日志缺失只有在覆盖和丢失已核验后，才可能支持“某事件未发生”。[ftrace](https://docs.kernel.org/trace/ftrace.html)、[trace-cmd](https://www.trace-cmd.org/Documentation/trace-cmd/trace-cmd-record.1.html)、[Perfetto 时钟](https://perfetto.dev/docs/concepts/clock-sync)、[缓冲与丢失](https://perfetto.dev/docs/concepts/buffers)。

## 13A. 崩溃定位工具：符号化、监视点和内存检查

业务步骤与待收集字段见[跨核崩溃复位与内存破坏专项](../问题定位与修复/跨核崩溃复位与内存破坏_根因定位实施指南.md)。这里统一维护工具接入和验收方法。先执行本指南盘点与报告规则；这些能力均为按需选择，不要求全装，也不把本机工具运行成功当作板端支持。

### 13A.1 从已有 SDK 找到完整实例

优先从原镜像/SDK 的工具清单、构建日志和既有调试工程找到目标对象工具及调试器。`command -v gdb` 不会自动找到带厂商/架构前缀的工具；按已知 SDK 根和配置有界查找。记录 WSL 客户端、容器工具、调试服务、探针固件及板端监控程序各自的位置、版本、目标支持和连接配置，不能合成一个“GDB 已装”。

缺失时，先确定需要的能力：离线符号化可只补兼容对象工具；目标调试优先原 SDK/厂商受支持渠道；ASan/UBSan 需要实际编译器及匹配运行库。普通主机 `gdb` 或 `gdb-multiarch` 软件包是否支持该目标、远程协议、寄存器和 RTOS 线程视图须核实。厂商工具、服务和探针按平台官方说明取得，不猜包名、不替换原 SDK。下载、存放和摘要记录按第 4 节，选定后将绝对路径登记在唯一报告。

### 13A.2 离线符号化先核对产物身份

收集故障域对应的实际部署 ID、未剥离 ELF/调试文件、构建标识或摘要、运行加载地址/重定位依据、PC/LR/SP 及其有效性。多个执行域分别对应自己的产物；不能用主核 ELF 解析另一侧地址。原始地址与换算规则都要保留，不凭经验统一减一个偏移。

GNU 兼容示例仅在 `FACT_ADDRESS` 已转换为该 ELF 所需地址时使用；变量由本次证据填写：

```bash
FACT_ADDR2LINE='/实际SDK或工具根/兼容的addr2line'
FACT_ELF='/本次故障对应的未剥离ELF或调试文件'
FACT_ADDRESS='0x经加载映射核对的地址'
"$FACT_ADDR2LINE" --version
"$FACT_ADDR2LINE" -a -f -C -i -e "$FACT_ELF" "$FACT_ADDRESS"
```

`-i` 可补内联调用信息；输出 `??` 或行号 0 表示未解析出，不证明没有对应源码。`llvm-symbolizer` 或厂商等价工具可替代，命令按实际版本帮助。验收至少用一个已知符号/行号进行正向核对，并保留故障地址解析原文、输入摘要和映射；优化、缺失栈、异步异常或延迟报告可能使结果只能定位近邻，不能把某一行直接写成最早错误写入。[GNU addr2line](https://sourceware.org/binutils/docs/binutils/addr2line.html)。

### 13A.3 硬件监视点须验证“监视了谁”

仅在地址、对象生存期、访问宽度和正确执行域已明确，且能够连接目标调试端时使用。按原调试工程加载匹配符号和连接；不在通用文档虚构目标 IP、端口或复位命令。实际停止前明确是否停一个核、全部核或影响看门狗/实时任务，记录探针配置。

下面是在已连接正确目标的 GDB 会话里操作**真实已知符号**的写法；先将 `ACTUAL_GUARD_SYMBOL` 替换为本次对象，不能原样执行：

```gdb
watch -location ACTUAL_GUARD_SYMBOL
info breakpoints
```

核对是否建立硬件监视点，并在恢复执行时检查能否插入；硬件资源、长度和对齐可能受限。普通 `watch` 主要报告值发生改变；要观察读取或同值写入，需核对 `rwatch/awatch` 及目标硬件能力。若退化为软件监视点，必须明确其额外开销和线程覆盖限制，不据此宣称已抓住实时原始行为。[GDB watchpoints](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Set-Watchpoints.html)。

用独立受控样例确认命中来源和停止域，再应用于疑似地址；动态对象重新分配后核对代次和重设条件。命中时保存寄存器、相邻指令、访问地址/大小、当前任务及可见栈。PC 是否指向实际写指令由平台异常语义确认。对另一处理器、DMA 或未受当前调试器控制的执行域，不推定有覆盖；未命中不能排除它们写坏内存。复位后监视配置是否保留也要核实。

### 13A.4 C++ 异常捕获依赖真实运行时

在支持的 GDB/ABI/运行时组合中，可用 `catch throw` 在抛出时停住，再查看原始栈。按类型过滤和异常对象查看有额外运行时条件；先用同环境的受控抛出样例验收，再定位真实异常。[GDB catchpoints](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Set-Catchpoints.html)。

捕获 `bad_alloc` 只定位到异常报告点；还须核实实际分配失败，或是否由业务显式抛出/包装产生。泄漏、碎片、错误长度或更早的堆破坏要按专项继续取证。运行时不支持时采用可改边界前的记录；不要通用替换 `__cxa_throw`、分配器或全局异常处理，也不要把 unwind 后的栈当作抛出前完整栈。

### 13A.5 ASan/UBSan/TSan 先在支持环境做代表验证

先确认实际主机/DT/板端架构、OS、编译器和运行库组合支持，再在独立诊断构建目录接入。ASan 需要编译插桩及运行库，通常在编译和最终链接使用 `-fsanitize=address`，用编译器驱动链接；`-g`、适用的帧指针选项及符号工具便于还原。不要只给链接命令加参数就声称所有目标已插桩。[LLVM AddressSanitizer](https://clang.llvm.org/docs/AddressSanitizer.html)。

UBSan 可按疑点选择 `-fsanitize=undefined` 或更窄检查；编译与最终链接需匹配选项。部分检查可用 trap 模式，所需运行库、恢复/停止行为须按所选检查确认，不等同“发现后必停”。[LLVM UndefinedBehaviorSanitizer](https://clang.llvm.org/docs/UndefinedBehaviorSanitizer.html)。

并发数据竞争可在受支持环境另选 TSan：编译和链接使用相应的 `-fsanitize=thread`，验收真实线程与同步模型、运行库、资源和已知竞争的阳性样例；它不会自动理解跨盒消息或所有自定义同步。[LLVM ThreadSanitizer](https://clang.llvm.org/docs/ThreadSanitizer.html)。ASan 与 TSan 不能用于同一程序，应分开构建和运行；UBSan 与其中一种的组合以实际工具链支持为准，不把所有 sanitizer 开关堆在一起。[Clang 检查器组合规则](https://clang.llvm.org/docs/UsersManual.html#controlling-code-generation)。

最低验收包括：原正常代表用例、隔离测试工程中人为构造且应能被检测的阳性用例、完整编译/链接及报告原文、实际被插桩文件范围、未插桩库和不能复现的差异。阳性用例只用于隔离验证，不加入产品正式逻辑。自定义分配器、未插桩代码、共享内存/DMA 与板端时序可能留下盲区。主机发现同类错误可帮助形成假设；主机未报错不能证明板端没问题。是否将诊断包部署由该专项的包身份、开销和回退步骤决定。

### 13A.6 平台能力和每次实际使用的证据

MPU/MMU 保护、厂商 trace、保留 RAM、异常 hook 等必须在平台确认后，链接该版本官方手册与现有工程接口，记录区域粒度、可覆盖访问者、复位/供电域、调试及记录开销。不在此给未知平台的寄存器写入或全局权限修改命令。能力不具备时继续使用可改产品/EMAP 边界记录、受保护对象和检查点缩小区间，并说明能证明到哪里。

每次符号化、调试会话、sanitizer 运行或平台 trace 都按第 6 节保存所用工具实例、部署/输入身份、命令或会话转录、原始结果、代表对照、覆盖/盲区及下一步。交互工具也必须留记录。只有具体环境验收过的能力才回写当前工具报告为通过；候选工具清单不是通过清单。

## 14. Mutagen、OpenSSH 与同步辅助工具

仅在仍采用 Windows/WSL 两份工作树时需要这一组；单份 WSL 工作树方案不因此加装。仓范围、冲突、Git 操作端、首次试验和日常操作场景由 [Mutagen 同步场景指南](../Windows与WSL开发环境/03_Mutagen_Windows与WSL双向同步详细使用指南.md) 说明；工具身份、准备和验收统一记当前工具报告。

先查 Windows 已有 Mutagen 完整发行目录、版本、daemon 所用用户/状态目录/SSH 客户端和会话；已有会话时不先切 `MUTAGEN_DATA_DIRECTORY`。缺失时从 [官方 Releases](https://github.com/mutagen-io/mutagen/releases) 下载适合 Windows 主机架构的固定版本完整二进制发行包，保留代理等配套内容；不只拿 `mutagen.exe`。原包用 `Get-FileHash` 留摘要并核对可得的发布方校验。位置采用已有环境结果，以下都是待替换变量：

```powershell
$MutagenExe = '实际版本目录\mutagen.exe'
$SyncSshDir = '实际已选OpenSSH工具目录'
$SyncSshExe = Join-Path $SyncSshDir 'ssh.exe'
$SyncScpExe = Join-Path $SyncSshDir 'scp.exe'
Test-Path -LiteralPath $SyncSshExe
Test-Path -LiteralPath $SyncScpExe
& $MutagenExe version
& $MutagenExe sync create --help
& $MutagenExe sync list --help
& $MutagenExe sync flush --help
& $SyncSshExe -V
```

`Test-Path` 两项须为 True；核对所选版本支持场景中所用 `--paused`、`--mode`、`--no-global-configuration` 等选项，参数不支持就修订配方，不静默忽略。SSH/scp 优先复用公司已有可用组合（包括已装 Git for Windows 的 OpenSSH），不根据历史兼容说明断言所有 Windows 原生 SSH 一律不能用；PuTTY/plink 不是此调用方式的直接替代。

只有建立**全新**同步环境、且已确认没有需要继承的另一套状态时，才在首次启动 daemon 前设置：

```powershell
$env:MUTAGEN_SSH_PATH = $SyncSshDir
$env:MUTAGEN_DATA_DIRECTORY = '实际已确认的Windows状态目录'
& $MutagenExe daemon start
```

已有环境继承其原值，不能照示例另建一套会话历史。Windows CLI、AI 进程、计划任务和 daemon 使用同一套用户、客户端和状态目录；需要持久化时写专用启动配置并核对旧终端是否已重新加载。不要改变 HOME/USERPROFILE 达到迁移目的。Windows 状态目录配置不自动迁移 Linux 代理目录，两端分别记录；状态目录不放源码同步根或自动云盘中。已有 daemon 的停止会影响其会话，不能当无影响检查。[Mutagen 安装](https://mutagen.io/documentation/introduction/installation/)、[SSH](https://mutagen.io/documentation/transports/ssh/)、[daemon](https://mutagen.io/documentation/introduction/daemon/)。

Ubuntu SSH 服务先查已有 `sshd`、监听、用户与认证。确实缺失才按该发行版渠道安装；已确认 Ubuntu、现有软件源适用时可按需执行：

```bash
sudo apt-get update
sudo apt-get install openssh-server
```

安装可能启用默认服务，须记录真实监听；系统可能由 ssh.service 或 ssh.socket 管理，不能只改 Port 就认定已生效，也不自动停止现有服务。服务和连接别名沿同步场景的实际配置执行，不为同机同步默认开放局域网。

密钥优先复用组织允许的专用密钥。`$SyncKey` 必须指向所选私钥实际路径；下面只有需要**新建**密钥时执行，避免覆盖：

```powershell
$SyncKey = Join-Path $env:USERPROFILE '.ssh\id_ed25519_wsl_sync'
if (Test-Path -LiteralPath $SyncKey) { throw '密钥已存在，核对后复用；不覆盖。' }
$SyncKeyDir = Split-Path -Parent $SyncKey
if (-not (Test-Path -LiteralPath $SyncKeyDir)) {
    New-Item -ItemType Directory -Path $SyncKeyDir
}
& (Join-Path $SyncSshDir 'ssh-keygen.exe') -t ed25519 -f $SyncKey
```

确认 `ssh-keygen.exe` 与所选客户端同组且可用；按组织要求设置口令。仅将 `.pub` 公钥完整单行追加一次到正确 Ubuntu 用户的 `~/.ssh/authorized_keys`，保留原内容；私钥不复制到 Ubuntu、不进入仓库。核对目标用户所有权及 `.ssh`/`authorized_keys` 权限，通常分别为 700/600；只改需要调整的项，不递归修改整个 home。

以选定 SSH 客户端核对目标发行版、用户和服务主机指纹，再检查 `BatchMode=yes` 无交互重连。带口令私钥需要与该客户端匹配且后台可访问的凭据代理，不能把终端曾输过口令当成后台可重连。随后在全新试验目录验证双向新增/修改/删除/冲突和中断重连；具体连接别名、独立 SSH 入口和同步 YAML 见同步场景文档。

**创建普通同步会话会开始改变文件，暂停会话不自动提供完整只读差异清单。** 真仓接入前由同步场景完成范围与差异评审；不能用两次反向 rsync 冒充可靠双向同步。`rsync -n` 的只读内容比对也需保存输出、错误和期间文件变动，退出 0 不表示没有差异。正式验收还须记录会话配置、忽略规则、同步两端实路、内容/链接/执行位等验证，以及实测耗时；不根据仓总 GB 数承诺传输时间。

通用日常调用在 Windows、同一用户和状态目录下进行。`$SyncSession` 填已核对的唯一名称或会话 ID，不直接使用示例仓名：

| 目的 | PowerShell 调用 | 效果和验收 |
| --- | --- | --- |
| 查看全部关系 | `& $MutagenExe sync list --long` | 查看不证明内容一致 |
| 查看指定会话 | `& $MutagenExe sync list --long $SyncSession` | 同时核对两端问题、冲突和暂停状态 |
| 监视 | `& $MutagenExe sync monitor $SyncSession` | Ctrl+C 退出监视，不停同步 |
| 完成一轮 | `& $MutagenExe sync flush $SyncSession` | 不加 skip-wait；完成后仍查冲突和代表文件 |
| 暂停 | `& $MutagenExe sync pause $SyncSession` | 两侧继续修改会积累变化 |
| 恢复 | `& $MutagenExe sync resume $SyncSession` | 会处理积累变化，应先确认范围 |
| 删除会话 | `& $MutagenExe sync terminate $SyncSession` | 不删除两端源码，但丢失该会话同步历史；只在明确停用时用 |

flush 不是仓锁，也不保证之后没有新写入；list 退出 0 不代表没有冲突。[官方会话操作](https://mutagen.io/documentation/introduction/getting-started/)。升级时先保存版本、配置、状态位置及需要的恢复资料，按实际影响暂停会话/停止对应 daemon，在新目录完整解压新版本和代理，沿同一状态目录启动并验证连接及代表操作。状态兼容性依据发布说明；状态升级后不随意降级。记录变化并使原实例的受影响验收失效，不能只改版本号。

## 15. 后续任务怎样只读本指南和当前报告就开始工作

任务总入口应依次做四件事：

1. 定位本指南和当前报告，记录报告修订与摘要；核对所需工具实例和执行环境，没有就按本指南补齐对应项。
2. 把已选路径、镜像、挂载和初始化引用填入本次任务配置。目标问题、关键文件、预算和业务验收由任务文档定义。
3. 按所选工具方法执行或明确复用已有结果；每个任务保留自己的原始证据，新增查询有新增执行记录。
4. 将新环境能力/失效/受阻结论回写当前工具报告；任务事实与业务结论仍保留在任务结果，不搬到工具底账。

现有 `environment-reuse.md`、`tool-inventory.csv`、`execution.json` 可作为报告引用的环境原始资料或该次任务快照；补充其来源报告修订/摘要，避免另行维护相互冲突的“当前工具清单”。`workflow-state.json` 维护任务进度，不能替代工具底账。

成熟工具增强探查的机械接口统一为：

| 接口字段 | 内容约定 |
| --- | --- |
| `workflow-state.json` 顶层 `tool_report_reference` | 一个位于本次结果根内部的引用索引文件路径，例如 `tool-report-reference.md`。索引记录权威报告的实际路径、修订/ID、SHA-256、采用时间、选中的环境/实例/配置和适用性核对结论；它只是本次引用凭据，不是另一份工具报告。 |
| 工具阶段 `task_run_evidence` | 字符串数组；S03/S05/S06/S07/S10，以及采用可选工具的 S12 标为 completed/reused 时，引用本次结果根内真实执行元数据或已验证复用索引。内容满足第 6 节：输入、argv/cwd/环境、原始日志/输出、核对项、结论边界；reused 说明旧证据身份和本次适用性检查。 |
| 兼容导出 `tool-inventory.csv` | `report_id`、`report_sha256`、`tool_instance_id`、`derived_snapshot_at` 必须对应同一当前报告的明确快照；其他列是该次任务所需信息，不能独立改写权威状态。 |

流程检查器只验证接口形状、必需引用和结果根内文件等机械条件；它不会读一个 exit 0 就推断工具用对了。业务验收者仍须审阅原始证据及代表对照。接口文件只是任务输出，规则始终只在本指南维护。

现有脚本职责保持清楚：

| 脚本/文件 | 能证明的范围 |
| --- | --- |
| `probe.py baseline` | 指定仓基线和状态记录，非全输入快照 |
| `probe.py compdb / preflight` | 参数资料/路径/已知关键文件等机械审核，非全部语义正确 |
| `probe.py record` | 真实命令与输入输出记录，非业务结论自动正确 |
| `run_codeql.py` | 所给初始查询确有执行及结果检查，不补建数据库或模型 |
| `probe.py compare-definitions` | 所选关键文件定义出现情况，非完整配置覆盖证明 |
| `probe.py validate-ledger` | 证据账本结构/引用等机械一致性，非因果真实性证明 |
| `check_workflow.py` | 当前任务约定步骤和证据引用；不自动安装/编译/调用成熟工具 |

受阻工具不能通过删除 required_tools 一项就变成原任务通过；替代工具须说明覆盖的能力、实际对照和留下的缺口。也不因为一个可选工具受阻就停止其他可证工作。

收尾先补齐账本与 raw 证据，再对**整个本次结果根**运行：

```bash
"$FACT_PYTHON" "$FACT_KIT/scripts/probe.py" validate-ledger \
  --ledger "$FACT_RUN/ledger.json" --evidence-root "$FACT_RUN" \
  --out "$FACT_RUN/ledger-check.json"
```

不要把单个配置目录 `FACT_CASE` 当成总结果根；重复验证使用新的输出名，保留旧结果。随后沿任务总入口执行 `check_workflow.py` 和对应业务内容验收，分别记录已完成、受阻、不适用、未验证。机械校验通过不代替内容复核。

给本地 AI 的统一执行约定可直接引用：

> 先读 `工具接入与共享能力/工具统一管理与使用指南.md` 和同目录当前工具状态报告；继承 `Windows与WSL开发环境` 中已经执行的成果。先核实已有工具及精确路径，再按需补装。按每个真实执行环境接入，不把 WSL 可用当容器可用。依照本任务的范围调用工具并保存原始执行与内容核验；复用旧结果则留下本次复用证据。只更新同一当前工具报告，不另写一套安装规范，不把安装/版本检查当成分析已经完成。缺失和未验证如实记录。
