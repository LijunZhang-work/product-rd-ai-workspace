# 产品仓事实探查：工具增强任务 A

版本：v1.2，2026-09-18。由 00 唯一入口分派；先承接已有环境及当前工具报告，再按统一工具指南实际调用或核验复用结果。此处的“目标”先指已确认的编译配置，核/执行域尚未知时不要求用户先提供答案。

先读 [00](00_总入口与执行约定.md)、[统一工具指南](../../工具接入与共享能力/工具统一管理与使用指南.md)，用 [04](04_证据与结果记录模板.md) 记证据。本任务最终回答产品是什么、代码怎样组织运行、有哪些核/域、怎样通信和管理状态、当前能够留下什么故障证据。

先读取[当前工具状态报告](../../工具接入与共享能力/工具状态与验收报告.md)并核对环境、版本和适用范围；本任务实际命令、查询输入、输出及人工核对另行留证。报告中的已安装或已接入不能替代本次分析。

## A1. 范围与业务概览

建立产品仓、子仓、生成代码、外部 SDK/依赖的边界表；登记不可变 commit、未提交差异及实际输入快照。先枚举本次涉及的目标，标出故障版本、开发版本、宿主 DT，不能默认以最容易编译的目标代表板端。

用现有文档和范围搜索发现程序入口、初始化、组件注册、外部接口，再用语义与配置证据验证。查 Web、北向、南向、配置管理、消息分发、图元/算法、维护与诊断等实际模块；不存在的部分不按历史补写。分清电脑侧 BEH 工具和设备侧图元执行环境。

每个主要模块至少记录：业务职责、入口、上游/下游、状态所有者、运行域和任务、编译条件、成功与错误出口。识别周期任务、状态机、订阅/回调等实际编程模式；不是只交目录树。

成果：一页产品大白话说明、模块表、版本与目标矩阵。每个重要模块要有工具可定位的符号/配置证据或明确缺口。

## A2. 核、执行域和部署拓扑

核对板级/BSP、启动代码、装载表、链接脚本、包清单和已有启动记录；读取 ELF 架构只作为产物证据的一部分。分别统计芯片物理核、已启用核、软件逻辑 CPU、系统实例、角色；尚不明确时使用执行域 D01 等占位编号，不伪造物理核 ID。

| 要确认的事实 | 工具与资料 | 必须排除的混淆 |
| --- | --- | --- |
| 名称对应谁 | 板级配置、启动/装载、版本记录 | 主核、实时核、EROS 可能是别名、OS 或角色 |
| 镜像运行位置 | 链接与打包记录、启动表、已有运行身份 | 一个 ELF 不必对应一个物理核 |
| CPU/OS/调度模型 | 目标参数、BSP、OS 接口与启动事实 | 不同 OS 不自动等于硬件异构，DT 不等于设备系统 |
| 任务与 ISR | 创建/注册调用语义、配置和已有任务列表 | 调用者目录不等于回调执行线程 |
| 内存/复位域 | 链接区域、平台配置、启动清理与硬件资料 | 共享地址不等于同一地址空间，noinit 不等于掉电保留 |

成果：域—镜像—模块—任务表、别名表、内存/复位关系图。每个关键节点与边引用证据 ID。

## A3. 真实构建上下文

按每个目标查构建入口、宏、头文件搜索路径、编译器、生成步骤、库、链接、打包和装载。用户当前无编译数据库，按[统一指南的编译上下文流程](../../工具接入与共享能力/工具统一管理与使用指南.md#cdb)核实获取方式与采集结果；可复用的同配置资料须记录来源，不能假设普通编译自动生成。审核时提供已通过业务/配置发现的关键翻译单元清单。

关键清单至少涵盖本目标的启动/初始化、代表性外部入口、消息发送/接收、EMAP 接口使用者、图元交接、内存和异常路径；以实际文件为准。头文件通常不是独立翻译单元，改用引用它的真实 `.c/.cpp` 文件和编译器 include/预处理证据验证。

对同文件多条命令、宏冲突、不同 SDK 同名头文件、响应文件、Unity Build、缓存和容器路径逐项处理。数据库生成成功只是获得上下文，须对关键条目核对真实构建记录。

成果：编译数据库及摘要、目标配置记录、关键文件覆盖与未覆盖解释、有效宏/头文件证据。构建数据库没有链接步骤，不能凭它宣布库已进入最终固件。

## A4. 建立语义索引并查询

1. 使用本目标编译数据库运行 clangd 关键文件检查，保存实际采用的命令和诊断。修复分析环境的缺头文件/错误目标问题时记录变更，不能删除目标宏或换成宿主 ABI 来消除报错。
2. 对关键入口与接口，通过 clangd 的定义/引用能力或 clang-query 获取语义关系。直接调用、虚调用静态绑定、函数地址引用和未解析间接调用分别登记。
3. 在本目标 CodeQL 数据库运行 Q00/Q01，先检查关键实现提取及错误；再运行 Q10/Q11/Q12、Q20、Q30，形成调用、注册候选、直接写入和条件线索。
4. 本包初始查询是盘点起点。AI 还需围绕实际消息类型、状态字段、内存对象和边界参数编写项目查询；验证输入、作用域和代表性预期结果，再用于报告。

完整列表很大时按目标和模块导出索引；深度查询围绕关键机制和代表路径展开。不能只读一条路径后声称整个产品已查完。

成果：原始查询、实际执行记录、CSV、语义解析问题表、经过复核的模块和关系表。图形只能从核验后的边生成。

## A5. 消息与状态机制盘点

按实际接口区分核内队列、进程间、跨核、设备协议；消息路由与物理搬运分开。每类记录发送/入队、对象所有权、传输、通知、接收、校验、分发注册、业务处理、完成/失败、释放/复用。

工具查询与上下文阅读必须覆盖相关状态写入者和决定是否处理的条件，不只沿成功调用追踪。检查存在的去重、合并、过滤、脏标志、版本、队列容量、超时重试、晚到消息、初始化/重启清理、任务模式、周期消费等机制。

双缓冲/翻面仅在实际找到时登记；不得围绕翻面预设全部设计。共享内存若存在，继续核对地址形式、长度/布局、缓存属性、屏障/同步、通知顺序和消费条件。静态调用到某个屏障函数不足以证明整体同步正确。

成果：`mechanisms.csv`、消息端点和契约卡、成功及已有错误/恢复分支。回调必须追到注册点/表项和目标选择，函数名相同不算绑定完成。

## A6. 内存、异常与现有定位能力

内存至少覆盖实际 malloc/new、EMAP、堆/池、共享/DMA、栈和静态对象路径。跟踪一块代表性缓冲区的分配、长度、对齐、填充、交接、异步读取、完成、释放/复用，以及超时/取消/对端复位分支。直接字段写入查询不覆盖全部指针别名、整块 memcpy 或第三方写入，缺口必须列出。

异常分别查 CPU 异常、C++ 异常/terminate、分配失败、断言、监控超时、看门狗、主核复位对端及启动恢复。查谁检测、在哪个上下文、谁保存什么、保存介质、导出路径、版本/符号配套、覆盖/丢失与复位保留条件。

能力状态分成存在、当前编入、当前使能、实际验证。保护字检查点是发现时刻，不是自动定位写坏者；调用栈和寄存器主要描述触发现场，不等于源头根因。

成果：生命周期表、原有诊断与复位覆盖表、下层不可见边界。此次只调查，不加保护字或诊断补丁。

## A7. 代表路径与产品报告

按重要目标/机制组合至少尝试贯穿：外部输入到业务/图元消费、核内消息、跨核请求与完成/失败、内存生命周期、异常/监控到记录或复位。一条路径可以覆盖多个问题；尚不支持的边保留断点与最小补证。

交付 `产品仓事实报告.md`：范围基线→产品概览→模块/核/域→构建部署→消息/状态机制→内存→异常与原有定位能力→代表路径→未知冲突→给 EMAP 的具体问题。交接 API 时带目标、调用点、真实头文件、包/库路径、参数契约和待确认行为。

按 03 验收工具增强要求，不能只提交文字报告、搜索命中或未解释的工具输出。
