# EMAP 仓事实探查：工具增强任务 B

版本：v1.2，2026-09-18。由 00 唯一入口分派；先承接已有环境及当前工具报告，再按统一工具指南实际调用或核验复用结果。此处的“目标”先指已确认的编译配置，核/执行域尚未知时不要求用户先提供答案。

先读 [00](00_总入口与执行约定.md)、[统一工具指南](../../工具接入与共享能力/工具统一管理与使用指南.md)，采用 [04](04_证据与结果记录模板.md)。目标是查清 EMAP 自身是什么、实现了什么、当前产品各目标选择什么，以及更深层不可见部分的边界。

先读取[当前工具状态报告](../../工具接入与共享能力/工具状态与验收报告.md)并核对环境、版本和适用范围；本任务实际命令、查询输入、输出及人工核对另行留证。报告中的已安装或已接入不能替代本次分析。

## B1. 建立身份和支持矩阵

登记仓库/子仓 commit、实际输入变更、生成代码、构建系统、公开接口、后端目录、OS/BSP 适配、第三方依赖和发布产物。沿用已有工程环境，不把产品仓旁边的 EMAP 目录自动认作产品正在使用的版本。

两张表必须分开：仓库能够支持的平台/OS/配置；当前产品各目标实际使用的包/后端。后者需与任务 A 的头文件路径、实际库和构建身份核对。

以真实代码建立 API 家族：初始化、任务同步、内存、消息/事件、跨核、时间/中断、诊断和复位等；没有的类别明确说明。历史名称只能当搜索线索，不能虚构配对接口。

## B2. 各目标生成可验证的分析上下文

针对当前产品使用的每种不同 EMAP 后端，取得其真实编译数据库、编译器、宏和依赖路径；执行 compdb 检查并提供关键实现文件。不能只把产品 C++ 的头文件导入情况当作 EMAP 实现已提取。

若产品只消费预编译库：产品数据库调查调用方；用对应 EMAP 构建目标单独提取实现方；保留两者包/源码身份的证明与缺口。两边不同目标不为了方便而强行混库。

按[统一工具指南](../../工具接入与共享能力/工具统一管理与使用指南.md)建立 clangd/CodeQL 分析，先检查 Q00 定义和 Q01 错误，再查 API 绑定、函数表/回调引用、写入和条件。保存关键 API 的宏/inline 展开、真实定义和编译选择证据。命中默认 Linux/DT 后端时先核对目标，不能据此解释 RTOS 行为。

## B3. 从公共 API 到实际后端

每个关键接口追：公共声明→宏/inline→实现→配置条件→函数表/注册→OS/BSP/第三方→实际库。对同名多实现、weak/strong、库抽取、LTO/内联和节丢弃，使用产物/链接记录补证。

| 比较维度 | 逐目标必须确认 |
| --- | --- |
| 任务/ISR | 可调用上下文、阻塞能力、回调执行者、调度和临界区 |
| 返回/完成 | 成功代表排队、复制、处理还是确认；异步完成由谁通知 |
| 编码/ABI | 位宽、端序、结构体布局、packing、地址/偏移/句柄；使用目标上下文 |
| 内存 | 堆/池、分配释放配对、所有权与借用期限 |
| 传输 | 核内/跨核实现、路由和搬运边界、通知与消费机制 |
| 状态恢复 | 取消、超时、重试、启动代次、复位清理和重新握手 |
| 可观测性 | 已存在的日志、统计、hook、保护检查、dump 与对应开关 |

成果：每目标 API—后端—下层—产物关系表，列已核验、推断、未知。接口名相同不代表各平台的契约相同。

## B4. 内存与生命周期

完整追至少一个实际分配/释放配对：参数/长度转换、对齐、堆池选择、元信息、失败语义、释放者、复用时机、异常清理。补查绕过 EMAP 的系统分配、第三方私有堆、静态和栈对象。

查询申请释放调用、变量写入和条件只能提供候选；继续检查借用方、异步回调、DMA/对端访问和指针别名。记录“未见释放”和“已证明泄漏”的区别。

若已有保护字、填充值、延迟释放、堆检查、统计或分配追踪，查实际覆盖范围、检查触发点、可重入性、锁/分配依赖和记录容量。块前后保护不能被预设成现有机制，也不能在本阶段被擅自加入。

## B5. 消息、共享区和状态机制

按机制卡追提交、路由、排队/搬运、通知、接收、反序列化、分发、回调、完成/失败和资源回收。为每条关键跨核路径保留两端消息 ID、通道、版本、实例、目标选择和字段布局；仅相同 ID 不足以配对。

对实际状态变量列初始化、读写者、置位/清除、版本推进、重复/迟到处理、复位路径和消费条件。通过写入/条件查询补查成功链之外的路径；双缓冲、翻面、队列合并、去重等均按是否实际存在逐项核对。

共享内存若存在，查可访问地址、对象所有权、读写指针、同步规则、内存属性、缓存维护与通知顺序的资料依据。CPU 屏障、DMA、MMIO 等平台语义超出普通 C++ 调用图，不能把图上的一个函数调用解释成整体正确性证明。

## B6. 第三方和诊断能力

为每个不可见组件建立边界卡：实际库/包和摘要、可见头文件、调用点、可见输入输出、返回/完成语义、配置/hook、符号情况、能够取得的最小补证。继续分析双仓可见部分，不把闭源段画成已知实现。

盘点异常、断言、分配失败、看门狗、复位、日志/trace、dump 和启动清理路径。区别空壳、关闭分支、当前编入、当前使能和运行验证；分开根因线索、传播、首次发现和最终触发现场。

记录仅改产品可以调用的接口、需要重编 EMAP 的能力、需要更深层或硬件支持的能力。这里是控制范围事实，为下一阶段方案选型提供依据。

## B7. 发布消费与交付

核对 EMAP 源码→目标配置→库→包→产品实际消费路径。相同版本字符串或相同导出函数不足以证明源码与包一致；缺历史构建来源时保留证明边界，不临时替换产品依赖“让它一致”。

交付 `EMAP仓事实报告.md`，包括职责、支持/实际使用矩阵、API 后端、消息/状态、内存、第三方、异常诊断、构建发布、查询和覆盖状态、给产品侧的精确问题。

每种当前实际后端都有覆盖状态；至少贯穿一个分配释放配对、一条消息及其已有错误/恢复分支、一项存在的诊断或监控能力。缺材料的项带最小补证任务，不用“EMAP 已分析”一句话掩盖未覆盖目标。
