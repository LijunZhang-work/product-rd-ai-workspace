# 产品与 EMAP：成熟工具增强事实探查任务包

版本：v1.2｜日期：2026-09-18｜阶段：建立事实基础｜执行器：公司已有本地 AI／DeepSeek Harness。

## 1. 这次交付是什么

本包把双仓摸底变成可执行、可复核的探查流程。需要查清产品是什么、有哪些核和执行域、各自运行什么、代码怎样构建部署、消息和内存怎样运作、产品实际怎样使用 EMAP，以及现有异常定位能力的范围。它承接普通版的完整问题范围，增加成熟工具、明确命令、覆盖检查和可保存的原始结果。

本包包含任务书、Python 辅助脚本、CodeQL 初始查询、Clang 查询示例、记录模板和验证记录。辅助脚本只负责采集记录与机械核对；C++ 语义和关系分析由真实 Clang／CodeQL 等工具完成，没有自造一个代码理解引擎。

当前尚未取得真实产品及 EMAP 仓，包内不存在已核实的产品核数、后端选择或问题根因。CodeQL 和 Clang 查询已按官方接口编写，本次未执行对应引擎验证，需在本地实际编译运行后才可作为项目证据。脚本和主机 GCC／Binutils 样例的已执行验证见 [07](07_验证记录与适用边界.md)。

大白话：给 AI 配好量尺、测量步骤和检查表。以后报告中的重要结论，要能回到同一版本的编译记录、代码关系和产物，避免研究了另一套配置还浑然不觉。

## 2. 唯一总入口：从这里完成全部适用步骤

用户只需把本文件交给本地 AI。本文件负责分派；AI 按指向读取和执行其他材料，不能要求用户逐份点名。不是只读 00 就凭空完成，也不是看完几个文件就宣告任务已执行。

### 2.1 先确认完整任务包

必须同时具备 00～08 文档、`scripts/`、`queries/`、`config/`、`templates/`，以及工作区内的 [工具统一管理与使用指南](../../工具接入与共享能力/工具统一管理与使用指南.md)和[工具状态与验收报告](../../工具接入与共享能力/工具状态与验收报告.md)。v1.2 随完整工作区包交付，保留原有相对目录结构；不要单独拷走本增强目录，也不从历史 v1.1 专项包抽取旧规则或脚本来补新文档。只有单个 00 或共享材料不可访问时，列出缺项，不能猜写替代文件。

工具的盘点、存放、安装、接入、调用、验收和状态字段只由统一指南维护。[05](05_成熟工具执行手册.md) / [08](08_工具盘点下载安装与存放指南.md) 保留为旧链接兼容入口，不再提供另一套规则。任务需要查什么仍由 01/02/03 规定；此处负责把工具管理和本次任务执行接起来。

先阅读 [07_验证记录与适用边界.md](07_验证记录与适用边界.md)，区分任务包自测与真实产品证据。用实际已有 Python 3.10+ 检查完整性；缺 Python 时先按统一指南的最小盘点复用解释器，不构成必须先通过脚本才能安装 Python 的循环：

```bash
"$FACT_PYTHON" "$FACT_KIT/scripts/check_workflow.py" package \
  --out "$FACT_RUN/package-check.json"
```

`FACT_KIT` 是完整工作区内的本增强子目录，**不是整个 ZIP 的解压根**；`FACT_RUN` 是依据既有成果选出的本次新结果目录，`FACT_PYTHON` 是当前环境真实解释器。首次还不知道位置时先只读定位已有成果，再创建结果目录；这些变量均非预设本机路径。

### 2.2 承接已经做过的工作

在实际工作区找到 **`Windows与WSL开发环境` 文件夹**，沿其报告和交接引用找到已执行的环境盘点、部署配置、成功编译记录。不要写死上层工作区名称，不因本次引用而重新执行环境迁移、全盘盘点和历史编译。目录规范只作规范，实际报告和配置才是本机事实；缺哪项补哪项。

本包当前不预设“目标核”划分。先登记真实代码仓、已有构建入口和编译配置；字段 `target` 是配置标识，核/执行域未知照实保留，随后由 01/02 探查。用户已说明当前没有 `compile_commands.json`：按统一指南确认已有构建入口和适用的采集方式；可以验证是否有兼容的原生导出，否则在真实编译环境用 Bear 等已验证方式采集。不能把普通编译自动生成当成现状，也不为获得文件直接全量清理重编。

### 2.4 初始化、更新与收口

读取 [06](06_本地AI执行与续接.md) 的执行约定后开始工作；06 是本入口的执行细则和续接说明，不是另一个需要用户选择的独立入口。

使用真实配置 ID 初始化本次工作状态；未确定 ID 时先完成 S01，不编造核名：

```bash
"$FACT_PYTHON" "$FACT_KIT/scripts/check_workflow.py" init \
  --mode full --config-id "实际构建组合ID" \
  --out "$FACT_RUN/workflow-state.json"
```

多个独立配置重复 `--config-id`，执行器按统一指南把各配置结果分存至本次结果根下的独立子目录。如果用户明确只要求下载安装，使用 `--mode preparation`，只验收 S00～S02 并标注本次范围；不能把准备完成包装成整个增强探查完成。中断后读取原状态继续，不用 init 覆盖既有进度。后来增加配置时保留旧状态，补入新增配置应有行，不能只把旧成功复制过去。

从 v1.1 续接时，保留旧状态和证据，在新的结果目录用 v1.2 初始化状态；逐项检查后引用可复用记录，并补上当前工具报告引用和实际执行证据引用。不要直接改旧状态里的版本号或摘要来绕过检查，也不要求为升级任务包重跑未变化的分析。未补齐的新字段保留待办。

步骤状态为 `pending`、`completed`、`reused`、`partial`、`blocked`、`not_applicable`。完成/复用提供证据文件，复用注明输入未变的依据；`tool_report_reference` 指向本轮工具报告引用索引；S03/S05/S06/S07/S10 以及实际采用工具的 S12 还须填写 `task_run_evidence`，不能仅用安装清单代替实际执行记录。字段解释与证据内容以统一指南为准，04 说明流程文件中的放置方式。仅 S11/S12 可以根据事实标不适用，其他必需步骤确实受阻就保留 partial/blocked。可选工具未采用不阻断其他层。

每次交付前运行。下面文件名用于首轮检查；再次检查改用新的编号文件名并更新交接引用，脚本不会覆盖旧结果：

```bash
"$FACT_PYTHON" "$FACT_KIT/scripts/check_workflow.py" check \
  --state "$FACT_RUN/workflow-state.json" --root "$FACT_RUN" --expected-mode full \
  --out "$FACT_RUN/workflow-check.json"
```

上例验收完整范围；只准备工具时明确传 `--expected-mode preparation`。不能通过修改状态文件的 mode 把完整任务降级。该检查只发现步骤缺失、状态未收口、非法跳过、报告/执行证据引用缺失或越界，不判断证据内容是否真实，也不会替 AI 运行工具。检查不通过仍可交付明确范围的部分成果，但不得称全流程完成；即使通过，也须完成 03 的内容核验。脚本输出、模板完整、版本号和命令退出 0 均不能单独替代实际查询证据。

## 3. 与普通版的具体差别

| 维度 | 增强版必须新增的可检查成果 |
| --- | --- |
| 分析对象 | 每目标的版本、核/域、实际编译器、编译数据库、依赖与产物身份；DT 单独建档 |
| 构建配置 | 原生导出或真实构建采集的命令；关键文件覆盖、多配置、响应文件和头文件选择检查 |
| 语义关系 | Clang／clangd 解析记录；CodeQL 定义、调用、引用、写入和条件查询结果；解析失败清单 |
| 最终实现 | 关键实现与实际库、链接 map、ELF、包和启动配置之间的证据链 |
| 未闭合关系 | 显式登记间接调用、跨核传输、闭源和生成模型等边界，不能由 AI 补成实线 |
| 可复跑 | 命令参数、工作目录、工具版本、查询文件、结果摘要、输入摘要、退出状态和覆盖缺口 |
| 验收 | 配置区分、同名实现区分、双仓提取、回调绑定、产物身份、未知保留等实证检查 |

文本搜索继续用于发现线索；它不能独自证明编译选择或运行绑定。也不能因为工具名字专业，就把未覆盖的结果升级成事实。

## 4. 工具使用与任务完成分开验收

工具选择、安装和调用的唯一规范是 [工具统一管理与使用指南](../../工具接入与共享能力/工具统一管理与使用指南.md)；当前环境中哪些实例已就绪、哪些受阻，以[工具状态与验收报告](../../工具接入与共享能力/工具状态与验收报告.md)的对应环境条目和原始记录为准。本任务不再复制一份工具操作表。执行器先核对报告适用性，再按任务问题调用需要的能力；不能“读到工具已安装”就跳过 S05～S07/S10 的实际工作。

每个实际构建配置仍须独立填写四项任务状态：构建上下文、语义分析、关系查询、产物关联。报告准备完成、某工具在另一项目可用，均不等于这四项通过。缺某层时交付已证实部分及缺口；一个配置受阻不要求其他配置重复执行。

CodeQL 查询默认覆盖本包明确选择的 C/C++ 范围；网页 JS/TS 若在任务范围内，按对应语言与版本另建分析范围。C++、JS、XML、IPC 和另一执行域之间的关联需要契约证据，不能假设一个查询自动穿透所有边界。

## 5. 先确定研究的是哪一棵树

先用实际构建配置建立身份键；未知的核/执行域保留未知，不作为开始准备工具的前置。身份记录至少包含：产品/板版本、产品源码基线、EMAP 源码基线、实际依赖包身份、执行域、构建配置、工具链。不同 key 的数据库、报告和产物分开保存。

同一个源文件可以被多个目标用不同参数编译。不得随便合并编译数据库后让工具取第一条；若确需组合，保留每条命令和目标归属，并证明工具如何选择。跨不同 OS/CPU/宏配置的库应分开分析，再通过接口契约关联。

主核、实时核、EROS、M3/M5 等历史叫法只作为检索线索。区分 CPU 型号、OS、编译器、角色、物理核、逻辑 CPU 与固件实例；不从目录名或 ELF 数量推算核数。EMAP 是本次仓库名称，链接器 `.map` 是另一类文件。

## 6. 执行边界

本阶段是事实探查和离线分析：读取源码、配置、已有产物和记录，在独立目录建立索引、数据库、报告及必要的构建证据。需要重新编译才能采集时，使用已有真实构建入口和配套环境，先核实命令作用与输出位置，按用户已给授权推进；不反复询问已授权的普通操作。

不改产品/EMAP 业务逻辑、不换依赖版本来凑通链路、不刷机或制造故障。新增诊断代码和上板复现由另一个《CodeQL 全链路追踪与机制诊断上板实施指南》承接。此次发现可疑机制时可记录待验证假设，不提前把它写成根因。

工具安装、版本、环境隔离及许可证处理遵循统一指南和既有环境成果；真正受阻的能力登记具体缺口，继续其他可做项。

源码、数据库和工具结果在公司可访问的本地环境处理，不自动上传第三方平台。`probe record` 可以执行传入的命令，`shell=False` 只保证参数不被 shell 隐式展开，不代表被执行程序没有副作用；AI 必须先读构建脚本，不能把录制器当沙箱。

## 7. 原始证据和结论分开

S=源码；C=配置/编译选择；B=产物/链接/包；R=运行记录；H=历史和设计线索。结论分别写“源码存在”“此配置选中”“此产物链接”“此次运行观察”。每条结论绑定适用版本和目标，保留限制与反证。

根因、传播过程、首次观察异常、最终触发点、复位机制分别描述。静态路径可以给出可证实的结构；没有运行因果证据时不宣布某次偶发故障已定位。

辅助脚本校验格式、引用、摘要和证据种类，不能判定 AI 对代码的解释正确。`exit 0` 不等于架构正确，CodeQL 的零结果也不等于不存在相关路径。最终仍要对关键问题执行 [03](03_双仓关联核对与事实验收.md) 的独立核验。

## 8. 最终交付

交付产品事实报告、EMAP 事实报告、双仓关联报告、目标与覆盖清单、机制与关系表、证据账本、缺口与冲突、命令/查询及结果、下次 AI 交接摘要。报告同时包含专业解释和紧凑的大白话概览。

普通版位于同级“普通事实探查（未指定成熟工具）”；本增强版独立维护。它是执行材料，执行器产生的真实产品报告另存带基线的运行目录，不回填示例文件伪装为本包内置事实。
