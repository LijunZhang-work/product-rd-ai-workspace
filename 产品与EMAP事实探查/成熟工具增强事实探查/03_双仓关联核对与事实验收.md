# 双仓关联核对与增强验收：任务 C

版本：v1.2，2026-09-18。由 00 调度，工具准备与接入结果是验收输入的一部分。

输入：两仓事实报告、目标矩阵、原始工具结果、配置/产物和证据账本。先确认版本、目标和解析覆盖，再核对关系。收到另一位 AI 的结论时必须回到证据，不能相互引用摘要形成循环证明。

## C1. 证明产品使用的是哪份 EMAP

逐目标核对：依赖声明→解析/锁定→实际缓存或源码目录→真实头文件→库/对象文件→链接产物→打包→启动装载→已有运行身份。

按证据分别标出：源码已定位、此配置选中、此产物已链接、包身份已核对、实际运行已观察。已编译的文件也可能被链接器丢弃；同名库/头文件可能来自不同缓存；一个源码仓存在并不保证参与产品构建。

CodeQL 同库只适合兼容配置且确实被采集的实现集合。若 EMAP 是预编译消费、目标工具链不同或语言不同，用分开的数据库与证据表关联，不以目录拼接充当数据流。链接器选择、运行时虚调用、回调注册和 IPC 都有各自的证明方式。

## C2. 建立带类型的关系表

`relations.csv` 每行包含双方基线和目标、调用/注册/协议位置、关系类型、证据 ID、限制和缺口。区分以下关系：

| 类型 | 需要的证明 | 不能直接推导 |
| --- | --- | --- |
| 命名调用的静态绑定 | Clang／CodeQL 的符号和参数签名、源码上下文、有效配置 | 该调用实际执行过 |
| 虚调用静态绑定 | 调用点的静态类型和声明；需要时补对象来源/构造与分派候选 | 静态目标就是唯一运行目标 |
| 函数地址/注册候选 | 地址引用、函数表赋值、注册参数、条件和实例 | 引用了地址就一定已注册/执行 |
| 链接实现选择 | 实际链接记录、map/符号、库来源和构建身份 | 导出函数名相同就一定同源 |
| 跨域消息契约 | 通道、ID/版本、目标路由、端点注册、编码/布局、完成语义 | 同一个数字 ID 就是同一条消息 |
| 图元/算法绑定 | XML/模型版本、实例/端口、生成代码或装载器映射、运行位置 | XML 中同名节点就是同一实例 |
| 运行观察 | 同版本、实例和关联标识的已有记录，说明丢失和时间边界 | 缺少一条日志就等于没有执行 |

图表应显示已核验关系和未知边。自动调用图不替代这个表；物理核/镜像归属也不能从调用图自动推断。

## C3. 三类路径贯穿

1. **业务与状态路径**：外部入口→产品校验/转换→EMAP 公共接口→当前后端→传输/通知→接收分发→产品回调→实际业务/图元/算法消费。记录决定是否接受、提交、传播、调度和消费的机制；查相关状态全部已发现写入者，翻面只是可能的一项。
2. **对象与内存路径**：申请→填充→借用/复制/转移→对端/第三方使用→完成/取消/异常→释放/复用。长度、对齐、地址域、异步生命周期、队列和复位行为逐跳核对。
3. **异常与复位路径**：异常/监控→可见处理→保存→通知/主核采集→导出→恢复/清理。分别写哪种故障能留下什么，不能把触发现场当源头根因。

每类按不同关键后端/执行域组合选代表路径，明确覆盖范围。若相关模块没有这类功能，记录证据支持的不适用。发送返回、异步完成、业务生效和网页回读来源必须区分。

## C4. 防止增强版仍然查错的验收

每项填 `acceptance.csv`：`complete`、`partial`、`blocked` 或 `not_applicable`，附证据和具体缺口。只在对应项证据充分时使用 complete。

| 检查 | 必须实际展示的结果 |
| --- | --- |
| G0 对象身份 | 源码、依赖、目标/域和配置有记录；故障/开发/DT 分组；工作区差异有保存依据 |
| G1 构建上下文 | 编译数据库与真实入口对应；关键翻译单元有记录；多配置/响应文件/生成文件和头文件选择已核对 |
| G2 语义有效性 | Clang 采用的命令已查；关键文件可解析；失败/缺定义/工具不支持的范围有清单 |
| G3 双仓查询覆盖 | 产品和 EMAP 的关键实现都有提取证据，Q00/Q01 及日志已检查；预编译边界未伪装成已提取实现 |
| G4 关系核验 | 一条关键 API 同时具备调用方、声明/后端选择和产物证据；间接/跨域边已分类 |
| G5 机制与状态 | 已发现机制的条件、状态写入者、成功和失败/恢复分支有记录；没有只做一条成功调用线 |
| G6 独立交叉核对 | 语义关系与实际编译/链接等不同来源核对；不是两个 AI 重述同一份摘要 |
| G7 可复跑交接 | 命令、查询、版本/锁文件、关键输入摘要、输出和缺口可定位；下一位 AI 能重做抽查 |

“工具增强完成”是限定目标和范围的结论，不是总通过率。账本脚本无错误只能证明机械检查通过，不能代替上述逐项复核。

## C5. 必做的代表性准确性检查

在真实工程中选择已找到的代表项，先通过实际配置/源码/链接资料建立预期，再运行工具核对。以下类别不存在时提供不适用依据；不能凭空制造产品事实来填表。

| 类别 | 通过条件 |
| --- | --- |
| 同名多后端或多版本 | 能列候选并说明当前目标选择了哪个、哪些未选，证据支持排除理由 |
| 条件编译或 DT/板端差异 | 在不同目标的输入与结果里看见正确差异，不把两套参数混用 |
| 产品消费预编译 EMAP | 能区分手头源码与实际库；来源无法证明时明确保留未知 |
| 回调/函数表 | 能找到引用/赋值、注册条件和实例；运行调用未证明时不升级 |
| 漏采/坏配置 | 关键实现遗漏或解析失败时，检查结果真实报缺口，不输出“完整架构” |

可用本包测试证明辅助脚本的部分行为，但主机合成样例不能替代上述真实工程检查。无需修改业务代码或人为制造板端故障来完成这类静态核验。

## C6. 覆盖与否定结论

分别报告：计划目标、捕获命令、可解析文件、可见函数定义、已深查机制、已贯穿路径、已核对产物。`compare-definitions` 只比较函数定义出现的文件集合；一个只有全局数据的翻译单元可能没有函数定义，因此需逐项解释差异，不能把它叫整个仓库解析覆盖率。

同一文件在不同宏配置下的解析不同，文件出现本身不能证明配置正确。CodeQL 全局数据流、间接调用、别名、异常、内联汇编、闭源或 DMA 等均有分析边界；未查到只能写“在本次范围/模型内未发现”。

工具间冲突时保存原始输出、参数和适用范围，先检查基线、目标、头文件、提取和优化差异，再决定是工具限制还是产品事实冲突。不得静默采用更符合预期的结果。

## C7. 交付和未来维护

交 `产品与EMAP关联事实报告.md`：一页概览、拓扑/关系图、三类代表路径、API—后端—包身份、机制与生命周期、原有定位能力、验收状态、未知与最小补证。

每条关键结论用稳定 ID 关联证据；更正时记录替代哪条旧结论。新版本到来，先比较 commit/差异、配置、依赖锁定、工具/查询版本及生成模型，再重跑受影响目标/关系。未受影响的结论也要说明复用依据，不能仅因为文件名不变就沿用。

下一阶段的诊断指南应引用这里已核对的入口、机制、包消费链和控制范围；若事实仍缺失，先补相关证据，不在错误架构上安排日志或保护方案。

## C8. 总入口覆盖检查

先看 `workflow-state.json` 与 `workflow-check.json`：完整执行需包含 S00～S14 的所有适用行，S03～S07/S10 按实际配置展开。再核对[统一工具状态报告](../../工具接入与共享能力/工具状态与验收报告.md)的版本和有效性，以及 04 记录的环境继承依据、工具实例引用、本轮执行位置与真实结果。工具规则只采用[主指南](../../工具接入与共享能力/工具统一管理与使用指南.md)；任务清单中的工具行是报告引用或导出，不是另一份独立维护的工具台账。WSL 安装成功不能代替容器接入；容器能输出版本不能代替实际采集；已有编译成功不能代替未发生的 Bear/CodeQL 提取。

核对每项 completed/reused 的证据内容，而非只看文件存在。受阻、部分完成或未确定的实现范围必须进入 gaps 和结论限制。仅准备模式通过时结论只能是“工具准备完成”。可选工具可以不采用，但理由必须显式记录。核/执行域未查明时保持未知，不用构建配置 ID 冒充核 ID。
