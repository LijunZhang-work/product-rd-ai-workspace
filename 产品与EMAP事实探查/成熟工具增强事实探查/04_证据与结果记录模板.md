# 证据、结果模板与机械检查边界

版本：v1.2，2026-09-18。

本文件定义探查任务的成果格式；工具管理字段与实际使用证据的契约统一由[工具统一管理与使用指南](../../工具接入与共享能力/工具统一管理与使用指南.md)维护。本文件只记录本次任务怎样引用它们，不另定义工具状态。`templates/` 内提供可复制的 CSV 表头和空账本；它们没有填写任何产品事实。按本次版本建立总结果根，每个构建配置分子目录；公共报告、流程状态、账本和交接摘要放在根内，命令与查询输出按配置分别留存。

## 2. 证据类别与结论状态

S：源码/头文件；C：配置/实际编译选择；B：链接/产物/包；R：实际运行观察；H：历史/注释/设计线索。

`verified` 已证实且限定范围；`inferred` 有依据推断；`unknown` 待确认；`conflict` 证据冲突。不适用在验收/缺口表解释，不用空白替代。不能把 H 单独用作当前代码或部署的 verified 证据。

账本的 scope 是关于某段代码/实现的证明层级：

| scope | 机械检查要求的类别 | 人工/AI 内容复核仍需确认 |
| --- | --- | --- |
| `source` | S | 相应基线中确实存在所述代码 |
| `selected` | S+C | 当前目标确实选中了该实现 |
| `linked` | S+C+B | 该实现与实际产物的绑定成立 |
| `running` | S+C+B+R | 所观察运行对应相应代码/产物身份 |

这些是代码—构建—运行关联结论的最低材料要求，不是所有工程事实的逻辑公理。独立的 ELF 架构属性、启动日志原始观察等可以只作为 B/R 证据记录，不为了通过表格虚构 S/C 证据。若要得出跨层结论，再按上表建立证据链。

## 3. `ledger.json` 字段

顶层包含 `schema_version: 1`、`baselines` 对象、`targets` 数组、`evidence` 数组和 `claims` 数组。

`baselines` 用稳定 ID 指向源码 commit/工作区差异、构建环境/工具链、包或记录来源。至少写清类型、路径/来源、版本和关键输入摘要。脚本只检查基线 ID 引用，不能自动验证所有基线字段。非 Git 输入须使用可追溯快照；单个 commit 不代表未提交内容。

证据对象字段：

| 字段 | 填写方式 |
| --- | --- |
| `id`、`kind` | 唯一证据 ID；S/C/B/R/H |
| `baseline_id`、`targets` | 指向顶层定义，使用实际适用目标数组 |
| `path`、`sha256` | 相对证据根目录的真实文件路径及 SHA-256；禁止跳出根目录 |
| `supports`、`limitations` | 此证据支持什么、不能直接推出什么 |
| 可扩展字段 | 原始源码位置/符号/行号、采集时刻、命令记录路径、工具版本、摘录和解析警告 |

结论对象字段：

| 字段 | 填写方式 |
| --- | --- |
| `id`、`text` | 稳定结论 ID；一句可检验的陈述 |
| `status`、`scope`、`target` | 使用本文件定义值，不混用目标 |
| `baseline_ids`、`evidence_ids` | 实际引用；证据的基线必须在结论范围内 |
| `limitations` | 结论不能扩展到哪些版本、目标或行为 |
| `review_note` | verified 必填；说明原始内容如何支持陈述、排除了哪些误配 |
| `gap`、`next_action` | 非 verified 必填；具体缺口与最小补证。inferred 仍要有依据 |
| 可扩展字段 | 反证 ID、关系/机制 ID、被替代结论 ID、复核者/时间 |

必要源码摘录保存到证据根目录，并记录其原始路径、基线、函数/行号；不要随意修改已经引用的 raw 文件。若需更正，创建新的证据版本并更新引用。

## 4. 机械校验的用法与边界

运行 `probe.py validate-ledger`。它检查路径存在及摘要、ID 是否重复或悬空、目标/基线引用一致、最低证据类别和未解决项是否交代；不会阅读 C++ 来裁定论证真假。

`semantic_truth_checked` 永远为 false。零错误但 `unresolved_claims` 非空表示账本结构可以使用、仍有事实未证实。即使 unresolved 为空，也要执行 03 的内容验收，不能以脚本通过代替准确性。

摘要一致只证明文件与记录摘要相符，不证明文件来自正确构建或内容真实；生成摘要和结论的 AI 仍可能犯错，因此关键链路要有独立来源交叉核对。

## 5. 必备事实表与卡片

除 CSV 外，报告内保留以下结构：

| 表/卡 | 最少包含的字段 |
| --- | --- |
| 仓与基线 | 绝对路径、commit/差异、子仓/生成来源、工具链和包身份 |
| 产品模块 | 职责、入口、上/下游、状态所有者、域/任务、选择条件、证据 |
| 核/执行域 | 物理/逻辑/角色分别标识、别名、CPU/OS、镜像、启动、内存/复位关系、未知 |
| 构建与消费 | 目标、宏/include、EMAP 源/包、真实库、链接、打包、装载与证明层级 |
| API/后端 | 接口、宏/inline、实际实现、注册/weak/链接选择、下层、各目标契约差异 |
| 消息/IPC | 类型/ID/通道/版本、发送和接收任务、路由/搬运/通知、编码/地址形式、完成语义、错误/恢复 |
| 状态机制 | 是否存在、状态变量、初始化/读写者、条件和转换、消费/丢弃/覆盖/复位行为 |
| 内存生命周期 | 分配堆池、长度/对齐、所有者/借用者、异步完成、释放/复用、异常分支、检查盲区 |
| 原有定位能力 | 适用核/故障、存在/编入/使能/验证、记录内容/容量/介质/导出、可回答的问题与限制 |
| 异常/复位 | 检测者、触发者、保存者、保留/清理条件、主核与对端协作、二次故障/丢失 |
| 第三方边界 | 包/库身份、接口、可见状态/返回/回调、不可见段、对方需要提供的最小信息 |
| 覆盖与未知 | 计划范围、实际覆盖、失败/不支持项、受影响结论、具体补证动作 |

## 6. 机制卡写法

每种机制先标已发现/待确认/有证据不适用；再给实现位置与当前选择证据。列状态集合、允许转换、所有已发现写入点、决定跳过/接受的条件、调度与同步、正常/失败/恢复行为。单独注明检索/数据流/别名分析未覆盖的写入者。

翻面、脏标志、版本、去重、合并、队列、通知、调度、初始化和回读仅为待调查类别，不预设存在。后续诊断插桩可以使用这里查实的状态和条件，不能把类别清单当作既有设计。

## 7. 交接摘要模板

摘要应一页可读：本次版本/目标和环境；三份报告与证据账本入口；已核实的产品与 EMAP 职责、核/镜像、后端消费关系；关键机制和路径 ID；已运行的工具及覆盖；重要未知/冲突；下一步最小动作；新版本需要重查哪些条件。

附“没有证实的内容”：例如某核物理身份、某闭源缓冲区契约、历史故障根因。让下一位 AI 看见边界，避免把交接摘要中的合理推断传成确定事实。

## 8. 引用既有环境成果与唯一工具报告

`environment-reuse.md` 保留本次使用的 `Windows与WSL开发环境` 真实位置、已执行报告/部署配置/成功编译记录入口及适用性。具体核对项、工具状态和失效条件统一读取 [工具统一管理与使用指南](../../工具接入与共享能力/工具统一管理与使用指南.md)，这里不再次要求整套环境盘点。

[工具状态与验收报告](../../工具接入与共享能力/工具状态与验收报告.md)是唯一当前工具状态入口。把本轮使用的报告身份、适用环境/条目和变化检查存为本次结果根中的 `tool-report-reference.md`，其内容与原始证据按统一指南填写。不能只链接一个会不断变化的“最新报告”而不记录本次引用的版本/摘要，也不能把当前未知或过期条目当作已通过。

原 [templates/tool-inventory.csv](templates/tool-inventory.csv) 仅为旧脚本或旧使用者保留。确需导出时，它只能从当前工具报告派生，并在本轮引用索引中记录来源版本/摘要及导出时间；此 CSV 不得反向覆盖当前报告，也不再另行盘点出一份竞争清单。

`execution.json` 参考 [config/execution.example.json](config/execution.example.json)，记录本轮真实配置 ID 与工具实例映射。字段值来自当前报告、已有部署成果和实际调用；示例不会替你创建容器或切换镜像，也不是工具可用证明。

本次执行证据与复用索引按统一指南留存，关联到下面的流程行以及对应事实证据。任务包的单测、假 CLI、主机样例属于包自身验证，绝不填为用户机器上的工具验收记录。

## 9. 流程状态格式与机械验收

用 00 的 `check_workflow.py init` 生成 `workflow-state.json`，不要手写一份缩减步骤的“全通过”。`config_ids` 是本次明确纳入的构建配置；准备模式为空，完整模式至少一项。每行包含 `step_id`、`scope`、`status`、`reason`、`evidence`，工具执行步骤另含 `task_run_evidence`；顶层含 `tool_report_reference`。所有文件引用都相对本次结果根。

`tool_report_reference` 指向上一节的本轮索引；S03/S05/S06/S07/S10 以及采用可选工具的 S12 在 completed/reused 时，`task_run_evidence` 必须引用真实执行记录或有适用性核对的复用索引。具体证据内容只在统一指南定义。检查器核对这些引用存在、非空且未越界，不读取日志来裁定是否真的调用了工具，也不自行解释工具状态。

- completed：该步骤实际完成，证据文件可定位；内容还要按 03 核验。
- reused：引用本次结果目录中的复用索引文件，其中指向原结果、标识输入和检查当前适用性，不要求复制大型数据库。
- not_applicable：只用于清单允许的条件步骤；理由与依据要保留。
- partial/blocked/pending：可记录并交接，不能充作全流程通过。

证据不在本次结果根时，使用根内的小型引用说明记录原绝对路径、版本/摘要与适用性；不为了绕过检查建立跨目录软链接。检查器只确认索引文件存在和基本状态，不会读取外部大数据库验证语义。即使把同一个说明文件填进所有引用而得到机械通过，若它没有实际运行证据，内容验收仍不通过。

流程检查和原 `probe.py validate-ledger` 分工不同：前者查工作有没有无声遗漏；后者查事实证据引用和摘要。两者通过也不自动证明架构解释正确，最终仍需 03 的代表性准确性核验。

## 编译数据库核实补充（2026-09-20）

每仓/配置分别记录检查位置、是否实际找到、路径、来源、源码/构建身份、参数与生成输入、路径可解析性、关键翻译单元覆盖和采用结论。未检查、范围内未找到、存在但不适用、存在且可复用分别标记。工具操作及详细验收只引用[统一指南](../../工具接入与共享能力/工具统一管理与使用指南.md#cdb)，不由一个仓的结果推广至全部仓。
