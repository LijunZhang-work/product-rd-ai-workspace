# 本地 AI 执行指令与续接

版本：v1.2，2026-09-18。唯一启动入口是 [00_总入口与执行约定.md](00_总入口与执行约定.md)，本文件是由入口调用的执行和续接细则。

## 1. 给执行器的总指令

以下指令可以直接交给公司已有本地 AI。用户提供或工作区已存在的路径、目标和授权应直接沿用，不要求用户重填全部信息。

> 请执行《产品与 EMAP 成熟工具增强事实探查任务包》。只从 00 启动，先检查任务包完整性并读取 07 的边界；定位 Windows与WSL开发环境 文件夹及其之前已经形成的真实报告、部署配置和成功构建记录，登记可复用成果。读取工作区内《工具统一管理与使用指南》和唯一《工具状态与验收报告》，先核对当前报告适用性；按指南复用已有工具、补齐必要缺项、接入真实执行环境，并更新同一报告。05/08 只保留兼容跳转。工具准备报告不能代替本次任务执行证据。随后按 01、02 探查双仓，用 04 持续留证，按 03 验收，最后按本文件交接。不要让用户逐份提醒，也不要因为引用原环境文件夹就重做原来的盘点、迁移和编译。本次目标是建立可以长期依靠的产品知识基础：产品是什么、代码怎样组织运行、到底哪些核/执行域、镜像和业务怎样分工、各类消息/内存/状态/异常机制怎样工作，产品实际使用哪个 EMAP 后端和包。
>
> 优先自动发现用户准备好的两份源码、匹配版本、已有构建环境、产品目标和已有产物。只对无法从资料判断的关键路径或目标提聚焦问题；一个目标缺资料时继续其他可做范围。不要把主核/实时核/EROS 等旧称呼直接当作已知 CPU 型号和核数，不把宿主 DT 当板端。
>
> 以现有仓和已确认编译组合建立配置与证据目录；未知核/执行域留待探查，不作为工具准备前置。逐仓逐配置实查 compile_commands.json 的存在性、版本、参数、路径和关键覆盖；有且适用先复用，缺失或失效再按统一指南导出/采集并审核，不预设一定有或没有。调用包内辅助脚本检查关键翻译单元和多配置。用真实 Clang／clangd 或经过验证的语义工具查询，用 CodeQL 建立可复跑关系盘点，结合实际链接 map、库、ELF、包和启动记录核对。工具操作只依统一指南执行；工具缺失时按已有授权和项目隔离方式解决；无法解决时准确记录受影响范围，继续其他层。不要仅仅推荐工具后停下，也不要以工具未运行的模板充当结果。
>
> 初始 CodeQL/Clang 查询在本包交付环境中没有引擎验证。请在本地依赖锁定后实际编译运行，先用 Q00/Q01、解析日志和代表性已知项检查工具有效性，再按实际 API、对象、类型和机制扩展查询。查询写错或参数不对，修好并重跑；不能静默跳过错误再宣布完成。
>
> 保留直接调用、虚调用静态绑定、函数地址引用、注册关系、跨域协议和运行观察的区别。跨核两端及 BEH XML/实例/端口必须用配置、注册、协议和版本逐段关联。查状态写入者、处理条件和错误/恢复，翻面只是可能存在的机制之一。闭源段保留可见接口、实际库身份和最小补证，不能脑补内部实现。
>
> 本阶段不改产品/EMAP 业务逻辑，不加诊断补丁、刷机或制造故障。为真实分析需要的预处理、索引和独立构建证据按现有工程约束与用户已有授权推进；不切分支、替换依赖或删除正式构建来凑通分析。工具原始输出保存在本地，不自动向外上传源码或数据库。
>
> 交付三份事实报告、目标/机制/关系/覆盖表、证据账本、真实命令与查询结果、验收和缺口、下次 AI 交接摘要。每条重要结论绑定基线、目标、原始证据和限制。辅助脚本通过不等于解释正确，还要按 G0～G7 做内容核验。区分根因、传播、首次发现、触发点和复位；没有因果证据就不判历史故障根因。

## 2. 分阶段完成要求

下表是阶段摘要，步骤清单及适用范围统一以 00 和 config/workflow.json 为准，不在此维护另一套顺序。所有阶段更新同一份 workflow-state.json。

| 阶段 | 具体成果 | 遇到缺口时如何继续 |
| --- | --- | --- |
| 0 继承与准备 | 已有环境成果索引、唯一工具报告引用及适用性、输入基线 | 只补缺项；已完成的不重装、不重盘 |
| 0a 实际接入 | 同编译环境的工具/挂载验证，容器与 WSL 路径分别登记 | 已安装不等于已接入；先打通一个现有组合 |
| 1 构建上下文 | 编译数据库、关键文件检查、实际宏/include/后端证据 | 缺一目标不停止全仓；记录最小补采 |
| 2 语义和关系 | 解析检查、查询/版本锁、实际结果、未解析调用清单 | 修正分析环境；保持目标语义；不能静默改宿主配置 |
| 3 产品与 EMAP | 各自职责/域/机制/生命周期/诊断报告和证据 | 闭源边界继续查可见接口，缺口精确到版本/契约 |
| 4 跨仓与产物 | 实际消费链、三类代表路径、关系表、G0～G7 | 身份未闭合时标 partial/blocked，交付已证实部分 |
| 5 交接 | 报告、账本、原始结果、缺口和复跑步骤 | 清楚区分工具包已具备与真实项目实际执行范围 |

## 3. 工具不能用时的处理

先区分缺安装、缺配置、目标不兼容、库/源码不可见和许可证问题。缺安装不是产品代码错误；语义解析失败也不代表产品编译失败。

已有环境中可补齐的依赖按正常工程方式处理；需要额外权限时说明具体工具/动作及原因。无法补齐则保持该层未完成，可用原编译器、产物和其他已验证工具补证。只有替代工具在关键问题上提供了等价证据并通过检查，才把对应项标完成。

不要只更换名字为“成熟工具增强版”；必须保留实际工具结果和覆盖边界。不要为了使用某个工具而重构用户工程、迁移整个环境或增加新的 Agent 平台。

## 4. 每次中断前保存

保存 workflow-state.json、环境继承索引、本轮工具报告引用与适用性核对、执行环境映射、当前基线、工具与查询锁版本、已跑命令目录、已核验结论 ID、未完成阶段、失败日志入口、最小下一步。新增工具实例或状态变化更新唯一报告；本次执行证据保存在本轮目录，不覆盖过去记录。长时间工具运行使用执行器已有的进程/日志管理能力，向用户简洁汇报进度，不以长时间静默等待代替状态管理。

续接时按统一指南检查机器/WSL/容器镜像/挂载/工具版本与许可等环境变化，以及源码/配置/依赖是否变化；变了则新建结果基线。没变时读取已有原始结果，避免重复全仓扫描和昂贵查询。需要重跑的具体原因写入运行说明。

## 5. 新版本如何维护知识基础

按目标比较：产品/EMAP commit 和未提交输入、依赖与真实库、有效宏/include、编译器/工具链、数据库和查询版本、BEH 模型/生成器及打包身份。根据变化重跑受影响的模块和关系，再更新结论，保留旧结论及替代原因。

不能仅靠文件修改时间或 AI 摘要确认结论仍有效。跨目标复用时注明为什么选择条件、类型布局、调用契约和产物绑定没有变化。

## 6. 与后续诊断建设的衔接

本次交接提供：真实网页/业务入口、各域实际后端和接收者、图元/算法消费位置、消息/对象身份、各机制状态与条件、原有观察接口、受控代码范围以及 EMAP 改动进入产品包的消费链。

后续使用独立的《产品与 EMAP CodeQL 全链路追踪与机制诊断上板实施指南》实施记录、编包和真实设备复现。这里的已核验事实成为它的输入；当前仍未知的关键链路先补证，再决定在哪里改代码。

## 7. 单入口收口

每次交付执行 00 的步骤覆盖检查，并核查 03 的内容证据。用户只要求准备工具时执行 preparation 范围；用户要求完整探查时执行 full 范围，不能自行降级模式来取得通过。阶段受阻时继续不依赖该缺口的任务，交付覆盖与限制，不把阻塞状态改成不适用。

版本/挂载变化导致需要重采时明确原因和受影响配置。旧结果适用且证据充分则标 reused，避免重复全仓建库和昂贵查询。命令模板、假 CLI 自测、版本号输出、数据库目录存在都不能冒充真实成熟工具执行证据。

当前工具规则入口：[工具统一管理与使用指南](../../工具接入与共享能力/工具统一管理与使用指南.md)。当前工具状态入口：[工具状态与验收报告](../../工具接入与共享能力/工具状态与验收报告.md)。工具调用、安装、验收及状态格式不在本文件另行维护。
