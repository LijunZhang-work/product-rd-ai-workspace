# 产品与 EMAP 事实探查：总入口与执行约定

版本：v1.0｜日期：2026-09-17｜阶段：事实探查｜用途：交给能访问公司代码的本地 AI 执行。

## 1. 本次先做什么

先把两个仓各自是什么、怎样构建运行、运行在哪些核上、怎样通信，以及它们之间真正生效的关联查清楚。拿到证据后，再决定故障定位能力怎样建设。本包是探查任务书，不是已完成的产品架构报告；本次未访问实际产品仓、EMAP 仓或设备，不含已核验的产品拓扑。

用户当前可掌握产品代码和 EMAP 代码；更深的第三方实现可能只有包、接口或二进制，不能指望修改。后续希望依靠这两个可控仓，改善单核内部和跨核故障的定位能力。当前阶段要给后续决策提供事实，不先选定保护字、日志、coredump 或硬件工具方案。

大白话：先搞清“家里到底有哪些房间、谁住哪里、门怎么连、东西怎么传、出了事现在能留下什么”。不能凭以前聊天给房间贴标签，更不能只画一张漂亮的猜测图。

## 3. 先前对话如何使用

以下仅为检索线索；只有本次取得相应证据后才可以升级为事实。

| 历史线索 | 本次必须核对的内容 |
| --- | --- |
| “主核 rtos llvm；实时核 a55 rtos lite RT” | 每个名称分别表示 CPU、操作系统、编译器、运行角色还是内部代号；实际型号与数量 |
| 主核、实时核、EROS | 是不同物理核、同一核的不同称呼，还是系统/固件名称；不能重复计数 |
| A7、A55、M3/M5、M33/R5、Renode 示例 | 不写入产品拓扑；只有板级、构建、部署、运行等证据支持时才采用 |
| EMAP／emap／宜麦普 | 本次用户明确是一个有源码的层/仓；核实它自己的职责。不要与链接器 `.map` 文件或历史提到的某种留档文件混为一谈 |
| artget、dependency.xml | 是否真实使用，解析到哪个版本、头文件、库和缓存路径；不假定所有依赖都在里面 |
| 外部输入→业务→跨核→接收业务→图元订阅→BEH | 作为候选路径逐段验证，不强行套到所有信号上 |
| Windows Java BEH 测试；BEH 工具连产品 IP 调试 | 分别确认运行对象和证据边界；不能认定板端也运行电脑上的同一 Java 引擎 |
| EROS 现场→共享内存→主核保存文件 | 查真实实现、哪些异常能进入、内容格式及复位覆盖范围；不能据此推断全部 IPC 都走共享内存 |
| WSL+产品镜像／远程 Linux；x86 DT 与板端有差异 | 分清分析宿主、编译目标、仿真/测试目标、实际设备，不把 WSL 当产品 OS |

此前生成的《产品多核与BEH架构背景记录_v1.0_2026-09-17.md》可供寻找线索。本次该文件及另外两份旧指南的直接读取均报错，未再次核验其当前全文；本包按本次完整会话重新编写，不声称已复核旧文档。旧聊天、旧文档和已有 AI 报告均不能代替当前目标的代码/构建/运行证据。

## 4. 必须交代的根因与触发点区别

| 概念 | 定义 | 例子及限制 |
| --- | --- | --- |
| 源头根因 | 最初违反约定、破坏状态，或形成异常积累/等待关系的操作或条件 | 越界写、提前释放、长度生成错误、长期未释放、错误锁序；不一定只有一行代码 |
| 传播过程 | 状态错误怎样经过对象、任务、时间和核边界影响后续 | 核 A 写坏数据，核 B 后续读取；发送内容正常但缓冲区在接收使用前被复用 |
| 首次观察到异常 | 某条现有证据最早显示不正常的位置 | 保护字检查失败是发现时刻，不自动等于写坏时刻 |
| 触发点 | 最终发生异常、申请失败、超时等的执行位置 | 可能是完全正常的代码使用了已经损坏的数据 |
| 复位机制 | 最终由什么使设备或核重启 | 看门狗、主核发命令、异常处理、硬件复位等；复位原因不自动等于源头根因 |

本阶段要查清目前能收集以上哪类证据、在哪个核、保留多久、在哪种复位后还在。不得从“存在 dump”“可看调用栈”推出“能够定位根因”，也不得从某个核崩溃推出根因在该核。

## 5. 任务开始时确认的输入

优先从现有工作区、构建记录和用户已给信息自动发现；不要把整张表都变成阻塞用户的问题。缺少某一项时继续可做部分，在缺口表里记录。

| 输入项 | 填写要求 |
| --- | --- |
| 产品仓路径、EMAP 仓路径 | 使用真实绝对路径；可以在不同机器；记录子仓、子模块、生成代码所在处 |
| 研究对象 | 产品型号/板版本/发布版本/故障版本/构建目标；未确定时先列候选目标，不擅自只挑一个代表全部 |
| 仓库基线 | commit、分支、工作区未提交变更；关键文件/差异的本地摘要；非 Git 仓则记录快照来源和摘要 |
| 构建环境 | WSL/容器/远程 Linux 的角色、编译器版本、目标架构、配置、依赖解析方式 |
| 已有产物 | ELF、库、链接 map、编译数据库、构建日志、包清单、符号、生成配置等；可以缺失 |
| 已有运行资料 | 启动日志、各核版本、故障留档、消息日志、配置导出；注明来源设备和时间 |
| 输出位置 | 使用独立探查目录，和源码、正式 build 产物分开；本地选择可用工作目录，不强制改用户仓库布局 |

只有遇到无法由现有资料区分的关键目标，才提一个聚焦问题，例如“这两个发布目标哪一个对应故障固件？”等待期间继续公共结构和依赖盘点。不要因缺某一个 ELF 就停止整个仓库探查。

## 6. 证据约定：每条结论都限定范围

使用证据类型与结论状态两个独立字段，不用一个含糊的“高置信度”覆盖所有情况。

| 证据类型 | 能支持的结论 | 不能直接支持的结论 |
| --- | --- | --- |
| S：源码/头文件 | 某函数、分支、契约在此版本存在 | 它一定编进当前产品、一定运行过 |
| C：配置/实际编译选择 | 当前目标选中了哪些源文件、宏、头文件、后端 | 最终链接/烧录结果必然如此 |
| B：构建产物/链接/包身份 | 某实现进入哪个产物、符号/地址/版本是什么 | 现场设备一定装的就是这个产物 |
| R：运行/设备/故障记录 | 某版本某次实际观察到了什么 | 未覆盖的路径也都如此；记录缺失等于事件未发生 |
| H：历史描述/注释/设计文档 | 检索线索、原设计意图 | 当前构建和现场事实 |

结论状态：`已证实（限定范围）`、`有依据推断`、`待确认`、`证据冲突`、`不适用（有依据）`。没有运行记录，可以交付很好的静态探查报告，但必须写“未运行验证”。静态事实不因缺运行证据全部作废；运行日志也不能反向证明源码仓就是生成该包的版本。

结论至少关联：结论 ID、适用目标/核、证据 ID、仓库基线、真实路径与符号/行号或产物摘要、推理过程和边界。行号只对记录的快照有效。跨仓关联引用双方证据，不相互引用摘要构成循环证明。出现冲突时保留各自适用范围和原证据，不悄悄选一个答案。

## 7. 执行权限与方法

本阶段授权的任务是探查与写报告：读取代码、配置、已有产物、日志，进行有范围的静态分析和离线解析；报告及临时分析文件放独立目录。先读项目已有 AGENTS.md/说明及执行限制，保留用户原有工作区变更。

不在此阶段修改产品/EMAP 逻辑、加保护字、替换依赖或打诊断补丁；不升级/安装整套工具，不自动运行故障注入、刷机、复位或改变在线设备状态。新的编译、预处理和运行验证如确有必要，先确认已有授权、脚本副作用和独立输出位置；没有授权时输出准确的补证步骤，继续其他探查，不反复索要大范围许可。

先用已有 rg、Git、编译数据库和对应工具链的产物查看工具。搜索先定位文件，再追符号、条件分支和调用关系。大量结果必须筛选、读上下文、记录实际选择，不能把 grep 命中清单当架构报告。函数指针、注册表、宏、生成配置和弱符号需要额外证明绑定关系。

公司源码、包和故障文件在可访问的本地环境处理；交接默认用报告与必要证据引用，不将整仓上传公网。不向报告抄入凭据。这是交付范围约定，不要求额外的形式审批流程。

## 8. 三阶段完成的含义

- A：产品仓报告。各核/域、模块、任务、构建、消息和异常路径均有结果或明确缺口。
- B：EMAP 仓报告。API 家族、后端选择、内存/消息实现、依赖及各目标差异均有结果或明确缺口。
- C：关联核对报告。绑定当前产品使用的包和源码，贯穿关键路径，识别未闭合边界，形成后续诊断建设的事实输入。

“全部搞清楚”在本包里落实为：范围内的重要问题逐项得到有依据的答案或具体缺证原因，而不是靠编造把空格填满。闭源边界也可以交付其可见接口、实际包身份、进出路径和需要对方提供的最小证据。

禁止用完成百分比掩盖关键缺口。报告结束给出四组内容：已证实事实、有依据推断、关键未知/冲突、下一步最小补证动作。关键未知不妨碍产出已有成果，但不得宣布相应架构已核验完成。

## 9. 可直接复制给本地 AI 的总指令

> 请执行《产品与 EMAP 事实探查任务包》。先读 00，再按 01、02 分别探查产品仓和 EMAP 仓，用 04 的统一格式记录，最后按 03 做关联核对。优先自动识别工作区、当前基线和已有构建目标；路径确实缺失时只询问缺失路径。用户目的是先查清实际架构、核组合、运行分工、消息/内存机制、实际依赖与两仓关系，为后续区分根因与触发点提供证据。本阶段不实施诊断代码修改。不要假定主核型号、核数、EROS 身份、EMAP 含义和每个模块所在核；不要把宿主 DT 当板端，也不要把已有源码等同于当前使用的二进制。读到闭源边界时记录可见事实与最小补证需求，继续可做部分。每条关键结论必须附基线、范围、证据和不确定性。不能只交目录树、关键词命中或通用科普。最终交产品事实报告、EMAP 事实报告、双仓关联报告、证据与缺口记录，以及供下次 AI 直接续接的摘要。

## 10. 外部参考的边界

本包的事实来源必须是目标工程；通用工具文档只用于理解证据形式。没有任何外部文章能证明用户产品型号或核分配。

- [Clang 编译数据库格式](https://clang.llvm.org/docs/JSONCompilationDatabase.html)：帮助解释每个翻译单元的工作目录、参数和同文件多配置。
- [GNU readelf](https://sourceware.org/binutils/docs/binutils/readelf.html)：帮助读取 ELF 的头、段、符号和注记等信息，不用于从一个 ELF 推算物理核数。
- [GCC 预处理选项](https://gcc.gnu.org/onlinedocs/gcc/Preprocessor-Options.html)：如需补证有效宏与头文件路径，须使用实际编译器和目标上下文。
