# 任务 A：产品仓事实探查

先读 [00_总入口与执行约定.md](00_总入口与执行约定.md)，统一使用 [04_证据与结果记录模板.md](04_证据与结果记录模板.md)。输出是产品事实报告，不是修改方案。没有 EMAP 源码也可以先完成产品侧，向任务 B 提交明确问题。

## A0. 这份报告最后要回答什么

1. 这是什么产品，主要输入、处理职责和输出是什么？本次查的是哪个型号/配置/版本？
2. 仓库怎样组织，主要模块怎样协作，哪些是自有、生成或第三方内容？
3. 一共有多少芯片/物理核，哪些被本产品启用；主核、实时核、EROS 各指什么？
4. 每个执行域运行什么系统、固件、任务和业务；是否共享调度、地址空间、内存和复位范围？
5. 代码怎样被选择、编译、链接、打包并部署到对应域？
6. 消息如何从发送方实际抵达接收方，接收回调在哪个上下文执行？
7. 内存由谁申请、传递、使用、释放；复位与异常如何发生和保存？
8. 现在有哪些能观察触发点、传播过程和早期异常的能力，哪些信息根本没有采集？

要让用户同时看懂“专业结构”和“大白话解释”。每节先说结论，再给证据与边界，不把原始输出直接堆给用户。

## A1. 建立研究基线与目标清单

读取真实仓库及子仓、构建说明、产品配置、依赖清单和发布记录。记录 commit/未提交修改、生成文件来源、现有编译环境和产物位置。不要自行执行拉取更新、清理、依赖刷新或重新生成全仓。

先枚举可识别的产品/板型/目标配置，再明确本次覆盖范围。针对当前故障版本和当前开发版本分别建档；两者不同不能混用证据。不存在足够线索时列出候选目标及未确认原因，不给出一个无范围的“产品共有 N 核”。

产出：基线表、目标清单、仓库边界表，使用模板 T1、T2。目录只写对架构有意义的模块，不逐个解释所有文件夹。

## A2. 从业务入口查产品是什么

寻找程序入口、初始化、组件注册和外部接口，结合实际配置回答：产品控制或管理什么；有哪些输入/输出；数据、配置和事件各如何进入与分发。

沿真实源码查 Web/北向协议/南向设备/BEH 等候选入口。未找到某入口时查是否由其他进程、其他仓或依赖提供，不能凭历史聊天补全。协议驱动、业务处理、图元执行、电脑侧调试工具分别列角色，避免把不同运行位置混成一个程序。

每个主要模块记录：职责、入口、上游、下游、状态/数据所有者、构建条件、执行域/任务、配置与错误出口、证据。识别业务周期、事件回调、状态机、订阅/发布或其他实际编程模式，不强行统一。

产出：一段产品大白话描述；模块职责表；一张以证据支持的模块关系图。未知节点和边明确标注“待核实”。

## A3. 查清到底有哪些核和执行域

从板级配置、BSP/启动文件、构建目标、固件装载表、链接脚本和已有启动记录交叉核对。分别统计：芯片物理核、当前启用的核、软件看到的逻辑 CPU、运行的固件/系统实例。缺哪一层就明确缺哪一层。

为每个已识别对象填模板 T3：

- CPU 架构/具体型号及证据，所属芯片/簇、物理标识与逻辑 ID；尚不知实际核时先用执行域编号 D01，不能伪造 CPU 编号。
- 主核/实时核/EROS 等别名到真实对象的映射及一对多/多对一关系。
- OS/运行库/裸机或未知、启动入口、初始化次序、调度模型、任务与中断角色。
- 所运行镜像、代码/数据/堆/栈所在区域、共享区域、地址空间、权限/安全域及与其他对象的关系。
- 哪些核一起复位，哪些能够独立复位；谁启动/停止/监控谁。没有硬件文档时“软件调用一个复位接口”不等于确认物理复位范围。

特别核对：同型号核运行不同系统不自动证明硬件异构；AMP/SMP 是运行组织，不能只从文件名判定；ELF 的架构字段或 `-mcpu` 说明编译目标，不能单独证明实际芯片、核数。多个镜像也不一定是一镜像一核，安全/非安全固件、引导程序和应用可能运行在同一个核上。

产出：核/执行域与镜像对应表、别名表、拓扑证据与未知项。画图时不要把操作系统名称画成额外物理核。

## A4. 查清代码怎样变成运行程序

逐目标追踪：入口构建脚本 → 配置与宏 → 翻译单元/生成代码 → 编译命令 → 库选择/链接 → 最终固件 → 打包清单 → 启动装载配置 → 已有设备版本记录。

必须检查：

| 内容 | 必须回答的问题 |
| --- | --- |
| 源文件选择 | 同名实现、平台分支、生成配置、测试桩与真实后端中，选中了谁？ |
| 头文件选择 | 真实 include 顺序指向产品目录、EMAP 源码、SDK 缓存还是另一版本？ |
| 链接依赖 | 哪些库真的进入链接；依赖清单声明与实际路径/版本是否一致？ |
| 最终实现 | 关键符号是否内联、被宏替换、由弱符号/强符号覆盖，或根本没进入最终产物？ |
| 包与部署 | 哪个产物被装入哪个包，由哪个核/域启动？现场版本能否对应？ |
| 编码与 ABI | 消息字段编码、位宽、大小端、对齐/packing、结构体版本、地址转换在哪定义？ |

优先使用现有 compile_commands.json、构建日志、link map、ELF、包清单和缓存元信息。编译数据库没有列出链接步骤时，不能据此宣称库已链接。工作区代码与发布包缺少构建对应记录时，明确身份未闭合。

产出：模板 T2、T4、T5 中的产品侧信息；每个关键包的来源/路径/版本/摘要；“此仓哪些文件修改后会进入哪个目标”的事实映射，而非修改建议。

## A5. 任务、调度和消息机制

先从实际使用的接口与对象出发，区分核内队列、进程间通信、跨核 IPC、设备协议。名称含 Send/Queue 的函数不一定跨核，消息路由层也不一定负责物理传输。

每种机制逐项填模板 T6：发送点、消息类型/ID、发送核和任务、分配/拷贝、排队、传输后端、通知机制、接收中断/轮询、分发注册、回调和接收任务、完成/错误/超时路径。

追踪接收函数时必须找到注册来源、表项/函数指针赋值或生成配置，以及当前构建选中证据。只找到同名 callback 不算调用边已确认。

核对同步/异步、返回成功的语义、发送与完成是否分离、消息顺序、容量与背压、超时重试、重复/迟到消息、对端重启后的清理或重新握手。若有消息关联 ID、序号、代次、CRC 或版本字段，记录实际生成与使用点；没有就写未发现，不能擅自给协议添加字段。

共享内存机制存在时，查地址映射、分配者/所有者、访问核/设备、缓存属性、数据可见性与通知顺序、锁/原子/屏障及相关配置。记录已实现的机制和未能证实之处，不从一个 flush 名称直接判定整条链正确。

产出：机制清单、端点表、消息契约、错误与恢复行为，以及至少一张实际跨核路径的时序图；缺某端时断开画并标缺口。

## A6. 内存与对象生命周期

查 malloc/free、new/delete、EMAP 接口、内存池、栈/静态内存、共享内存、DMA 缓冲区等实际路径。每类记录分配/释放匹配、执行域、调用者、长度/对齐约定、拥有者、异步借用期限、异常与重启时清理方式。

尤其追一块跨核消息缓冲区：谁分配 → 谁填充 → 传的是数据副本、偏移、句柄还是原始指针 → 谁什么时候读取 → 完成由谁确认 → 谁释放/复用 → 超时/取消/对端复位时怎么办。

同时查已有保护字、堆完整性检查、分配追踪、失败回调、栈水位、断言等能力。记录实现是否编入、是否使能、覆盖哪些分配路径；不要因为有 EMAP_MemFree 就说所有内存都经 EMAP。

产出：模板 T7、T8；对象/缓冲区生命周期图及中断或任务并发关系。没有证据时不判定存在越界或泄漏。

## A7. 异常、监控、复位与留档

分别追：CPU 异常、断言/panic、C++ 异常/terminate、分配失败、任务卡死、看门狗、主核主动复位对端、硬件复位。不存在相应路径或源码在平台侧时记录归属，不用主核已有能力代替对端能力。

每种情形查检测入口、运行核/上下文、是否经过可见处理函数、可调用接口、保存内容、保存介质、导出路径、恢复动作和限制。区分普通 RAM、共享 RAM、保留区域、非易失介质；`noinit` 只说明某段不被某启动流程初始化，不能证明所有硬件复位/掉电都保留。

核实历史“EROS→共享内存→主核文件”的每一跳；查是否只有寄存器与格式化调用栈、是否真的有原始栈/内存、是否带核/任务/时间/版本、写入是否完整、二次异常是否覆盖、启动时是否清零。若记录者依赖已经失效的消息通道，也记为条件限制。

识别已有调试接口、dump 解析器和符号配套方式；仅记录实际存在和可用范围，不采购工具、不触发复位。

产出：模板 T8、T9，回答“哪种故障现在能留下什么、取回什么、能定位哪一层”。

## A8. 至少贯穿哪些代表路径

对每个已确认的关键机制/执行域组合，选一条真实路径，不只做最容易的一条。至少尝试覆盖：

| 路径 | 关注点 |
| --- | --- |
| 外部输入到业务结果/BEH 交接 | 实际入口、消息/配置转换、跨核边界和图元映射；不存在 BEH 时给证据 |
| 一条核内消息 | 与跨核接口是否共用外壳但选择不同实现 |
| 一条跨核请求及完成/错误分支 | 发送、接收、回调、超时、重启边界 |
| 一个内存/缓冲区完整生命周期 | 分配、使用、转交、回收与异常退出 |
| 一个异常/监控到留档或复位的路径 | 谁检测、谁记录、谁复位、记录能否保留 |

可以让一条路径覆盖多项，避免机械重复。每一跳标注 S/C/B/R 证据和缺口；未运行的全链只称“静态贯穿”。

## A9. 产品仓报告与交接

生成 `产品仓事实报告.md`，结构依次为：研究范围和基线；一页大白话概览；模块与核/域拓扑；构建部署；任务与通信；内存生命周期；异常复位与现有证据；代表路径；关键未知/冲突；给 EMAP 的核对问题；续接摘要。

向任务 B 交接的每个问题要具体到：产品目标、API/类型、真实头文件路径、调用点、疑似后端、依赖包身份以及需要查实的行为。例如“当前目标调用 X 后能否立即释放 buffer，真正后端何时完成读取？”不要只写“请解释 EMAP 消息机制”。

完成标准：A0 的每个问题均有明确状态和证据；核心表不留无解释空白；至少完成已有证据能支撑的代表路径。无法确认核数时交“核数待确认及缺证原因”，不能虚构一个完整拓扑作为验收。
