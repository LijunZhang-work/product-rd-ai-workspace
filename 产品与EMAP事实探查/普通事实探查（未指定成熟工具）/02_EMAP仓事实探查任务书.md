# 任务 B：EMAP 仓事实探查

先读 [00_总入口与执行约定.md](00_总入口与执行约定.md)，使用 [04_证据与结果记录模板.md](04_证据与结果记录模板.md)。目标是查清真实实现与适配方式，不预设 EMAP 一定是某种“平台抽象层”，也不在此阶段加诊断代码。

## B0. 最后必须回答的问题

1. EMAP 在这个项目里是什么，公开了哪些能力，实际实现了哪些能力？
2. 支持哪些平台、OS、核/执行域和构建目标；当前产品选择哪些？
3. 同一 API 在不同目标下实际进入哪个实现？接口一致是否意味着行为一致？
4. 核内、跨核消息分别怎样运行；消息路由、搬运和通知由谁负责？
5. 内存申请释放、跨核共享缓冲区、对象生命周期怎样管理？
6. 哪些函数由 EMAP 自己实现，哪些转交 OS/BSP/第三方，边界和契约是什么？
7. 现有异常、复位、留档、追踪、保护检查接口如何工作，谁能接入？
8. EMAP 源码怎样构建成包，能否证明与产品实际使用的包对应？

## B1. 仓库结构与身份

建立独立 EMAP 基线：路径、commit、工作区修改、子仓/生成代码、构建系统、编译器与支持矩阵、发布版本和已有包。不要认为产品仓边上的 EMAP 目录天然就是当前依赖来源。

按公开头文件、核心实现、平台后端、OS/BSP 适配、生成层、打包层、测试/宿主替身分类，形成职责表。说明文件名/目录名和真实职责是否一致。使用命名相似性只能建立候选，必须追实际调用与构建引用。

找出版本宏、版本接口、包清单、生成日志或发布元信息；记录有哪些身份可以与产品对照，哪些不能。字符串版本相同只算线索，缺少构建来源时不能声称源码和包逐字节一致。

## B2. 从 API 追到当前目标真正选择的后端

对主要 API 家族建立清单：生命周期/初始化、任务与同步、内存、消息/事件/订阅、跨核、时间、中断、诊断和复位；实际不存在的家族注明，不补写理想架构。

每个关键 API 追：声明 → 宏/inline 包装 → 实现文件 → 平台条件 → 后端表/注册 → 下层调用 → 编译选择 → 库/包。记录以下替换机制是否存在及当前选择证据：

- 同名函数的多个实现、条件编译、头文件包含顺序、生成配置、运行时函数表/注册表。
- weak/strong 符号、链接顺序、静态库抽取、LTO/内联、未使用节丢弃。
- 宿主测试桩、DT 实现、不同 RTOS 适配、裸机实现、第三方预编译后端。

没有当前产品编译参数时先给“EMAP 支持矩阵”，不要冒充“产品实际使用矩阵”。任务 A 给出产品目标和包路径后再补真实绑定。

产出：模板 T4、T5、T10；回答“为什么这个调用最终进的是这个实现”，不只写“仓里发现了这个实现”。

## B3. 不同核/域上的行为差异

按已识别构建目标逐行核对，不按历史猜测硬编码核名称。

| 维度 | 必须比较的事实 |
| --- | --- |
| 系统与任务 | 初始化前置条件、调度/任务 API、ISR 可调用范围、临界区和锁 |
| 数据约定 | 指针/整数宽度、大小端、对齐、结构体布局与版本；用目标编译上下文核实 |
| 地址与内存 | 堆/池归属、地址空间、共享区、偏移/地址转换、是否可直接传指针 |
| 消息行为 | 同 API 在不同目标下是本地队列、系统 IPC、共享区还是第三方调用 |
| 完成与错误 | 返回成功表示已入队、已拷贝、已处理还是已确认；各目标是否一致 |
| 生命周期 | 回调任务、缓冲区有效期、超时/取消/复位后清理 |
| 可观测性 | 有哪些日志/计数器/hook、实际编译开关、保存位置及读取方式 |

同名 API 的语义差异比名称本身更重要。只读一个默认后端不算完成不同核/域比较。任何数据布局结论必须标注是头文件约定、目标编译确认还是运行观察，不能用宿主 `sizeof` 代替板端结论。

## B4. 内存分配、释放、池与保护机制

以实际找到的接口为准；历史 `EMAP_MemFree` 仅作搜索起点，不能编造对应 Alloc 函数名。

追完整配对：申请入口 → 参数处理 → 堆/池选择 → 元信息/对齐 → 下层分配器 → 返回给业务；释放入口 → 地址/类型检查 → 所有权/池定位 → 下层释放。若存在 new/delete、realloc/calloc、DMA 分配和共享分配，分别追踪。

对每条路径记录：

1. 谁持有分配账本，是否线程/中断安全；锁与失败时行为是什么。
2. 长度、对齐和大小计算是否转换；元信息位于块前、块后、旁表还是完全不存在。
3. 分配失败返回空、返回错误码、抛异常、断言还是调用回调；当前构建实际选择哪种。
4. 是否已有头尾保护值、分配/释放填充值、延迟复用、双重释放检查、堆完整性检查、峰值/剩余量统计；覆盖范围和检查触发时刻是什么。
5. 是否记录申请/释放调用者、任务、核、时间、对象身份；记录丢失、覆盖或再分配时如何处理。
6. 谁能注册 hook，是否可重入/阻塞/申请内存；现有异常路径是否可能依赖损坏的堆或锁。
7. 哪些路径绕过 EMAP：第三方私有堆、静态内存、栈、直接系统分配、跨域池等。

本阶段只盘点现有机制。不要因为后续想加保护字，就把所有分配替换成自写包装；不要假定添加块前后字节不会影响 ABI、对齐或跨核地址约定。

产出：内存入口与后端表、生命周期/所有权表、现有检查能力及覆盖盲区；区分“首次检查发现损坏”和“实际破坏发生时”。

## B5. 消息、路由、跨核与完成通知

把表面 API 与底层实际机制拆开。对每种有代表性的消息路径追到可见边界，不强求所有路径都经过同一组层。

| 段 | 要拿到的证据 |
| --- | --- |
| 提交 | 消息类型/ID、目标、长度、缓冲区、返回值约定 |
| 路由 | 目标核/域/任务如何选择，静态表、运行时注册或配置怎样生效 |
| 入队/传输 | 拷贝还是借用、队列/环形区归属、满队列行为、真正后端 |
| 通知 | 中断/邮箱/轮询/系统接口等实际调用及配置，不凭名字猜 |
| 接收与分发 | 消费者、读指针推进、校验、反序列化、目标回调的注册关系 |
| 完成/失败 | ACK、回调、超时重试、丢弃、取消、释放和对端复位后的行为 |

跨核共享区若存在，核实数据先写入再通知的实现与平台语义；记录缓存维护/屏障及内存属性来源。不把 `volatile`、函数名带 Barrier 或一段 memcpy 当作整体同步正确的证明。没有证明时写“同步/可见性契约待补证”，不直接宣布存在漏洞。

核实消息版本、字段宽度、packing、指针/偏移、边界检查、校验字段、启动代次与重复消息处理。不同核固件版本组合是否有检查或兼容规则，只有代码/配置/测试证据支持才写结论。

产出：模板 T6、T7；每种关键后端一条成功路径和至少一个已存在的错误/超时/重启分支；注明静态核对与已运行观察。

## B6. 第三方边界怎样交代

每个重要下层依赖记录：真实组件/包名、版本/摘要、接口声明路径、调用点、库文件、目标平台、调用契约、可见错误/状态/回调、可获取符号/头文件/配置，以及源码可见与修改权限。

源码不可见时仍继续做三件事：确认实际调用的包和符号；整理调用前后及异步完成的契约；列出当前能观察的状态和缺失信息。不能把“无源码”写成“整个路径不可分析”，也不能反编译猜测后写成源代码事实。

证据确实卡住时，向依赖方提出最小具体请求，例如某版本接口的缓冲区有效期、回调上下文、原始栈导出能力或构建 ID 对照。不要默认要求对方开放全部源码。

## B7. 异常、诊断、复位与可接入点

寻找 EMAP 自有或转发的异常/断言、内存失败、任务监控、看门狗、复位请求、日志/trace、dump 导出和初始化接口。追注册时机、实际回调、目标平台、执行上下文、使能条件、下层限制。

对每项填写模板 T8、T9：

- 是实现还是空壳/宏/关闭分支；当前目标是否编入、使能；是否有真实使用者。
- 能看到触发点、早期异常、分配历史、消息因果中的哪一类；不能覆盖什么。
- 写到哪里、容量/覆盖规则、是否跨复位保留、主核/对端谁来导出。
- 能否仅修改产品代码调用；是否需重编 EMAP；是否受更深层或硬件约束。这是控制范围事实，不是要求立刻修改。

查不见某核异常入口时，不随意建议安装进该核。先确认该核是否使用这份 EMAP、是否有可注册入口、当前异常处理者是谁。

## B8. EMAP 构建、发布与产品消费

追查各目标的库/包如何生成：构建配置、源文件清单、生成步骤、依赖版本、编译参数、静态/动态链接形式、符号裁剪、包命名与发布元数据。

回答两个不同的问题：

1. 这份 EMAP 源码能构建什么？
2. 产品当前实际消费的包，能否证明来自这份源码及相应配置？

两者不一致要保留差异，不为了“接上”而替换产品依赖、切分支或重新编包。若没有构建来源记录，可列举可比较的配置/符号/版本信息并给出证明强度，不能仅因 API 名称一致就认定二进制身份已核对。

## B9. 交付与自检

生成 `EMAP仓事实报告.md`：范围基线；EMAP 职责大白话说明；API/模块与平台矩阵；实际后端选择；内存；消息/跨核；第三方边界；异常/诊断；构建发布；给产品侧的问题；未知与冲突；续接摘要。

至少完整跟踪一个实际分配释放配对、一条消息路径、一项当前存在的异常/监控能力。每个当前产品用到的不同后端有明确覆盖状态；未探查的不能隐藏在“EMAP 已分析”下。

向任务 C 提供：API 到实际实现的证据索引、后端选择条件、包与源码对应信息、产品侧待提供的参数/库身份，以及不能跨过的证据边界。
