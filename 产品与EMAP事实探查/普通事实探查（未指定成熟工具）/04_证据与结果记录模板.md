# 证据与结果记录模板

配合 [00_总入口与执行约定.md](00_总入口与执行约定.md) 及任务 A/B/C 使用。下面全部是待填写模板，不是当前产品事实；尖括号字段要用实际数据替换。未知填“待确认＋缺口 ID”，不适用要说明依据，不能留一个空格让后续 AI 猜。

## 1. 建议输出组织与 ID

在执行器自己的独立探查输出目录中保存，不改产品/EMAP 仓布局：

| 文件/目录 | 内容 |
| --- | --- |
| `产品仓事实报告.md` | 任务 A 结果 |
| `EMAP仓事实报告.md` | 任务 B 结果 |
| `产品与EMAP关联事实报告.md` | 任务 C 结果 |
| `证据与缺口记录.md` | 证据索引、结论索引、缺口与冲突、执行状态 |
| `下次会话交接摘要.md` | 最新已核验背景、范围及续接入口 |
| `evidence/` | 有必要保存的原始命令输出、解析摘要、文件摘要；不复制整仓 |

P 表示产品任务，E 表示 EMAP 任务，J 表示关联任务。证据示例编号 `P-E001`，结论 `P-C001`，缺口 `P-U001`；这些编号样式是示例。结论 ID 不作为证据 ID。所有任务可使用同一模板，不要求每个 AI 创建不同工具体系。

## 2. 一条证据怎样记录

```yaml
evidence_id: <P-E001>
evidence_type: <S源码|C配置选择|B产物|R运行|H历史>
collected_at: <含时区的实际采集时间>
repo_or_source: <产品仓/EMAP仓/设备/构建系统>
baseline_id: <T1中的基线ID>
target_id: <T2中的目标ID或未知>
core_or_domain: <T3中的对象ID或未知>
locator:
  path: <真实路径，或设备记录来源>
  symbol_or_record: <函数/配置键/符号/日志事件>
  lines_or_offset: <实际行号/偏移/时间段；不可用则说明>
file_or_artifact_sha256: <关键文件/产物摘要或未取得原因>
command_record:
  command: <实际命令及必要参数；非命令证据则不适用>
  cwd: <实际工作目录>
  tool_version: <相关工具版本>
  exit_code: <实际退出码或不适用>
raw_output: <独立输出文件路径或不适用>
extract: <最小必要的原文/输出>
supports: <此证据能够直接支持什么>
does_not_prove: <例如：仅存在实现，不证明当前编入>
```

软件日志缺失、搜索无结果都不能写成“绝对不存在”。负面结果须记录搜索范围、构建目标、排除项与未覆盖目录/依赖，再表述为“在该范围内未发现”。

证据跨两个机器时用机器别名和仓内相对路径关联，不把一个机器的绝对路径当成另一台机器可用路径。采集输出只保留与结论有关的部分，避免把凭据或无关设备信息带入报告。

## 3. 一条结论怎样记录

```yaml
claim_id: <P-C001>
question: <要回答的问题>
statement: <一句可检验的结论>
status: <已证实-限定范围|有依据推断|待确认|证据冲突|不适用>
scope:
  baseline_ids: [<基线>]
  target_ids: [<目标>]
  core_or_domains: [<对象>]
evidence_ids: [<真实证据ID>]
reasoning: <证据怎样支持结论；中间不可跳步>
counterevidence_ids: []
limits: <尚不能推到什么程度>
gap_ids: []
supersedes: <若纠正旧结论，写被替代ID；否则不适用>
```

可接受的表述：“在目标 T 的编译记录中选中了实现 X，尚未核对现场镜像。”不可接受的表述：“搜到 X，所以产品所有核都用 X。”

| 目标 ID | 产品/板型/发布配置 | 入口及有效配置 | 已有产物/现场版本 | 本次覆盖状态与证据 |
| --- | --- | --- | --- | --- |

## T3. 芯片、核、执行域与镜像

| 对象 ID/类别 | 实际标识与别名 | CPU/OS/调度 | 镜像与业务任务 | 内存/复位关系 | 状态与证据 |
| --- | --- | --- | --- | --- | --- |
| `<D01：暂定执行域>` | `<真实名称；物理核未知>` | `<各字段分别填写>` | `<镜像/模块>` | `<共享/独立或待确认>` | `<证据ID/缺口ID>` |

为每个对象附卡片：

- 物理芯片/簇/核 ID、逻辑 CPU ID、启用状态；不知道不填假编号。
- 谁装载它、入口在哪里、什么时候启动、是否运行多个系统镜像。
- 主核/实时核/EROS 等名称映射依据；一个角色能否涉及多个核。
- 地址空间、共享区域、缓存/一致性域、复位/电源域，分别列证据和未知项。
- 核内任务/线程、ISR、回调与模块清单；任务数量不计作核数量。

汇总必须分别写：物理核数、当前启用核数、软件逻辑 CPU 数、系统实例数、角色数；未证实的标待确认。

## 4. 给本地 AI 的三个分任务指令

**产品仓 AI：**

> 读 00、01、04。在现有授权的本地环境探查产品仓，先自动发现当前目标/基线，查模块、物理核与执行域、构建部署、消息/内存/异常复位。关键路径要追真实选择和注册关系。输出产品仓事实报告、证据与缺口、给 EMAP 的具体问题。不要改业务代码，不凭历史聊天填架构，不因一个依赖闭源停止整个任务。

**EMAP 仓 AI：**

> 读 00、02、04。独立查清 EMAP 职责、API 和各目标实际后端、内存和消息生命周期、第三方边界、诊断接口与构建发布。区分支持矩阵和产品实际使用矩阵。有产品侧交接时逐条核对；没有则先完成 EMAP 内部事实并列待提供的目标/包信息。输出 EMAP 仓事实报告与证据，不实施保护字或日志补丁。

**关联核对 AI：**

> 读 00、03、04，再读两仓报告与原证据。核实实际头文件/库/包对应后，贯穿业务消息、内存生命周期、异常复位三类路径。把主核/实时核/EROS 的身份和数量、每域实际 EMAP 后端、闭源边界及证据缺口讲清楚。区分根因、首次观察异常、触发点和复位机制。交付关联事实报告和下次会话交接摘要；未闭合的关系不能宣布已完成。

## 5. 可选的低副作用证据采集起点

以下为命令示例，路径全是占位符。只在真实路径和既有工具确认后执行；不是一键脚本。Windows 原生环境使用已有等价工具即可，不因示例采用 shell 就迁移整个环境。

```bash
git -C "/真实路径/产品仓" rev-parse HEAD
git -C "/真实路径/产品仓" status --short
git -C "/真实路径/产品仓" submodule status
rg --files "/真实路径/产品仓" -g 'AGENTS.md' -g '*README*' -g '*dependency*' -g '*toolchain*' -g 'compile_commands.json' -g '*.ld' -g '*.lds' -g '*.map'
rg -n -i 'emap|artget|dependency' "/真实路径/产品仓/已定位的配置目录"
rg -n 'EMAP_MemFree' "/真实路径/EMAP仓/已定位的源码目录"
```

第一次搜索后必须根据真实目录和符号收窄，读取上下文，不能不断向整个仓追加大正则。不要把不存在的宏/函数名当确定接口。

对已有 ELF/库，可用安装好的匹配工具读取信息，例如：

```bash
readelf -hW "/真实路径/目标.elf"
readelf -lW "/真实路径/目标.elf"
readelf -nW "/真实路径/目标.elf"
readelf -sW "/真实路径/目标.elf"
nm -A -C "/真实路径/实际库.a"
sha256sum "/真实路径/实际库.a"
```

只有工具格式支持时才使用；LLVM/厂商工具选择以环境为准。符号表无结果可能是裁剪/内联/格式支持问题，不足以证明实现不存在。ELF 头用于确认产物架构，不用于推算产品物理核数。

如需预处理补证，从真实编译数据库条目提取对应目标的编译器、工作目录、include、宏和 ABI 参数，再人工审阅为仅预处理命令，输出到独立目录。不要直接执行数据库中任意 command，也不要丢掉目标参数、使用宿主默认值生成假证据。实际 GCC 支持的 `-E`/`-dM` 可用于对应目的，具体依本机编译器文档；这一步可能写文件，遵守 00 的范围约定。

不要假设项目构建脚本、所谓 dry-run 或配置阶段完全没有副作用。优先读已有记录；确需新构建时列清具体目标、必要性、输出目录及已有授权。不要为了本次探查把整个产品重编一遍。

## 6. 写报告前的最后自查

- 每个“已证实”都有正确基线、适用范围和原证据吗？
- 是否把源码存在、编译选中、链接进入、设备运行四件事混为一谈？
- 是否把某个域/固件/任务误算成一个物理核？
- 是否把 EMAP 与链接 map/同名留档文件混淆？
