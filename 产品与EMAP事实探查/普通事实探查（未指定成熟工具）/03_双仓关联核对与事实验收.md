# 任务 C：产品与 EMAP 关联核对及事实验收

先读 [00_总入口与执行约定.md](00_总入口与执行约定.md)。输入为任务 A、B 报告、双方证据及必要源码/产物。只核对当前事实；改代码建设诊断能力是下一阶段。

## C0. 目标与前置检查

这一步不能只是总结两份报告。必须沿同一构建目标，证明产品调用怎样落到 EMAP 实现、怎样进入下层和另一核，再返回产品业务，并说明哪里已经拿到实际运行证据。

先校验双方研究基线、目标、配置、包版本与证据可访问性。A/B 使用不同产品版本时，按版本分组对照；不要把开发分支 EMAP 的实现解释成故障版本行为。

只有一侧报告时先完成可做的关系候选和缺口，保留另一侧待补；不得宣布双仓核对完成。收到的结论没有原证据时，将其记为待核验，不把“另一个 AI 说过”当验证。

## C1. 产品到底用的是哪一份 EMAP

逐目标完成实际消费链：依赖声明 → 解析/锁定结果 → 下载/缓存或本地源码目录 → 真实头文件路径 → 库/目标文件 → 链接产物 → 打包 → 装载或现场版本。

用模板 T4、T5 建立证据关系。重点排查：

- 产品实际仍链接预编译包，手头 EMAP 源码没有参与构建。
- 使用一版头文件、另一版库；不同核消费不同 EMAP 包/后端。
- 同名库来自不同缓存/SDK；不同产品 target 混用证据。
- 符号由宏/inline/weak/注册表改变，源码命中与最终实现不同。
- ELF、符号文件与故障包版本不匹配；现场设备版本来源不明确。

上述是核对项目，不是预设缺陷。确认无此情况也要注明证据范围。

输出状态分开写：源码分支已定位、当前配置已选择、库已链接、包已生成、设备运行身份已核对。不能用一个“已打通”掩盖最后两步没有证据。

## C2. 双仓职责与修改控制范围

对主要能力填表：产品负责什么；EMAP 负责什么；下层负责什么；证据来自哪里。至少涉及业务、任务/同步、内存、消息路由、跨核搬运/通知、图元交接、异常/复位、诊断。

控制范围单独记录：有源码/无源码、当前实际编入/未确认、能否构建、是否有公开配置/hook、是否需要依赖部门、硬件前提。拥有源码不等于当前有可用的构建发布通路；无源码不等于完全无接口或配置能力。

本阶段不作诊断方案选型，只回答“将来若要使用这个已存在能力，要涉及哪些层和哪些产物”，并列证据。

## C3. 贯穿三类必须核对的关联路径

### 路径一：业务与消息

选择任务 A 中真实的关键业务输入，贯穿产品入口 → 产品调用 → EMAP 公共接口 → 生效后端 → 下层/传输边界 → 接收后端 → 产品接收回调 → 业务结果/图元交接。

每一跳必须写：核/域、任务或 ISR 上下文、函数/表项/消息、当前目标选择证据、数据形式/所有权、成功含义、错误/超时分支和证据 ID。不同产品的路径可以缺少某些层，不强加 EMAP 或 BEH。

跨核连线至少依靠协议/消息标识、目标配置、端点注册和数据契约互相对应；如果已有运行记录，再用同一消息编号/业务键与版本/启动批次关联。不同核时间戳未经校准时不能仅按大小判断先后。双方没有可关联标识时，明确目前只能形成静态候选配对。

静态消息 ID 匹配也可能误配不同版本、通道或实例；相同数字不是充分证据。发送成功仅代表入队时，不画成对端已处理。

### 路径二：内存与对象

从产品实际对象/缓冲区出发，贯穿产品申请 → EMAP 分配后端 → 使用/交接 → 第三方或对端读取 → 完成/取消/异常 → EMAP/其他释放。

核对实际分配者与释放者是否匹配、是否跨堆/池、指针/偏移与地址域、拷贝/借用/转移所有权、缓冲区复用时机、回调晚到、对端复位时仍持有的对象。

记录已有检查能覆盖哪部分，哪些内存绕过这条链。发现可疑矛盾标记“待复核风险”，不能因未见释放函数就直接认定泄漏，或因某次缺日志就认定丢消息。

### 路径三：异常、超时与复位

贯穿故障/监控来源 → EMAP/平台回调 → 现场保存 → 对端通知/主核采集 → 文件导出 → 重启/恢复。区分本核异常、远端无响应、主核主动重启、整片复位/掉电。

逐跳核对异常上下文、可读内存、锁/分配依赖、保存容量、有效性标记、部分写入、缓存可见性、二次故障、启动清理、符号/版本匹配。

不能承诺故障核总能执行保存函数；不能认为主核有留档就等于其他核完整留档；不能认为共享内存存在就能跨所有复位保存。

## C4. 把根因、传播和触发分开呈现

基于现有能力建立“证据能回答什么”表，而不是立即给工具推荐。

| 问题 | 需要核查的现有事实 | 本阶段的合理结论形式 |
| --- | --- | --- |
| 内存最早何时被破坏 | 保护标记/堆检查/观察点配置是否实际存在，在哪里检查，覆盖哪些写入者 | 只能发现于检查点／有指定核观察能力／当前无此证据 |
| 谁造成内存持续减少 | 分配释放记录、池统计、对象/队列账本的粒度和保留窗口 | 可追某类对象／仅有总量／分配路径未全覆盖 |
| 跨核哪一段开始异常 | 两端数据记录、消息关联字段、校验、共享缓冲区契约 | 静态契约已接上／运行记录可关联／某边仍不可见 |
| 哪个核先卡住、在等谁 | 任务进展、锁/等待对象、超时主体、看门狗/心跳信息 | 能看到等待关系／只见超时结果／当前无法区分 |
| 最后崩在哪里 | 异常寄存器、栈、程序版本和符号 | 可到地址／函数／源码行；是否有变量所需内存另列 |
| 为什么被复位 | 复位发起者、原因寄存器/软件原因、启动前记录 | 可区分机制／原因被清除／记录版本不明 |

每项用模板 T8、T9 写支持证据与限制。硬件观察点/trace 只在确认芯片和接口后记为存在；某核观察点不能自动覆盖其他核或 DMA。没有故障案例也可以盘点这些能力，不为了填表执行人为故障。

## C5. 实证据如何逐步增加

现有证据足够回答时停止扩展，不为形式上的完整执行昂贵操作。按需采用：

1. 读取代码、有效配置、已有构建/发布资料，形成静态事实。
2. 检查已有产物与符号/元信息，把源码和当前构建关联起来。
3. 读取已有启动/故障/消息记录，把产物和现场关联起来。
4. 仍有关键缺口时，输出最小补证任务：所需文件或已存在命令/接口、预计获得什么、能排除哪种歧义、由谁执行。

新编译、连接设备、测试、诊断补丁等若超出已有授权，不在本阶段默默执行；也不因此丢弃已完成的静态结果。新产物不能冒充历史故障固件，新测试记录不能反向证明旧故障根因。

## C6. 最终必须交付的事实地图

生成 `产品与EMAP关联事实报告.md`，至少包含：

- 一页大白话总览：产品做什么、有哪些已证实核/执行域、每部分怎样协作。
- 三张有证据的图：部署拓扑、关键业务/跨核时序、内存或异常生命周期。图可拆小图；未知连线标注，所有关键节点/边可回到证据表。
- 一组总表：核/域—OS—镜像—模块；产品目标—EMAP 包—源码/后端；消息端点与契约；内存所有权；复位与现有诊断能力。
- 两仓之间的依赖、调用、版本、构建和运行关联，分别写证明到哪一层。
- 根因/传播/首次发现/触发/复位这五类证据目前各能取得什么。
- 关键未知、冲突和具体补证动作；单独列需要第三方提供的最小信息。
- 后续工作输入：已经存在的可用接口/配置/构建入口及其控制范围，不提前提交保护字或采集方案。

所有已证实结论带证据 ID，所有未知项带缺口 ID。读者应能从任一关键结论回到对应版本的文件/符号/产物/记录，而无需再次遍历整仓。

## C7. 验收：防止“看起来很完整”

| 验收问题 | 通过条件 |
| --- | --- |
| 到底几个核 | 分清物理、启用、逻辑、角色，数量有范围与证据；未确认项显式列出 |
| 有没有硬件异构 | 有不同核类型的产品证据；否则写未确认，不把不同 OS 当结论 |
| 模块跑在哪里 | 能对应镜像/配置/启动；不能只按目录名或功能猜 |
| 产品真正使用哪份 EMAP | 至少证明到实际头文件/库选择；源码/包/设备的剩余身份缺口单列 |
| 跨核通信是否查透 | 两端注册与契约对上，传输边界/所有权/完成语义清楚；闭源段有边界说明 |
| EMAP 改动会影响哪里 | 有构建/消费关系支持，不以源码存在代替实际使用 |
| 原有定位能力是什么 | 按核和故障类型列覆盖范围，区分编入、使能、实际验证 |
| 是否混淆根因和触发点 | 每类证据标明能支持的结论，未提供因果证据就不判根因 |
| 是否真正完成两仓关联 | 抽查关键关系时能同时拿出产品、EMAP 及必要产物证据 |

验收结果用模板 T12 分项给出“已完成/受阻/不适用”，并写清证据与影响。可形成“静态关联已完成、现场身份待补证”等范围明确的结论；不要用一个总勾选把未知项盖掉。

## C8. 给下一阶段 AI 的交接摘要

按模板 T13 交接：本次覆盖范围、代码基线/依赖身份、已证实核心事实、关键路径入口、现有能力、控制边界、重要未知、下一步只需补什么。未来开始诊断建设时先读这份摘要和证据索引，不从旧聊天重新猜架构。

如某次具体故障也被分析，只附独立案例页：观察事实、触发点、最早异常、候选根因、支持/反证、还缺什么、是否已复现或修复验证。没有验证就保留“候选”；本包的交付不要求先解决历史故障。
