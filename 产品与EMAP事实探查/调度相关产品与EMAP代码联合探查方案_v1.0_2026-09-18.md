# 调度相关产品与 EMAP 代码联合探查方案

版本：v1.0｜设计日期：2026-09-18｜工具归一修订：2026-09-18（保留文件名兼容旧引用）｜适用对象：可访问真实产品代码、对应 EMAP 代码及已有构建资料的本地 AI 与工程人员。

本文沿用此前确认的 EMAP（宜麦普）名称。当前尚未取得用户电脑上的实际代码、output/all output、构建记录或运行数据；以下是可执行的调查设计，不是已经查明的产品架构或故障结论。90 GB 是用户提供的磁盘规模，尚未验证其中源码、历史、产物与缓存各占多少。

## 1. 最终选择及本次范围

采用“先列出调度体系的主要机制和未知项，再选代表过程核实；以专家提供的候选模块为起点，用产物来源及真实构建缩小范围，再沿调用、消息、状态和必要资源关系补全”的方法。

本轮最终目标是建立调度相关的架构基础。一个过程用于试点，不代表全部交付范围：先做轻量的横向盘点，再逐个验证不同机制的代表过程，避免把一条正常路径挖得很深却漏掉另一种调度方式。

首轮交付三个相互关联的视图：

1. **运行机制视图（区分静态推导与实际观测）**：输入或触发从哪里来，经过哪些处理、等待与状态变化，什么时候产生可观察结果。
2. **构建与来源视图**：这些实现来自哪个产品/EMAP 仓及版本，在什么配置下生成哪个库、程序或固件，如何进入对应产品。
3. **边界视图**：哪些能看、能编、能改、能部署、能观察；哪些仅能确认接口，哪些仍是缺口。

三个视图共享同一组证据编号和配置身份，不各画一张图后凭叙述拼起来。依赖可能分叉、循环或通过第三方分发，不预设为一棵树。

这次优先建立调度相关的事实基础，并为后续定位留出接口。事实探查本身不自动包含改业务代码、编诊断包、上板升级或故障注入。若后续要诊断具体偶发问题，另写明确的现象、预期、观测点与验证计划。

“调度”可能指业务任务/图元调度，也可能涉及操作系统线程调度；开始时先分清两者，不能用 Linux 线程时间线代替业务任务流。

## 2. 入口、旧材料与实际环境

本文件是**本次调度专题的入口**，按第 4 节 P0～P7 执行；无需用户逐份点名。旧的“成熟工具增强事实探查”仍负责原来的完整双仓摸底范围，本专题只引用其中适用的方法，不声称已执行其全流程，也不使用旧 `workflow-state.json` 的 `full` 检查结果冒充本专题验收。

旧全量流程不是本专题的前置，也不因本专题开始而自动启动。P0 记录“已有成果—本次用途—同版本/配置复用依据—未覆盖部分”；本专题状态独立保存，不覆盖或提升旧 `full` 状态。今后若要扩大到完整产品架构，再另行确定范围。

先在本地找到 **`Windows与WSL开发环境` 文件夹**，沿其中引用读取已经执行过的环境报告、仓库与镜像关系、挂载配置、原工具链初始化及成功构建记录。这里只引用文件夹名，不固定上层工作区名字、用户名、磁盘或 `/home` 路径。文件夹中的指南不等于机器上已经执行的事实；已有成果复用，缺哪项补哪项。

工具操作的唯一规则来源是 [工具统一管理与使用指南](../工具接入与共享能力/工具统一管理与使用指南.md)，当前可复用的实测状态只从 [工具状态与验收报告](../工具接入与共享能力/工具状态与验收报告.md) 读取。先按指南的[环境继承](../工具接入与共享能力/工具统一管理与使用指南.md#environment)定位上述已执行成果，再核对报告中的机器、WSL 发行版、镜像、工具实例与本次任务是否对应。报告缺失、待盘点或失效时，只按指南补做受影响项并更新同一报告，不在本专题另建一份并行工具台账，也不为本专题重跑旧的完整环境部署。

本专题仅决定研究范围、待回答问题和任务验收；工具发现、安装、存放、容器接入、通用调用与验收方式由统一指南维护。进入任何工具阶段前，记录所引用报告的版本/摘要、环境身份和工具实例；安装通过或其他项目试用通过，不代表本次已经分析过。

已知约束：用户当前普通构建**没有**生成 `compile_commands.json`。它是编译命令数据文件，不是待下载工具。获取与验证遵循指南的[编译上下文流程](../工具接入与共享能力/工具统一管理与使用指南.md#cdb)；没有它仍可先查版本、构建入口、依赖与产物来源。工具执行位置、容器复用和路径核对遵循[容器接入](../工具接入与共享能力/工具统一管理与使用指南.md#containers)，不得由“WSL PATH 中存在”推定容器可用。板端证据必须来自实际产品运行环境。

每次分析仍须按[执行证据规范](../工具接入与共享能力/工具统一管理与使用指南.md#evidence)留下本次输入身份、实际命令、输出和覆盖检查；读取状态报告不能计作已使用工具。已有结果可复用，但必须指出同版本/配置适用依据，并标明“复用”而非“本次执行”。

## 3. 开始需要什么，以及如何控制 90 GB 的成本

### 3.1 最小输入

能够开始的最小集合是：一个可访问的候选产品仓路径，以及要研究的调度能力或问题。随后定位产品/构建配置或现有产物、output/all output 位置及下载入口；这些身份待核实时仍可盘点和定位候选实现，但不能提前给出“此配置成立”或“对应当前运行”的结论。例如：“查清此配置下任务从注册到执行完成的过程”。不能凭示例认定实际产品已有某类任务或接口。

入口符号、完整仓名单、完整运行日志可以随后补。专业同事优先提供预期行为、关键交接点、代表场景和已知例外；候选仓名单作为线索，不作为不可越过的名单。没有运行条件时先做静态调查，并保留证据等级。

身份至少记录：产品配置、产品提交和相关未提交变更、EMAP 来源版本、依赖包身份、工具链、镜像身份、构建入口与关键选项、产物身份。执行域、操作系统、处理器或核身份未确认时填写“未知”，不以此阻塞初查，也不从目录名推算核数。

### 3.2 先形成轻量的调度机制清单

综合专家线索、产品入口、配置/注册表、现有构建目标与模型，列出目前可见的调度对象、入口、决策点、执行者、任务或执行类型、队列/触发方式、状态与配置通道、候选后端、相关执行域及例外机制。各项标明已确认、候选、未知或不适用，允许后续新增，不能从一份工具结果反推“机制已经全部列全”。

随后为不同机制选择代表过程，记录“哪个过程验证哪项机制、还有哪些尚未覆盖”。第一条过程用于检验方法与成本；最终的架构基础交付须同时交代已发现的机制及其覆盖状态，不以第一条链走通就收工。该清单不要求扫描全部源码，也不预设产品具备特定 OS、核或调度器。

### 3.3 三种研究深度

| 深度 | 包括哪些对象 | 做到哪里 |
| --- | --- | --- |
| 背景清单 | 已发现的仓根、主要目录、产物、依赖包和外部入口 | 名称、位置、版本来源、体积线索；不解析全部文件 |
| 专题内部 | 有证据与选定调度过程相关的模块、接口、状态及实际构建依赖 | 精确到代码位置、配置条件、读写者、交接与观测点 |
| 接口边界 | 暂不需要深入的公共库、告警、系统服务或供应商组件 | 输入输出、同步/异步、等待、失败语义、责任和剩余不确定性 |

90 GB 的第一步是利用已有目录/版本/包清单判断规模构成。若确需容量统计，先估计遍历成本并限定文件系统范围；`du` 等也会产生 I/O，并非免费操作。首轮不全仓内容哈希、不全仓解压、不全仓语义索引、不逐个初始化无关子模块，也不迁移源码。

优先使用下载 manifest、锁文件、构建文件及 Git 跟踪文件清单；对选中的产物和关键输入计算摘要。生成源码可能不在 Git 清单中，必须结合实际构建、生成器和输出目录补齐。排除 `.git` 对象、历史产物和缓存的语义索引，不等于排除其中必要的版本记录或当前生成头。

先试一个实际配置和一个代表过程，测量耗时、内存、磁盘和解析质量，再决定扩展量。时间/空间预算由机器实况记录，不承诺 90 GB 一定能缩到某个固定大小或在固定小时内完成。预算耗尽标记暂停，不改成“已完整摸清”。

每次昂贵操作**执行前**填写输入范围、可用空间、内存/时间限额、输出位置和停止条件。尤其检查 clangd 是否会按整个编译数据库后台索引、选定构建是否会触发大批依赖。保存原始构建数据库，必要时在结果目录生成范围明确且可追溯的分析副本，保留必要头文件/生成物和后续扩展能力。不能只在报告里写“小范围”，实际却让工具默认扫描整个工程。无法限制范围时评估成本并使用已有证据继续，不能默认改成全仓构建。达到限额保留已得结果和续接点。

| P7 收口交接 | 按第 9 节逐项验收；交付报告和可复核原始结果；确定下一步 | 执行状态、结论、缺口、续接说明 | 每项标为完成/复用/部分/受阻/不适用，并附证据或理由 |

阶段可以往返：运行发现版本不匹配，就回到 P1；查到未覆盖的 EMAP 后端，就回到 P3。只补受影响的范围，保留已经验证且输入未变的结果。

### 4.1 P1：确认 output 到底代表什么

检查下载脚本、依赖声明、版本锁、缓存复用、目录清理策略和打包脚本，区分以下事实：被声明、被下载、参与编译、参与链接、被打包部署、某次实际执行。这些状态不能自动升级。

对应关系至少包含：产品模块/配置 → 依赖包版本与摘要 → EMAP 来源提交或可核验的发布标识 → 生成该包的构建入口与选项 → 对应源码/生成配置 → 实际使用的产物。

文件名相同、时间较新、符号相似或 ELF Build ID 本身都不自动证明源提交身份。优先发布 manifest、锁文件、构建证明和匹配的调试信息；重建结果可能受时间戳等因素影响，不把非可重复构建的字节不一致直接判作源码错误。无法建立准确来源时保留“候选映射”。

分别核对本产品实际涉及的各程序/盒的产物。某个主程序的 output 不能自动代表消息接收端的源码、固件或部署配置。

### 4.2 P2～P3：探查 EMAP 自己如何构建

除跟随已知调用，还对选定产品实际采用的注册表、生成绑定、启动/部署配置、插件/动态加载声明、消息路由和脚本入口做一次有限核对。将发现的入口与机制清单对照；无法核查的地方记录为动态盲区。这样发现名单外的候选关系，而不需要递归阅读所有插件或服务实现。

先读 README、CI 配置、构建脚本、CMake/Make/Ninja 文件、工具链定义、下载脚本与已有日志，产出：

- 真实入口及必要初始化；原镜像/SDK和环境；产品或组件选择参数。
- 下载/生成/配置/编译/链接/打包的步骤与输入输出。
- 外部依赖的来源、固定版本、本地位置、是否已有、是否需要编译。
- 与产品使用包的对应依据，以及哪些内容尚未执行验证。

默认不运行未知 `build.sh`、不拉取全部可选依赖，也不把 EMAP 默认配置当产品所用配置。配置阶段也可能下载依赖或执行探测。先复用现有构建信息，再在隔离结果位置、原工具链下验证选定组件及其必要依赖。

若工程只能整体构建，真实记录该限制，先评估磁盘/时间与已有数据能回答的问题；不能为了“缩小范围”发明不存在的构建选项，或关闭影响产品行为的功能开关。

产品仅链接预编译 EMAP 库时，产品的一次构建采集不会自动获得库内部源码的编译过程。对匹配版本的 EMAP 组件另行采集；拿不到对应源码/配置时，停留在明确的接口边界与证据缺口。

### 4.3 P3：本专题需要的编译上下文和语义证据

获取方法和实际调用集中在统一指南的[编译上下文](../工具接入与共享能力/工具统一管理与使用指南.md#cdb)及[Clang 语义分析](../工具接入与共享能力/工具统一管理与使用指南.md#clang)。本节只定义本专题必须核查的内容：

1. 依据 P1/P2 独立列出的产品接口、对应 EMAP 后端、调度决策/执行入口及关键状态读写者，选择代表翻译单元。不能用工具恰好提取到的文件反过来声称范围完整。
2. 对每项核对真实配置、源文件、实际宏与头文件选择、生成输入，以及当前工具能否解析。将“可解析”“存在错误但局部可用”“未覆盖”分别记录，并指出影响哪条关系。
3. 产品使用预编译 EMAP 时，核验匹配版本 EMAP 自己的构建上下文；产品包装层解析成功不代表库内部已被分析。
4. 保留不同部署目标或互斥构建变体的身份，防止同名不同实现混用；同一真实构建中逐文件宏不同本身并不是拆库依据。
5. 记录上下文来自既有导出、实际捕获还是其他经过核验的来源，并附本次代表文件检查结果。生成的命令存在不等于文件已经编译，更不等于某次运行执行。

按 P0 的资源预算执行；只对证据支持的范围作语义结论。工具不适配某些厂商扩展时，登记具体文件/关系缺口，继续其余可验证部分。

### 4.4 P4：双侧分工与联合对接

产品侧回答：调度需求从哪里进入、对象/任务如何创建和标识、参数如何校验及转换、调用或消息怎样进入 EMAP、结果/失败如何反馈，以及哪里会再次写入状态。

EMAP 侧回答：对应接口实际绑定哪个实现，初始化/注册/配置如何生效，执行者如何被触发，数据从接收、保存到实际消费经历什么，以及所需外部接口和产物如何形成。

对实际存在的调度机制，必须说明**谁决定能否执行、何时执行、先后或并发关系以及执行位置**，配置和运行状态怎样改变这些决定；同时记录任务身份、生命周期和关键约束。优先级、抢占、核分配、周期或截止时间等按实际存在情况核实，不事先给产品套模型。

联合核对者不能只拼接两份摘要。对每个交接点核对同一配置下的接口/消息标识、参数或协议字段、单位与布局、注册条件、时序/线程或执行域、同步或异步、所有权、返回/确认的含义以及最终可观察结果。

消息链同时找发送端、路由/注册、接收端、分发、实际处理及结果消费；回调同时找注册与触发；共享状态同时找写入者、读取者、覆盖者和必要同步。只有出现相关证据才继续追关键资源持有者，不遍历所有公共库。

构建依赖、直接调用、可能的间接调用、消息交接、配置控制、状态读写、资源等待分别标注。对于共享内存、缓存维护、DMA、双缓冲/翻面等机制，先证明项目中确实存在且与该状态相关，再研究条件；不能预设问题一定由翻面导致。

可用的代表过程包括初始化/注册、正常触发至完成、参数更新至实际消费、取消/超时/失败、重启恢复。它们是候选题目，由真实产品筛选；不适用应说明依据。一个正常过程查清，只能证明该范围，不能宣布整个调度体系完整。

## 5. 本专题的问题如何对应工具能力

完整工具清单、盘点、缺项安装与正确调用只在 [工具统一管理与使用指南](../工具接入与共享能力/工具统一管理与使用指南.md) 维护；本节不再维护第二套工具手册。按实际问题选择能力，而不是为了“成熟工具增强”安装或运行所有工具。某工具受阻，只限制依赖它的结论，不阻断全部调查。

| 本专题要回答的问题 | 阶段及所需证据 | 统一能力入口 |
| --- | --- | --- |
| 当前研究哪个配置、仓和包？ | P0～P2：版本基线、候选入口、下载/构建/打包来源；文本命中只作为线索 | [盘点与基础工具](../工具接入与共享能力/工具统一管理与使用指南.md#inventory)、[编译上下文](../工具接入与共享能力/工具统一管理与使用指南.md#cdb) |
| 这一配置实际选择哪个实现？ | P3～P4：独立关键文件清单、真实编译语境、解析结果与错误；构建图不代替消息图 | [编译上下文](../工具接入与共享能力/工具统一管理与使用指南.md#cdb)、[Clang 语义分析](../工具接入与共享能力/工具统一管理与使用指南.md#clang) |
| 状态由谁写、哪些分支跳过执行？ | P4：有明确范围的查询问题、关键函数定义覆盖、调用/数据/状态结果 | [CodeQL](../工具接入与共享能力/工具统一管理与使用指南.md#codeql) |
| 产品中真正链接或部署了哪个实现？ | P1～P4：包与源版本对应、链接选择、产物身份；存在符号不证明已运行 | [二进制与链接工具](../工具接入与共享能力/工具统一管理与使用指南.md#binary) |
| 现有语义或关系查看能力仍有缺口？ | P3～P5：先说明哪个缺口、替代能力能验证什么，再做受控试点 | [可选工具](../工具接入与共享能力/工具统一管理与使用指南.md#optional) |
| 本次运行在哪个步骤发生等待、覆盖或失败？ | P6：实际平台事件、业务关联、时钟/丢失/扰动证据；线程事件不自动等于业务任务 | [运行观测](../工具接入与共享能力/工具统一管理与使用指南.md#runtime) |
| 如何证明本次确实执行而且结论可复核？ | 每阶段：输入和工具身份、实际命令、原始输出、退出状态及任务覆盖结果 | [执行证据](../工具接入与共享能力/工具统一管理与使用指南.md#evidence)、[已有任务脚本衔接](../工具接入与共享能力/工具统一管理与使用指南.md#adapters) |

汇编入口、上下文切换、厂商内建函数和动态注册可能超出所选工具覆盖。按实际文件和关系登记边界，用接口、链接资料及必要运行证据补足；不能用一张调用图掩盖漏边。

### 5.1 CodeQL 在本专题回答什么

先有明确问题再提取：例如“这个配置值有哪些写入者”“任务状态有哪些转换入口”“哪个返回/取消分支跳过应用动作”。不从 90 GB 全量建库开始，也不用默认安全告警列表代替调度结构调查。

依照统一指南选择经核验的工具实例、构建模式和执行环境；本专题额外要求：

- 数据库与实际产品/EMAP 版本、部署目标和构建变体一一说明。两侧能在同一兼容真实构建中提取时可同范围查询；独立数据库用接口证据关联，不随意拼成“完整跨仓语义”。
- 调用、值传播、状态读写、消息交接及配置控制分开建模。JS/C++、IPC、另一盒或闭源边界的连接，必须有真实接口/字段/注册语义，不能靠同名补边。
- 用独立关键清单核验产品和 EMAP 的实际函数体与条件；同时检查诊断。数据库存在、查询返回零或进程退出 0 均不等于覆盖通过。
- 留下查询、模型依据、原始结果及本次执行记录。静态可达或数据影响不等于某次运行已发生，更不等于故障根因成立。
- 许可、平台或提取受阻时，按统一报告记录该环境的限制，在本专题列出受影响问题；继续其他证据链，不报“CodeQL 全面通过”。

## 6. 怎样找到边界，又避免漏掉根因

### 6.1 扩展规则

每次新增一个仓、组件或执行域前写两句话：“哪条证据把它与本轮问题关联起来”“继续调查会改变哪个判断”。若只是一项普通链接依赖，先记录接口；若它实际生产/消费关键状态、决定注册/唤醒、持有关键等待资源或参与交接，再展开相应部分。

告警不是默认重点，也不是永久排除项。发现调度同步等待告警返回、共同持锁或共享关键状态时，只追有关调用与资源关系；不顺带研究整个告警业务。CPU/内存/队列等竞争也不能凭可能性无限扩展，应由等待、负载或代码关系等证据触发。

反向检查与正向追踪同时进行：从最终消费者核对输入来源，从关键状态核对其他写入者，从等待点核对唤醒者、取消者和必要资源持有者。这样减少只沿一条调用链走到底造成的漏查。

### 6.2 边界分类

| 边界 | 应留下的说明 | 能否当作该范围的结束 |
| --- | --- | --- |
| 已说明的外部接口 | 版本、输入输出、同步/异步、等待/超时/错误、可观察内容 | 若足以回答本轮问题，可以停止深入 |
| 修改责任边界 | 源码可见性、负责方、能否编译/修改/部署 | 只说明责任；仍可分析或在接口两侧观测 |
| 当前专题之外 | 排除理由、涉及的接触点、触发重新纳入的条件 | 作为明确范围限制，不断言永远无关 |
| 证据缺口 | 缺少的源码/包版本/注册表/日志/权限及获得方式 | 不能写成真实依赖终点 |
| 资源预算用尽 | 已完成范围、未查的具体关系、续接所需资源 | 标记暂停或部分完成 |

“有源码、能编译、有权修改、能替换部署、有观测能力”分别记录，不用一个“可改/不可改”遮盖差异。

### 6.3 结构事实与故障根因

如果出现异常，分别记录：候选根因、传播过程、首次可见偏离、最终失败/复位触发点。最后一个报错接口或最后一条日志不能直接当根因。

架构调查给出可验证的假设和观测位置。要确认某次偶发故障的原因，需要与该次运行匹配的证据，必要时用受控复现、边界不变量检查或改动前后对照排除竞争解释。不能为了根因要求而在本轮提前铺满插桩或部署未经评估的检测器。

## 7. 条件性运行核对

先复用已有日志、版本记录和观测能力。有条件时选择少量与核心交接有关的事件：输入/版本变更、发送/接收、入队/出队、选择或等待、应用、实际消费、完成/拒绝/超时。事件名随真实机制确定。

关联字段按需要选择：运行/启动标识、设备或进程/执行域、请求或任务 ID、消息序号、配置代次、关键值或摘要、结果原因、本地单调时间及时间单位。跨盒不能直接把墙上时间排序当成因果；优先用消息/任务标识连接事件，再标明时钟同步方式和误差。

必要时另记产物身份、记录序号、重试次数/attempt 和 clock_id。记录序号用于识别日志缺口，不能由消息序号代替；发送成功、接收确认、应用提交和实际消费分别定义，不能把 ACK 自动解释成参数已经生效。

同盒不同核也要核实时钟可比性；例如 ftrace 的 local 时钟可能跨 CPU 不同步。没有可靠跨盒时间映射时，只报告盒内耗时和有标识支撑的交接关系，不计算伪精确的单向延迟，也不强行对跨盒事件排序。[ftrace][s-ftrace]、[Perfetto 时钟模型][s-perfetto-clock]

记录启用范围、缓冲容量、丢失/覆盖计数、采样率及运行开销。异常时没有某条日志，可能是没有执行，也可能是丢失/覆盖/复位未保存，不能直接下结论。频繁 printf、无界日志或全函数跟踪可能改变调度时序，先小范围评估。[Perfetto 缓冲及丢失说明][s-perfetto-buffers]

具体工具选择、接入、采集与导出遵循统一指南的[运行观测](../工具接入与共享能力/工具统一管理与使用指南.md#runtime)。本专题的事件含义、关联字段和成功契约由实际机制决定；时间线展示不自动证明业务因果。

本阶段未运行时，按实际情况说明静态链已核对与尚未核对的范围，并明确“运行链未验证”；不伪造日志或把时间接近当作消息配对。

## 8. 双侧研究与红蓝交叉复核

实际执行可由一个 AI 分阶段完成；有多代理能力时，将产品侧和 EMAP 侧在统一基线下并行交给两个研究者。双方先提交接口表和证据，不仅提交文字总结，再由联合复核者逐项对接。

多代理共享总资源预算。对同一构建目录、缓存或分析数据库的写入由一个执行者负责，避免重复编译、重复建库和相互覆盖；产品侧/EMAP侧的只读研究可以并行。没有多代理能力时，一个 AI 也要按同样的证据表对接和反证。

蓝队负责给出最有证据的链路解释与边界。红队优先寻找：错误版本、同名后端、未注册回调、另一盒的接收实现、状态的第二写入者、公共资源等待、取消/恢复路径和日志缺口。红队不需要机械地反对每项结论，提出反例必须指出它可能改变哪个判断。

至少做两轮：第一轮审查范围、工具和证据方案；第二轮对真实链路报告提出反例，由研究者补证、缩小结论或保留缺口。文档设计的同行评审不能冒充真实产品结果已经通过第二轮验证。

最低反例清单：

| 反例 | 本方案的处理 |
| --- | --- |
| output 下载了公共库/旧包，但该调度过程没有使用 | 区分下载、链接、部署和执行，核对配置及来源 |
| 回调/消息链没有直接 C++ 调用边 | 查注册、路由、协议及对端绑定，必要时运行关联 |
| 产品运行旧库，本地源码却是新提交 | 先恢复产物—源码对应；对应不清不作运行结论 |
| 告警模块持有调度所需资源 | 只按已发现的资源关系扩展相关部分 |
| 最后消费者拿到旧值，真正错误发生在更早的配置覆盖 | 查版本、写入者、应用条件和实际消费，分开根因与触发点 |
| 编译数据库或 CodeQL 只覆盖产品包装层 | 单独核验 EMAP 实现提取；预编译边界明确保留 |
| 无源码或预算耗尽 | 保留具体缺口或暂停状态，不写“已摸到系统最底层” |

## 9. 交付、证据记录和验收

实际运行的结果放在既有规范允许的结果目录，与原仓源码、工具安装及缓存分开；路径由本地环境成果决定。主报告可以合并为一份，但必须有产品侧、EMAP 侧、联合关系及剩余边界四部分。

**第一批交付**包含：调度机制清单、一个配置下首个代表过程、当前可确认的产品—产物—EMAP 来源映射、边界及动态/语义缺口。已有资料足够时，无须新构建或上板也能交付。核心决策或交接仍不清楚时称“阶段性事实”；关键结构已核实但未运行时称“该范围的静态架构基础”；运行验证另标状态。最终调度专题交付还需回到机制清单，逐项交代覆盖，不能把第一批试点当成整个专题完成。

建议最小结果集合：

| 文件 | 内容 |
| --- | --- |
| `00_调度专题报告.md` | 大白话概览、问题/范围、三个视图、证据结论和下一步 |
| `baseline.json` | 版本、配置、镜像/工具链、实际路径及关键输入身份；引用工具状态报告版本/摘要、环境和工具实例，不复制维护工具台账 |
| `artifact-source.csv` | 产品组件、包/产物、EMAP 源码与构建对应、证据状态 |
| `relations.csv` | 带类型、条件和证据的关系；图从此生成，保留方向与跨域信息 |
| `mechanisms.csv` | 已发现/候选调度机制、来源、代表过程、未覆盖问题及范围状态 |
| `coverage.csv` | 独立列出的关键问题/实现及实际解析、提取、关联、运行覆盖 |
| `boundaries.csv` | 边界类型、能力、缺口、责任、下一步和扩展条件 |
| `execution-state.csv` | P0～P7及各配置的状态；本次执行/有依据复用/未执行分开，实际采用工具、运行记录 ID 和原始结果入口 |
| `evidence/` | 命令、查询、构建/解析输出和必要运行片段，按证据编号保存 |

每条证据记录：证据 ID、仓及版本、文件/符号或产物/事件位置、配置与成立条件、获取命令/工具版本/工作目录、原始结果位置、支持的结论和限制。原始证据与解释分开保存，不用 AI 摘要替代输出。

对支撑结论的采集保存可复核原始结果；探索性搜索可保留可复现命令、范围和相关片段。大输出注明筛选、截断或丢失，不能用截断结果证明不存在；已有大产物引用身份和位置即可，不重复归档每个副本。

关系至少区分“源码显示存在”“此构建配置选择”“产物包含”“已部署”“此次运行观察”“假设”“当前无法核查”；一个字段不能把这些含义混成已证实。关键关系还应记录源/目的、接口或状态标识、同步/异步、所有权和结果含义。

覆盖问题和关键实现由场景、接口与构建资料独立提出，再与工具结果核对，不能从工具恰好提取的文件反过来生成一份百分之百覆盖清单。

验收标准：

1. 一个不参与调查的人，能沿所给位置和原始证据复核代表过程，而不是只能相信图和总结。
2. 核心交接、关键状态及必要等待都有解释，或具体列出足以影响结论的缺口；不得藏在“其他依赖”中。
3. 输出/源码/构建/运行的版本与配置一致性有依据；未知保持未知。
4. 每个新纳入或排除的模块说明原因；没有因关键词或仓库名直接认定相关/无关。
5. 工具按[统一执行证据规范](../工具接入与共享能力/工具统一管理与使用指南.md#evidence)留痕，所用状态报告有效且能指向实际环境/实例；本次输入、执行、覆盖范围和失败可查。仅阅读报告或通过安装验证不得算作本次完成；未运行不报通过，未检出不等于不存在。
6. 结论明确限定在所调查配置、机制与过程；机制清单包含尚未验证的部分。首个过程完成只算试点完成。未执行运行阶段只能验收静态结论；有关键缺口时交付部分结果，不能称端到端已闭合。
7. 停止深入有接口或范围理由；暂停有具体阻碍和续接点。无需证明无限范围内不存在任何间接影响。

零结果、数据库体积、扫描文件数、图节点数、测试日志条数均不单独作为完成指标。

## 10. 可直接交给本地 AI 的启动指令

### 11.2 两轮设计评审中保留、修改和否决的意见

本次由构建/语义工具研究者、运行/产物工具研究者和独立反例评审者参与。第一轮分别研究工具与风险，第二轮检查综合稿，随后按具体问题修订。以下是设计取舍记录，不是产品测试结果。

| 议题 | 评审意见与最终处理 |
| --- | --- |
| 专家列仓 → output → 递归依赖 | 保留作为来源线索；否决封闭名单、下载即使用、递归到无源码即完整这三种推断 |
| 只围绕一条链控制规模 | 红队指出会漏其他调度机制；改成先粗列机制与未知项，代表过程逐项核实，试点和最终交付分开 |
| 启动时需要哪些工具 | 两名工具研究者对“首轮”定义不同；统一为启动先用已有资料，精确语义阶段再补上下文和解析能力 |
| P3 解析成功才能 P4 | 否决整体硬门槛；按文件/关系降级，厂商工具不适配不阻断其余有证据的调查 |
| 是否先跑 CodeQL | 放到有明确查询问题和可验证提取范围之后；无构建能力、许可和缓存限制写入采用条件 |
| “只分析一点”是否足够控成本 | 红队指出后台索引、传递构建和多代理重复建库会失控；增加执行前资源限额、范围核对与单写入负责人 |
| 告警等非重点模块 | 不深入其全部业务；出现实际共享状态/资源关系时，限定范围纳入 |
| 不运行产品能否交付 | 可以交付阶段性事实或指定范围静态架构基础；不能称运行链或故障根因已证实 |
