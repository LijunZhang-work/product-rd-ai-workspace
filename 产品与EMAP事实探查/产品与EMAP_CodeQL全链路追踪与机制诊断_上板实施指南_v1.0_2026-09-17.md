# 产品与 EMAP：CodeQL 全链路追踪与机制诊断上板实施指南

版本：v1.0｜日期：2026-09-17｜工具归一修订：2026-09-18（保留文件名兼容旧引用）｜面向：有产品源码、对应版本 EMAP 源码及原产品构建环境的本地 AI。

## 0. 任务是什么，最终交付什么

针对真实产品中“网页修改参数后，另一核上的 BEH 图元/算法偶发没有按预期更新”，完成以下闭环：

**双仓版本与构建核对 → CodeQL 和源码分析 → 实际生效机制梳理 → 产品与 EMAP 双边诊断插桩 → 编译打包 → 真实产品复现 → 导出证据 → 逐步定位源头。**

用户所说的 email 码/宜麦普统一指 EMAP，code QR/code QL 统一指 CodeQL，图源统一按 BEH 图元理解。主核、实时核、EROS 等称呼先按线索核实，不据此猜核数或硬件异构组合。

本文件是新写的实施指南，不是实际代码探查报告，也不是已经编译出的产品包。本次未访问两仓或真实设备。本文要求后续本地 AI 在真实路径、符号、目标与工具链上完成适配、修改、构建及验证，不把示例名当项目已有接口。

### 0.1 用大白话理解三个工具角色

| 角色 | 做什么 | 交付什么 |
| --- | --- | --- |
| CodeQL＋源码/配置分析 | 找“值可能怎样走”“哪些条件和状态决定它能不能继续” | 路径、条件、状态修改者、接口与缺口证据 |
| 产品与 EMAP 中的诊断代码 | 真实运行时记录“这一次走到哪里、为什么执行/跳过、当时使用什么状态” | 有关联关系的运行事件 |
| 本地解析/对照工具 | 将多核、多层、网页与图元记录拼接，并检查证据是否完整 | 成功/失败对照、首次分叉、候选根因与证明边界 |

CodeQL 不会自动把日志写进产品，也不需要作为运行库装到板上。AI 根据静态分析结果修改两个仓的可控代码，将诊断记录器与记录点编入对应固件，再按原升级流程形成诊断产品包。

### 0.2 与此前“事实探查任务包”的衔接

已参考此前《00_总入口与执行约定.md》和《03_双仓关联核对与事实验收.md》的当前内容。此前任务包负责事实探查；本指南在选定信号相关事实足够明确后，继续实施诊断代码与编包。本阶段不能被旧任务书的“仅探查不改代码”限制为只交报告，也不必等无关产品模块全部研究完才开始。

继续遵守：结论有基线和证据；闭源边界明确；不把源头根因、首次发现异常、最终触发点和复位机制混为一谈。新版文件独立保存，不覆盖此前任务书。

工具盘点、安装、位置、接入、通用调用和验收的唯一规则来源是 [工具统一管理与使用指南](../工具接入与共享能力/工具统一管理与使用指南.md)；已核验实例和限制从 [工具状态与验收报告](../工具接入与共享能力/工具状态与验收报告.md) 读取。先按指南的[环境继承](../工具接入与共享能力/工具统一管理与使用指南.md#environment)复用 `Windows与WSL开发环境` 文件夹中的已执行成果，核对报告与本机/镜像的对应和有效性。只补缺失或失效项并更新同一报告，不重新部署已经验证的环境，也不在本任务另建一份工具台账。

本指南只定义诊断任务的问题、查询/模型需求、插桩与上板验收。工具状态报告证明可用条件，不能证明本次已经用过；每次本项目建库、查询、编译、解码均须按[执行证据规范](../工具接入与共享能力/工具统一管理与使用指南.md#evidence)保存真实输入、执行记录与输出。复用旧结果须有匹配版本/配置依据，并标记复用。

### 0.3 本地 AI 的最终交付

1. 两仓可审阅的诊断改动与基线记录。
2. 覆盖产品和 EMAP 的 CodeQL 数据库说明、实际查询、原始结果及覆盖核查。
3. 从网页到目标图元/算法的实际路径图、机制清单和插桩清单。
4. 真实构建完成的产品升级包，以及精确匹配的 ELF/符号、库、配置、图元映射和构建清单。
5. 运行事件的导出、解码和对照工具及使用说明。
6. 安装核验、正常路径验证、偶发问题复现和根因分析步骤。

不以“代码改完”“库编出来”或“CodeQL 有路径”代替完整交付。没有实际构建环境、发布签名或某核源码时，完成其余可做部分，列准确阻塞点，不能生成空包或宣称可上板。

## 1. 本次必须覆盖的范围

### 1.1 从网页到真正应用，再到读回

根据真实实现核对如下候选阶段。它们是核对框架，不是已确认的产品拓扑；实际可以缺少、合并或增加阶段。

| 阶段 | 必须确认什么 |
| --- | --- |
| 网页提交 | 参数键、目标对象、原始值、请求字段；浏览器究竟有没有发送 |
| 服务端接收与校验 | 实际端点、解析、类型/单位转换、权限或运行模式条件、拒绝原因 |
| 产品配置/业务状态 | 保存到哪里；“已保存”“待应用”“已生效”是否不同 |
| 产品调用 EMAP | 实际 API、消息/对象、所有权、同步/异步语义 |
| EMAP 内部与第三方边界 | 真正后端、路由/排队/传输/通知、返回和完成语义 |
| 对端接收与业务处理 | 接收域/任务、注册映射、解码/转换、过滤或延迟应用 |
| BEH 图元/算法 | 配置映射、实例与端口、实际输入采样、调度执行、结果/状态 |
| 实际读回/展示 | 观察的到底是业务有效值、配置副本、算法输出还是显示缓存 |

成功不能只定义为 HTTP 成功、发送函数返回、数据到了接收回调。必须事先定义终点：目标实例在适用执行周期读到了期望输入，或目标业务有效变量完成更新。算法输出不一定等于输入，需按算法、模式和其他输入判定。

电脑侧 BEH Java 引擎仿真与板端真实执行分别记录。仿真通过不能替代跨核上板验证；板端图元映射不明时，不把链路终点停在某个任意 C++ 变量。

### 1.2 值、机制、旁路共同覆盖

同时查：目标值的传播；允许/阻止传播的条件；相关状态的其他修改者；异步完成和任务调度；失败、跳过、覆盖和恢复分支。翻面只是用户已知的一项线索，不是预先认定的主因。

“关键点都加上”的含义：当前目标信号的关键交接与影响其生效的机制均有可用证据点；不是每一行代码打印，也不是给整个产品所有变量无限记录。

### 1.3 执行环境与控制范围

公司工作沿用现有 DeepSeek Harness 或其他本地编码 AI；产品与 EMAP 在各自仓里修改。使用原有 WSL+产品镜像或配套远程 Linux 构建环境，Windows 继续承担已有网页/BEH 工具操作；具体以项目为准。

当前由用户准备两份匹配源码。更深层第三方无源码/无修改权时，在可控入口、出口和回调上记录，保留内部未知。用户计划将生成包升级到真实产品复现；本地 AI 先完成可审阅的包、版本清单和具体步骤，已有明确目标设备与执行授权时沿用，不重复索要同一授权。

## 2. 开工输入与成功契约

AI 先自动读已有构建/发布/配置和先前探查成果，只问不能由现有资料确定的关键问题，不要求用户手工填写所有字段。

```yaml
diagnostic_case:
  product_repo: <实际路径、commit、未提交差异>
  emap_repo: <实际路径、commit、与产品使用包的对应证据>
  product_target: <产品型号、板版本、构建目标、原故障版本>
  build_environment: <真实工具链、镜像/环境标识、构建入口>
  tool_report: <统一报告路径、版本/摘要、环境身份、所选工具实例；不复制工具台账>
  signal:
    parameter_key: <真实参数/点表标识>
    object_instance: <真实目标对象/通道/设备>
    web_request: <页面操作、服务端点、字段映射>
    expected_sink: <目标业务变量或图元实例/端口及算法位置>
    value_semantics: <原始类型、单位、缩放、范围、规范化规则>
  application_contract:
    completion: <到哪一步才算应用成功>
    timing: <由现有规范/周期/实现确定的时限或触发条件>
    update_policy: <逐次处理/允许合并且最终为最新值/其他>
    valid_modes: <允许应用的产品模式与必要前置条件>
    permitted_terminal_results: <应用/合法拒绝/被后续更新替代/其他>
  runtime_assets:
    target_firmware: <各执行域实际固件>
    beh_model: <模型/XML/生成文件及映射版本或不适用>
    existing_export: <当前可用的日志/留档/调试数据导出通道>
```

在异步周期系统里，不设未经依据的“立即更新”断言。把连续修改中的合法合并、量化后值相同、模式不允许生效、目标实例选错和读回缓存分别判定，避免制造假故障。

先选一个确实能触发问题的参数，建成可重复流程；扩展其他参数通过配置与映射，复用记录器，不复制出多套互不兼容的实现。

## 3. 阶段一：锁定真实构建与双仓身份

### 3.1 核实源码、包和设备的关系

逐核/执行域形成：产品配置 → 实际头文件 → EMAP 实现/后端 → 库/包 → 产品链接 → 最终镜像 → 升级包 → 设备启动身份。

重点防止“手里有 EMAP 源码，但产品仍使用 artget 缓存里的旧包”。对应版本应有 commit/发布清单/构建记录等证据；单个版本字符串相同不足以证明实现与配置相同。

分清核/域、OS、镜像和任务，不能把主核/实时核/EROS 直接计成三个物理核；不以一个 ELF 的架构或 `-mcpu` 推断芯片全部核数。只要当前信号涉及的域与构建选择查清，即可推进局部诊断，其他未知保留。

### 3.2 保留原始基线

两仓分别用项目惯例的诊断分支/独立工作目录，保留用户已有修改。记录基线源码、依赖锁定、配置、模型、工具链、原包摘要和已知复现步骤。

诊断改动与根因修复分开提交/记录。第一版先观察原行为；不顺手改翻面顺序、加业务锁、延长超时、重排消息或扩大业务队列，否则可能先掩盖问题。

## 4. 阶段二：CodeQL 同时分析产品与 EMAP

### 4.1 明确双仓分析范围与真实构建身份

CodeQL 实例选择、使用条件、容器接入、构建模式和建库/查询操作，统一按指南的 [CodeQL](../工具接入与共享能力/工具统一管理与使用指南.md#codeql)与[容器接入](../工具接入与共享能力/工具统一管理与使用指南.md#containers)执行。若本任务还需要编译数据库与其他语义工具，使用[编译上下文](../工具接入与共享能力/工具统一管理与使用指南.md#cdb)及[Clang 语义分析](../工具接入与共享能力/工具统一管理与使用指南.md#clang)，不能假设普通构建已生成 `compile_commands.json`。

本任务必须交付数据库与分析范围的对应表，回答：

| 需要核对的情况 | 本任务必须留下的事实 |
| --- | --- |
| 产品与 EMAP 在同一兼容真实构建内提取 | 两仓关键函数体的真实路径、配置和覆盖证据 |
| 产品只链接预编译 EMAP，或 EMAP 独立构建 | 与产品使用包匹配的 EMAP 来源、独立提取结果或内部缺口；头文件可见不等于实现已分析 |
| 不同部署目标、语言或互斥构建变体 | 分析身份及边界；同一真实构建内逐文件宏不同本身不是拆库依据 |
| 编译/提取范围受缓存、远端执行或工具不适配影响 | 哪些关键定义未覆盖、影响哪个问题，以及补证结果；不改用宿主宏冒充实际产品配置 |
| 暂时无法获得真实构建语境 | 已能确认的源码事实与不能确认的构建选择，分别列明 |

不得把数据库放在同一目录或使用多语言数据库集群，写成已经贯通跨库、跨语言或跨核数据流。匹配本项目的实际构建脚本与数据库身份属于任务交付，通用工具调用方式不在本文另行定义。

网页若有可访问 JS/TS 源码，单独分析其字段与请求生成；HTTP 与 C++、跨核消息、XML/图元配置边界都用有证据的契约衔接。两仓未包含网页前端时，使用真实请求/服务端接收作为明确边界，不能写“前端源码已完整分析”。

### 4.2 数据库验收先于路径查询

先输出 `database_coverage.csv`，至少逐项核查：网页服务端处理函数、产品业务 setter/转发函数、实际 EMAP API 和后端、接收分发/回调、目标图元/算法入口是否存在函数体，来自哪个目标和真实路径。

区分函数声明、实际定义、未编入、提取失败、闭源边界。检查关键宏/平台分支与实际链接来源一致。数据库创建成功或显示很多文件，不能代替这项检查。

### 4.3 先精确定义 source 和 sink

source 使用真实参数/对象映射后的节点；sink 使用真实目标实例/端口或算法输入读取点。先人工/AI 读源码核实定位，再把选点写入版本化配置。不要把所有 setter 视为同一个入口，或把所有图元输入视为一个终点。

正向追“网页值影响到哪里”，反向追“目标最终值可能来自谁”，两边对照。若缩放、限幅、枚举转换等改变数值，记录转换规则；数值不相等并不一定是故障。

### 4.4 本地 AI 必须实现和运行的查询组

以下是查询交付要求，不是预先存在的项目文件名或承诺可覆盖所有动态行为。

| 查询组 | 查询内容 | 结果必须包含 |
| --- | --- | --- |
| Q00 覆盖 | 两仓关键源文件、定义与目标配置 | 仓、文件、符号、目标、定义/声明/缺失状态 |
| Q10 正向值流 | 参数从入口到转换、消息、接收字段、图元端口 | 节点、边、变换、实际源码位置 |
| Q20 反向来源 | 目标值、缓存、更新状态可能由哪些入口改写 | 所有已识别来源、别名/间接写入候选与盲区 |
| Q30 调用与注册 | 同步调用、回调、分发注册、函数表、生成映射 | 调用者、选择条件、接收者和证据 |
| Q40 条件与分支 | 阻止/允许转发与应用的判断、早返回、失败处理 | 位置、条件、相关状态、影响的步骤 |
| Q50 状态修改者 | pending/dirty/序号/有效面/有效版本等实际状态的读写 | 初始化、置位、清除、覆盖、重启路径及上下文 |
| Q60 对象与生命周期 | 分配、拷贝、借用、转交、释放、复用 | 对象身份、拥有者、异步完成与异常分支 |
| Q70 终点与观察 | 图元实例/端口/周期、算法输入及读回链 | 实际有效值和展示来源的差异 |

使用当前 modular C/C++ 数据流库，结合 `DataFlow::ConfigSig`、`DataFlow::Global` 或按需要采用 taint 分析。指针本身和指针指向的数据分开建模；taint 只表示影响关系，不证明数值保持，也不证明实际执行。具体 API 以所锁版本为准。[C/C++ 数据流说明](https://codeql.github.com/docs/codeql-language-guides/analyzing-data-flow-in-cpp/)

Q40 可用控制流/Guards 辅助定位条件，但查询结果不说明某次运行条件是真是假；Q50 也不能自动识别所有第三方、DMA 或动态别名写入。将未知边与未覆盖写入者列入报告。[Guards 说明](https://codeql.github.com/docs/codeql-language-guides/using-the-guards-library-in-cpp/)

### 4.5 跨边界如何接起来

同步可见调用、经证据确认的复制/转换、协议跨核连接、闭源契约假设分别标记边类型。自定义额外数据流关系必须有真实接口与参数语义依据；不允许为了得到一条漂亮路径，把任意 send 与 receive 强行连接。复杂 C/C++ 间接访问需按实际对象和解引用层次处理。[高级数据流场景](https://codeql.github.com/docs/codeql-language-guides/advanced-dataflow-scenarios-cpp/)

HTTP 用端点＋字段＋对象身份衔接；IPC 用通道＋消息类型＋版本＋目标＋字段布局＋接收注册衔接；BEH 用模型/生成映射＋实例＋端口衔接。只有同名函数、同一数值或同一消息数字 ID 不足以证明配对。

拆库时先导出各库内结果，再用明确映射构成端到端工程关系图。不要声称在一条普通 CodeQL 查询里自动贯通了不同数据库和物理核。

### 4.6 输出、复跑和缺失结果

实际建库、query pack/模型准备、查询编译/运行和结果导出方式，按统一指南的 [CodeQL 操作](../工具接入与共享能力/工具统一管理与使用指南.md#codeql)执行；本任务据第 4.3～4.5 节产生真实选点、查询和模型，不能以通用示例或默认安全扫描替代。

交付至少包含：每个数据库的基线与覆盖表、Q00～Q70 的采用/不适用/受阻状态、查询和模型版本、完整候选节点/边及未知项、可复跑的实际任务脚本和[本次执行证据](../工具接入与共享能力/工具统一管理与使用指南.md#evidence)。表格和路径展示均须对应原始查询结果；显示的一条路径不能当成唯一实际路径。

零结果先查 source/sink、提取覆盖、构建分支、指针/别名、间接回调及模型缺口，不直接宣布“没有这条链路”。安装验收、数据库目录存在或别的任务曾运行成功，不能替代本信号、本配置的查询执行和覆盖验收。

## 5. 阶段三：先发现机制，再决定记录点

### 5.1 机制清单来自代码，不来自猜测

对目标信号的前向/反向链与相关状态修改者逐项核对。下表是检查类别，不是假定产品一定存在这些机制，也不是穷尽所有实现。

| 类别 | 需要查什么 | 诊断时要能区分什么 |
| --- | --- | --- |
| 参数与对象映射 | 点表、索引、实例、通道、模型映射 | 更新送到正确对象还是别的实例 |
| 校验与规范化 | 类型、缩放、量化、限幅、合法范围、运行模式 | 被拒绝、变为相同值、合法延迟应用 |
| 配置与生效状态 | 持久配置、暂存、提交、激活、周期采样 | 已保存但未激活，还是已激活但未采样 |
| 变更检测 | dirty/pending、相等判断、版本、去重 | 应处理的更新被误判为已处理 |
| 队列与流控 | 容量、入队/出队、背压、合并、重试 | 未提交、合法合并、失败、排队未消费 |
| 缓冲与发布 | 单/双/多缓冲、A/B 翻面、快照、序号 | 写到哪里、发布哪批、读到哪批 |
| 通知与调度 | 中断、邮箱、轮询、任务唤醒、周期、回调注册 | 数据已准备但通知/执行没有发生 |
| 同步与可见性 | 锁/原子/屏障、缓存属性、数据与标志的顺序 | 双方看到不同批次；尚不能直接认定缓存缺陷 |
| 生命周期 | 拷贝/借用、所有权、释放复用、DMA、迟到回调 | 正确数据何时被复用或失效 |
| 并发覆盖 | 其他入口、恢复任务、默认值加载、回写 | 曾经生效又被谁覆盖 |
| 恢复与版本 | 对端重启、重连、启动代次、协议/模型版本 | 旧请求/旧确认影响当前更新 |
| 图元与算法 | 订阅使能、连接、执行条件、扫描周期、算法内部状态 | 输入已到但未执行，或输出本就不应等于输入 |
| 观测与回显 | 读回接口、缓存、刷新、观察对象 | 实际未更新与显示未更新 |

每种真实机制形成一张卡：作用、相关路径、状态变量、读写者/任务/核、执行/跳过条件、正常完成定义、异常分支、现有证据与需要插入的事件。未知机制继续通过真实调用/注册/共享状态追查，不只填写表内熟悉名称。

### 5.2 给机制定义可检验规则

规则必须来自已有实现/规范并明确适用模式。例如“当前请求允许应用且没有被合法替代时，应在约定周期内进入目标输入”；“消费者使用的版本必须与所选快照一致”；“异步借用缓冲区的有效期覆盖实际读取”。

不能强制所有请求逐次应用，也不能假设每条消息都有 ACK。将合法拒绝、相同值无变化、合并替代、待条件满足与异常停滞分开。

对 A/B 机制只有确认存在后才记录写面、发布面、读面和代次。面索引相同可能经历了多次翻转，不作为“没有翻面”的充分证据。新加诊断代次不改变业务翻面或消息顺序。

### 5.3 从机制卡生成插桩清单

```text
点位 ID | 仓/文件/符号 | 构建目标/核/上下文 | 对应机制
记录发生在原操作哪个位置 | 值/版本/条件/结果 | 正常与跳过分支
关联方式 | 原始证据 | 预计频率/预算 | 启用级别 | 未覆盖范围
```

同一关键状态要查所有已识别的修改位置，包括置位、清除、初始化、超时清理和恢复；只记录“读取到 false”不能解释谁清掉了它。需要关注其他核/任务时，扩展对应记录点，或明确留下不可见边界。

## 6. 阶段四：实施双仓诊断代码

### 6.1 先复用现有能力，再补公共记录器

先评估现有日志/trace、任务跟踪、共享区留档和导出通道：能否低开销记录固定事件，能否在目标核/中断上下文使用，是否包含丢失计数，能否保存前因窗口。满足需求就复用并补事件格式。

现有能力不足时，在可控层新增薄的诊断记录接口与目标适配，产品和 EMAP 共用事件格式、版本与解码器；各核可有各自缓冲区和实现。不要让 EMAP 反向依赖产品业务对象；目标参数筛选可通过项目已有配置或有界诊断配置传入。

记录接口、配置名和目录名必须结合仓库实际设计，本文没有预定义项目 API。框架初始化后可用、初始化前如何处理、嵌套调用与故障时行为都要明确。

### 6.2 事件至少表达三类信息

| 类别 | 意义 | 内容 |
| --- | --- | --- |
| 值与版本 | 这次使用了什么数据 | 参数/实例、类型、原始值、转换后值、数据代次、对象身份 |
| 决策与动作 | 为什么执行或没执行 | 机制、真实分支、条件操作数、结果码、跳过/失败原因、相关状态变化 |
| 运行上下文 | 谁在什么时候对哪次请求做事 | 核/域、任务/ISR、事件序号、局部时间、请求/消息关联、启动批次 |

只记 `enter/exit` 不够；只记结果值也不够。对关键步骤至少覆盖开始/成功/有依据的合法跳过/失败或延后。在异步路径上，调用返回与后续完成分别记录。

一旦原代码发现失败、丢弃或跳过，应在该分支直接记录原因。不要事后看一个状态快照猜测当时走了哪条分支。

### 6.3 从网页到图元的点位覆盖要求

下面的事件语义是设计要求，实际名称由实现统一编码；不存在的阶段标不适用并附依据。

| 位置 | 必须记录的事实 | 所属层 |
| --- | --- | --- |
| 网页提交/服务端入口 | 请求与参数对象、原值、服务端接收、响应语义 | 浏览器证据＋产品服务端 |
| 解析/转换/校验 | 原始/规范化值、单位/类型、校验结果及原因 | 产品，必要时 EMAP 转换实现 |
| 配置/业务写入 | 暂存/提交/激活的对象和版本；被覆盖时的来源 | 产品 |
| 产品调用 EMAP | API/消息、参数、目标、长度、所有权、调用结果 | 产品侧边界 |
| EMAP 选择与路由 | 生效后端、通道、目标、路由或注册失败 | EMAP |
| 入队/发布/通知 | 队列/缓冲对象、代次、尝试结果、拒绝/延迟原因 | EMAP 可控实现 |
| 第三方调用与回调 | 输入边界、返回、实际完成回调、可见错误 | EMAP 的可控边界 |
| 对端接收/解码 | 消息身份、接收上下文、字段与版本校验 | 接收核的 EMAP/产品 |
| 接收侧业务决策 | 过滤/合并/模式条件、实际使用数据和处理结果 | 产品 |
| 图元交接 | 目标模型/实例/端口、输入版本、映射结果 | 可控交接层 |
| 图元输入消费/算法执行 | 实际采样输入、周期/执行条件、输出或内部状态变化 | 可控实际运行时/算法层 |
| 读回与展示 | 生效值/版本、读回来源、返回值、客户端观察结果 | 产品读回＋浏览器证据 |

每个涉及域单独确认插桩已经编入。若图元执行器或某个核的内部只有二进制，只在真实可控边界或已存在调试接口获取记录，并在覆盖清单写清“看到了交接、尚未直接看到内部消费”。不能把主核日志当成对端内部执行证据。

### 6.4 关联一次更新：不能只比较值

优先复用已有请求 ID、通道序号、消息版本和对象 ID，在边界记录转换关系。一次网页请求可能生成多个消息，也可能多次更新合并为一次发布；保留父子、拆分、合并、重试、替代关系。

推荐的身份组合为“设备/测试会话＋源域启动代次＋对象/信号＋请求序号”，再映射到各域本地消息与对象。重新启动、计数回绕或对象地址复用不能误合并成同一请求。

若现有协议无可用关联字段：

1. 先核实是否可用已有业务键、版本或可证明唯一的序号组合。
2. 本域可用有界旁表保存“请求—本地消息—缓冲区代次”关系；旁表要处理回收、并发、满表和地址复用。
3. 旁表不会自动把身份带到另一核。跨核若仍无法唯一配对，明确缺口；不要用“时间接近、值相同”冒充确定关联。
4. 只有在双方格式/实现可控且兼容性验证完成时，才考虑独立诊断扩展或现有预留字段。不得擅自增加业务结构体字段、改变报文长度、packing 或 CRC 范围；不能为加 trace 破坏原协议。

只有概率关联时在解析结果标注“候选关联”。信息不足的案例不能强行排成一条唯一链。

### 6.5 统一逻辑事件模型

以下是离线解码后的逻辑结构，不要求设备热路径序列化 JSON。板上采用有界的定长或明确限长记录，离线再转换。

```yaml
event:
  schema_version: <事件格式版本>
  build_id: <由流头或事件关联的诊断固件身份>
  test_session: <测试会话，若未绑定则明确为空>
  origin: <核/执行域/任务或ISR>
  boot_epoch: <当前域启动代次>
  local_sequence: <此事件流内递增序号>
  local_time: <原始时钟读数与单位，不能假定跨核同步>
  point_id: <映射到代码版本及位置>
  mechanism_id: <真实机制卡ID>
  phase: <接收/转换/决策/发布/消费/应用/读回等>
  signal_object: <参数键、实例、通道>
  correlation: <请求、消息、数据版本及父子/替代关系>
  values: <有类型和单位的必要值；不存在则缺省>
  decision: <真实分支、返回码、原因码>
  state_observed: <原操作实际使用的安全可读状态与版本>
  state_change: <发生时的原值/新值、操作者、成功与否>
  evidence_quality: <一致快照/单字段观察/候选关联/截断等>
```

流头或导出清单另含：各核 build ID、产品/EMAP 版本、模型/映射版本、采集配置、起止序号、丢弃/覆盖/未提交记录计数、时间校准信息、冻结/导出状态。字段缺失要显式表示，不用 0 冒充未知值。

大对象只保存必要字段与类型、长度、代次；摘要可辅助核对，但摘要相同不能替代完整身份关联。原始指针不是跨地址空间稳定对象 ID。

### 6.6 不让记录代码改变要观察的语义

这是偶发时序问题，插桩本身会消耗时间；目标是使扰动有界、可测、可关闭，而不是承诺完全无扰动。

- 优先记录原代码已经取得的局部值、原子操作返回值和真实分支结果；不为日志再次调用 getter、接收函数、状态判断或可能清标志的接口。
- 不重复求值带副作用的表达式，不破坏短路条件、锁范围、异常行为和原有返回码。对 read-to-clear 寄存器不得额外读取。
- 需要观察共享状态时，遵守原对象的有效期、锁/原子协议和平台内存访问约定。多字段不一致快照必须标记；不能记录一个混合时刻状态，再据此宣布业务竞争。
- 热路径不动态分配、不同步写文件/发网络、不调用可能阻塞的普通打印、不递归进入同一内存或日志封装；异常时也不假定堆和锁可用。
- 记录器自身的同步仅服务记录安全，不给业务对象偷偷补屏障、flush、锁或重试。新增系统范围屏障/缓存维护也可能掩盖原问题，必须显式评估和对照。
- 第三方执行后才读取可能已释放的缓冲区不安全。应在合法存活阶段取有限快照或使用已有操作结果，不能为了日志新增越界/UAF。

先做局部代码评审与必要验证。是否允许额外读共享对象、是否具备无阻塞的原子操作和中断上下文能力，按目标平台核实。

### 6.7 缓冲区与导出可靠性

优先复用项目现有可靠 trace 缓冲。新增时按域及写入上下文设计：每核并不天然等于单生产者，任务可被中断或其他任务打断；“一个数组＋普通自增索引”不能作为并发正确性的证明。Linux 官方环形记录器设计也明确处理嵌套写入、提交与读取关系，不能把其特定假设直接照搬到你们 RTOS。[环形记录设计参考](https://docs.kernel.org/trace/ring-buffer-design.html)

必须定义：预分配容量、写入预留与提交、记录完整性、溢出/覆盖策略、重入处理、局部序号、导出时一致性、丢失计数，以及不同架构上原子宽度与对齐的限制。缓冲区满时保持业务原有行为，不能为了等日志空间阻塞业务；丢失要可见。

首版针对选定信号完整记录关键事件。高频机制可在状态变化/处理目标请求时记录，配合有界快照；不能对唯一的失败、完成或状态清除事件任意抽样，然后声称能够证明事件没有发生。

### 6.8 捕获偶发不更新：保留出事前的窗口

这种问题可能不崩溃，不应只依赖异常处理。提供以下可复用的采集方式：

- 手工：用户发现目标未按约定更新后，执行真实可用的诊断快照/导出动作。
- 自动：按已确定的应用契约监测目标请求未完成、版本未推进或实际规则违例，发出诊断触发；只采集，不改变业务处理/复位策略。
- 时间窗口：保留触发前的关键事件，视容量保留少量触发后事件，再固定快照。各核单独报告是否收到快照请求和覆盖窗口；不宣称瞬间同时冻结。

先估算容量：`记录长度 × 目标事件峰值速率 × 所需保留时长`，加必要余量并实测。不能先写死“保存最近 10 秒”而不算事件量。

“导出”路线必须实际可用：现有文件/诊断命令/串口/共享区由主核取回等；受损 IPC 不能是唯一取证通道而不注明限制。若要求跨复位保存，确认内存/介质与启动覆盖；普通 RAM 或 noinit 不保证所有复位/掉电保留。

### 6.9 开关与范围

诊断包至少提供关闭、目标链路基础记录、指定机制深入记录三种配置，默认按目标信号限制范围。配置变化写入事件；不同核配置一致性可查询，避免一边开一边关。

检查不开启时的残留开销，以及开启后的最坏热路径耗时、CPU/栈/内存、队列延迟和调度影响。阈值依据产品约束，不能随意承诺“低于某百分比”。对比原包、诊断包关闭、诊断包开启三种可用状态；关闭仍有静态内存等差异，要如实记录。

## 7. 阶段五：编译出真正含双仓改动的诊断产品包

### 7.1 先编 EMAP，再证明产品消费它

沿当前产品真实依赖方式重编所需目标的 EMAP。诊断库进入独立本地包/版本或项目支持的依赖覆盖入口，再构建产品。不得覆盖公共发布包冒充同版本，也不让 artget 更新重新拉回旧库。

产品直接源码集成 EMAP 时，记录实际编译对象与链接即可；独立包方式则保留包摘要、构建来源和依赖解析结果。不能只因为 EMAP 仓有新的代码就认为产品获得了这些事件。

### 7.2 所有受影响核/域都需要核对

一个升级包可能包含多个镜像或不包含某个对端镜像，必须按实际打包清单确认。记录哪些域有产品插桩、哪些有 EMAP 插桩、哪些只能观察边界。主核升级成功不等于对端也更新。

为每个域生成可查询的诊断身份与事件表版本，尽量复用产品已有版本导出；启动或启用记录时写一次流头。最终核验应来自实际产物/运行报告，而不是只看源码中字符串。

### 7.3 包旁边必须带的配套资料

| 文件类别 | 必要内容 |
| --- | --- |
| 升级包 | 按原产品打包/校验/签名流程生成的实际产物；需要内部发布步骤则明确状态 |
| 构建清单 | 两仓基线和诊断差异、目标/工具链、依赖身份、各库/镜像/整包摘要 |
| 调试资料 | 与每个域精确匹配的 ELF/符号、链接 map、关键生成配置；不一定进入设备升级包 |
| 点位与事件字典 | point ID、代码基线、路径/符号、机制、事件布局与原因码 |
| BEH 资料 | 实际部署的图元模型/XML/生成映射的版本和摘要；非必需内容不重复打包 |
| 采集与解析工具 | 启用/查询/触发/导出方法、解码器、配置样例和结果说明 |
| 使用说明 | 安装目标、版本核验、复现步骤、输出位置、恢复原包/配置步骤 |

“编译成功”还不足以叫可升级包；必须完成现有发布格式与兼容性检查。若缺内部签名或不可访问的打包工具，明确“固件已构建、升级包尚未完成”，不绕过校验或假装就绪。

### 7.4 上板前需要的针对性验证

不为形式增加整套无关测试；针对插桩会引入的具体风险验证：

1. 查询真实编译/链接来源，证明两仓选定修改进入对应域的产物。
2. 正常路径下业务输入输出与原行为一致；诊断开启/关闭不改变返回与分支语义。
3. 记录器遇到并发/嵌套、满缓冲、部分记录、计数回绕/重启时，解析器能辨识有效数据和缺口。
4. 为实际发现的跳过、拒绝、延迟、合并和失败分支验证至少能留下对应原因；不为了覆盖不存在的机制造测试。
5. 用一份正常样例和一份有证据缺口/失败路径样例检验解析结果不会自动把缺日志判成业务未执行。

主机测试验证记录格式与解析器有用，但不能替代目标 RTOS 的并发/时序验证。需要受控故障或时序操控的测试与正常观察包分开，标明只用于指定测试环境，不悄悄混入日常复现包。

## 8. 阶段六：真实产品安装、正常样本与偶发复现

### 8.1 先核验到底运行了哪个包

用户按原升级流程安装诊断包后，读取每个相关核/域的固件和 EMAP 诊断身份、事件格式、启用配置、模型映射，确认与构建清单一致。再触发一次目标参数的正常修改，核对产品层与 EMAP 层事件确实出现。

某个域没有启动身份或关键事件时，先查升级覆盖、使能、记录导出和实际调用路径，不把它当作业务链路已经断了。

### 8.2 先拿一个“完整成功过程”

记录页面操作/真实请求、服务端接收与响应、各域事件、目标图元/算法消费及实际读回。网页可由人工操作或已有 Playwright 流程执行；浏览器 trace 作为外部操作证据，不代替板端记录。

保存初始配置、输入序列、产品运行模式、负载条件、观察端点、各域版本与采集配置。确认合法转换、合并、模式条件、应用周期和读回来源后，再判断偶发失败。

如果要求每次更新完整消费，逐请求核验；若契约允许合并，则核验最终有效版本，并为被替代请求保留合法终止/合并关系。不要人为串行化全部请求后宣称原并发问题已消失。

### 8.3 复现时保持可比较条件

先按原先容易出现问题的人工步骤/自动化脚本复现。记录请求序列、间隔、目标对象、并发来源及环境变化，输入在产品允许范围内。失败时优先导出现场，不通过再次修改同参数、自动重试或重启把证据覆盖。

采集触发应包含失败请求前后的窗口和成功对照；自动监控仅基于已知契约判定“超时/未应用”，没有足够证据时记录为疑似现象，不自动认定根因。

诊断开启后问题不再出现，不能直接说修好了；对比开启范围和开销，必要时缩小高频记录点或采用已有更低扰动入口，再继续观察。每次换包/配置形成独立测试批次。

### 8.4 单次复现证据包

```text
测试会话与版本清单
页面操作/请求和响应证据（必要字段，去除凭据）
各域原始 trace、事件流头、丢失/覆盖/冻结状态
部署模型/实例/端口映射与实际读回
诊断配置、正常对照、异常发生前后条件
解析结果、首次分叉候选、未闭合边界
```

不同核的本地时间戳没有同步证明时，保持局部顺序，用请求关系、消息版本、发布/消费关系建立因果；不要硬拼成毫秒精确的全局时间线。时钟对齐只作为有误差范围的辅助。

## 9. 阶段七：从“哪段没更新”追到“为什么没更新”

### 9.1 先检查记录是否足以支持推理

解析器先校验事件格式和固件/字典版本、各域身份、序号缺口、丢失/覆盖、部分提交、采集开关、目标过滤、对象复用和关联歧义。缺事件时至少区分：没执行、未插桩、被关闭/过滤、丢失、尚未导出。

记录本身缺失时给出缺口，不能把“不在日志里”自动变成“业务没有发生”。有效值快照与分支操作数来自不同时刻时，也要标注，不推导不存在的矛盾。

### 9.2 对同一更新构建事件关系

按真实请求/对象/版本配对，允许一对多、多对一和合法替代。逐阶段显示：期望的转换/动作、实际事件、实际条件、结果/原因、下一个可观察点。

输出“最后已证实正常的位置”和“首次有证据异常的位置”，同时列是否存在不可见区间。正常对照用于发现分叉，不能要求两次异步运行拥有完全相同的时间或事件顺序。

### 9.3 按分叉证据继续追机制

| 证据显示 | 下一步具体追什么 | 不能直接下什么结论 |
| --- | --- | --- |
| 服务端接收正确，未提交更新 | 校验、模式、相等判断、暂存/激活、实际决策操作数 | 不能先怪跨核传输 |
| 产品提交成功，EMAP 未发布 | 返回语义、路由/队列、合并、pending 修改者、发布条件 | 不能把“API 返回成功”当发布成功 |
| EMAP 已发布，对端没有消费证据 | 通知/轮询/任务进展、接收注册、队列状态及记录完整性 | 不能仅缺接收日志就认定消息丢失 |
| 读到的版本/数据不匹配 | 缓冲选择、生命周期、并发复用、转换布局、可见性契约 | 不能只凭不一致就认定缓存问题 |
| 对端业务已更新，图元输入未变化 | 点表/实例/端口、订阅、执行模式、采样周期、其他写入者 | 不能把任意 C++ 变量等同目标图元 |
| 图元已消费，观察仍显示旧值 | 算法条件/其他输入、结果覆盖、读回来源/刷新 | 不能把显示旧值等同链路未更新 |
| 更新曾生效，后来回退 | 所有已识别的目标写入者、恢复/默认值/旧请求/迟到回调 | 不能把末次旧值当从未更新 |

这张表用于确定下一步，不预设真实原因。发现新机制就补机制卡、查询与相应记录点，保留原基线和已取得证据。

### 9.4 明确区分五层结论

1. **现象：**在哪个观察位置、何时未看到预期变化。
2. **首次证据异常：**最早哪条可信记录不符合当前契约。
3. **局部机制原因：**哪个动作没有推进，以及由什么状态/条件导致。
4. **源头候选：**谁更早改变了该状态或破坏了前置约定；是否仍存在闭源/并发盲区。
5. **已证实根因：**有可检查的因果链，且受控验证/修复对照支持，反例与替代解释已得到处理。

“没有翻面”“队列没有消费”“更新标志被清了”可能只处于第 3 层；继续查谁、在处理哪次操作时、依据什么条件改变了状态。不能用最后一条日志自动指认责任方。

如果有了受损地址或可疑状态，下一阶段可以针对特定写入者、保护检查或硬件观察能力补证；当前不为一个改值问题默认全局开启堆保护或更换同步机制。

### 9.5 验证候选根因，再做修复

候选明确后，在可控测试环境安排能检验该因果假设的输入/时序，并记录预期会出现的违例。若使用延迟、钩子或故障注入，它们属于独立验证配置，要说明与原始现场的关系。

修复单独留变更，与同一观察手段和相近条件的未修复版本对照。一次未复现不能证明根因已解决；记录样本、覆盖模式和仍未覆盖的条件，不承诺彻底证明所有并发情况。

## 10. 各阶段完成标准与断点续接

| 阶段 | 交付 | 完成标准 |
| --- | --- | --- |
| 版本与目标 | 基线/包/核/模型映射 | 选定信号相关目标清楚，未核实处明确 |
| CodeQL 双仓分析 | 有效工具报告引用、本任务执行记录、实际查询、覆盖表、路径和模型清单 | 产品与 EMAP 的关键实现均被分析或明确标缺口；安装通过或读过工具报告不算本阶段完成 |
| 机制梳理 | 机制卡、状态读写者、契约 | 不只覆盖翻面；每个已识别关键机制有证据与观察计划 |
| 双仓插桩 | 代码改动、点位/事件字典、记录器 | 值、决策、状态变化与失败分支可关联；不改变业务语义 |

允许某个闭源节点只覆盖接口，但验收必须指出它影响哪种根因判断。不能为了说“全链路”删掉未知边；也不能因为一处未知就放弃其他已可部署的记录能力。

每次停下时写交接：当前两仓基线、目标信号、工具报告版本/摘要及环境/实例引用、数据库/查询版本、本次执行记录入口、构建产物身份、已插点位、实际测试、未完成项、最小下一步。环境或实例变化时按统一指南更新状态报告，检查受影响的任务证据，不能直接沿用过期通过状态。源码变化后更新点位映射；影响路径/机制的改动重新核对相关查询，不拿旧 CodeQL 结果解释新包。
