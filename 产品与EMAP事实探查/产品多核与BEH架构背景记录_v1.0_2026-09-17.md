# 产品多核与 BEH 架构背景记录

初稿：v1.0，2026-09-17｜当前修订：v1.2，2026-09-20（保留原文件名兼容链接）｜用途：供后续聊天、分析与设计直接引用，避免重复翻查历史。

## 1. 可直接用于下次会话的背景摘要

我们讨论的是公司能源控制器/工业控制产品中的 C++ 业务、多核通信和 BEH 图元。用户曾描述“主核 rtos llvm；实时核 a55 rtos lite RT”。这确认了用户提供过主核、实时核及 A55 等线索，但主核 CPU 型号、总核数、正式系统名称、启动方式和各模块所在核仍未核实。LLVM 是编译工具链线索，不能当作核型号。EROS 是用户在死机分析中使用的称呼，不能未经核对把它算成主核、实时核之外的第三个核。

当时梳理的业务信号链为：外部界面/协议输入 → 产品业务组件 → 跨核发送与接收 → 接收侧业务处理/换算 → 图元订阅与交接 → BEH 图元处理和输出。这是分析与验证的链路框架，不表示每段已经实测贯通，也不表示已经确认每个模块所在核。历史环境中，消息路由、核间传输、GOOSE/Modbus 驱动通过 artget 二进制依赖包提供，接收侧业务源码在产品仓可见。当前工作范围已扩展为产品源码加对应版本的 EMAP 源码；旧二进制依赖能否对应到所备 EMAP 源码，仍须逐项验证。

BEH 必须区分电脑侧 Java 引擎测试与连接真实产品的图形调试：前者已可自动注入、运行图元测试；后者由人工通过产品 IP 连接，查看实时 debug 值、打断点。不能将电脑侧测试通过等同于板端跨核链路通过，也不能把电脑上的 Java 引擎直接认定为板上实现。

用户明确说过的死机留档链路是：EROS 核异常现场 → 共享内存 → 主核写成文件。该信息只确认异常留档这一用途，不能据此断言全部业务核间通信均采用同一种共享内存方案。下次优先读取本记录，再补充新证据；不要把候选架构、仿真示例或助手建议改写成产品事实。

## 2. 名词与硬件/系统层

| 名称 | 历史内容 | 可以据此理解什么 | 尚未确认什么 |
| --- | --- | --- | --- |
| 主核 | 用户原话线索“rtos llvm” | 主核与 RTOS、LLVM 工具链相关 | CPU 型号、核数、正式系统名、启动和部署方式 |
| 实时核 | 用户原话线索“a55 rtos lite RT” | 用户明确提到 A55 和实时运行侧 | lite RT 的正式名称、数量、系统版本及实际产物 |
| EROS 核 | 异常现场先写共享内存，由主核落文件 | 有一条由主核协助保存异常现场的跨核关系 | 与“实时核”是否同一对象；EROS 是何种正式名称 |
| A7 | 先前 Renode 调查中的候选架构线索 | 曾研究过相应仿真能力 | 没有足够依据确认它是产品主核 |
| M3/M5 | 本次用户回忆中的不确定名称 | 是检索线索 | 未找到可确认的产品型号表述 |
| M33/R5 等 | 历史检索返回的 Renode 示例相关名称 | 只用于理解仿真/AMP 示例 | 不属于已确认的产品核组合；不同检索摘要对示例组合有出入，不能据此定型 |

历史中用户还曾要求暂不假设“异构核”，只确定“多核”。因此本记录不把异构、AMP、SMP、多芯片或单芯片多核中的任一种写成已核实的部署结论。“主核+实时核”是目前可复述的角色描述，不等于确认产品恰好只有两个物理核。

## 3. 产品业务信号怎样流动

专业表述：外部输入经协议/配置转换和产品业务组件处理，在跨核边界通过发送、传输、接收交给另一侧业务，再经过处理或换算，进入图元订阅/交接和图元内部节点，最后形成结果。该顺序来自历史讨论的目标整链，应在分析具体信号时按实际代码与配置核对。

大白话：从外面改一个值，产品先接住它并处理，再把需要交给另一侧的数据传过去，另一侧继续处理，最后让对应图元使用这个值。我们要解释的不只是“值变了”，还包括从哪里进来、经过谁、哪里换算、跨核前后是否一致、最后哪个图元端口收到了它。

| 环节 | 已有背景 | 不能省略的边界 |
| --- | --- | --- |
| 外部入口 | 讨论过 Web 界面/北向协议输入 | 不同入口可走不同路径，不能假定所有输入共用同一链路 |
| 产品业务组件 | C++ 业务与配置/协议处理参与信号传递 | 尚无完整的“组件—核”分配表 |
| 消息路由与核间传输 | 历史通过 artget 提供二进制依赖；本轮准备匹配的 EMAP 源码 | 按依赖清单、版本、构建和部署证据确认映射；不把下载到的源码都算作已使用 |
| 接收侧业务 | 本仓源码可见，可追接收后的处理 | 具体回调、结构体、单位换算和消息字段需按具体信号定位 |
| 图元交接/订阅 | 历史方案明确要追到这一层 | C++ 对象/字段与图元实例/端口的对应尚未完整核实 |
| 图元内部与输出 | 已有 BEH 引擎自动测试基础 | 独立图元测试不证明真实产品的外部输入和跨核边界正确 |

不能把表格前半段自动归给主核、后半段自动归给实时核。也不能将消息路由、核间传输、GOOSE、Modbus 理解为所有信号必然依次经过的四个串联模块。

## 4. 依赖和源码的可见范围

历史讨论明确涉及以下二进制依赖：GOOSE/Modbus 驱动、消息路由、核间传输。它们通过 artget 下载。接收侧 C++ 业务代码在产品仓可见。

“只能修改产品业务源码”属于先前条件，**不再是本轮的工作边界**。用户于 2026-09-20 反馈已在 WSL 完成产品及对应 EMAP 首轮成熟工具探查，允许从两层设计记录、保护检查和诊断改动；本会话未直接取得其本地报告和源码，后续执行 AI 应承接核对，不能将未收录误写成用户未完成。

| 当前层级 | 允许推进的工作 | 必须另核对的条件 |
| --- | --- | --- |
| 产品代码 | 架构摸底、参数链路、调度、边界记录、诊断改动 | 源码版本、实际配置、原构建入口与上板包一致 |
| EMAP 代码 | 继续追组件内部和间接依赖；在可控位置加诊断 | 对应源码是否真正生成产品所用依赖，能否构建及被产品包采用 |
| 更深的第三方/开源/固件 | 有界查找可见源码、接口、符号和前后边界证据 | 可见、可构建、可替换、允许修改分别登记；本轮不默认允许修改 |
| 缺源码或无重编条件的边界 | 记录已知输入输出、时序、契约及最小协作需求 | 不能将“本机没找到”写成底层终点，也不能杜撰内部根因 |

EMAP 约 90 GB 不意味着全量阅读或建库。从具体产品配置、专家提供的调度候选及 output 依赖入手，区分声明、下载、链接、部署、运行证据，按真实依赖向外展开。专家清单是种子，不能变成拒绝新增关联仓的白名单。详细执行见[调度联合探查方案](调度相关产品与EMAP代码联合探查方案_v1.0_2026-09-18.md)。

先前“不上板”方案使用现有依赖包，是原方案的条件；当前需要改 EMAP 时必须补上重编、替换、封包和部署身份验证。CodeQL 只能帮助分析所提取范围；跨核/跨进程和二进制边界须结合协议、配置和运行证据。

## 5. BEH 的两种运行方式与产品的关系

| 方式 | 运行对象 | 历史进展 | 能回答的问题 |
| --- | --- | --- | --- |
| 电脑侧 BEH 引擎测试 | Windows 上的 Java 引擎、图元模型与测试输入 | 已可自动注入并运行测试；此前未连接真实产品 | 给图元这些输入时，运行结果是什么 |
| BEH 图形工具连接产品 | 经产品 IP 连接真实设备，查看运行中的图元 | 人工可连接、查看 debug 值和打断点；自动连接/采集尚未实现 | 界面显示及调试位置；要证明产品执行值须核实时刻、绑定和 Debug 影响 |

两者围绕相同业务逻辑提供不同证据，但并不自动具有完全相同的执行环境、数据入口和跨核行为。BEH 工具在电脑上使用 Java，不能推导出产品某个核也运行同一套 Java 引擎。

后续 AI 测试、AI 解释和 AI 开发所做的，是利用这些已有入口补齐观察和验证；这些工作台/自动化设计不等于产品硬件本身的架构。

## 6. 外围输入与测试环境的补充背景

- Web 入口：可用 Playwright 模拟人工初始化/设置，并结合导出日志解析；全链路自动化是建设方向，不能概括为已经全部贯通。
- 北向 485：用户使用专用仪表工具，涉及 10/06/03 指令；不能擅自改说成 Python 北向工具。
- 南向设备：讨论过 Python 模拟设备，与北向专用仪表工具是不同对象。
- 产品编译/分析环境：WSL+产品镜像，或配套产品环境的远程 Linux 执行机。Windows 侧继续使用 BEH 图形工具/Java 引擎。
- DT：x86 Linux 测试环境与真实产品存在架构/对齐差异，不能因在 WSL 运行就认为已经等同板端。

## 7. 异常留档架构与已有资料

用户在 2026-09-07 描述：EROS 核发生异常后，把现场写入共享内存，由主核进一步写成文件。留档涉及寄存器 R0/PC/SP 等、停机地址、调用栈、异常类型、任务和内存分配信息；还提到 ASM、emap 等资料。

当时的限制包括：回溯只看到约 10 层，emap 没有可用于手动扫描的原始栈内存。C++ 异常展开是否是回溯不足的原因，不在本记录中认定为已证实结论。monitor/慢速任务只是当时的候选线索，不等于故障根因。

这一关系不能变成“实时核、EROS 核和主核三个核”的图，也不能变成“所有业务通信都用共享内存”的结论。

## 8. 尚缺的准确对应关系

| 待补项 | 为什么影响架构描述 | 可用于补齐的产品证据 |
| --- | --- | --- |
| 实际芯片、核数、核型号 | 决定真实硬件组合 | 产品硬件说明、板级配置 |
| 主核与实时核的正式系统名、运行方式 | 决定启动和调度关系 | 构建配置、启动记录 |
| EROS 与实时核的关系 | 避免重复计数或错误命名 | 项目命名、产物和运行配置 |
| 各核运行的最终固件/可执行产物 | 建立“角色—程序—核”的映射 | 构建产物、链接信息、部署记录 |
| Web/协议/路由/接收业务/图元分别部署在哪 | 形成真实组件部署图 | 模块配置、代码入口、运行日志 |
| 业务跨核的数据与通知机制 | 不再只看到发送端和接收端 | IPC 接口、结构体、通知与同步配置 |
| C++ 字段到 BEH 实例/端口的映射 | 解释值如何真正进入图元 | XML/配置、订阅代码、debug 值或运行日志 |

这是历史讨论尚未补齐的项目，不是要求用户现在重新说明一遍。后续只需追加真正的新证据，不应为维持会话连续性反复检索相同背景。

网页参数偶发未生效使用[全链路与机制诊断指南](产品与EMAP_CodeQL全链路追踪与机制诊断_上板实施指南_v1.0_2026-09-17.md)；崩溃、复位、内存破坏使用[根因定位专项](../问题定位与修复/跨核崩溃复位与内存破坏_根因定位实施指南.md)。翻面只是待查机制之一，不能先认定它是根因。
