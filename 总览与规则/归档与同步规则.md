# 归档与同步规则

更新日期：2026-09-20。

## 正式内容与入口

根目录 README 是统一入口，模块 README 负责分派。正式内容在模块目录维护，代码包按自身结构展开。共有资料只维护一处主位置，其他模块用链接关联。模块名称继续不编号。

工具盘点、安装、存放、接入、调用和验收统一依据 [工具统一管理与使用指南](../工具接入与共享能力/工具统一管理与使用指南.md)，当前环境结论引用 [工具状态与验收报告](../工具接入与共享能力/工具状态与验收报告.md)。任务文档只维护任务目标、输入、证据和验收要求，不再复制一套工具操作规范。报告为待盘点、过期或受阻时如实继承；有安装记录不等于本次任务已实际使用。

已有资料先比较版本、适用范围和具体内容；只对字节完全相同的副本直接合并。不同任务模式、不同运行环境或不同验收策略分别保留并标明用途。历史文件名中的“最新”不赋予当前优先级。

## 历史与交付

- `历史资料/`：旧方案、原入口与原整理记录；不作为默认执行规则。
- `交付包/当前版本/`：唯一当前完整展开版；当前交付名称见交付包 README。
- `交付包/专项包/`：满足依赖完整性要求的专项交付副本；不能默认每个任务目录都能独立打包。
- `交付包/历史版本/`：旧总包与 Git 备份；保留来源和恢复能力。

原始实测证据留在相关模块，内容不因整理而改写。证据包中历史 PASS 只表示原来声明的测试范围，本轮归档校验不重新认证产品功能。

## 修改和打包

1. 修改正式目录，记录适用版本与变更原因。
2. 更新 `总览与规则/工作区文件清单.json` 的现行摘要；保留来源表中的输入摘要，不能把来源摘要改成新内容摘要。
3. 执行 `python tools/verify_workspace.py` 检查文件、链接和 ZIP 可读性，检查结果另存，不覆盖原运行证据。
4. 先核对任务入口引用的依赖。专项包必须包括共享工具指南、状态报告、所引用环境指南、脚本、配置、模板和图解资产等全部必要本地依赖，并保留其在工作区中的完整相对目录关系；继续检查这些文件的依赖，直到离线可用。不能直接将任务子目录孤立压成 ZIP。不能满足时明确该任务只支持完整工作区，不发布缺依赖的专项包。交付副本中的共享文件只从唯一正式源生成，不独立编辑。
5. 整包保留 `交付包/README.md`。下载后的展开版不携带旧整包和重复专项 ZIP；原包列表只作说明，不设指向这些缺失文件的可点击链接。
6. 完整展开包包含正式资料、工具源码、必要历史资料、已有实测证据及指南配套图解，排除交付包目录下的 ZIP、缓存和临时运行目录，避免包套包。示意图需要注明是目标例子还是已核验现状，不能把部署示意当成用户电脑的真实布局。
   每次完整交付还须按下文“交付快照差异与本地合并”生成基线说明、变更列表和文本差异；保存在正式工作区中并随 ZIP 一起交付。未取得 GitHub 基线时明确降级为交付快照比较或记录受阻，不能省略状态说明。
7. 新包发布前在临时目录解压，核对根入口、任务入口、共享依赖和图解的本地链接，并检查清单、ZIP 可读性及文件内容一致性。图解若内嵌为 Mermaid，应保持源码随文档完整交付；静态图应连同原始可维护文件一起入包。只检查压缩包能够打开不等于依赖完整。
8. 新整包通过核验后，将前一完整包归入历史版本，当前版本目录只保留一个完整包；更新交付说明、索引和核验记录。旧包保留原内容，不在旧包中回写新结论。

普通文件整理不自动触发公司代码编译、安装工具、上板或远程推送。已有授权的后续实际任务按相应任务入口执行。

## Git 与同步

当前采用固定交付流程：**本聊天维护正式工作区并更新完整 ZIP → 用户下载 → 用户电脑上的本地 Codex 对比既有 Git 仓库 → 按本地任务授权提交并更新 GitHub。** 本聊天不直接尝试远程推送，交付完成也不以远程推送为条件。

本地 Codex 接续时先读取实际仓库路径、当前分支、工作树状态、remote 配置和相关提交，记录真实值；本文件不预设仓库 URL、分支名或已上传状态。将 ZIP 解到单独暂存目录，与既有仓库逐项比较后合并需要的变更。未出现在 ZIP 中的文件不自动视为应删除；本地未提交修改、额外资料、配置和 Git 历史不得被整目录覆盖。重名内容有分歧时保留双方版本并说明差异。

对来源表、迁移记录或交付说明明确标出的移动、替换和退役项，先核对旧摘要与本地内容：未改动的按记录迁移归档并更新入口；有本地改动的合并或保留差异后再处理。单凭 ZIP 缺项不推断删除，但也不能只增不减，留下第二个默认工具规范或任务入口。

沿用既有仓库历史，不在解压目录另造一套历史去替换远程，不通过硬重置分支、强制推送或抹掉本地修改来完成同步。若远程已有新提交，按既有协作流程合并或变基并处理冲突。最终记录导入包的名称及 SHA-256、实际提交、推送结果和剩余差异；尚未执行时写“待本地接续”，不能声称已同步。保留旧 Git 备份仅用于来源追溯和必要恢复。

## 交付快照差异与本地合并

从本约定起，完整 ZIP 与交付差异说明一起提供；正式文件仍在工作区展开维护。本节是唯一规则，交付包 README 只链接这里。更新规则本身不等于已经生成新 ZIP、读取远程仓库或完成同步。

### 1. 两份差异共用一个明确基线

| 对象 | 定义 | 谁提供或核对 |
| --- | --- | --- |
| B：比较基线 | 本次约定的 GitHub 仓库、分支在指定时刻的完整 commit SHA，以及该提交中工作区子目录的内容 | 可读取远程时直接取得；否则由本地 AI 导出对应提交的快照和身份记录 |
| N：本次交付快照 | 本聊天维护并交付的正式工作区内容，记录交付 ID、范围和文件摘要 | 本聊天提供完整 ZIP 与 B→N 的差异参考 |
| L：电脑本地状态 | 同一工作区范围的实际文件，包括本地额外提交、暂存/未暂存修改，以及范围内新增的未跟踪文件 | 用户电脑上的本地 AI 比较 B→L，保留本地事实和改动 |

“GitHub 最新”在基线获取时冻结成具体 SHA 和获取时刻，不是以后自动变化的分支标签。commit SHA 只说明身份，不能代替对应文件；仅有文件名、截图、提交信息或哈希清单时，不能生成完整的文本差异。上次交付 ZIP 也不能未经核对就当成 GitHub 当前提交。

首次建立 B 时记录仓库来源、分支、完整 SHA、仓内工作区相对路径及获取方式。不要要求用户先在电脑上删除自己的修改；可以从 Git 对象导出指定提交，另存工作树状态。无法取得 B 时，仍可交付新 ZIP，并将比较明确标为“上一交付快照 P→本次交付 N”或“GitHub 基线待提供”；列明缺口，不冒称已完成 B→N。

### 2. 每次随包提供的差异资料

在正式目录 `总览与规则/交付差异/<交付ID>/` 展开保存，ZIP 携带同一份文件：

| 文件 | 内容 |
| --- | --- |
| `基线与范围.json` | 比较类型、B 的来源/提交/子目录、N 的交付 ID、生成时间、纳入与排除规则、双方文件路径/类型/大小/SHA-256 清单；状态区分完整、部分、待基线 |
| `变更清单.csv` | 新增、修改、缺失、确认删除、确认移动/改名或候选移动；列旧/新路径、旧/新摘要、文本/二进制、变更原因及处理提示 |
| `文本差异.diff` | 从 B 到 N 的标准逐行差异，包含文本新增及删除内容；使用 Git 等成熟工具生成，保留实际命令与结果，不能只让 AI 凭记忆写变化 |
| `变更说明.md` | 人能读懂的列表：哪里变了、为什么变、影响什么、需本地重点合并哪些文件，以及比较范围、未比较内容和证据入口 |

差异基于解压后的文件内容，不能比较 ZIP 的二进制差异或只凭修改时间。图片、压缩包等二进制记录旧/新摘要和大小，不伪造逐行差异。文本编码或换行变化照实记录，不默认忽略空白掩盖变更。涉及文件模式、可执行位或符号链接时也记录；ZIP 无法完整表达的 Git 元信息须单列。

双方使用相同的范围规则，明确工作区子目录。排除 `.git/`、交付 ZIP、缓存和本次生成的差异目录等递归项；不要把整个“总览与规则”排除掉。文件清单、索引等生成资料单列为元数据变化，业务文档与脚本变化另列，避免清单更新淹没真正改动。未知或部分范围不能写成“零差异”。

`文本差异.diff` 是审阅参考，不代表可直接整包覆盖或自动套用。移动/改名需内容与来源记录支持；相似度推测只标候选。尤其是 GitHub 已有、资料库未承接的产品事实或本地新增资料：N 中没有只能先标“本次快照缺失”，不能自动当成删除意图。确认删除必须有范围内的明确变更记录和理由；本地内容已变时仍需合并复核。

### 3. 本地接续：先保存状态，再做三方比较

1. 把新 ZIP 解到独立暂存目录，记录 ZIP SHA-256；保留 L 的原始状态，包括已有本地提交及未跟踪资料，不能先用新包覆盖本地。
2. 读取交付记录中的 B，核对确实是同一提交、仓内目录和比较范围。若只收到 P→N，先找到 P 与本地 Git 历史的对应关系；不能直接套用 B→N 的结论。
3. 本地 AI 生成 B→L，覆盖本地额外提交、暂存、未暂存和相关未跟踪文件；仅执行默认 `git diff` 不代表覆盖了这些全部变化。无需用户再手写第二份清单。
4. 使用 B、N、L 三方核对：只有 N 改的按交付意图合入；只有 L 改的保留；两边都改、删除/修改、移动/修改或新增同名文件的，逐项合并并复核。文本无冲突不代表业务事实无冲突，仍须核对产品版本、核/域和证据适用范围。
5. 如果 GitHub 在 B 之后出现新提交，单独取得远程变化并纳入合并。不能把最新远程状态悄悄替换成 B，也不能据此丢弃 L。无法自动判断的项目保留双方内容和待处理状态。
6. 完成文件、链接和入口核验，审阅最终差异，再依本地已有授权提交与推送。本聊天继续负责 ZIP 及差异参考，不直接尝试推送。

两份差异是对照资料，不保证新 ZIP 已经吸收远程与本地新增事实。如果 N 的编辑起点早于 B，应另外核对上一交付到 N 的实际维护变化，区分“本次主动修改”和“尚未同步回来的内容”；以此决定合并，不能把机械差异全部解释为应执行的修改。

### 4. 同步回执与下一次基线

本地同步后保存回执：本次交付 ID 与 ZIP 摘要、实际使用的 B、合并前本地/远程提交、合并后提交、推送结果、保留的本地资料和剩余冲突。推送失败或未执行时照实记录。

下一次若以同步后的 GitHub 为基线，需要取得该提交的身份和对应工作区快照，或能直接读取该提交内容；本聊天不能仅凭“已推送”三个字更新基线。回执与快照可由本地 AI 一次导出后交回，避免用户手工逐文件说明。GitHub 中新增的产品事实仍由其实际证据与适用版本决定，不能被资料库中的旧说明覆盖。
