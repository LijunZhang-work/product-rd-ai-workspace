# 术语、事实源与信任边界

## 1. 权威术语

### Original JAR

BEH 原始可执行 JAR。其在明确版本、资源、配置与输入下的可复现结果，可直接证明该工具实际表现，包括可能的缺陷；不自动证明业务正确或板端某次执行值。在线 GUI、Headless/POU 引擎和板端采集各自核实通道与适用范围，详见[证据矩阵](02A_按事实域划分的证据可信度矩阵_v1.0.md)及[BEH 已知问题](../../工具接入与共享能力/BEH原生能力/BEH已知问题与观测适用边界.md)。

注意：JRE 是运行环境，不等于业务事实源本身。

### Recovered Java Reference

通过 CFR、Vineflower 等反编译器得到的参考 Java 代码。用于理解、定位和设计 Bridge，不等于原始源码。

### Bytecode Evidence

直接来自 `.class` / JAR 字节码的证据，例如 `javap -c -v`、ASM 类结构和调用指令。用于在关键问题上交叉验证反编译结果。

### Headless Full Scene

不实例化 JCanvas、不启动 GUI，通过原始 JRE + JAR 加载 POU 并生成完整场景。

### NativeSceneBundle

Headless Service 输出的原生场景包，至少包含 `scene.svg / scene.json / hit-map.json / properties / diagnostics`。

### Workbench

本地 Web 工作台。负责查看、圈选、标注、导出任务、显示结果和联动，不负责定义 BEH 语义。

### Analysis Task

Web 根据用户选择和意图生成的结构化分析任务。

### External Skill

运行在 DeepSeek Harness 或兼容环境中的分析能力。初期由人触发；后期通过 Adapter 自动触发。

### Analysis Result

Skill 输出的结构化结果。Web 右侧只显示该结果，不表示 Web 直接调用 AI。

### Proposal

AI 提出但尚未提交到正式工程的图元操作或代码补丁。

### Fact Domain

某个结论实际要证明的事实类别。项目不使用“一条全局排行榜”处理所有事实，必须先识别 Fact Domain。

### Evidence Class

证据的产生方式，统一分为：

```text
RAW_SOURCE
DETERMINISTIC_DERIVED
STATIC_INFERENCE
HEURISTIC
MODEL_INFERENCE
```

## 2. 事实源原则：不再使用单一全局层级

以前容易产生误解的写法是：

```text
原始 JAR > Scene > XML/代码仓 > 工具 > AI
```

这只能表达“直接事实通常优于模型推理”的总原则，不能处理所有具体问题。

正确规则是：

```text
先确定 Claim
↓
识别 Fact Domain
↓
在该域内部排序
```

权威细则见：

[按事实域划分的证据可信度矩阵](02A_按事实域划分的证据可信度矩阵_v1.0.md)

主要事实域：

```text
A. BEH 解析、模型、图形与自身行为事实
B. C/C++ 代码与构建语义事实
C. BEH 图元 ↔ C/C++ 代码绑定事实
D. 用户圈选、标注与手绘意图
E. Web / Workbench 运行与交互事实
F. 产品执行与观测通道
G. 业务应有行为与测试预期
```

任何域中，AI 推理都不得覆盖更直接、可复现、版本一致的原始或确定性派生证据。

## 3. CFR 信任边界

CFR 可以帮助恢复：

- 类、方法、字段；
- 控制流；
- 调用关系；
- 常量和大部分普通逻辑。

CFR 不能保证恢复：

- 原始注释；
- 原变量名；
- 原源码结构；
- 编译前语法；
- 混淆前语义；
- 所有异常控制流的原貌。

因此：

```text
原始 JAR 实际行为
= BEH 运行事实

class 字节码 / javap / ASM
= class 直接证据

CFR 输出
= Recovered Java Reference，仅供阅读与定位
```

发生关键冲突时，不得用 CFR 覆盖原始 JAR 的实际行为。

---

## 4. BEH 私有 XML 与 IEC 语义

BEH XML 以私有格式处理。IEC 61131-3 可提供：

- Function Block；
- 输入/输出；
- FBD；
- 变量；
- 控制逻辑；

等语义参照，但不得推断 BEH 私有标签一定等价于某个标准标签。

真实 XML 可以证明“输入里实际写了什么”，但最终 BEH 如何解释仍应由原始 JAR 的可复现行为确认。

## 5. Scene 与 Web 交互边界

Headless 负责：

- Node / Port / Relation 身份；
- 显示文本；
- 几何；
- Relation 路径；
- 箭头；
- 属性。

Web 负责：

- 点击；
- 矩形、椭圆、Lasso；
- 手绘；
- 标注；
- 分析高亮；
- Proposal 展示。

Web Hit Test 根据 `hit-map` 实现，不依赖 JCanvas。

Web 不得重新推导正式 BEH Relation、Port、Arrow 或 Display Text。

---

## 6. C/C++ 代码分析信任等级

C/C++ 代码事实首先由：

```text
当前真实代码仓源码
+
与当前分析一致的 Build Profile / compile_commands / 宏 / include / target
```

确定上下文。

在此基础上：

### HIGH

来自 `compile_commands.json + Clang/clangd` 的确定义、引用、类型和调用信息，并能回溯到真实源码与构建 Profile。

### MEDIUM

来自 Tree-sitter、确定性生成映射、唯一名称匹配或有限静态推导。

### LOW

来自启发式名称、模糊匹配或缺少完整构建上下文的推导。

### UNKNOWN

缺少必要编译参数、宏环境、动态调用、别名信息或运行时证据。

UI 和结果包必须显示等级。

更细的域内排序见 `02A_按事实域划分的证据可信度矩阵`。

## 7. Scene-Code Binding 信任类型

图元与 C/C++ 的绑定必须记录证据类型：

```text
DIRECT_NATIVE_BINDING
GENERATED_MAP
EXACT_SYMBOL
UNIQUE_REFERENCE_PATH
DATA_FLOW_INFERENCE
HEURISTIC_MATCH
AI_HYPOTHESIS
```

不得仅凭名称相同就自动升级为 VERIFIED。

---

## 8. 圈选、标注与自由手绘

- 矩形、椭圆、Lasso 的稳定几何命中结果是“用户选中了哪些对象”的确定性事实。
- 结构化箭头、框、连接线和文字是用户明确操作，可作为结构化 Intent。
- 自由笔笔迹本身只是原始向量数据；除非用户文字说明或视觉模型证据确认，不得赋予明确语义。
- 文本模型不得把未解释的自由笔自动当成正式 Relation 或开发指令。

---

## 9. 版本一致性

比较两份证据前，应尽可能确认：

```text
JAR_SHA256
XML_SHA256
Repo Commit / Workspace State
Build Profile
compile_commands Hash
Exporter Version
Render Profile
```

如果关键版本不一致：

```text
VERSION_MISMATCH
```

不能直接用一份证据覆盖另一份。

---

## 10. 冲突状态

允许明确存在：

```text
FACT
INFERENCE
HYPOTHESIS
UNKNOWN
CONFLICT
VERSION_MISMATCH
```

项目宁可保留 UNKNOWN / CONFLICT，也不得为了输出完整而硬凑出一个确定答案。
