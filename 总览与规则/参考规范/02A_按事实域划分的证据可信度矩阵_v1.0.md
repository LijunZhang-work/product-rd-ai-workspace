# 按事实域划分的证据可信度矩阵

## 1. 文档目的

本项目禁止使用一条简单的“全局可信度排行榜”处理所有问题。

原因是不同事实源回答的问题不同。例如：

- BEH 原始 JAR 最适合证明“BEH 实际如何解析、建模和渲染”；
- 当前真实 C/C++ 代码仓最适合证明“某个函数或变量实际写了什么”；
- 用户在 Web 中完成的圈选几何最适合证明“用户明确选中了哪些对象”；
- CFR 反编译 Java 适合帮助理解 JAR 内部实现，但不是原始源码，也不是运行事实。

因此，任何开发、调试、AI 分析或证据冲突处理，必须先回答：

> **当前究竟在证明哪一类事实？**

然后进入对应事实域，再按该域内部的证据优先级处理。

---

## 2. 总规则：先判断事实域，再判断证据等级

固定流程：

```text
提出一个结论 / 发生证据冲突
↓
明确 Claim：到底要证明什么
↓
识别 Fact Domain（事实域）
↓
选择该事实域的权威事实源
↓
检查版本 / Hash / 构建 Profile / 输入是否一致
↓
比较证据的直接性、确定性和可复现性
↓
得到 FACT / INFERENCE / UNKNOWN
```

禁止：

```text
看到“Original JAR 是最高事实源”
↓
就认为它对所有 C/C++ 代码事实也拥有最高优先级
```

事实源的权威性必须与它所回答的问题匹配。

---

# 3. 事实域 A：BEH 解析、模型、图形与自身行为事实

适用问题：

- POU XML 实际被 BEH 解析成什么对象；
- Node / Port / Relation 的真实身份；
- Display Text；
- Relation source / target；
- Relation path；
- Arrow direction；
- Geometry；
- 原生 SVG / Scene；
- 原生属性；
- BEH 保存或生成结果。

## A1. 域内优先级

```text
A0  原始 BEH JAR 在指定原始运行环境中的实际行为
>
A1  同一原始 JAR 生成的 Headless Native Model / NativeSceneBundle
>
A2  当前真实 BEH XML、原始资源文件和明确配置
>
A3  JVM 字节码直接证据（javap / ASM / class metadata 等）
>
A4  CFR / Vineflower 等反编译 Java 参考代码
>
A5  AI 对上述材料的推理
>
A6  未验证假设
```

### A0：原始 JAR 实际行为

这是证明该版本 BEH 在该条件下实际怎样表现的直接证据，适用范围限于所观察的工具行为，包括其可能存在的缺陷。它不自动证明业务语义正确，也不自动证明 GUI 数值就是产品早先某次执行使用的值；产品执行与业务预期分别按下述 F/G 域判断。

注意：

- **JRE 是运行环境，不是业务语义事实本身。**
- 更准确的表述是：`原始 BEH JAR + 对应原始资源/配置/输入，在指定运行环境中的实际行为`。

### A1：Headless Native Model / Scene

如果由原始 JAR 本身生成，并且版本、Hash、输入、Render Profile 明确，则属于该工具模型/场景的原生派生证据；仍需核对导出正确性及适用范围。GUI 与 Headless 共享同一实现时不能算两套独立正确性证明，已知缺陷及复用的 Debug 通道需单独评估。

它不能被 Web 自己重新计算出的 Relation / Port / Arrow 覆盖。

### A2：真实 XML / 原始资源

它证明“输入中实际写了什么”，但不一定能单独证明“BEH 最终如何解释”。

例如 XML 中一个引用方向，不应仅凭字段方向直接推断最终 UI 箭头方向；如果原始 JAR 的实际行为给出明确结果，以 JAR 行为为准。

### A3：字节码直接证据

`javap -c -v`、ASM 等用于验证：

- 方法真实存在；
- 字段真实存在；
- 调用指令；
- 常量；
- 类型；
- class 结构。

它比反编译器重新构造的 Java 语法更接近 class 文件事实。

### A4：CFR 等反编译 Java

用途：

- 快速阅读；
- 找类、方法和字段；
- 理解控制流；
- 设计 Native Bridge；
- 定位需要进一步验证的代码路径。

禁止把它称为：

```text
原始 Java 源码
```

发生冲突时：

```text
原始 JAR 行为 > 字节码直接证据 > CFR 重建的 Java 表达
```

# 4. 事实域 B：C/C++ 代码与构建语义事实

适用问题：

- 某个 C/C++ 文件实际写了什么；
- 函数/变量在哪里定义；
- 类型是什么；
- 某个调用是否真实存在；
- 指定 Build Profile 下宏如何展开；
- include 环境；
- 参数/返回值；
- 编译单元语义。

## B1. 域内优先级

```text
B0  当前真实代码仓中、与目标 Commit/工作区一致的 C/C++ 原始源码
+
     与该结论相关的真实 Build Profile / compile_commands / 宏 / include / 目标平台
>
B1  Clang / clangd 基于上述真实编译参数得到的确定性语义结果
>
B2  编译器/链接器生成物、符号表、明确生成映射等直接派生证据
>
B3  Tree-sitter 等结构语法解析
>
B4  ripgrep / 精确文本搜索 / 唯一名称匹配
>
B5  有限 Call Graph / Def-Use / 静态数据流推导
>
B6  AI 推理
>
B7  未验证假设
```

## B2. 必须同时记录“源码版本 + 构建上下文”

C/C++ 源码本身并不足以证明所有编译语义。

例如：

```text
#ifdef PRODUCT_A
...
#else
...
#endif
```

必须知道：

- 当前 Commit / 工作区状态；
- Build Profile；
- compile_commands；
- 宏定义；
- include path；
- target platform。

缺少关键构建上下文时，不能把相关结论标成 HIGH / VERIFIED。

## B3. Clang/clangd 与源码冲突怎么办

如果源码明确存在，但 clangd 返回异常：

```text
先检查 compile_commands / 宏 / include / target 是否正确
```

不能直接得出“源码不存在”或“代码错误”的结论。

工具输出必须能回溯：

```text
file + range + symbol + build_profile + evidence_type
```

# 5. 事实域 C：BEH 图元 ↔ C/C++ 代码绑定事实

适用问题：

- 某个 Node 对应哪个变量；
- 某个图元对应哪个函数；
- 某个 Relation 的值进入了哪段 C/C++；
- 图上的输入/输出如何与代码仓数据流关联。

这是跨域事实，不能仅凭“图名和变量同名”就判定真实绑定。

## C1. 域内优先级

```text
C0  DIRECT_NATIVE_BINDING
    BEH 原生模型 / 原生元数据明确给出绑定
>
C1  GENERATED_MAP
    原生生成物、官方生成映射、确定性生成链明确给出
>
C2  EXACT_SYMBOL
    类型/作用域/编译上下文一致的精确符号绑定
>
C3  UNIQUE_REFERENCE_PATH
    通过唯一引用链证明
>
C4  DATA_FLOW_INFERENCE
    静态数据流 / 参数 / 返回值 / 调用路径推导
>
C5  HEURISTIC_MATCH
    名称相似、字符串、附近关系等启发式候选
>
C6  AI_HYPOTHESIS
    AI 假设
```

每个 Binding 必须保存：

```text
binding_type
source_native_id
code_ref
build_profile
evidence_refs
confidence
status
```

C5/C6 不得自动升级为 VERIFIED。

# 6. 事实域 D：用户圈选、标注与手绘意图

适用问题：

- 用户明确圈中了哪些 Node / Relation；
- 用户画了什么结构化箭头；
- 用户写了什么文字；
- 自由笔到底意味着什么。

## D1. 域内优先级

```text
D0  用户明确输入的文字指令
     + Web 记录的明确结构化操作
>
D1  Web 根据稳定 hit-map 对矩形/椭圆/Lasso 进行的确定性几何命中结果
>
D2  结构化 Annotation（箭头、框、连接线、文字）的对象与坐标记录
>
D3  自由笔原始向量轨迹本身
>
D4  视觉模型对自由草图的解释
>
D5  文本模型对未说明自由笔语义的推测
```

### 重要区别

`Lasso` 是自由形状的**选择工具**，只要命中算法确定，就可以确定“选中了谁”。

`Freehand` 是自由笔**表达工具**，如果没有文字或视觉证据，只能确定“用户在这里画了这些笔迹”，不能自动确定其语义。

禁止把：

```text
用户在某处随手画了一条线
```

自动解释成：

```text
用户要求新增一条正式 Relation
```

# 7. 事实域 E：Web / Workbench 运行与交互事实

适用问题：

- 页面是否真正加载；
- SVG 是否实际存在；
- 按钮是否真的可点击；
- 圈选后选中对象是否正确；
- 面板折叠是否生效；
- 分析结果是否能联动画布与代码。

## E1. 域内优先级

```text
E0  实际运行页面中的可复现行为
>
E1  Playwright 对真实页面的 DOM / SVG / Event / State 验证
>
E2  浏览器 Console / Network / Runtime 日志
>
E3  Unit / Component / Contract Test
>
E4  build / typecheck
>
E5  AI 依据代码推测“应该能工作”
```

因此：

```text
build PASS ≠ UI 功能完成
```

涉及 Web 的阶段必须有 Playwright 运行态证据。

<a id="runtime-observation"></a>
# 7A. 事实域 F：产品执行与观测通道

此域回答“产品哪次执行实际上用了什么、做了什么”。先核对版本/实例、调用或周期/阶段、消息关联、取值来源、完整性和采集扰动，再判断证据能支持的结论；不按 GUI、C++ 打印、文件或数据库的名字固定排名。

实际操作数和分支结果的有界记录通常比事后读取同名可变对象更贴近该次执行，但取值代码、并发一致性和身份仍须验证。GUI 显示只能直接证明界面显示；要推导产品执行，须证实采样/缓存/刷新及绑定。不同核时钟不默认同步，入库时间不是发生时间，缺记录不自动表示业务未执行。

当前已知的两类 BEH 观测问题统一见[BEH 已知问题与观测适用边界](../../工具接入与共享能力/BEH原生能力/BEH已知问题与观测适用边界.md)。适用版本和根因尚待本地补证，不把用户观察抹掉，也不推广成所有版本/引擎能力均不可用。

<a id="normative-expectations"></a>
# 7B. 事实域 G：业务应有行为与测试预期

此域回答“在指定条件下应该怎样”。依据适用需求、协议/算法契约、设计或有理由的专业确认，明确条件、状态、时间和容差。规范也可能不完整或矛盾，冲突保留并追溯，不按材料名称自动判正确。

产品、Java 引擎与 DT 输出属于实现行为；即使相同，也不能作为自身业务正确性的唯一证明。代码推导 Expected 只能标实现快照/条件推导，不能复制实际结果后宣布业务验证通过。Golden 必须标用途：结构/显示兼容、实现行为回归或独立业务断言。

观测资格是使用证据的前提。格式确定、数据直接或同源生成只描述来源，不保证来源无缺陷；下述 Evidence Class 不能代替本域所需的核验。

# 8. “原始源”与“工具结果”必须分开

任何 Evidence 必须归类为以下一种，而不是统称“工具输出”：

## 8.1 RAW_SOURCE

原始事实材料：

- 原始 JAR；
- 原始 XML；
- 当前 C/C++ 源码；
- build config；
- 用户明确文字输入。

## 8.2 DETERMINISTIC_DERIVED

由固定程序从明确输入确定性产生：

- NativeSceneBundle；
- javap / ASM class 信息；
- Clang AST / definition / reference；
- SHA256；
- 明确生成映射。

## 8.3 STATIC_INFERENCE

需要静态分析假设：

- Call Graph；
- Def-Use；
- 跨函数数据流；
- 指针/别名有限分析。

## 8.4 HEURISTIC

启发式：

- 名称相似；
- 字符串匹配；
- 坐标附近；
- 模糊搜索。

## 8.5 MODEL_INFERENCE

AI / 视觉模型推理。

等级越低，不代表“不能使用”，而是必须更明确地保留不确定性，不能冒充更高等级事实。

# 9. 证据冲突处理 SOP

任何冲突必须按下面执行。

## Step 1：写出 Claim

例如：

```text
Claim：TON_17 的输出最终控制 low_freq_alarm。
```

不要先争“哪个文件更可信”。

## Step 2：识别 Fact Domain

本例是：

```text
Scene-to-Code Binding
```

## Step 3：检查是否比较了同一版本

至少核对：

```text
JAR_SHA256
XML_SHA256
Repo Commit / Workspace State
Build Profile
compile_commands Hash
Exporter Version
```

不同版本证据不得直接互相覆盖。

## Step 4：在该域中排序

例如：

```text
DIRECT_NATIVE_BINDING > EXACT_SYMBOL > DATA_FLOW_INFERENCE > AI_HYPOTHESIS
```

## Step 5：保留冲突，不静默吞掉

输出：

```text
CONFLICT
```

并保存双方 Evidence。

## Step 6：需要更高等级证据时，主动升级验证

例如：

- CFR 与实际行为冲突 → 查字节码、运行原 JAR；
- clangd 与源码冲突 → 查编译 Profile / 宏 / include；
- 图元与代码匹配不确定 → 找原生绑定或生成映射；
- 自由笔语义不确定 → 要求用户文字或视觉模型证据。

# 10. AI / Skill 强制执行规则

DeepSeek V4 Flash、GLM-5.2 或其他模型执行任何分析时：

1. 先标明当前 Claim 所属 Fact Domain；
2. 不得跨事实域套用另一域的“最高事实源”；
3. 每个关键结论必须带 Evidence Ref；
4. 每个 Evidence 应包含 `evidence_class` 与 `fact_domain`；
5. 结论状态只允许：

```text
FACT
INFERENCE
HYPOTHESIS
UNKNOWN
CONFLICT
```

6. 不能因为需要“给出完整答案”而把 UNKNOWN 填成 FACT；
7. 低等级证据不能覆盖高等级直接事实；
8. 如果证据版本不同，先标记 `VERSION_MISMATCH`，不得直接比较；
9. CFR 只作为 Recovered Java Reference；
10. Web 运行事实必须由真实运行 / Playwright 验证，而不是模型依据源码自行宣称。

# 11. 最简决策表

| 要回答的问题 | 第一事实源 | 第二证据 | 低可信参考 |
|---|---|---|---|
| BEH 最终怎么解析/渲染 | 原始 JAR 实际行为 | Native Headless Scene | CFR / AI |
| class 里真实有什么调用/字段 | class 字节码 | javap / ASM | CFR |
| CFR 代码是不是“原源码” | 不是 | 仅 Recovered Reference | — |
| C/C++ 某函数实际写了什么 | 当前真实代码仓源码 | 构建配置 + Clang语义 | AI摘要 |
| 指定 Profile 下符号是什么 | 源码 + Build Profile | Clang/clangd | Tree-sitter / AI |
| 图元对应哪段代码 | 原生直接绑定/生成映射 | 精确符号/唯一引用 | 数据流推导/AI |
| 用户圈中了谁 | Selection几何 + hit-map | selected IDs | 模型视觉猜测 |
| 用户自由笔是什么意思 | 用户明确文字/结构化操作 | 视觉模型证据 | 文本模型猜测 |
| Web 按钮是否真的工作 | 实际页面行为 | Playwright | build / AI推测 |
| 产品某次执行使用什么值 | 通过时刻/实例/完整性核验的实际使用值记录 | 独立采集与对应执行证据 | 未核实时序的 GUI 当前值 |
| 业务应该输出什么 | 适用需求/契约/设计及独立断言 | 专业确认与不同依据交叉核对 | 当前实现输出或 AI 猜测 |

---

# 12. 核心原则

> **不是“谁永远最可信”，而是“谁对当前这个事实最有资格作证”。**

项目必须先识别事实域，再评估证据等级、版本一致性、直接性和可复现性。

这条规则优先于任何简单全局排行榜。
