# 多仓多镜像：目标部署与迁移实施指南

版本：v1.0，2026-09-18。前置输入：[01_WSL与磁盘现状只读探查_AI任务书.md](01_WSL与磁盘现状只读探查_AI任务书.md)及本机实际探查结果。

本文件把已讨论的嵌套示意图变成可实施的目标设计。目录、仓号、产品和配置均为示例；当前尚未访问用户机器，不代表现有环境已整理或新脚本已实现。先根据01形成具体变更清单，在获得相应实施授权后执行；本次文档编写请求不等于要求立即改动用户机器。

配套图解：[04_WSL与Docker关系图解.md](04_WSL与Docker关系图解.md)。先按图理解层级、源码与容器挂载、三组独立产物；图中的路径和D盘位置都是示例，实际以本机证据为准。

## 1. 能否实现图里的效果

可以实现：以代码仓组织源码，用配置显式保存“仓→产品目标→镜像→容器→产物”的多对多关系，并把最终数据位置映射到Windows卷。需要保留工程本身约束，而不是让工程硬套示意图。

目标原则：

1. 源码以repo1、repo2等仓为入口，仓内公共/通信等子仓保持真实结构。产品目标放在构建配置中，不将根目录按产品重建。
2. 同一个仓可为多个产品构建；同一镜像可被不同仓使用。组合有效性必须由真实构建参数和验证支持。
3. 镜像是环境模板；容器是运行实例。镜像选择、挂载、入口和产物路径由配置明确，Docker不会猜。
4. build、logs、packages按仓和组合隔离，进一步按执行编号留档；缓存共享必须符合工具链/目标兼容条件。
5. Ubuntu整体迁到D盘可以保留/home等Linux路径；不等于把源码改放/mnt/d。
6. 沿用已工作的Docker形态：原生Docker或Docker Desktop。无需为了外观像图而更换引擎。
7. 公司定制版编辑器和Windows AI工具的兼容性是部署选择的一部分，不能假设全部支持WSL远程执行。

## 2. 两层位置：Windows存大箱子，Ubuntu管理内部目录

### 2.1 Windows层的建议位置

| 对象 | 可选目标示例 | 必须核对 |
| --- | --- | --- |
| Ubuntu发行版数据 | D:\WSL\Ubuntu | D实际设备、空间、WSL版本和迁移支持；VHDX实际名称由系统确认 |
| Docker Desktop数据（若使用） | D:\DockerData | 在本机Docker Desktop支持的设置中迁移，独立于Ubuntu迁移 |
| 备份 | E:\Backups\WSL，或其他容量足够的受控位置 | 同一物理盘上的D备份不能抵御整盘故障 |
| Windows工作树（若保留） | D:\repos\repo1 | 这是独立副本，明确同步与Git职责 |
| WSL交换/工具缓存 | 按容量与现有配置决定 | 不承诺所有WSL相关字节均离开C盘 |

D盘若为HDD而C为SSD，不能因为D剩余容量大就断言编译更快。普通同盘分区主要改变容量安排；不同盘则依据硬件、负载、容量与实测取舍。Windows组件留在C盘可以接受，优先管理持续增长的数据。

### 2.2 Ubuntu层的建议目录

以 `/home/dev/workspace` 为演示根。dev必须替换为实际用户，或选择现有合适位置。若现有 `/home/仓名`权限、用途和映射清晰，可暂时保留，用配置登记，不为整齐先搬动。

| 路径（相对工作根） | 放什么 | 关系 |
| --- | --- | --- |
| repos/repo1、repos/repo2 | 正式日常源码及真实子仓 | 按仓组织 |
| worktrees/repo1/组合ID | 必要的独立工作树/隔离副本 | 仅在不同分支或源码树内构建需要时建立 |
| config/repos.yaml | 仓ID与路径、子仓、Windows配对等 | 描述代码来源 |
| config/images.yaml | 引擎context、镜像引用和固定ID | 描述环境 |
| config/builds.yaml | 组合ID、仓、目标、镜像、入口与路径 | 保存多对多关系 |
| tools/ | 构建/校验入口或既有脚本适配器 | 读取配置并执行 |
| artifacts/repo1/product-a/运行ID/ | build、logs、packages、metadata | 仓1产品甲独立产物 |
| artifacts/repo1/product-b/运行ID/ | build、logs、packages、metadata | 仓1产品乙独立产物 |
| artifacts/repo2/product-c/运行ID/ | build、logs、packages、metadata | 仓2产品丙独立产物 |
| caches/ | 可重建缓存，按工具链和目标分组 | 不能无条件跨组合共用 |
| reports/ | 盘点报告、迁移记录、验证结果 | 与源码分开 |

这里的workspace只是目录名字。VS Code的.code-workspace文件则是编辑器配置，可引用上述目录，不会自动复制代码或替你管理Docker挂载。

若工作根实际位于Ubuntu根文件系统，且Ubuntu的VHDX在D盘，这些目录的字节通常落在D盘的该VHDX内；若其中含软链接、单独挂载或/mnt/c路径，需按01逐项追踪，不能直接概括为全部D盘。

## 3. 每个容器具体用哪份代码、产物在哪儿

| 组合 | 实际仓目录 | 编译镜像 | 容器里的源码入口 | 容器里的输出入口 | Ubuntu真实输出目录 |
| --- | --- | --- | --- | --- | --- |
| repo1-product-a | /home/dev/workspace/repos/repo1 | 镜像A，固定版本 | /src | /out | /home/dev/workspace/artifacts/repo1/product-a/运行ID/ |
| repo1-product-b | /home/dev/workspace/repos/repo1 | 镜像B，固定版本 | /src | /out | /home/dev/workspace/artifacts/repo1/product-b/运行ID/ |
| repo2-product-c | /home/dev/workspace/repos/repo2 | 镜像A，固定版本 | /src | /out | /home/dev/workspace/artifacts/repo2/product-c/运行ID/ |

绑定挂载的含义：容器的/out/build与该行Ubuntu目录下的build是同一处数据的不同入口；不是编完以后才复制出来。容器删除不删除这些外部目录，但容器内命令仍能删除其可写挂载内容，因此目录隔离不等于备份。

同仓共享源码只适用于相同源码状态、已验证的源码树外构建。若两个产品的脚本都向仓内生成config.h、Makefile或其他中间文件，单独/out并不能隔离它们：要串行并保证状态恢复，或使用独立worktree/工作副本，并处理子模块、未提交文件及LFS；不能强行并行挂同一可写源码。

/src、/out是建议容器路径；若厂商环境固定要求/workspace、/opt/project等，保留兼容路径并把真实映射写入配置，不先改业务脚本。只读挂源码也要先验证入口、子挂载及生成行为。

## 4. 谁管理组合：配置为准，入口负责执行

由人或AI维护可审阅配置；每次构建由统一入口读取配置。优先复用现有Docker Compose、Make任务或成熟构建脚本，补一层薄适配，不新造调度系统。下面是配置设计草案，不是Docker自动支持的格式；若采用此格式，必须另行实现并验证读取它的入口。

```yaml
schema_version: 1
workspace_root: /home/dev/workspace
repositories:
  repo1:
    path: /home/dev/workspace/repos/repo1
  repo2:
    path: /home/dev/workspace/repos/repo2
images:
  image-a:
    docker_context: REPLACE_WITH_VERIFIED_CONTEXT
    immutable_reference: REPLACE_WITH_REAL_IMAGE_ID_OR_DIGEST
  image-b:
    docker_context: REPLACE_WITH_VERIFIED_CONTEXT
    immutable_reference: REPLACE_WITH_REAL_IMAGE_ID_OR_DIGEST
builds:
  repo1-product-a:
    repository: repo1
    target: product-a
    image: image-a
    source_mode: readonly_after_verification
    workdir: /src
    command_argv: [REPLACE_WITH_REAL_BUILD_ENTRY]
    artifact_base: /home/dev/workspace/artifacts/repo1/product-a
  repo1-product-b:
    repository: repo1
    target: product-b
    image: image-b
    source_mode: readonly_after_verification
    workdir: /src
    command_argv: [REPLACE_WITH_REAL_BUILD_ENTRY]
    artifact_base: /home/dev/workspace/artifacts/repo1/product-b
  repo2-product-c:
    repository: repo2
    target: product-c
    image: image-a
    source_mode: readonly_after_verification
    workdir: /src
    command_argv: [REPLACE_WITH_REAL_BUILD_ENTRY]
    artifact_base: /home/dev/workspace/artifacts/repo2/product-c
```

实施AI要把实际CPU/产品、EMAP版本、厂商SDK、用户/组、必要设备和许可证访问、缓存等补入适配配置。源码版本不是只填一个HEAD，还要记录子仓和未提交状态。不同DT/真实板目标必须明确区分，不将同仓名视为同目标。

入口的最低行为约定：

- 提供list、show、dry-run和run等价能力；dry-run只展示解析后的context、不可变镜像、挂载、目标、命令、输出目录，不运行构建。
- 拒绝占位符、未知组合、路径不存在或不符合所属根的输出目录；不因找不到镜像就静默换latest。
- 通过参数数组调用工具；不把未经审阅的配置拼接给eval。需要shell初始化的厂商入口封装成明确受版本控制脚本。
- 每次生成唯一run-id，创建独立输出子目录，避免重复容器名称和产物覆盖；并行资源超限则排队。
- 显式选择有效Docker context，查对应引擎能访问的路径。远程Docker不能直接挂载本机路径；Docker Desktop路径共享也要验证。
- 检查UID/GID及工程权限需求，避免产物全部变为root所有，也不擅自chmod 777。
- 保存源码/子仓基线、镜像ID、配置摘要、命令、挂载、开始结束时间、退出码、日志和产品包摘要。失败输出也留存。
- 先验证持久化和故障记录，再确定容器清理策略；不默认--rm删除诊断线索，不自动清理旧产物。

## 5. 分阶段实施：先小步证明，再扩大

### 阶段A：现状封存与具体方案

完成01。列出每项“原位置→新位置”、预期影响、依赖引用、容量预算、停止窗口、验证项和回退方法。只改确实需要改的地方；允许先配置登记现有路径，再逐步迁移。

保留未提交/未跟踪文件、子模块状态、必要Git元数据、构建配置、镜像引用和运行容器挂载。备份需包含实际重要数据，不用一个成功退出码代表可恢复。停止写入后制作一致性备份；VHDX运行期间直接复制不当作可靠备份。

### 阶段B：有需要才迁Ubuntu到D盘

此阶段会停止工作负载并改变存储位置，不属于01只读盘点。先确认本机wsl --help实际支持的命令、发行版名称、备份可恢复、D空间及目标目录状态。

优先考虑本机支持的 `wsl --manage <发行版> --move <目标目录>`。模板仅在上述条件满足后用真实参数执行：

```powershell
# 模板：执行前保存工作并安排停止窗口；名称和目标目录须核对。
wsl --shutdown
wsl --manage '实际发行版名' --move 'D:\WSL\实际发行版目录'
```

若本机不支持move，使用官方export/import流程：停止写入并导出到新备份文件，先用不同发行版名称导入新位置，验证源码、权限、默认用户、构建和工具连接；切换期间旧新环境不能同时写同一外部挂载。不要先unregister旧发行版再验证导入。导入后的默认用户、发行版名称和编辑器连接可能需调整，Linux内部目录并不会因此必然改变。

验证后检查注册BasePath、新磁盘文件、原内部路径、用户/权限、Git状态、挂载和一项代表性构建。迁移不等于压缩，也不保证C盘所有数据消失。失败时按所选路线迁回或恢复备份；保留旧配置和原始基线。旧副本删除另行列出明确对象和已验证恢复条件，不把清理混入迁移命令。

### 阶段C：Docker数据单独处理

- Docker Desktop：核实其本机设置和当前支持的数据迁移流程，使用官方设置入口迁移Disk image location；先备份所需命名卷/容器可写数据并停止写入，完成后核对镜像、容器、卷和集成。Ubuntu迁移不替代此步骤。
- Ubuntu内原生引擎：如果其data-root就在Ubuntu根文件系统中，整体Ubuntu迁移可能已经带走该数据；不要再重复搬动。若data-root或卷在外部挂载则分别处理。
- 若还要改原生引擎data-root：先据实际版本和存储驱动制定停机、备份、权限/扩展属性/链接保留及配置更新方案，不直接复制正在使用的Docker目录。
- 镜像tar、旧备份、BuildKit缓存、交换文件单独列账。不要运行docker system prune来“验证空间变大”。

### 阶段D：整理源码与编译组合

先选择仓1的一个已知可构建产品，建立真实配置和隔离输出。保留原入口，先dry-run，再执行一次真实构建，核对源码、镜像和包版本。

通过后增加仓1的第二产品，再增加仓2共用镜像的组合。不要强求不同环境产物字节完全相同：可重复构建才采用整包摘要一致，否则比较产品身份、目标参数、关键文件、构建测试和必要功能结果。

要移动源码目录时，先复制到新空目录、校验已跟踪/未提交/未跟踪内容及权限和链接，再更新脚本、Compose、编辑器、同步会话等引用。保留旧目录作为已停用回退源，不能新旧两边同时继续改。存储空间不足时先调整方案，不靠删除未知旧目录腾空间。

### 阶段E：Windows编辑与AI工具的实际接入

有两种可选形态，不预先强制：

| 方式 | 适用条件 | 实施要点 |
| --- | --- | --- |
| WSL为唯一日常工作树 | 公司版编辑器、AI读写与命令执行均经验证可用 | 分别验文件访问、插件、Git及Linux执行；不能仅“能打开文件”就验收 |
| Windows保留工作树，与WSL同步 | 公司工具强依赖Windows目录 | 先只读差异审查，再小范围试验同步；明确Git操作端和产物排除 |

双向同步候选为Mutagen的two-way-safe等成熟方案，不写成无条件开箱即用。Windows主程序到WSL SSH代理只是可选拓扑，需要核对公司环境中的SSH、访问和服务策略。两边活动Git元数据不能持续双向文件同步；若Windows负责Git提交，WSL构建依赖Git信息需单独设计元数据来源并验证。两边独立clone但只同步工作树，会出现HEAD和工作状态不一致，必须解决而不是忽略。

启用同步前确定哪些是源码、必需生成文件、依赖、缓存和产物，不直接把所有gitignore项当同步排除项。验证创建、修改、删除、重命名、大小写、软链接、可执行位、冲突与中断恢复。编译前等待同步完成且无冲突，并防止编译期间继续读到新旧混合源码；必要时构建固定快照。

速度用本机实测：首次完整扫描/同步、10个源码修改、大批量变更、重启恢复，分别记录文件数、字节数、工具配置、总耗时和校验结果；不要将聊天里的示例MB/s当承诺。

## 6. 图中每个设计的验收证据

| 图上的设计 | 实际验证 |
| --- | --- |
| Ubuntu主要数据放D盘 | BasePath＋真实VHDX位置＋相关目录的findmnt；列出仍在C盘的例外 |
| 多仓目录清楚 | 每仓身份、权限、子仓和真实路径明确，无未解释的同名副本 |
| 同仓甲乙使用不同镜像 | 两次运行metadata记录同仓基线、不同固定镜像和正确目标 |
| 多仓共用一种镜像 | 两组合实际记录同一镜像ID，各自使用正确源码和输出 |
| 每次运行独立容器 | 容器ID/名称、context、inspect映射与组合配置一致 |
| 产物位于容器外 | 宿主可见文件、Mounts一致；在新建验收目录做唯一标记双侧核对 |
| 容器结束后产物保留 | 构建容器停止后仍能从宿主访问；删除测试仅针对明确可丢弃的测试容器 |
| 甲乙不互相污染 | 输出目录不重叠；源码树写入行为经验证，必要时独立工作树 |
| 组合由配置管理 | list/show/dry-run与实际run一致，无人工口头补充隐藏步骤 |
| 日常工具继续工作 | 公司版VS Code、Git提交/推送、Windows AI读写/WSL命令执行分别验收 |
| 有回退能力 | 已保存备份和旧配置，给出明确恢复步骤及验证状态 |

测试改动只在明确创建的验收文件或工作副本中进行；不要为了验证Git推送向公司正式分支提交演示改动。可采用已授权测试分支或记录该项待验证，不虚报成功。

## 7. 实施结果必须交付什么

1. 本机目标架构图：沿用Windows、WSL、Ubuntu位置嵌套，画出每个实际容器；源码、配置、产物和Docker数据均标真实路径。引擎在Docker Desktop中时按实画出。
2. 新旧路径和引用变更表：包含同步、IDE、构建脚本、引擎挂载、默认用户、Git凭据影响。
3. 实际可执行配置/入口及其使用说明；未实现部分明确标记，不拿本文的YAML草案当成可运行系统。
4. 代表性构建结果、持久化/隔离证据、工具兼容结果、容量对照和剩余问题。
5. 回退说明与保留数据清单，独立的候选清理清单；不自动删除。

后续扩大到更多仓或镜像，只追加仓登记、固定镜像和经过验证的组合。产品代码与EMAP事实探查工具的数据库、日志也按仓/目标/运行编号放入artifacts或reports，不能混进源码或其他产品build目录。

## 8. 交给本地AI的阶段指令

> 先读01并完成本机现状报告。再根据本文件提出适配当前机器的目标结构，不为图形一致强制迁移或更换Docker。明确C/D选择依据、代码主副本、编译组合、镜像固定身份、容器挂载和产物位置，保留公司版编辑器与Windows AI工作方式。先生成可审阅的真实配置和实施/回退清单；现有授权已涵盖的准备工作直接完成。对尚未授权的停机迁移或数据删除，不提前执行。实施阶段从一个已有可构建组合开始，验证后逐步扩展，最终交付实际路径图和运行证据。

- [WSL跨文件系统工作](https://learn.microsoft.com/en-us/windows/wsl/filesystems)：Windows卷路径与Linux文件系统不同。
- [Docker Desktop WSL数据与设置](https://docs.docker.com/desktop/features/wsl/)：其存储可独立于用户Ubuntu。
- [Docker bind mounts](https://docs.docker.com/engine/storage/bind-mounts/)：引擎侧路径、持久化与读写权限。
- [Mutagen双向同步](https://mutagen.io/documentation/synchronization/)、[Git配合边界](https://mutagen.io/documentation/synchronization/version-control-systems/)：安全冲突处理与工作树同步。

这些工具资料支持设计原则，不证明用户现有路径和环境。文档未执行真实迁移、产品构建、设备测试或Windows工具兼容测试。
