# AI 解释：两档模式与测试增强规范
日期：2026-09-16｜性质：用户新需求的设计规范，尚未宣称接入运行。
用户原意：基础解释可以不用 AI 测试支撑；需要更扎实依据时，选择由 AI 测试支撑的解释。统一术语为“基础解释”和“测试增强解释”。

## 当前实施入口

先读 [AI 测试与解释融合：双环境实施指导](../AI测试/测试与解释融合/02_AI测试与解释融合_双环境实施指导_v1.0_2026-09-16.md)，再按本文理解两档模式。作者没有查看源码，具体接入建议需由本地 AI 调查与验证后决定。产品连接情况“不连产品/连接产品”与解释程度“基础/测试增强”是两个独立维度；连接状态不能推出运行位置或引擎依赖。

本期重点是两种环境下的测试增强解释。测前讲明场景和预期依据；测后专门讲解实际关键过程、状态、原因、场景对照、业务联系和未知，必要时提出有预算的最小补测。不能只把基础解释贴上 PASS。预期依据、实际执行与检查、解释证据分别显示；业务不清楚时给人可理解的问题，并允许回答“不知道”。

## 1. 两档分别交付什么
| 项目 | 基础解释 | 测试增强解释 |
|---|---|---|
| 依据 | 实际图元、端口、参数、关联源码、配置和明确需求 | 基础证据＋匹配当前对象与版本的真实测试证据 |
| 是否必须运行行为测试 | 不要求 | 必须有相关有效证据；可复用已核对结果，不必每次重跑 |
| 主要回答 | 结构是什么，按代码与配置预计如何工作 | 指定条件下实际如何工作，哪些行为与预期一致或冲突 |
| 结论标签 | 结构事实、源码结论、条件推断、未知 | 在前述标签外增加实际观测、指定场景验证、冲突、未覆盖 |
| 输出 | 逐步解释、来源、条件和未知 | 可读场景卡＋测后过程讲解、逐条证据、场景对照、业务联系与缺口 |
| 成本 | 通常较低，具体取决于检索范围 | 取决于场景和现有 Runner 覆盖，不预先承诺时长/成功率 |

两档不等于“随便猜”和“绝对正确”。基础档仍有确定性结构解析、ID 对应、来源查询等支撑；增强档只能证明已经测试的条件和范围。

## 2. 解释和测试的工作关系
解释可以提出行为假设和需要区分的条件；AI 测试负责组织真实执行、取得输入输出并核对有依据的期望；解释再根据结果修订。
优先由程序完成执行、读值、比较、Schema 验证等确定性动作。模型参与选择场景、解读含义，但不能把其文字判断当作真实执行结果。
测试也不能替代静态解释：为什么存在某逻辑、设计意图是否合理，仍可能需要需求与源码证据。

## 3. 请求、结果与兼容
以下为待实现的逻辑字段，不宣称现有 Task/Result Schema 已支持。接入时显式升级契约或使用已约定扩展，不静默改变旧字段。
- 请求：模式、选区与对象、要解释的问题、要验证的关键结论、允许的测试范围/资源预算。
- 基线：源码与未提交差异、XML/图元定义、引擎、配置、输入数据的版本或内容标识。
- 每条结论：对象、内容、适用条件、静态来源、测试引用、验证状态、未覆盖条件。
- 每次测试：run_id、case_id、版本、前置状态、输入序列、时间/周期条件、实际输出、Expected 及其来源、比较规则、原始记录与运行状态。
- 总结果：请求模式、实际证据范围、已验证/未覆盖/冲突条目以及下一步。

旧请求未提供模式时保持旧基础解释行为；缺字段不能导致旧结果被标成已验证。运行编号用于关联，不能单靠编号证明内容正确或相同版本。

## 4. 增强档流程
1. 先识别真实图元、范围、端口和代码绑定，形成带依据的解释草稿，列出关键可验证结论。
2. 查询现有 8 个 FB 基线及相关用例，判断定义、参数、输入、环境、版本和观察点是否适用。不要把同名 FB 的结果套到另一版本。
3. 优先复用匹配证据；已有测试若缺少某个关键条件，只补相关场景。无法接入的对象列为未覆盖或阻塞。
4. 先由本地 AI 查明两种连接情况下的完整执行链，特别是各自是否需要本地引擎、已有 Runner 或其他组件，再选择适用路径与接入方式。记录已知状态、实际输入、执行位置、数据来源和时间语义；仅观察、主动测试和不可覆盖条件分清。不要只测单点输出后解释完整状态机。
5. 将结果关联回每条解释。若执行结果与预期或原解释冲突，保留原记录并指出冲突，检查假设、版本、测试期望和实现，不能自动改 Expected 让测试通过。
6. 生成独立的测后讲解：为什么这样测、关键步骤发生什么、状态如何变、原因依据、跨场景对照、业务含义和未覆盖条件。“一拍”的含义、输入生效和取值时点从实际入口核验，不能虚构毫秒或中间状态。
7. 对疑点先查已有记录与源码，再在任务预算内做能区分候选原因的最小补测。输出用户可读解释与证据表；专业版和小白版共享同一事实结构，不改变阈值、时序、方向或失败含义。

首次验证建议选择一个已有证据的 FB，复用输入和运行结果。示例可以是带阈值/延时的行为，但真实类型和参数从当前样本获取，不虚构已支持图元。

## 5. 区分“观察到了”与“业务正确”
程序真实跑出一个值，能支撑“该版本在该输入条件下输出此值”。只有与可信的独立期望、接口规则或明确性质比较，才支撑“该条件下符合预期”。
禁止“AI读实现→按实现生成Expected→完全一致→业务正确”的循环。Expected 来源可以是明确需求、审核过的规则或独立参考；隐藏测试、变异测试与性质测试按具体风险补充，不要求每次解释都重跑整套验真。
浮点比较需有合理容差及 NaN/Inf 处理依据；异步和周期行为需记录观察时点。源代码推算仍标推算，模拟/桩替代范围显式标明。
Java 图元测试不能直接证明生成后的 C/C++、跨核通信或真实硬件时序正确，除非另有对应执行证据。

## 6. 状态与失败表达
| 状态 | 可显示的含义 |
|---|---|
| 未测试 | 基础档或该条无相关测试 |
| 已观测 | 取得真实结果，尚缺可信业务期望 |
| 指定场景已验证 | 明确输入和条件下，输出与有依据的期望相符 |
| 部分验证 | 一部分关键结论有证据，其余列明未覆盖 |
| 测试阻塞 | 环境、接入、依赖或输入条件阻止执行 |
| 发现冲突 | 实际结果、期望或解释之间不一致，保留证据待定位 |

状态按结论记录。增强档缺测试时可交付基础部分并明确“增强验证未完成”，不能静默降档、伪造 PASS 或以高置信度掩盖缺口。不得把局部验证汇总成“整个图元/整个工程无问题”。

## 7. 网页呈现
只给用户两档选择；内部细分状态不变成一堆设置项。解释正文保留简洁语言，每条结论可展开依据和验证记录。展示“哪些关键结论已验证、哪些未覆盖”，除非分母有明确定义，不给虚假的全局覆盖率。
用户可以先看基础解释，再升级同一问题的测试增强解释；版本变化后保留旧结果身份，生成新的结果或明确失效，不能混合成一次测试。

## 8. 最小验收
| 场景 | 预期 |
|---|---|
| 基础档 | 不触发要求之外的行为测试，结论有静态来源与不确定性 |
| 增强档复用匹配证据 | 准确展示版本、输入、输出和结论对应 |
| 引用不同版本或输入 | 拒绝错误复用，说明差异 |
| 仅有真实输出、无可信期望 | 显示已观测，不显示业务正确 |
| 一个分支未测 | 已测和未测部分分别显示 |
| 输入错误/执行失败 | 保留失败，不能显示已验证 |
| 测试反驳解释 | 解释指出冲突，禁止改预期取巧 |
| 延时/状态行为 | 有初始状态、周期或时间条件和输入序列 |

本轮只交付设计与文件整理，以上场景还需本地工具实现并执行。
