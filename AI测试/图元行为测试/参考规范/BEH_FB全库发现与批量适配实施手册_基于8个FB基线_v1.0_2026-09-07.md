# BEH FB 全库发现与批量适配实施手册

**版本：** v1.0  
**日期：** 2026-09-07  
**适用基线：** 已完成 8 个真实 FB 的测试接入及前序回归、复用与可信性验收工作。  
**本轮目标：** 利用现有 Runner，将逐个接入升级为“全库发现、能力匹配、受控批量试跑、共同阻塞治理”，逐步扩大真实可执行范围和业务测试覆盖。  
**文档性质：** 新增阶段手册；不要求重做已完成的 MVP，不授权推翻现有工程，也不授权直接批量执行全部未知 FB。

> **给开发 AI 的首要指令：复用已经跑通 8 个 FB 的成果，不再按“第九个更复杂 FB”逐个攻坚。先把库内 FB 及现有能力对齐，提出批次和公共缺口，与用户讨论并获准后执行。扩大的是经过证据确认的覆盖范围，不是控制台里的 PASS 数量。**

---

## 0. 执行摘要：读完这一节就知道下一步

本轮分两条并行推进的主线：

| 主线 | 要做成什么 | 不得冒充什么 |
|---|---|---|
| **批量适配** | 尽量自动发现 FB、准备真实运行上下文、注入合法输入、驱动真实执行并观察结果 | 能运行不代表业务正确 |
| **行为验证** | 为已适配 FB 配置有依据的业务场景、Expected 或性质断言，验证错误检出能力 | 大量录下实际输出不代表有了正确答案 |

推荐工作循环：

```text
现有 8 个 FB + 现有 Runner + 已验证的构建环境
        ↓
读取全库目录、注册信息及定义，建立清单
        ↓
把每个 FB 的运行要求与已有能力匹配
        ↓
提出第一批候选、需补能力、资源预算和验证目标
        ↓
用户批准范围与必要修改
        ↓
自动生成接入描述/夹具 → 使用现有 Runner 批量运行
        ↓
逐项记账，区分适配结果、业务断言和阻塞
        ↓
按共同根因补一次公共能力，重跑受影响整组和原有回归集
        ↓
展示实际增量，再决定下一批
```

**这不是要求重建一套大平台。**清单、匹配器、批处理和报告优先采用现有项目可用的文件、脚本及测试设施；有成熟实现就复用。不要为此默认引入数据库、Web 控制台、CodeQL、CUA、容器、虚拟机或新的 AI API。

## 1. 已知事实、适用范围与不作承诺的边界

### 1.1 当前起点

用户确认当前已经完成 **8 个 FB**。本轮接续已有成果，开发 AI 应从实际代码、运行记录与前序报告中登记这 8 个 FB 的身份、用例范围和版本；有现成证据就引用，不要求把过去的审查重新做一遍。

本手册未读取公司 BEH 源码、全部 FB 清单或这 8 个 FB 的具体日志。因此本文不指定真实类名、图元名称、运行配置数量或全库规模；相关字段必须由本地工程事实填充。

### 1.2 范围

本轮测试的是 **BEH 中真实 FB 在声明运行环境下的行为**。CB、其他 FB、资源和父级模型可以作为真实依赖进入夹具，但不能因依赖数量多就把它们改成替身。

本轮不自动涵盖：生成后 C/C++ 与 Java 模型的行为等价、跨仓/跨核整机运行、上板启动、GUI 编辑正确性、渲染保真。它们可另设测试，但不得由 FB 测试通过直接推导。

### 1.3 当前目标不是覆盖所有可能配置

同一种 FB 可能有不同参数、通道宽度、父级环境或执行模式。本轮先明确“支持哪些变体和场景”，逐步扩大；不能用一个配置的成功证明该 FB 在所有上下文中都成功。

不能承诺“所有 FB 都能自动适配”“覆盖 80% 业务”或“通过即可无 Bug”。这些结论必须有清单、分母和实际测试证据。

## 2. 三个必须分开的统计对象

| 对象 | 定义 | 用途 |
|---|---|---|
| **FB 定义** | 当前批准版本中的一个真实可复用图元定义，不按显示名判断唯一性 | 回答库里到底有多少种 FB |
| **FB 运行变体** | 某定义在确定参数、通道、父级上下文和运行配置中的一个组合 | 回答哪些具体用法已适配 |
| **测试用例** | 对某变体施加的一段输入/事件/时间序列，以及明确观察和断言 | 回答已验证哪些业务行为 |

同一 FB 在一个 POU 中出现很多次，不等于很多种 FB；同一 FB 跑很多用例，也不能膨胀“已适配 FB 数”。不同版本的同名定义、不同作用域对象，不能静默合并。

建议稳定标识由“来源仓/包 + 原生类型或定义路径 + 定义版本/内容标识”组合产生，并保留原生 ID。运行变体再引用参数和上下文摘要。**仅用于识别的指纹不能替代业务等价判断，也不得用它去重正式模型中的 Relation。**

## 3. 不推翻的基础与允许改变的内容

### 3.1 保留现有成果

保留已验证的 Runner、BEH 原生 Loader/Runtime、测试入口、构建配置、运行环境、8 个 FB 的现有用例和验证记录。后续新增公共能力必须保护这些已有行为。

“一个通用 Runner”表示一个共同的接入协议和调度入口，**不要求全部代码塞在一个 Java 类里**。已有合规的运行配置、输入适配器、输出观察器可以继续存在。

### 3.2 不因规模扩大重新发明环境

继续采用当前成功的仓库构建方式、JDK、Maven、ECJ 和已确认的依赖配置。Tycho、p2 或 OSGi 的具体用法以工程事实为准，不因文档提及而强制引入。

已通过的 baseline 不因进入新阶段而重新“考古”。发生工具链、依赖、模块或运行配置变化时，才对受影响部分重新验证并说明范围。

不能为了少量 FB 通过而复制零散生产类、拼装另一套小 Runtime、伪造同名依赖，或无依据删除 GUI/RCP 模块。反过来，若现有工程已有经过验证的测试模块和依赖集合，也不要求启动所有产品 UI 或编译每个无关交付物。

### 3.3 对不成熟测试框架的处理不再反复争论

沿用当前已审计并跑通的路径。本轮不重新接回整个不成熟 FB 框架，也不为了“代码必须全新”重写已经证明真实、可靠的薄封装。

新增依赖或迁移执行器必须先讨论。判断依据是被测行为、调度及输入输出是否仍来自真实实现，而不是仅凭文件名、代码年代或类名带不带 `Test`。

## 4. 授权边界：批次授权，不是每个 FB 都来问

### 4.1 收到本文后的默认动作

在用户已提供且允许读取的仓库范围内，可以读取代码、注册目录、模型定义、构建信息和现有日志，汇总清单与候选方案。不修改生产 FB、不更新 Expected、不新增工程依赖，不执行未知 FB 的初始化或业务逻辑。

已有成功测试的运行授权继续有效；不因本文收回，也不自动扩展成“可以执行库内任意对象”。需要新增扫描脚本时，先说明输出位置和读取范围，在确认的测试/诊断目录内实施，不修改原始图元。

### 4.2 合并成一次可理解的决策

第一批之前提交一张决策卡，至少说明：

| 必须讨论的内容 | 用户需要看到的信息 |
|---|---|
| 盘点与执行范围 | 哪些仓、分支、图元集合；“全库”的边界是什么 |
| 第一批目标 | 只验证接入，还是包含已有业务断言；各能证明什么 |
| 候选及顺序 | 哪批复用能力最多，哪批业务价值高，困难在哪里 |
| 拟改公共能力 | 改哪些模块，为何不能只改配置；不用新改动的替代选项 |
| 资源与安全 | 隔离方式、并发上限、超时和输出预算、允许访问的资源 |
| 验收门槛 | 必须完成的项目，允许延期的项目，失败后如何处理 |

用户批准一个批次和公共改动后，AI 可在该范围内自动生成描述、准备夹具、运行、汇总及按约定重试，不要每个 FB 重复请示。

### 4.3 必须重新讨论的变化

新增执行语义/Director 策略、替换真实依赖、引入外围模拟环境、修改 DUT、修改判定依据/容差、升级工具链、提高资源上限、扩大仓库范围或启用外部设备/网络，均需要新的明确授权。

一个项目无法继续时可记为阻塞并处理已获准的其他项目；**不需要把整个批次停下来，也不得擅自用替身绕过阻塞。**

## 5. 从 8 个 FB 提取“已经证明的能力”，不是重新审计它们

建立一份很小的 `baseline-8.json`，引用已有证据，记录每个 FB：定义/变体 ID、测试入口、用例、运行配置、BEH/Runner 版本、结果记录和限制。

再提取 `capabilities.json`，每项能力包含以下信息：

| 字段 | 必须表达的内容 |
|---|---|
| 能力及版本 | 例如某种真实加载方式、类型输入适配、输出序列采集 |
| 验证范围 | 哪些 FB、通道、执行模式和参数范围已经实际使用 |
| 实现入口 | 当前项目的真实方法/模块，不是文档发明的 API |
| 前置条件 | 依赖上下文、原生调度、资源、线程要求 |
| 验证证据 | 对应日志、用例、负向检查、已知限制 |
| 状态 | 已验证 / 已实现未验证 / 尚未实现 / 未知 |

同为 `double` 端口，不表示父级调度和通道语义相同；相同 Java Class 也不表示所有变体执行条件相同。**能力必须带适用条件，不能写“8 个能跑，所以所有 FB 都可跑”。**

## 6. 全库发现：先登记，再有控制地加载

### 6.1 寻找真实目录入口

优先检查 BEH 图元注册/工厂、产品启用的库、插件配置、模型定义、类型索引及正式示例。用它们与源码/资源目录相互核对；不要仅扫描全部 `*.xml` 或全部 Java 类，然后全部算 FB。

必须区分：可实例化 FB、抽象类型、模板、CB、示例工程、废弃定义、未启用库、缺依赖项目，以及待分类对象。不能因为没有测试就把它从全库清单中移除。

解析大型工程时按目录/库分页登记，按需加载真实定义，避免一次把全部模型常驻内存。建立带来源的依赖索引；识别定义引用异常与合法反馈环的区别，不能因数据流存在环就把 FB 判为非法，也不能任意拆环后试跑。

输出应声明 `inventory_complete` 为 `true / false / unknown`，并记录未读取目录、解析失败和无法访问的依赖。完整性未知时不报“全库覆盖率”，只报“已发现范围内的覆盖”。

### 6.2 两级发现，避免扫描触发业务运行

| 层级 | 动作 | 限制 |
|---|---|---|
| **元数据发现** | 读取注册信息、定义位置和已有结构信息 | 不加载任意类、不调用 FB 初始化、不生成产品代码 |
| **受控原生解析/内省** | 在批准的测试副本和资源限制下，用真实 Loader 获取接口及上下文 | 加载/构造也可能执行代码；须遵守批次授权和隔离，不当作无副作用文件读取 |

某些类型、宽度和动态端口必须在原生预初始化或类型推导之后才能确定，就记录它们的解析阶段；暂时不能确定时保留 `UNRESOLVED`，不补猜测默认值。

Ptolemy 的 `inputPortList()` 能枚举当前 Actor 的直接输入端口，但不能由此推导任意 FB 已可独立执行。复合 Actor 与外部通信还涉及父级 Director 提供的接收器等上下文。[R2]

### 6.3 FB 清单最小字段

| 分类 | 记录内容 |
|---|---|
| 身份 | 定义/原生类型/显示名、来源仓与包、源文件、版本及别名关系 |
| 接口 | 输入输出角色、原生端口引用、声明/解析类型、通道、multiport、连接约束 |
| 参数 | 原始表达式、解析值、单位和范围的证据、作用域、必填/默认状态 |
| 组合依赖 | 子 FB/CB、基础类型、引用库、资源文件、父级参数和配置 |
| 执行条件 | 本地/父级 Director、调度域、事件或时间要求、初始化和线程限制 |
| 测试素材 | 已有夹具、合法示例、输入序列、规格和 Oracle 的出处 |
| 扫描状态 | 已解析字段、未知字段、加载错误、证据来源 |

**接口内省能告诉程序“有哪些端口”，不一定能告诉它“什么输入才有业务意义”。这两项必须分开。**

## 7. 自动匹配与分组：匹配是候选，不是通过

### 7.1 用能力需求匹配，不靠 AI 每次临场判断

将 FB 的已知运行要求与现有配置的支持条件比较。对已有规则可以确定性匹配；AI 可提出新分组和缺口解释，但不能用“看起来相似”直接认证。

匹配结论：

| 结论 | 含义 | 下一步 |
|---|---|---|
| `MATCHED_CANDIDATE` | 所有已知硬要求被已有能力覆盖，且关键上下文已确定 | 批量准备并实际试跑 |
| `NEEDS_CONFIGURATION` | 能力已有，但合法参数、父级配置或激励不齐 | 补有证据的数据，不改 Runner |
| `NEEDS_CAPABILITY` | 明确缺某项公共加载/输入/执行/观察能力 | 汇总影响范围，提出代表和补齐方案 |
| `EXTERNAL_DEPENDENCY` | 必须连接本轮未获准的环境、资源或设备 | 留档、隔离、讨论，不用空实现替代 |
| `UNRESOLVED` | 关键需求、身份或映射尚未确定 | 定位缺证据处，不能强配最近似策略 |
| `NOT_EXECUTABLE_ENTRY` | 抽象定义、纯模板等本来就不是独立执行入口 | 保留清单和原因，不算执行失败 |

一个 FB 可以同时有多个阻塞，设主阻塞便于统计，但完整保留其他原因。`ORACLE_MISSING` 另作验证状态，不等同于 Runtime 不支持。

### 7.2 Execution Profile 的正确含义

Profile 是**对一套真实运行契约的受控配置/适配**，不是为 FB 另造业务解释器。它可描述 Loader、上下文工厂、原生调度器配置、端口转换、输入事件策略、观察方式、停止条件和清理方式。

禁止直接固定“无状态/周期/定时/事件”四个互斥家族；一个 FB 可能同时具备状态、时间和事件特征。按真实依赖组合表达要求，Profile 数量由证据决定。

特别禁止为方便统一而给所有 FB 挂同一个 Director、循环固定次数后宣称完成，或将一轮调度解释成固定毫秒。Ptolemy 中 Director 的时间和调度语义并不统一，一些 Director 不推进模型时间，`fireAt()` 的实际处理也依具体实现而定。[R3]

### 7.3 选批次的方法

候选至少给出两种取向：“已覆盖能力最多、快速扩大适配”和“当前业务最重要、可能需补公共能力”。说明预计适配数、所需配置、风险和证据；不要给没有依据的精确工时或通过率。

优先选可用现有能力、具备合法输入和清楚观察条件的 FB。不要只选复制变体凑数，也不要首先处理依赖最复杂但短期价值不清楚的项目。

## 8. 新增的是自动接入层，不是第二套 Runtime

建议职责如下，**是逻辑模块，不强制新增同名 Java 类或独立服务**：

```text
Catalog：发现并登记真实 FB
    ↓
Capability Matcher：判断缺口，选择已验证运行配置
    ↓
Descriptor / Fixture Builder：生成元数据与最小真实外围
    ↓
现有共同 Runner + 已验证 Profile
    ↓
现有 BEH Loader / Runtime / 目标 FB
    ↓
Result Collector：逐项结果、观察、断言和证据
    ↓
Failure Grouper：整理共同阻塞，供后续公共修复
```

AI 参与调查、提出规则、分析失败、设计业务用例；已明确的枚举、匹配、执行和比较由固定程序负责。**不要求运行每个 FB 时都调用一次 AI。**

### 8.1 Descriptor、Fixture 与 Case 分工

| 内容 | 负责什么 | 不能包含什么 |
|---|---|---|
| **Descriptor** | 谁是 DUT、有哪些接口、需要什么上下文和能力 | 当前实现推导的业务答案、任意脚本注入 |
| **Fixture** | 用真实对象建立输入源、DUT、观察点和必要上下文 | 重写内部逻辑、重路由内部图、剪掉难测子模块 |
| **Case** | 参数设置、输入/事件序列、观察窗口、独立 Expected/性质 | 偷改执行器、按输出更新 Expected |
| **Profile** | 统一驱动某类原生执行条件 | 某个具体 FB 的业务判断和输出计算 |

Descriptor 不能变成藏有大量 `setup_script`、反射私有调用和 `eval` 的第二套编程语言。否则只是把专用 Runner 换了存放位置。

### 8.2 最小外围不等于孤立执行

优先复用已有合法示例和原生工厂形成的测试上下文。若 FB 依赖父级参数、作用域、共享资源或子图元，保留必要依赖闭包；需要将 FB 放入外层测试 Composite 时，说明外层执行上下文为何符合原生语义。

不能直接把 FB 变成一个没有父级的顶层 Actor 就假定端口照常收发。Ptolemy 对顶层 CompositeActor 和嵌套 CompositeActor 的端口通信有不同约束；这些应当在 BEH 当前版本中核实并封装成公共规则，而不是逐个试错。[R2]

输出观察器必须读取真实输出，并考虑 Token 消费、背压、端口宽度和调度影响。观察器放在 DUT 外围，不能为取数直接篡改内部状态，也不能从 Expected 区域拿值充当 Actual。

### 8.3 合法激励来源

按已知可用性选择：已有可信用例/示例；原生默认配置且其合法性可确认；规格明确的有效值及事件序列；有证据的领域输入模板。

不能统一填零、任意常量或随机值。随机/生成式激励只有在输入域、关联约束、种子和判据明确后采用。数组长度、枚举、记录字段、单位、Token 缺席与默认值都不能静默转换。

遇到必填配置未知，返回 `NEEDS_CONFIGURATION`；没有业务预期，仍可做获准的运行接入检查，但只能报告对应等级。

## 9. 批处理必须如何执行

### 9.1 先形成不可变的批次清单

每批保存计划 ID、批准记录、FB/变体/用例列表、目标验证等级、Profile 版本、构建与依赖指纹、资源限制和允许的外部访问。

执行器按清单处理。每个计划项必须落到一个明确结果，不得因筛选器、异常或超时而从报告中消失。没有收集到用例应报 `NO_CASES`，不能以“0 个失败”宣布通过。

### 9.2 隔离与预算

优先复用当前验证过的隔离方式。扩展到未知 FB 时，推荐先串行、独立模型上下文；有不可清理静态状态或进程退出风险时，采用经批准的独立 JVM/原生启动进程。通过隔离验证后再提高并发。

这是测试进程与工作副本隔离，**不要求新操作系统或 CUA Sandbox**。但独立 JVM 并不是安全沙箱：未经授权的文件写入、网络、设备访问仍须受控；不能认为换个进程就可以执行任意未知代码。

至少限制单例墙钟超时、内存、输出体积、工作目录和并发数；模型时间/事件数上限与墙钟超时分别记录。不得在失败后私自不断调大预算直到通过。

进程控制需要同时处理输出流、退出码、超时和清理；Java 8 的 `Process` 已提供限时等待与进程终止接口，但它们本身不保证复杂子进程树或外部资源全部被清理，具体行为要在当前启动环境验证。[R6]

### 9.3 每项执行协议

下面是阶段语义，不是要求所有 FB 用同样的 API 顺序：

| 阶段 | 必须记录的事实 |
|---|---|
| 准备 | 源版本、DUT 身份、依赖闭包、夹具和合法配置 |
| 加载/解析 | 实际 Loader、定义路径、原生模型身份 |
| 初始化 | 实际生命周期、类型/通道解析、调度上下文 |
| 激励 | 输入/参数/事件何时注入，类型及通道如何对应 |
| 执行 | 原生调度发生的证据，停止条件和模型时间/周期含义 |
| 观察/断言 | Actual 来源、样本数量及时间、Expected/性质依据 |
| 清理 | wrapup/释放状态、线程/文件/进程清理、源文件未污染 |

参数可能需在初始化前设置，Token 可能需在接收器准备后注入；以已验证的 Profile 定义顺序，**禁止照抄一个固定的 `initialize → setInputs → fire` 用于全部 FB**。

### 9.4 不靠“无异常”推导实际执行

至少证明指定 DUT 已加载，并按预期原生调度参与了该场景。证据可来自现有只读执行监听、受控 Trace、模型状态和输出采样，不能只有外层入口方法返回。

对被原生调度扁平化的复合 FB，不强求某个外层 `fire()` 必须被调用；应记录其实际内部执行映射。不是“方法名存在”就证明业务跑过了。

输出缺席可能是合法事件语义，也可能是夹具/调度错误。必须根据 Case 的观察契约区分：预期出现但未出现、预期一定窗口无事件、无需该输出、未知。不能把“一个 Token 都没拿到”视为默认成功。

### 9.5 不吞错误、不以重试洗绿

业务断言失败、运行错误、超时、未知依赖和清理失败分别记录。每次重试保留 attempt ID、原因和前序结果；后续一次成功不能抹掉先前不稳定失败。独立用例顺序可调整以检查污染，单个时序用例的步骤不能随意打乱。

若已使用 JUnit 参数化测试，可继续复用其每次调用的生命周期；若使用动态测试，需显式保障每个生成测试的独立 setup/cleanup，不能假设 `@BeforeEach/@AfterEach` 为每个动态子测试执行。[R4]

## 10. 判定体系：运行状态和业务证据分开

### 10.1 一个结果至少有三个维度

| 维度 | 建议值 | 说明 |
|---|---|---|
| **最高完成阶段** | `DISCOVERED / DESCRIBED / INITIALIZED / EXECUTED / OBSERVED` | 只表示实际到达哪一步，不能因后续失败掩盖前面事实 |
| **用例结果** | `PASS / FAIL_ASSERTION / ERROR / BLOCKED / TIMEOUT / SKIPPED / INCONCLUSIVE / NOT_RUN` | 明确区分业务不符、环境错误、未运行和证据不足 |
| **验证依据** | `EXECUTION_ONLY / CHARACTERIZATION / REQUIREMENT_ASSERTIONS / PROPERTY_ASSERTIONS` | 声明“通过”到底指运行完成、历史特征不变，还是有业务依据 |

`CHARACTERIZATION` 指已记录行为的回归检查，不自动证明该历史行为正确。抓错能力另用 `NOT_EVALUATED / PARTIAL / ASSESSED_FOR_LISTED_FAULTS` 及变异实验记录表达，不宣称覆盖全部缺陷。

### 10.2 对外名称必须准确

允许写：

- “本批 X 个变体完成运行接入检查，Y 个执行了有需求依据的业务断言。”
- “某 FB 在 Profile P、配置 V、用例集合 T 下通过；其他配置未验证。”
- “缺 Expected，但已具备真实输入、执行与输出采集能力。”

禁止写：

- “没有崩溃，因此业务测试通过。”
- “相同类型组中一个通过，因此整组通过。”
- “8 个已通过，因此这个 Runtime 适配全部 FB。”
- “一次通过证明该 FB 在产品异构核上也没有问题。”

### 10.3 测试任务完成与全库业务通过是两件事

一个盘点/试跑任务可以正常完成并如实报告许多阻塞；它的任务成功不是业务 PASS。CI 对已纳入正式回归的用例应有单独门禁：预期执行项未执行、未知结果、错误或超时不能被汇总成全绿。

命令退出码和测试报告映射优先沿用现有规范；如需扩展，明确“批处理任务状态”和“业务门禁状态”，禁止一个 `exit 0` 混淆两者。

## 11. Expected 与批量业务用例的来源

### 11.1 继承现有可信性规则，不批量制造答案

现有 8 个 FB 的有效 Oracle 和测试直接复用。新用例必须标明依据：需求/规格、数学定义、独立参考、已确认历史回归基线或其他经批准来源。

从当前 DUT 的运行输出采集的数据，只能先进入观察/特征记录区。**不能同一次流程“运行 → 写 Expected → 再运行全绿 → 宣布业务正确”。**Ptolemy `NonStrictTest.trainingMode` 会收集输入作为参考值而不是执行检查，因此不得在正式验收中误开训练模式；与其共享的相关配置也要核实。[R5]

不要求用户手工计算每个 FB 的答案。AI 可基于规格提出用例，固定程序可按明确公式计算预期，已有可信数据也可复用；但所有来源均需可追溯。缺依据的项目进入 Oracle 待补队列，不阻止其他项目接入。

### 11.2 行为模板的迁移需有语义依据

可按实际业务定义复用边界、Reset、重复运行、合法范围等模板；但不能看到类型或名字相似就认定单调性、线性、复位后等价等性质必然成立。

模板必须同时声明适用条件、输入域、参数限制、状态前提和出处。浮点容差、无事件窗口、样本数量、允许随机性由测试契约规定，不在失败后随意放宽。

### 11.3 不把“人参与验收”设成批量吞吐瓶颈

用户负责批次与关键方案授权，不要求逐个操作图元、录制鼠标或人工给每个用例签字。运行、比对、留证据和大部分汇总都自动完成。确实缺少业务定义时，集中汇总一个决策问题，而不是让 AI 擅自补答案。

## 12. 失败治理：先聚类，再证明根因，最后公共修复

### 12.1 两级归组

**症状分组**可根据失败阶段、异常类型、关键栈帧、Profile、端口类型和依赖信息自动产生。但异常文本相同不代表根因相同。

**根因分组**要在代表案例中证明：哪个共同前置条件/实现缺陷导致失败、最小修复是什么、为何该修复可能覆盖组内对象。未验证成员仍标为候选受影响，不直接通过。

推荐错误类别：

```text
DISCOVERY_ERROR / IDENTITY_CONFLICT / DEPENDENCY_MISSING
CONTEXT_UNRESOLVED / TYPE_UNRESOLVED / CHANNEL_BINDING_ERROR
UNSUPPORTED_CAPABILITY / INPUT_INVALID / INITIALIZATION_ERROR
EXECUTION_ERROR / OUTPUT_OBSERVATION_ERROR / ORACLE_MISSING
ASSERTION_MISMATCH / TIMEOUT / RESOURCE_LIMIT
CLEANUP_ERROR / FLAKY_RESULT / UNKNOWN
```

### 12.2 共同阻塞单

每组至少记录：组 ID、症状摘要、具体成员、候选共因、证据与反证、代表选择、拟修改组件、预计覆盖范围、需补配置、验证计划和批准状态。

**成本预估可以给区间和不确定性，不能把“预计可解锁 30 个”写成“已经支持 30 个”。**

### 12.3 公共修复归宿

| 发现 | 正确归宿 |
|---|---|
| 端口名称/参数/输入序列不同 | Descriptor 或 Case |
| 数组/记录/多通道等已有语义缺适配 | 公共类型/绑定适配器 |
| 生命周期或清理错误 | Runner/Core 修复 |
| 原生上下文和调度契约有真实差异 | 经批准的 Profile/上下文适配 |
| DUT 本身业务错误 | 独立缺陷与业务修改任务，不借“适配”顺手改掉 |
| 特殊外部依赖 | 显式外部适配或暂时阻塞，披露验证范围 |
| Runner 为特定名字计算答案 | 禁止，移除业务污染 |

### 12.4 一次修复的完整验收

```text
保留原失败 → 在代表案例复现 → 按批准范围最小修改
→ 代表恢复 → 重跑组内所有批准成员
→ 回归原有 8 个及当前已纳入的受影响用例
→ 检查新增真实覆盖与未解决成员
```

批次内一个特殊问题超过约定调查预算，就记录证据和下一步建议，继续其他条目。不得无限陷在单个 FB，也不得静默跳过。

## 13. 测试系统自身必须通过的检查

以下为新增批量层的验收，已有项目已具备的直接复用证据，不重新造框架。

| 检查 | 应得到什么 |
|---|---|
| 清单中一个无效路径或未知 ID | 明确错误，不少算一个条目 |
| 批次实际收集到 0 个测试 | `NO_CASES`，不报全通过 |
| 输入类型/通道不符合契约 | 明确拒绝或失败，不静默截断/转换 |
| DUT 被正确加载但没有实际执行 | 不计入已执行覆盖 |
| 预期输出未出现 | 按观察契约失败/不确定，不用上一次结果填充 |
| 一个任务超时或退出 | 有记录，能清理且其余条目按策略继续 |
| 顺序、独立运行与批量运行比较 | 确认隔离；不能交换同一用例内部时序 |
| 原始输入文件和定义校验 | 未被训练模式、保存或变异实验污染 |
| 描述/测试/依赖变化后重跑 | 不使用过期缓存冒充新执行 |
| 每批对账 | 计划项全部有结果，失败和阻塞没有被隐藏 |

可为批处理调度器本身创建测试替身来模拟“超时/进程退出/异常”。这类测试只证明**调度器**能处理异常，不得计入真实 FB 覆盖，也不得把替身置入 FB 正式执行链。

### 13.1 代表性变异检查的准确用途

对新增公共适配能力和纳入行为验证的关键 FB，沿用已冻结测试，在副本中制造合法、相关的业务错误，检查是否被断言检出。若只改了 Expected 后失败，只能证明比较器有效，不能代替 DUT 变异。

分别报告被业务断言检出、仍存活、无覆盖、无效变异/加载失败、超时、可能等价等状态。没有证据不能把存活变异宣布等价，编译失败也不能计为业务断言检出。PIT 等成熟变异测试工具也区分多种结果；这里只借鉴结果记账，不要求引入 PIT 去处理私有 XML。[R7]

代表性检查不能证明“所有隐藏步骤完整”，作用是积累当前支持范围的证据并暴露缺口。无需为每个接入层 smoke case 强制建设复杂隐藏测试平台。

## 15. 增量执行与变更影响

记录模型定义、传递依赖、父级配置、参数变体、输入 Case、Oracle、Runner/Profile 和构建环境的指纹，用于判断哪些结果过期。不要只用目标 XML 的 Hash。

变更规则：

| 变化 | 最低重跑范围 |
|---|---|
| 某 FB 定义/参数变体/用例 | 该项及已知依赖它的测试 |
| 公共输入类型/观察器 | 使用该能力的所有已适配变体 + 基线保护 |
| Profile / 调度契约 | 使用该 Profile 的用例，不能只重跑代表 |
| 公共依赖或父级定义 | 依赖图中的受影响项目；依赖图不完整时扩大范围并披露 |
| Runner 核心或运行环境 | 8 个基线以及影响分析确定的现有回归范围 |
| Expected/业务规则 | 单独记录变更理由和授权，重新计算有关验证结论 |

缓存可复用描述与已有结果作为历史证据，但报告必须标 `CACHED` 和原 run ID，不能冒充本轮重新执行。依赖闭包未知时不做精确缓存命中承诺；先失效或保守重跑。历史成功不能覆盖当前失败，取消/超时结果不能在续跑时被直接当成已完成成功项。

## 16. 复用边界：哪些改动需要，哪些属于走偏

允许将已证实的公共能力增加到 Runner/Profile。并非“Runner 一行都不能改”，也不是“出现 FB 类名一律非法”：原生工厂可能合法使用类型标识。真正要审查的是**是否按具体 FB 业务含义计算输出、跳过生命周期或隐藏专用修补**。

下列做法不允许作为扩展成果：

- 同一个 FB 一份专用执行程序，把它们包进统一按钮后声称通用化。
- 用 Descriptor 内的任意代码重新实现每个 FB 的初始化、调度或业务算法。
- 在测试核心中按 FB 名称固定输入输出，或把 Expected 返回给观察端。
- 遇到缺依赖就添加空类、默认返回值，遇到输出缺失就跳过断言。
- 为获得更多成功，改变原生调度、删除子图元、缩短场景、静默改类型/通道/容差。

测试外围可注入输入源、时钟/环境或观察器，**但必须在已声明的执行契约中，且明确不替代被测逻辑**。通过原生虚拟模型时间调度并不等于伪造时间；以随意自增计数器代替定时语义才有问题。不能仅按 `Mock/Fake` 名字分类，也不能因“它是原生类”就证明配置适当。

不能为了批量化改变正式 FB 业务代码。发现真实缺陷时提交证据与修复建议，待用户单独批准；修复记录与测试适配记录分开。

## 17. 覆盖与效率报告：不要只给总 PASS 数

### 17.1 覆盖分母

同时报告三个集合：已发现定义总数、已确认可执行候选定义数、已批准测试范围。抽象定义、未启用库、未知和阻塞项目保留原数及理由，不通过删清单制造高覆盖。

对已批准范围分别统计：具备实际运行证据的定义/变体数、有独立业务断言且当前通过的定义/变体数、Case 通过/失败/错误/未执行数。一个定义部分变体通过、部分失败要标 `PARTIAL`，不能只取成功记录。

百分比写明分母、版本、目标和是否来自实际运行；发现范围不完整时不报“全库 100%”。如无法得到可靠分母，先报告绝对数量与未确认范围。

### 17.2 一轮必须回答的效率问题

1. 不改 Runner 核心，实际新增接入了多少 FB/变体？新增了多少配置和 Case？
2. 每项公共修复实际解锁了多少，而不是预计解锁多少？
3. 还剩哪些根因组，占未适配范围多少？是否有大量重复的专用配置代码？
4. 时间主要花在运行接入、构建、运行、业务 Oracle 还是定位缺陷？
5. 哪些工作下一批不应再重复？

若当前没有工时或操作记录，就写 `NOT_MEASURED`，不得倒推编造。业务用例设计仍可能昂贵，不要把它伪装成“批量接入失败”。

### 17.3 给用户的短报告模板

```text
FB 批量适配进展（实际运行范围：……）
起始基线：8 个 FB；本轮 Runner/Profile 版本：……
库内已发现：……种定义；清单是否完整：……
本批批准：……种定义 / ……个变体 / ……个用例
新增实际可执行：……；新增业务断言通过：……
失败：……；阻塞：……；未运行/不确定：……
原有 8 个及受影响回归：……（证据……）
公共改动：……；各自实际解锁数量：……
主要剩余阻塞：……
下一轮建议：……
需你批准的事项：……
```

附结构化结果和可定位日志，不把几十页原始输出直接当结论。

## 18. 具体行动包与退出条件

不是机械顺序清单：有现成产物就复用，能并行读取就并行。固定的是关键授权、真实执行和如实记账。

### 行动包 A：全库清单与第一批提案

**做：** 登记已有 8 个；在授权范围发现定义和边界；整理现有能力；标注候选匹配/缺口；提出第一批及资源预算。

**交付：** 清单、能力表、未知项、2–3 个有实际依据的批次选项、一张决策卡。

**退出：** 用户看得出库内规模、可复用范围和下一批价值，并明确批准。此时不承诺候选均会通过。

### 行动包 B：自动接入与首批运行

**做：** 按批准目标补最薄的自动接入层；现成模块不重写；准备真实夹具；运行并逐条记录；无可靠 Oracle 的项目只做声明的运行检查。

**交付：** 可复用执行入口/原命令说明、批次清单、逐项结果、观察记录、完整错误与清理证据。

**退出：** 本批计划项全部对账，运行/业务等级明确；没有虚报适配，也没有卡死拖垮全批。通过数量按实测，不规定必须全绿。

### 行动包 C：最高价值共同阻塞

**做：** 分组并证明代表根因，提交改动方案；获准后补公共能力；重跑批准组内全部成员和已有回归。

**交付：** 根因证据、最小 patch、前后结果、真实新增覆盖和剩余阻塞。

**退出：** 能解释一次公共改动为何有效、影响谁、未覆盖谁；不能只用代表案例盖章。

### 行动包 D：扩大与增量维护

**做：** 根据已有能力继续增加经批准的批次；补业务素材和关键错误检出验证；为定义/依赖变化触发保守增量回归。

**退出：** 同类新 FB 主要增加描述和 Case；新问题按公共缺口治理。无法适配的项目有明确界限与后续选项，不无限投入。

## 20. 本阶段总验收

| 验收项 | 成功证据 |
|---|---|
| 继承现有成果 | 8 个基线及前序证据已被引用保护，不是重新起炉灶 |
| 清单可核对 | 定义、变体、用例分开，未发现/未知范围明确 |
| 匹配不冒充成功 | 候选和实跑结果分离，未知条件不自动选 Profile |
| 同类可以批量接入 | 原生定义和上下文真实，主要新增数据而非专用 Runner |
| 公共缺口可以批量修复 | 代表定位后有整组实际回归及原有基线保护 |
| Runner 不决定业务答案 | Expected/性质有来源，观察数据与正确性区分 |
| 批处理稳定 | 超时、错误、清理、空用例、重试、缓存都可审计 |
| 报告不夸大 | “能跑”“通过具体业务用例”“有抓错证据”分别统计 |
| 用户保持决策权 | 批次和重大改动先讨论，授权内自动执行不反复请示 |

本阶段可以成功交付批量能力，同时如实存在未适配 FB；“批量系统可用”不等于“全库全部正确”。如实际发现 FB 存在另一套执行模型，不强行塞进现有 Profile，先给出证据与备选方案。

## 21. 开发 AI 开始工作的直接指令

> 现在以已经完成的 8 个真实 FB 及当前可用 Runner 为基线，启动全库发现与批量适配。先复用已有回归、隔离和可信性验真成果，在授权范围读取图元目录/注册/定义与真实依赖，建立 FB 定义清单和已验证能力表。不要默认逐个研究全部业务算法，不按“第九个更复杂 FB”继续写专用 Runner，也不要推翻构建环境。
>
> 将候选划分为现有能力可覆盖、缺配置/激励、缺公共能力、外部依赖和未确认；业务 Oracle 是否齐备另记。先提交第一批候选、验证目标、必要修改、隔离预算及风险，待我批准后执行。授权后自动生成描述/夹具、批量运行、逐项报告；按共同根因提出公共修复，而不是为每个 FB 加补丁。
>
> 所有结论绑定具体定义、运行变体、Case、版本和证据。“能加载”“能执行”“业务断言通过”分别报告；不得以无异常或当前输出自动回填的 Expected 证明业务正确。无法确定的项目留档并继续其他已授权项目，不用空 Stub、改变调度或删内部结构来凑成功数量。

## 22. 参考依据与适用限制

以下为公开技术依据，核查日期为 2026-09-07。它们用于解释机制，不代替公司 BEH 当前分支的源码和实际运行证据；也不授权迁移构建方式或安装新工具。

**[R1] Ptolemy II — Testing Ptolemy II**  
https://ptolemy.berkeley.edu/ptolemyII/ptII11.0/ptII/doc/coding/testing.htm  
官方记录模型测试的 `test/auto/` 组织与批量运行机制，并区分单元测试、模型系统测试和 JUnit 入口。本手册借鉴“统一入口承载模型集合”，不照搬其 Ant/Tcl 构建环境，也不把“没有异常”作为本项目业务正确性标准。

**[R2] Ptolemy II — CompositeActor**  
https://ptolemy.berkeley.edu/ptolemyII/ptII11.0/ptII/doc/codeDoc/ptolemy/actor/CompositeActor.html  
参考 `inputPortList()`、`getDirector()` 以及 local/executive Director 与端口接收器的关系。用于强调原生接口枚举和正确上下文，不保证 BEH 所有 FB 可独立实例化。

**[R3] Ptolemy II — Director**  
https://ptolemy.berkeley.edu/ptolemyII/ptII11.0/ptII/doc/codeDoc/ptolemy/actor/Director.html  
参考生命周期、模型时间和 `fireAt()`。用于避免以统一手工循环或任意计数器替代不同运行域的语义。

**[R4] JUnit 5.10.3 User Guide**  
https://docs.junit.org/5.10.3/user-guide/index.html  
参考 Supported Java Versions、Parameterized Tests 和 Dynamic Test Lifecycle。该固定版本文档支持 Java 8；不是推荐升级到此版本，更不是宣称任意最新版兼容现有 JDK。继续使用项目已验证版本优先。

**[R5] Ptolemy II — NonStrictTest**  
https://ptolemy.berkeley.edu/ptolemyII/ptII11.0/ptII/doc/codeDoc/ptolemy/actor/lib/NonStrictTest.html  
参考 `trainingMode` 记录输入而非执行检查的定义，用于区分观察数据与验证依据。

**[R6] Java SE 8 — Process**  
https://docs.oracle.com/javase/8/docs/api/java/lang/Process.html  
参考等待、进程退出、终止与输出流管理接口。用于批处理资源控制，不代表独立进程本身是安全沙箱。

**[R7] PIT — Basic concepts**  
https://pitest.org/quickstart/basic_concepts/  
参考变异测试中的 killed、survived、no coverage、timeout 等结果区分。不要求本轮安装 PIT，也不推定它能直接变异私有 FB XML。

**关联的本地项目规范：** 已有 FB MVP、Runtime 真实性、Runner 通用化审查和测试可信性文档继续作为历史证据与补充约束。已完成阶段不重走；若与本手册的当前授权或口径确有冲突，记录冲突并提请用户决定，不能由 AI 静默选更容易通过的一条。
