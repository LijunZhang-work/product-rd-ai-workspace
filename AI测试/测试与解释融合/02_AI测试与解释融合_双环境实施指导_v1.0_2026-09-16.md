# BEH AI 测试与解释融合：双环境实施指导

版本：v1.0｜修订：2026-09-16（按用户要求改为源码探索优先）
适用对象：能够访问 BEH 工具源码、现有 FB/CB 测试、图元工程及相关配置的本地执行 AI。
默认执行宿主：现有 DeepSeek Harness；文字模型为主，多模态仅用于必要的静态视觉核对。
文档性质：目标说明、源码调查问题与候选建议。作者没有查看 BEH 源码，没有运行工具或连接产品；本文不代表已经查明的系统架构或确定的技术方案。

## 阅读前提：先研究源码，再决定怎样实现

**“不连接真实产品”和“连接真实产品”是用户的两种使用场景，不能据此推断底层是两套执行链，也不能据此确定引擎在哪里运行。** 两种场景是否共用引擎、连接产品时是否仍需启动本地引擎、本地与产品是否协同运行、GUI 只是呈现还是承担必要执行职责，目前均未知，需要本地 AI 自行调查。

本文件区分三种内容：
- **用户已明确的目标**：优先融合 AI 测试与 AI 解释；普通人能理解场景与依据；覆盖有产品与无产品的使用情况；以文字与结构化信息为主；保留回看及夜间持续工作的能力。
- **用户反馈与历史资料线索**：已有 FB/CB 测试、Windows Java 入口、GUI 在线取值和断点等。它们帮助定位调查入口，但不证明新任务中的完整调用关系或当前版本支持范围。
- **作者的候选建议**：运行入口、复用方式、适配器、报告格式、样本数量和推进顺序。均由本地 AI 根据源码、配置与最小运行验证选择、调整或否定，不得为了符合本文而拼出不存在的架构。

本地 AI 应明确记录“源码已证实、运行已验证、仅有线索、尚不清楚”。对实现事实，以匹配版本的源码、配置和实际运行证据为准；源码显示当前行为是什么，并不自动决定业务应该怎样。业务正确性仍需适用需求或其他独立依据。发现本文建议与事实不符时，说明证据与调整理由，在用户既有目标和授权范围内继续推进。

## 0. 最终要交付什么

形成一套可持续执行的“业务场景—实际测试—真实记录—检查—过程解释—必要补测”工作方式，研究并支持两种使用场景：
1. **不连接真实产品**：查清现有工具在这种情况下实际能测试什么、怎样执行、需要哪些组件；据此实现适用测试与解释，明确缺口。
2. **连接真实产品**：查清连接前后完整执行链、各组件职责和真实数据来源；据此实现适用测试与解释，明确缺口。

希望两种场景的业务含义、证据表达和解释体验保持一致。是否共用执行器、是否需要不同适配、哪些场景可以复用，均在查清实现后决定；不预设两个后端，也不强行把所有行为抽象成同一种“step”。

当前优先融合解释与测试。AI 开发考试、自动删图修图、完整画布重建、高级动画和多模型编排均不作为本期前置。只留下将来可复用的对象标识、事件记录和场景资料。

### 用户能获得的结果
- 看懂每个测试在测什么、为什么测、预期有什么依据。
- 看懂真实运行中的关键周期、状态和输出变化，而不只收到 PASS 表。
- 知道哪些结论已验证、哪些只是观察、哪些业务规则待核对。
- 不连接产品时也能持续运行适用测试；有产品时补充真实环境证据。
- 夜间任务能保存进展、隔离单个阻塞，并把少量真正需要业务判断的问题集中呈现。

## 1. 继承的事实与新增线索

| 项目 | 当前依据 | 本地执行要求 |
|---|---|---|
| 工具源码 | 用户确认拥有原生工具源码，包含 GUI 相关源码 | 从源码查能力与调用链；不以 AI 看懂动态画布为前提 |
| 现有测试 | 既有手册记录 8 个真实 FB 已接入；用户提到已有 CB 测试工作 | 先核对当前成果与实际支持范围，适用时复用，不推定都已接通 |
| 在线能力 | 用户新观察：GUI 可连接产品 IP，显示 debug 真实值，并支持断点等 | 视为待源码和实测确认的功能线索，不虚构协议、API、暂停范围 |
| 原生仿真 | 用户希望复用专业人员的仿真/调试方式，具体入口尚未核验 | 查清是否存在、执行在哪里、覆盖哪些依赖；不能由“能出图”推导“能完整仿真” |
| 解释现状 | 用户反馈解释不踏实、看不懂技术用例，业务符合性不明 | 先把已有用例与预期来源讲清，不只增加更多用例 |
| 运行环境 | 历史资料描述 Windows Java、WSL/镜像及 SSH/Linux 等已有环境 | 核对当前用途与依赖，不据此预设两种使用场景的执行位置 |

已有进展不因本期任务重新归零。读取现有代码和有效记录后直接继续；仅针对缺口与冲突补查。

## 2. 产品连接情况与解释程度是不同选择

| 选择维度 | 值 | 含义 |
|---|---|---|
| 产品连接情况 | 不连产品 / 连接产品 | 用户是否接入真实产品；实际执行位置另行查明 |
| 解释程度 | 基础解释 / 测试增强解释 | 是否要求相关运行与验证证据 |

本期优先研究并实现两种使用场景下的“测试增强解释”。保留基础解释入口，不要求每次阅读图元都执行测试。连接状态与运行位置分别记录，前者不能替代后者。选择连接产品不自动意味着证据更充分：错误版本、错变量或过期缓存同样可能误导。

### 两种使用场景共有的证据要求
查清被测实现是什么、在哪里执行、由谁驱动，以及输入和输出经过哪些环节。无实物产品时可能存在可运行能力，但不能预先认定具体引擎或仿真功能。连接产品时也不能省略本地组件和引擎依赖调查。若采用仿真、夹具、替代依赖或历史记录，说明它验证了什么、没有验证什么；不能用 AI 生成的数值冒充真实执行。

### 涉及实际产品时的边界
连接成功、取到一次值、完成行为测试是三个不同结果。只有读取且没有完整记录输入和相关前置状态时，通常先形成观察报告；有明确规则且观察信息充分时，可检查对应性质，但不能冒充主动控制了全部场景。
主动写值、强制值、暂停、单步、复位或下载等，只在已有明确授权和适用的测试设备范围内执行；读取失败不能自动升级到这些操作。

## 3. 首要任务：自主研究源码并验证真实执行链

### 3.1 可用的调查线索，不限定检索顺序
可从已有成功测试、项目启动代码、原工具使用说明、菜单命令、调试视图或界面字符串入手，由本地 AI 根据仓库实际组织选择路径。沿实际调用关系追到任务完成和数据返回，避免只看到某个类或界面按钮就猜其职责。
需要联合阅读实现、构建配置、工程数据、测试与日志；必要时做最小实验确认生命周期与数据流。若关键实现位于未提供的依赖中，标明调查边界，再利用可访问的接口和运行证据验证，不编造缺失调用链。

现成 API、插件点、脚本、命令、原生宿主内调用、少量源码适配都是候选方向。调查后比较适用性与维护成本，再决定采用什么；不预定一定能做到无 GUI、一定有可用接口或一定只需薄适配。优先复用经验证可用的能力，避免重复实现被测行为。

### 3.2 建议调查的问题
下面各项均同时研究“未连接产品”和“连接产品”两种情况，记录相同点、差异、条件与未知；表中组件名称仅用于提示检索，不保证系统具有这些模块或边界。

| 问题 | 要查清的事实 | 可采用的验证方式 |
|---|---|---|
| 加载与准备 | 工程、图元、配置怎样加载，是否编译/生成/部署，依赖和初始状态是什么 | 追踪已有成功路径并记录前置条件 |
| 引擎是否参与 | 两种情况各需启动什么，本地引擎是否必需、何时启动、实际承担什么职责 | 启动链、调用关系与匹配的运行记录交叉核对 |
| 被测逻辑在哪里执行 | 本地、产品或其他组件各完成什么，状态由谁持有 | 根据实现与实际观测标明位置；不能只凭连接状态推断 |
| 调度与时间 | 谁驱动计算，是否存在周期/事件/单步，“一拍”实际意味着什么 | 用代表场景验证输入生效和输出读取阶段 |
| 连接会改变什么 | 建连前后哪些路径、数据源或状态变化，断开后怎样处理 | 有设备时做限定范围验证；无设备时标待验证 |
| 对象与数值对应 | 图元实例、端口、内部对象与产品变量如何关联 | 追踪一个真实值从来源到解释输出的完整路径 |
| 数值是否可信 | 是否经过计算、转换、缓存、代理或订阅，类型与有效性如何表示 | 核对数据生产端和消费端；区分未知、旧值与有效值 |
| 调试与控制 | 断点/单步作用于谁，是否改变时序，哪些控制实际支持 | 结合实现和适用场景验证，记录影响范围 |
| 自动化接入 | API、命令、宿主生命周期、线程与 GUI 之间有什么依赖 | 在所需的真实上下文中完成最小调用 |
| 解释和回看 | 能取得哪些结构、状态、事件和历史记录，哪些拿不到 | 将一条解释关联到实际来源，明确未观测部分 |

用简洁表格或现有项目记录保留源码位置、配置条件、调用链、运行证据与未知项即可，不强制新建文档系统。仅有源码线索时标“待运行验证”；只列出类名或“看起来可以”不算接通。

### 3.3 源码与运行物一致
记录实际涉及的源码版本与未提交改动、运行组件（例如实际存在的 JAR/插件/可执行文件）、构建或生成配置、图元工程版本；涉及产品时也核对目标程序身份。哪些组件参与两种情况由调查确定。源码与实际运行版本不一致时，限制“原因分析”的确定性。
如果增加日志或适配，记录改动并检查其是否改变状态、调度或输出；不能用任意重编译版本替代原发布行为后不作说明。

### 3.4 GUI 与多模态的处理原则
用户希望以文字模型和结构化信息为主，因此优先调查能否直接取得模型、变量与事件。若真实服务依赖宿主生命周期、线程或界面动作，保留这些必要条件，再研究适当的自动化方式；不能事先认定 GUI 可完全绕过，也不宜默认靠 AI 持续观看动态画布。
关键静态画面、特殊绑定或无法由其他证据消除的视觉疑点，可少量使用多模态。GUI 树看不到画布内部对象，只能说明该观察入口的局限，不能代替对内部实现的调查。

调查围绕当前融合目标逐步展开，有条件就验证小范围路径并继续实现，不要求先读懂全仓。先交付“已知事实、未知项、推荐路径与理由、最小实验结果”，再据此推进；路径若需调整，更新依据，不反过来迁就本文猜测。

## 4. 融合工作：把现有测试变成可读业务场景

### 4.1 先解释已有用例
建议从已有成功样本选一个实际业务会用到的 FB，整理少量代表场景，例如 3～5 个，再考虑 CB 的适用样本。对象、数量和先后按现有接入及业务价值调整；这是控制首轮范围的建议，不是规定测试技术路线。FB/CB 是否共用执行器由源码决定。
如果没有找到产品中的实际用途，先标“组件行为测试”；不能根据名字杜撰新能源业务含义。

每个场景的数字、参数、步骤及观察结果来自可追踪的配置、测试代码和记录。中文说明与实际执行相互引用，不能成为另一份脱离程序的故事。

### 4.2 场景卡模板
| 字段 | 面向人的内容 |
|---|---|
| 场景标识与版本 | 场景属于哪个对象和哪份配置 |
| 业务/组件目的 | 检查什么行为，出错可能影响什么；未知影响保留未知 |
| 初始条件 | 启动、复位、使能、已有状态、输入/依赖前提 |
| 操作过程 | 输入/事件按怎样的顺序改变，等待或执行怎样安排 |
| 预期与来源 | 应发生什么；原始规则位置、适用条件和来源类型 |
| 实际结果 | 来自哪次运行、哪个环境、哪些采样/周期 |
| 差异和解释 | 哪里符合，哪里冲突，哪里证据不足 |
| 待确认问题 | 具体、可理解的业务问题及不同答案会改变什么 |

业务规则确认与执行状态分开。人可以反馈“符合我的理解、存在问题、不知道”；“不知道”进入待核对队列，不强迫用户读源码或承担不熟悉的设计责任。阅读确认不等于正式需求批准。
有明确现行规格即可据其执行，无需每条场景重新询问用户；真正有歧义的规则再集中交给能判断的人。

### 4.3 预期来源
- 可用依据包括适用需求/接口规则、明确数学或逻辑定义、经过验证的历史基准、独立参考模型。
- 从当前实现或当前输出得到的预期，先归为观察/行为快照；不能单独支撑“业务正确”。
- 更换一个 AI 不会自动让预期来源独立。AI 可以归纳草案，但必须保留推导来源与未知。
- 变更预期要记录规则依据与版本，并重跑受影响用例；不能为了 PASS 静默覆盖旧 Expected。

来源盘点不意味着废弃所有 AI 写的测试：逐项保留、纠正、补证据或降为观察。

## 5. 使用场景A：不连接真实产品时怎样测试

### 5.1 请本地 AI 自行查明
- 现有测试在没有产品时实际运行了哪些实现？是否依赖其他进程、环境、服务或生成产物？
- 原工具是否有可用的仿真、执行或调试路径？与当前测试入口有什么关系？各自支持范围和限制是什么？
- 输入如何进入、状态如何建立、计算由谁驱动、输出从哪里取得？哪些步骤可控制，哪些只能观察？
- 哪些行为能在当前条件下验证，哪些依赖未提供的环境？已有结果能否支撑当前版本的解释？

这些问题的答案决定实际测法。本文不能确定必须使用哪个引擎、现有 Runner 是否足够，或“无产品”一定意味着完全在本机执行。

### 5.2 可考虑的方向，按证据选择
若现有 Runner 已执行适用的真实实现，可优先补充场景说明、记录与解释；若找到更适合的原生入口，可用小样本核对能力和差异后采用。若需要夹具或替代外部依赖，注明替代范围及结论限制。
若当前条件下不能执行相应对象，应记录具体阻塞，继续可做的源码分析、已有记录解释或其他场景工作。分析历史记录时保留其采集身份，不能把它当本轮新增运行。
这些方向都不意味着重写一个与被测对象同名的算法就完成了验证，也不要求为符合本文而重建已有能力。

### 5.3 调查后制定适合该入口的运行步骤
可能需要准备工程与状态、施加输入或事件、驱动或等待运行、读取数据、检查并清理；具体需要哪些步骤、怎样排序和调用，由真实入口的语义决定。已有成熟入口能够完成这些工作时直接复用。
无论最终采取什么路径，都应能说明被测对象与版本、已知初始条件、实际输入或事件、有效输出、检查规则和未覆盖部分。涉及状态的测试需考虑状态污染；涉及非确定性的测试说明可重复程度，不承诺必然逐值一致。

### 5.4 “一拍”是待查语义
若实际入口或现有报告使用 cycle/step/tick/fire 等词，逐一查明它在当前上下文的含义。可能是一次模型调用、调度周期或测试动作；这些只是调查提示，不能直接套用。
只有查明周期号、逻辑时间或时钟关系后，才按相应口径讲解；否则仅说明已知顺序或时间来源。输入生效与读值阶段需要核对。没有证据不能写“一拍=100ms”，也不能凭首尾值补出中间状态。此要求同样适用于连接产品的情况。

## 6. 使用场景B：连接真实产品时怎样测试

### 6.1 重点调查完整执行链，包括本地引擎
从用户观察到的连接、debug 值和断点功能追踪真实实现，但不把“能显示产品值”推导为“工具仅负责连接与读值”。需要查明：
- 连接前后需要启动哪些组件？**是否仍需本地引擎、已有 Runner 或其他运行服务，它们具体承担什么？**
- 被测逻辑、调度、状态维护和数据转换分别发生在哪里？连接模式是否改变这些职责？
- 界面上的值实际由谁产生，经过哪些处理，如何对应到当前图元实例和产品程序？
- 连接、运行、监视、断点和单步之间有什么真实依赖？断点暂停的是哪个执行部分，其他部分是否继续？
- 无设备、断线或重连时，原工具保留什么状态、返回什么数据？

本地引擎可能参与，也可能不参与，或只在特定功能下参与；这些均是待查情况。**必须依据源码和可取得的运行证据作判断，本文不给预设答案。**

### 6.2 调查后选择自动化接入点
建议优先考虑原工具已有、经验证适用的能力，以减少重复实现。但复用的可能是完整运行链，也可能是其中一部分；是否通过 API、原生宿主、现有测试入口或新增适配接入，由真实依赖决定。
可从一个目标明确、范围有限的实际场景验证输入到输出的路径；条件不足时先验证能完成的环节。仅完成建连或取值，就按相应范围报告。执行位置、数据来源、场景控制程度与验证范围分别说明，不能用连接状态代替。

### 6.3 根据实际链路核对的数据和操作语义
以下是调查提示，发现相关能力后落实到实现中；不存在的能力可说明不适用，不能凭空增加字段值：
- 目标身份、程序/工程对应关系、图元和实际数据的映射；两端如有引擎或其他运行组件，分别核对版本与职责。
- 输入与初始状态是否可知、可控，实际注入或观察经过哪些环节；直接写内部变量时说明绕过了什么。
- 时间、周期和采样批次来自哪里；是否能证明多个值属于同一时刻；GUI 刷新是否仅是显示频率。
- 是否存在转换、缓存、旧订阅、断线和重连；新鲜度无法确定时如实显示未知。
- 实际控制能力与影响范围，以及本轮任务结束时需要进行的清理。

主动写值、强制、断点、复位或下载等按现有明确授权执行；不能从“能读取”推导出允许所有控制。断点若改变运行时序，应在结果中说明。

### 6.4 没有设备时可推进到哪里
按已取得的源码与环境条件，继续可做的调查、实现、适配验证或资料整理；哪些事情确实能完成，由本地 AI 判断，不预先承诺在线代码一定能脱离设备验证。需要实机的结论保持待验证。
可复用历史真实记录做解释，但说明时间、版本和来源；网络替身只验证其实际覆盖的适配逻辑，不算产品实测。继续其他不依赖设备的有效任务，不把一个阻塞扩大到全部工作。

## 7. 两种使用场景怎样融合，由调查结果决定

### 7.1 先查真实关系，再决定共享和适配范围
用户希望两种使用场景都能获得可理解、可追溯的测试与解释。可复用场景含义与证据表达，但并不因此必须在同一 Runner 上增加模式开关。共享实现、按功能适配或复用原工具其他入口，均由源码调查决定。
准备、输入、执行、观察、清理可作为职责检查提示，不是必备 API 清单。能力不存在时标明限制；不能通过延时等待假冒单步，也不能强制拆分原工具本来耦合的生命周期。

同一业务场景可绑定不同环境的对象、单位、输入方式和检查时点。适配差异透明展示；禁止为让两边一致而偷偷改变业务预期或参数含义。

### 7.2 能比较的条件
同一行为定义、适用参数、初始状态、输入/事件序列、执行时序及观察点可对齐时，才比较结果。核对实际参与的实现、运行库、构建配置和执行条件；是否涉及 Java、生成代码或其他模型，以及它们之间的关系，均以调查为准。
浮点容差、时间窗口与单位转换必须有依据，不能为消除差异任意放宽。非确定性与采样丢失先解释，不强行逐行比对日志。

差异可能来自执行环境、采样、映射、输入方式、测试预期或程序本身；不能预设一边永远正确。两边一致也可能共享同一实现缺陷，仍不替代独立业务依据。

### 7.3 建议保留的结果信息
| 类别 | 建议记录内容；未知明确标记 |
|---|---|
| 身份 | run_id、case_id、场景版本、对象、配置；产品连接情况与实际执行位置分开记录 |
| 版本 | 源码/运行物/图元工程；在线目标程序身份及匹配状态 |
| 输入与初始状态 | 实际施加的值/事件/顺序，已知状态与未知前提 |
| 观测 | 类型、单位、实际值、来源、有效性、采样批次/周期与时间；缺失明确为空 |
| 检查 | 规则、Expected来源、比较方式、实际结果、覆盖与未覆盖 |
| 解释 | 每条结论对应对象、规则、运行记录或源码，推断与未知单列 |
| 执行状态 | started/completed/failed/interrupted；部分结果不能补成成功 |

按能力可选记录内部状态、线程/任务、原生事件和画面；不能要求不存在的字段导致整个任务无法开始。模式与字段变更显式兼容旧结果，保留 Schema 版本。

## 8. AI 解释必须贯穿测前与测后

### 8.1 测前：解释场景与待检验问题
说明对象作用、场景目的、输入安排、初始状态、候选预期及其依据。将原始术语解释成当前场景中的具体意义，列出缺少证据的假设。
这一步不预先写成“已证实运行过程”。已确认规则可以直接驱动测试；未确认规则可以帮助设计观察，但不能假装业务已获确认。

### 8.2 测后：单独进行一次运行过程讲解
测后解释需要比测前概览更深入。以下角度按实际场景组织，不要求每次机械输出七个栏目；没有相应证据时说明未知：
1. **实验导航**：这次为什么这样安排输入，想区分哪种行为。
2. **关键步骤时间线**：变化前后是什么，关键周期/事件如何对应。
3. **状态解释**：已观测状态与源码推断分别呈现；状态不可见时不编造数值。
4. **因果依据**：哪段代码或原生执行规则支持原因；仅有相关性时保留候选原因。
5. **场景对照**：正常、边界、复位、使能等适用场景合起来说明什么，实际没测的列出。
6. **业务联系**：对产品实际用途的含义及未知；区分组件定义正确与产品用法正确。
7. **使用边界与疑点**：哪里容易误解，修改/使用时需注意什么，什么问题还需规则或补测。

原始逐步记录保留，默认讲变化与决定行为的关键步骤。专业版与小白版共享事实，不因通俗化删除方向、单位、阈值、时间或限制。

### 8.3 解释驱动的有限补测
先查现有记录与源码，再提出能区分候选原因的最小实验。记录“问题—候选解释—新增输入/观察点—预期区分结果”。一次只改变必要条件，保留原实验身份。
补测总次数、单对象时间和资源预算使用现有任务预算，缺省可从小额上限起步并在任务配置中明示。超预算保存疑点并继续其他独立对象，不无限研究。
补测能辨明“程序怎样运行”；业务究竟应该怎样仍由适用规则决定。避免事后为实际输出编理由。

### 8.4 独立显示三个状态
| 维度 | 可能状态 |
|---|---|
| 预期依据 | 有规则依据 / 独立参考 / 仅实现推导 / 待业务确认 |
| 实际执行与检查 | 未运行 / 已观测 / 符合约定预期 / 冲突 / 阻塞 |
| 解释证据 | 有直接证据 / 有源码支持的推断 / 存在多个候选原因 / 未知 |

可以同时显示“执行符合预期；预期仅来自实现；业务待确认”。人反馈“不知道”不会被算法变成同意。不得把高语言置信度当测量或业务证据。

## 9. 回看与复跑，从结构化记录开始

本期优先完成“运行过程回看”和“适用场景重跑”，暂不建设完整开发操作播放器。

- **过程回看**：按实际事件与采样顺序显示输入、可观测状态、输出、断点/错误及解释关联；只呈现真实记录覆盖的过程。
- **重新执行**：研究怎样利用保存的版本、初始状态、输入序列和执行条件重跑。两种连接情况下都要查清哪些条件能控制、哪些不能；依实际能力说明可复现程度，不能仅凭“离线/在线”判断是否确定性运行。
- **历史记录再分析**：没有设备也可解释已有真实记录，但标记采集日期/版本，不能声称本次又在设备上运行。

GUI 刷新与设备采样分别记录；不能把两次读值之间插值生成的曲线当逐拍实测，不能自动填补丢帧、断线或未采到的内部状态。
记录对象与步骤标识、状态差异，为以后 AI 开发操作回看留接口即可。若未来要记录创建/删除/连线，再接真实编辑命令；本期不扩展考试系统。

## 10. 推进建议：调查与小范围实现交替进行

以下是需要覆盖的工作内容，不代表已确定的模块划分或固定开发顺序。本地 AI 根据源码和现有成果调整；不必先完成全仓研究，也不要求拆成两个后端。

| 工作内容 | 可尝试的做法 | 需要留下的依据 |
|---|---|---|
| 源码调查与小实验 | 追踪一条实际功能的完整调用链，研究两种连接情况下的依赖 | 已证实事实、待验证假设、最小运行结果和选择理由 |
| 代表样本融合 | 选已有接入且有解释价值的 FB/CB，连接场景、测试记录与测后讲解 | 可核对来源；预期、实际结果和解释证据分清 |
| 不连产品的适用测试 | 按查证后的路径实施；能复用的结果和能力直接复用 | 实际执行组件、覆盖范围、限制及可复跑程度 |
| 连接产品的适用测试 | 按真实的本地与目标依赖接入；设备可用时验证适用场景 | 各组件职责、真实数据来源、运行证据；无实机项标待验证 |
| 共用证据与过程回看 | 尽量利用原有报告和记录，按真实关联串起解释 | 对象、场景、版本和过程能够对应；缺失不编造 |
| 夜间扩展与必要对照 | 首轮流程可用后扩展；只有条件可对齐的场景才比较 | 完成范围、冲突、阻塞、待业务核对问题 |

一个 FB 再一个 CB、每个先取少量用例，是便于控制首轮范围的候选安排，可按实际接入与业务价值调整。最终仍需说明 FB、CB 两类各自达到什么范围。
无设备时继续不依赖设备的有效工作。无法实现的目标如实报告部分完成或阻塞，不用调查报告冒充运行完成，也不把未经验证的建议作为必须服从的方案。

## 11. 夜间无人值守怎么安排

### 下班前任务应包含
选定对象或允许的批次、可读取的工程范围、环境选择、已许可操作、时间/资源预算、结果位置。优先读取现有配置，不要求用户重复手填可查到的信息。
在线会话如果由多方共用，明确占用与控制范围；无法保证时仅按允许的观察方式执行，不争抢控制。

### 运行期间
每个对象完成一个小闭环就落盘。开始、结束、失败或中断分别记录；任务恢复时先核对版本、最后完成步骤与目标状态，不盲目重复有副作用动作。
发现业务歧义时记录具体问题及候选后果，继续其他有依据的测试与观察；技术阻塞按根因归组，公共问题修一次后重跑受影响样本。
不因单个对象卡住停止整个批次。只对明确可恢复的失败做有上限重试，不通过修改 Expected、跳过初始化或伪造依赖凑 PASS。

### 次日给人的首页
优先展示：实际完成范围、主要运行结论、关键异常、少量待业务判断问题和一键可查看的关键过程。详细原始记录可展开，不把数百条断言原样当首页。
用户不懂技术时，解释先呈现场景后果与可核对来源；业务仍不清楚时保持待确认，不把“读过报告”当需求批准。

## 12. 需要落地的最小产物

使用现有项目目录和报告格式优先。以下是逻辑产物，不强制新造这些文件名或新增独立模块：
1. **调查事实与方案依据**：实际组件、调用关系、两种连接情况下的依赖、运行证据、未知项，以及采用或否定某条建议的理由。
2. **场景与规则清单**：中文场景卡、Expected来源、适用环境、对象/输入映射。
3. **运行证据包**：基线、实际输入、事件/采样、检查、失败、中断、可复跑信息。
4. **运行过程解释**：场景导航、关键步骤、原因依据、业务联系、对照与未覆盖。
5. **夜间汇总和待核对队列**：完成范围、冲突、阻塞、具体业务问题。
6. **接入与使用说明**：沿用实际命令、配置和入口；没有设备时如何执行离线，设备可用后怎样接入。

可以是一份报告加少量机器可读记录，无需为每项建设独立系统。小型静态 HTML、Markdown 和表格即可承载首版。网页工作台之后读取同样数据，避免先陷入完整 UI 开发。
新增解释文字、断言和原始数据必须能对应到同一版本与同一 run/case，不能混用旧成功记录。

## 13. 验收：既验能力，也验它会不会误导人

| 验收场景 | 通过要求 |
|---|---|
| 无产品连接 | 用调查确认适用的路径运行代表场景并解释；说明实际执行位置及 FB/CB 各自支持范围，未完成部分如实列明 |
| 拍/时间语义 | 能说清当前 step/cycle含义、输入生效与取值阶段；未知毫秒映射不捏造 |
| 场景卡与执行一致 | 中文中的参数、序列、Expected及实际值可跳转或对应到真实配置/记录 |
| 预期来自当前实现 | 显示观察/业务待核对，不能作为独立正确性证据 |
| 测试反驳解释 | 保留冲突与原预期，更新解释而非改数据取巧 |
| 错版本/错对象 | 拒绝错误关联或明确阻塞，不能拿同名变量继续 |
| 断线/过期/混批次 | 旧值不伪装新值；无同步保证不拼成同一拍 |
| 无内部状态记录 | 原因可标推断，不制造内部数值或完整时间线 |
| 无设备 | 在线保持未实机验证，离线和资料工作可继续 |
| 完整执行依赖 | 两种连接情况下均查清必要组件与执行位置；是否需要本地引擎有证据，未知保留未知，不按本文建议擅自删去依赖 |
| 场景间状态污染 | 初始化/清理有效；有状态样本重复执行不偷用前次状态 |
| 错误检出能力 | 在隔离副本和适用场景中，固定预期，对代表性可运行错误能报错 |
| 夜间中断恢复 | 已完成结果可保留；未完成项不补PASS，不重复未知副作用 |
| 人的理解 | 报告足以让读者说明测什么、依据是什么、实际如何、还有什么不知道 |

错误检出可以复用已有变异/性质测试证据，只针对新增风险补做；语法错误或加载失败不能冒充业务变异有效。检错能力也不证明需求本身正确。
本地实现最终按“两种使用场景的支持情况、业务规则、解释质量”分别报告完成/部分完成/阻塞；这些是用户结果维度，不要求对应不同引擎或代码模块。不能一个总完成掩盖未实机验证。

## 14. 直接交给本地 AI 的启动指令

以下指令在用户现有授权范围内执行，不额外授予真实产品控制权限：

> 当前优先完成 BEH 的 AI 测试与 AI 解释融合。本文作者没有查看工具源码，也没有运行工具或连接产品，文中的技术路径、接口、样本安排和实施顺序都是候选建议，不能当成已知架构。
>
> 你能够访问源码，请把自主研究源码、现有测试、配置与运行记录作为首要工作。围绕目标逐步调查并做最小运行验证，查清原工具到底怎样工作，再选择具体测试和接入方式。发现本文建议不符合源码时，以证据修正建议并说明理由，在用户目标与现有授权范围内继续实现。
>
> 用户需要覆盖“不连接真实产品”和“连接真实产品”两种使用场景；它们不预设两套引擎、两套后端或不同执行位置。两种情况都要查清启动依赖、被测逻辑、调度、状态、输入与数值来源，尤其查明连接产品时是否仍需本地引擎、Runner 或其他组件，以及各自实际职责。不要因为本文某一段没有提到某组件，就认为它不需要。
>
> 现有 FB/CB 测试、原生 GUI 的连接/debug/断点功能都是调查线索。查清完整调用链与实际支持范围，优先复用适用能力，比较可行接入方案后选择。API、插件、原生宿主调用或源码适配都可考虑，不预定接口一定存在或一定能无 GUI。以文字和结构化信息为主，必要的关键画面核对可少量用多模态。
>
> 保持以下目标：把现有用例变成普通人能核对的业务场景；说明预期从哪里来；保存真实执行记录；测后专门解释关键变化、原因依据、场景对照、业务联系与未知；有疑点时进行有预算的必要补测。“一拍”、时钟、内部状态和数据新鲜度都从实际证据取得，拿不到就说明。
>
> 预期来源、实际检查、解释证据分别表达。当前实现反推的预期不能单独证明业务正确；业务歧义变成具体问题，允许人回答“不知道”，继续其他有效工作。源码能说明当前实现，适用需求和独立依据才支持应有行为。
>
> 先做代表样本融合再扩展是推荐节奏；FB/CB 的对象、数量、先后由你根据实际情况确定并说明理由。无设备时完成可做的工作，相关实机结论保留待验证。在线操作沿用已明确的目标与操作范围。
>
> 根据真实可取得的信息建立过程回看、适用范围重跑和夜间逐项保存，复用现有格式与成功成果。调查与实现交替推进，不止于建议报告；最终交付查明了什么、选择了什么方案及理由、实际完成与证据、使用入口、限制和待核对事项。本轮优先解释与测试融合，开发考试和完整回放平台留待后续。
